# Protected predecessor owner configuration

Current operator reference for the implemented opt-in dependency seam.
The original T-010 addendum remains historical evidence.

## Protected configuration contract

The owner must provision the existing externally protected provider control Policy
(`AZURE_CONTROL_POLICY` / `AWS_CONTROL_POLICY` in the literal prepare/apply jobs),
not the untrusted uploaded bundle or an approval CLI flag. Two Policy fields extend
its existing closed dataclass parser:

| Field | Required counterpart and format |
|---|---|
| `dependency_request_sha256` | Lowercase 64-hex SHA-256 of the exact consumer request bytes, including its entire predecessor list. Default `""` only retains legacy no-predecessor behavior. |
| `predecessor_trust` | JSON array of the closed records below, converted to a tuple by each governed loader. Default `[]`. Exactly one entry per declared predecessor unit; no omitted/additional/duplicate entries. |

Every nonempty trust record has exactly these fields (unknown/missing fields fail):

| Field | Owner-pinned counterpart |
|---|---|
| `unit_id`, `run_id`, `provider` | Exact original predecessor request and verification identity; provider is `azure` or `aws`. |
| `request` | Original predecessor request `{path, sha256}`; contained relative path and exact bytes. |
| `verification` | Original `verify-result.json.verification.json` `{path, sha256}`; equals consumer predecessor reference and authenticated original output. |
| `scope` | `{account_id, region, deployment_scope}` of the predecessor request; never inferred from the consumer's possibly different provider/scope. |
| `profile` | `{id, version, path, sha256}` of original selected profile; current supported cloud-compute version is `2`. |
| `repository`, `repository_id` | Exact GitHub producer repository name and positive numeric immutable repository ID. |
| `workflow`, `workflow_revision`, `ref` | `.github/workflows/<name>.yml` or `.yaml`, exact lowercase 40-hex commit and protected `refs/heads/...` branch of original producer. |
| `workflow_sha256` | Hash of the entire reviewed original workflow file bytes. Supported workflow is generated JSON (valid GitHub YAML), not arbitrary YAML or an unreviewed job lookalike. |
| `executor_repository`, `executor_revision` | Reviewed executor repository and lowercase 40-hex checkout commit. Fixed verify job must exactly match the shared generator. |
| `producer_run_id`, `artifact_id` | Positive integer original GitHub successful verify run and immutable artifact ID. Artifact digest must be present and match; nullable/missing digest is NOT proof. |
| `environment_id` | Positive numeric ID of producer's protected `sandbox-verify` environment. |
| `actors`, `reviewers` | Nonempty unique arrays of `[positive stable user ID, exact login]`. Exact protected reviewer set; approval cannot be actor or triggering actor by stable ID. |

Positive integer config IDs are bounded below 10^20. Record path/hash/profile/scope
fields reuse existing strict cloud contracts. No foreign workflow, repository or
scope pin is guessed from a receipt. Owner review and external Policy provenance
remain necessary; a local file saying PASS/native or a digest alone is insufficient.

## Producer and acquisition prerequisites

Use the supported fixed verify job generated by the provider governed module. It
checks out only the reviewed executor at its immutable commit, uses the protected
`<PROVIDER>_VERIFY_POLICY`, invokes the literal read-only verify command, and uploads
with pinned upload-artifact v4. Its request and preview hashes are in run-name. Verify
is a separate first-attempt workflow_dispatch run, successful/completed, with exact
original workflow/job/step/code and environment approval bindings. The verifier
requires successful actual verify and upload steps and collection within their
bounded original execution window. Apply/reconcile success is not verify success.

The existing GitHub Runtime token must read the producer repository's artifact
metadata/archive, original run/attempt jobs, pinned workflow contents, protected
environment and approval history. Owners must arrange that access explicitly across
repositories; missing permissions fail closed. This code does not widen tokens or
create another trust authority. Artifact download uses the established bounded
32 MiB no-automatic-redirect/no-credential-forwarding mechanism, fresh extraction
root, no-follow path policy and immutable artifact digest. The redirected blob GET
has no GitHub bearer. Neither provider plugin imports the other for acquisition.

The original collector must publish genuine fresh authenticated profile evidence:
cloud-compute v2, verification-contract/v3, selected-verification-plan/v2 and all
observations/payloads/context. The consumer replays the existing strict reducer
against the protected registry. File-only saved-contract/plan evaluation remains
BLOCKED, never an override or authority. A synthetic producer output stays synthetic;
configured native-class protocol doubles in tests are still synthetic test evidence.

## Consumer and orchestration behavior

Admission occurs at shared WriteBoundary entry and again after audit publication,
for both prepare and apply. Each write freshly reacquires proof. After the final
remote dependency work, consumer GitHub metadata is rechecked and local request/
preview bindings, predecessor freshness and credential expiry are checked immediately
before submit. No impossible atomic revocation claim is made across independent
GitHub/provider systems. Original exclusive publication/replay and IAM checks remain.

`ordered_units` rejects duplicate/self/missing/cyclic graph edges before callbacks;
`dispatch` orders ready units lexically, uses actual adapter callbacks and only
releases dependents after authenticated original verified output. Failed/UNKNOWN
predecessors block transitive dependents; independent successes retain original
result/receipt bytes. UNKNOWN retains original operation identity; reconciliation
stays provider-owned, without automatic resubmission or resource rollback.

## Packaging and first live execution limits

Install one provider with all four shared runtime modules (cloud_contracts,
cloud_authorization, cloud_verification, cloud_dependencies) and the existing protected
verification registry/references. T-007 owns complete installer wiring; T-010's
standalone fixture proves import/render without the opposite provider, and cross-
provider protocol tests prove admission at both shared boundaries. Both providers'
existing acquisition negative tests continue to apply after extraction.

The newly reachable AWS verify job and Azure sandbox-verify policy path are exercised
synthetically. Their first real CI execution remains pending. Verify Policy has
operation `apply` for original-operation collection but environment `sandbox-verify`;
WriteBoundary explicitly rejects it as a writer. The owner must supply the existing
read-only verify IAM identity and correct original operation artifact/preview;
read-only verification must not reuse a prepare/apply write environment.

Live sandbox execution is BLOCKED: this session has no authorized live sandbox
credentials/resources. Real local Bicep compilation/CDK synthesis does not establish
live deployment, GitHub IAM or health correctness. No cloud writes, generic IaC
engine, destruction, cross-cloud transaction or automatic resource rollback was added.

## Final callback deadline propagation

The existing cloud-authorization-receipt/v1 expires_at is capped by authenticated
predecessor freshness as well as consumer credential, provider, policy and preview
deadlines. Exclusive whole-second expiry is conservatively bounded; both provider
callback guards consume this same deadline. A dependency that expires after
admission cannot be kept alive by a longer consumer lease. No new receipt schema
is introduced. Refresh external dependency_request_sha256 and predecessor_trust
authorization whenever immutable predecessor references change; do not patch
original inputs or extend an unsigned receipt.
