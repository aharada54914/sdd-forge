# SQL開発の共通手順

この手順はSQL案件の仕様化、承認済み実装、独立検証で共有する。
呼び出し元の権限・状態遷移を増やさず、公開 `sql-develop` 入口は再起動しない。
SQLを含まない案件へ適用を広げない。

## 役割とトラック

| 呼び出し元 | SQLで追加する仕事 | 進めてはいけないこと |
|---|---|---|
| 入力整理／仕様化 | SQL開発契約、受入条件、既存owner・アプリとの依存を明確にする | DB接続、SQL実装、承認欄の変更 |
| 承認済み `implement-task` | 同じ契約に基づきSQL・アプリ・試験を実装し、隔離DBで検証する | 共有／本番DBへの接続、未承認の変更、Done判定 |
| `lite-gate`／`quality-gate` | 独立したコンテキストで要求と実行結果・副作用を確認する | 自己申告や未実施試験だけを根拠にPASSにする |

Lite候補は、再作成できる隔離DB、合成データ、共有利用者なし、限定された変更が
すべて確認できる場合だけ。本番を対象にする設計・移行、共有DB、PII、権限／RLS、
テナント分離、破壊的移行、大規模backfillはFullへ渡す。engine、版、対象環境、
管理主体、データ分類、影響が不明なら先に情報を確認し、実装・接続を止める。

既存ContextのFull指定と既存risk checkerの昇格を維持する。
`high_risk_migration` 等の既存語彙はSQLの完全な自動分類器ではない。
SQLキーワードや「low risk」という自己申告だけで許可を出さない。
この手順はSQLファイアウォールではなく、実行権限の強制にはDB権限・ネットワーク隔離が必要。

## 仕様化

[SQL開発契約](../templates/sql-development-contract.md)を既存 `design.md` に組み込み、
必要な期待結果を `requirements.md` と各タスクのDone Whenへ反映する。
既存Full成果物が必要なら、その形式も維持する。新しい承認ファイルやSQL専用状態は作らない。

- 実エンジン、正確な版、compatibility／collation／SQL mode、対象製品を確認する。
  Azure SQL DatabaseとManaged Instance、RDSとAuroraなどを同じ検証済み環境とは扱わない。
- 既存migration ownerを継続する。同一オブジェクトをORM、Flyway、DACPACなどで二重管理しない。
  ownerが未定なら選択理由を仕様に含め、衝突があれば解消前に実装しない。
- 行の意味、キー、型、NULL、重複、参照整合性、日時、照合順序、金額の精度・丸め、保存期間を整理する。
  クエリには入力と出力列・型、順序の要否、空集合と境界値を定める。
- 変更の対象オブジェクト、新旧アプリが読み書きする契約、既存データ量・分布、必要な性能条件を定める。
  型や名称が似ていることを、同じ値や同じ意味の保証にしない。
- 既存利用者がいる変更はexpand → 移行・backfill → 新旧アプリ確認 → contractへ分ける。
  旧列・旧形式の撤去は別タスクとし、並行更新と二重書込みの不整合も設計する。

## 承認済み実装と隔離

実装は既存 `ship → implement-task` から行い、選択したownerとプロジェクトの既存コマンドを使う。
独自のmigration runnerやSQLパーサーを追加しない。

1. **検証先を確定する。** 承認範囲で新規作成した隔離資源のID、engine、DB名、作成主体を記録する。
   既存の共有開発DB、本番の複製、環境変数に偶然ある接続先を使わない。
   初版のデータは合成データのみ。外部DBへ接続できる資格情報・ネットワークを検証環境に渡さない。
   正しい検証先と所有する資源だと確認できなければ、接続・適用・破棄を停止する。
2. **実行環境を確認する。** DBとCLIの版、container digest、利用条件を記録する。
   アプリ用の最小権限と、検証用migration権限を分ける。CLIやfixtureが使えない場合はBlockedとし、
   モックや他engineで合格に置き換えない。
3. **SQLと設定をレビューする。** 値はパラメーター化する。表・列・ソート方向などの識別子は、
   アプリ所有の許可した候補から選ぶ。文字列連結やescapingだけをSQL injection対策にしない。
   ストアド処理・trigger・UDF・動的SQLと、migrationのcallback／pre/post scriptもレビュー対象。
4. **lint／buildも隔離する。** 選択済みのdialectと信頼する設定を使う。初版はraw SQLを基本とする。
   SQLFluffのtemplating、library、dbt macro、project buildはコードやSQLを実行し得る。
   未信頼設定を読ませるために本番資格情報を渡さない。必要なmacroの処理は別途明示した隔離条件で行う。
5. **履歴と実スキーマを別に確認する。** ownerの履歴／checksumを検証し、対象オブジェクトのschemaを
   期待する前版と比較する。履歴が同じでも手動DDLによるdriftはあり得る。比較範囲を記録し、
   比較手段が利用できなければ未確認とする。適用済みの版付きmigrationを書き換えない。
   CLIの終了コードだけで成功にしない。例えばFlyway 13.12.1のJSON `validate` は、
   検証失敗でも終了コード0を返す。`validationSuccessful` と `invalidMigrations` を確認し、
   checksum不一致などの実際の結果を保存する。適用ツールの版と出力形式に合わせて判定する。
6. **適用と回復を試す。** ownerの排他と適用履歴を使い、同じ版を二重適用しない。
   backfillは安定したキー・処理済み境界・冪等な更新条件を定める。
   `repair`、`clean`、`baseline`、down migrationで失敗を自動的に消さない。
   一度だけ適用するmigrationと、再開可能なbackfillを混同しない。
7. **失敗後を観測する。** statement／lockの時間上限とキャンセル時の動作を確かめる。
   client timeout・切断だけでDB側の停止やrollbackを断定せず、実行中処理、transaction、lock、
   schemaと適用履歴を確認する。結果不明のまま再実行しない。atomicでないDDLは残存状態からの
   roll-forward／復元手順と損失範囲を決める。
8. **後片付けを限定する。** 作成時に記録した資源だけを片付け、証跡は残す。
   名前の部分一致や共有DBの一覧から削除対象を推測しない。

## 検証と独立レビュー

必要な検証コマンドは導入先のプロジェクトチェックとして宣言し、既存gateの共通実行器で実行する。
SQLの実行結果を別のPASSフラグへ手で複製しない。

| 対象 | 実際に確かめること |
|---|---|
| 新規構築と前版更新 | 同じ最終契約、schema、期待キー・値・制約になる。行数だけで合格にしない |
| アプリ互換性 | 旧アプリと新アプリが移行の各段階で期待どおりに読み書きする。接続コード・transaction境界も対象 |
| データ境界 | 空集合、NULL、重複、欠損参照、Unicode、日時・精度など当該要求の境界値 |
| 履歴とdrift | 履歴改変を検知し、履歴を変えない手動schema変更も別に検知する |
| 失敗・並行実行 | 途中失敗、二重実行、ロック待ち、timeout、再開後の状態と保持すべきデータ |
| 権限・情報 | アプリに不要なDDL権限がない。異なる検証先に適用しない。ログに秘密や実データがない |
| 性能 | 必要な案件で、結果の正しさを確認後、同じデータ・分布・負荷・環境で前後を反復測定する |

性能の閾値、warm-up、反復回数、データ量・偏り、同時実行数を実行前に決める。
遅延、読み取り量、lock待ち、実行計画を必要な範囲で残す。
推定コストだけで高速化とせず、実測のばらつきと制約を示す。
`EXPLAIN ANALYZE`や副作用のある関数を使うSELECTは実行を伴うため、隔離DBに限定する。
性能が受入対象でなければ理由を記録し、計測したとは書かない。

既存の実装報告・品質レポートに、共通実行器の `execution.json`、対象revision・dirty状態、
実測したDB／tool版、fixtureの識別、commandと終了状態、期待値、観測した副作用、未実施項目を残す。
SQL用の署名evidence-bundleをLiteへ追加しない。生の接続文字列・秘密・実データを保存せず、
query planやエラーログ内のliteral・パラメーターも公開前に点検する。
独立レビュー担当は報告の自己申告だけでなく、受入条件と実行結果を照合する。
必須試験が未実施・失敗・BlockedならPASS／Doneにしない。

## クラウドと運用への引き継ぎ

[運用引き継ぎ](../templates/sql-operations-handoff.md)を既存設計・実装報告に組み込む。
SQL側はDB内部とアプリ互換性、Azure／AWS側は基盤・network・cloud IDの担当。
cloud adapterの `apply` にSQLを混ぜず、その成功をDB migration成功に読み替えない。

初版は共有・本番DBへ接続しない。本番には別途、対象DB、実行主体、DB権限、保護CIの承認、
接続条件、対象成果物・revision、前提schema／履歴、drift再確認、停止条件、復元先・切替と
RPO／RTOを確定して引き継ぐ。確認後に対象や成果物が変われば再レビューする。
バックアップ取得だけでは回復可能と判定しない。適用後に受け付けた更新が失われる場合も明記する。
Azure SQL／RDS／Auroraの実環境受入、本番性能・復旧、本番適用は未実施として分けて報告する。
