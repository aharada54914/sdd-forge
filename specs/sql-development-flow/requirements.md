# 要件（lite）: SQL開発フロー

- **Issue/出典**: 2026-11-05の依頼「SQL開発のフローを追加するならどういう仕様にするか。Azure・AWS・ソフト開発との対応を含め、2026ベストプラクティスを調査して仕様書を提案。SDD Lite形式、承認後に実装」。
- **状態**: 提案・未承認。今回の成果はこの要件、[設計](design.md)、[タスク](tasks.md)の3文書。製品コード、DB、CI設定は変更しない。
- **調査基準**: 2026-11-05 UTC、リポジトリ `75c6919b466a929566d6d29a1d17c01b741bfd25`。公式資料と本提案の判断を設計書で区別する。
- **目的**: SQLを生成するだけでなく、データの意味・互換性・変更時の影響を確かめて、アプリと一緒に開発できるようにする。既存の仕様化、承認、実装、独立検証を使い、AzureとAWSでSQLの工程を重複させない。

## ユーザーストーリー / 要求

- **REQ-001 共通の入口**: 開発者は `sdd-implementation:sql-develop` に要求を渡し、SQLに必要な情報を整理して既存のLite／Full仕様化へ進める。入口は仕様化までを担当し、承認後の実装は既存の `sdd-ship:ship` から行う。既存のソフト開発フローからも同じSQL手順を参照できる。
- **REQ-002 対象の確定**: DBエンジン、版、互換性設定、環境、スキーマの管理主体、変更の種類、データ分類、影響するアプリを記録する。推測でDBに接続しない。未確定の対象や複数の管理主体がある場合は、実装・接続へ進まず質問する。
- **REQ-003 初版の範囲**: PostgreSQL、T-SQL（SQL Server／Azure SQL）、MySQLを扱う。テーブル・制約・インデックス・ビュー・ストアド処理・クエリ・データ移行の設計と実装、隔離DBでの検証を対象とする。対応エンジンとクラウド製品の受入済み範囲は別に表示する。
- **REQ-004 データの契約**: キー、行の意味、型、NULL、重複、参照整合性、日時・タイムゾーン、照合順序、精度・丸め、保存期間を必要な範囲で定義する。クエリでは入力、出力列・型、並び順の要否、空集合、境界値と期待結果を明示する。
- **REQ-005 既存方式の継続**: Flyway、Liquibase、ORM migration、SQL Database Projectsなど導入先の方式を優先する。同じオブジェクトを複数の方式で更新しない。新規案件で方式が未定なら、選択理由を示して仕様承認に含める。独自の移行エンジンは作らない。
- **REQ-006 安全な変更**: 既存利用者がある破壊的変更は、追加、アプリ移行、必要なバックフィル、旧構造の撤去に分ける。データ量、ロック、タイムアウト、トランザクション境界、再開方法、復旧時のデータ損失を評価する。適用済みの版付き移行ファイルを上書きして履歴を直さない。
- **REQ-007 実DBでの検証**: 実装承認後、合成データを使う隔離DBで新規構築と既存版からの更新を試す。結果の正しさ、アプリ互換性、変更履歴、実スキーマとの差異、途中失敗後の状態を確認する。SQLiteやモックだけの成功を別エンジンの成功に置き換えない。
- **REQ-008 性能の受入条件**: 性能改善や高負荷の対象では、同じデータ分布・環境・負荷による変更前後の計測、実行計画、遅延、読み取り量、ロック待ちを記録する。目標値は実行前に案件ごとに合意し、計画の推定コストだけで高速化を宣言しない。
- **REQ-009 権限と情報保護**: アプリ、検証、移行、クラウド基盤の権限を分離する。値はパラメーター化し、動的な識別子は許可した候補から選ぶ。認証情報、実データ、機微なSQLパラメーターを仕様・ログ・モデル入力へ保存しない。コメント、DBメタデータ、SQLテンプレートを実行許可として扱わない。
- **REQ-010 Liteの境界**: Liteは、隔離した開発DB・合成データ・影響の限定された変更にだけ使う。本番・共有DB、個人情報、権限変更、テナント分離、破壊的移行、影響不明の変更はFullへ渡す。既存Full指定と既存のリスク昇格を維持する。SQL危険度の完全な自動判定を保証しない。
- **REQ-011 クラウドとの接続**: SQL側はDB内部の変更とアプリ互換性、Azure／AWS側は基盤・ネットワーク・クラウドIDを担当する。本番には、適用対象、成果物、前提状態、停止条件、復旧手順をまとめた引き継ぎを用意する。初版は共有・本番DBに接続せず、既存cloud adapterへ任意SQL実行を追加しない。
- **REQ-012 完了の意味**: SQL専用の承認欄やDone状態を増やさない。既存gateが実行証跡と一度の独立レビューを確認して実装完了を判定する。必須試験の未実施は未完了とし、本番未適用・クラウド未検証・性能未評価を成功に含めない。

## スコープ外

- 初版での本番・共有DBへの接続、移行の自動適用、当該DBの作成・削除・権限付与、および実クラウドDBの有料資源作成。別の運用仕様と対象環境の承認が必要。承認済みの隔離検証用資源の作成・移行・権限設定・破棄と、受入用CIは初版の対象に含む。
- 新規 `sdd-sql` プラグイン、独自SQLパーサー、DB接続MCP、独自migration runner、既存ガードをSQLファイアウォールにする変更。
- Oracle、SQLite固有の移行、Redshift／Snowflake／BigQuery／Fabric Warehouse、dbtによる分析パイプライン、異種DB移行、CDCの運用。検出した場合は未対応として既存方式へ引き継ぐ。
- すべてのエンジン版・クラウド製品・ストアド言語・拡張機能の互換性保証、無停止や自動rollbackの一律保証。

## Open Questions

- **承認を求める製品判断**: 既存 `sdd-implementation` への追加、3エンジン系統、隔離DBまでの実装・検証を初版とする案を推奨する。この一式への承認後に [T-001〜T-005](tasks.md) を開始する。
- **実案件の対象**: 利用するリポジトリ・DB・移行方式は未指定。初版の受入は設計書の3つの参照案件で行い、実案件やAzure／AWS実機での評価済みとは記録しない。
- **本番接続の次段階**: 対象DB、実行主体、ネットワーク、承認者、RPO／RTO、監査先が決まってから別途仕様化する。今回の実装承認を本番実行の承認に流用しない。
