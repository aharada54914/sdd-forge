# workshop-enrollment 受け入れ条件と検証計画

この文書の TEST は将来の検証計画であり、実行済みのテストではない。

## Acceptance Criteria
- AC-001 (REQ-001, G-01): 期間の両端を含むワークショップだけが開始日時昇順で返り、各要素に `id`、`title`、`start_at`、`capacity`、`remaining_seats` が含まれる。200件で p95 ≤ 500ms。
- AC-002 (REQ-001, CON-001): オフセットのない日時や実在しない日時は `400 INVALID_DATETIME`、`from` > `to` は `400 INVALID_RANGE` を返す。 必須パラメータ欠落も `400 INVALID_DATETIME`、未認証の要求は `401` で状態不変。
- AC-003 (REQ-002, G-01): 空席があれば `201` で `remaining_seats` が1減る。満席は `409 FULL`、重複は `409 DUPLICATE`、開始後は `409 CLOSED` で状態不変。 同時に定員より多く申込しても確定申込数は定員を超えず、判定は開始日時→重複→定員の順である。
- AC-004 (REQ-003, CON-003, G-01): 承認記録前の公開要求は `409 APPROVAL_REQUIRED` で `roster-outbox` は空のまま。`admin` の承認記録後の公開要求で表示名のみの名簿が1件送信され、再要求は `409 ALREADY_PUBLISHED`。`member` の承認記録・公開要求は `403 FORBIDDEN`。 開始前の承認記録は `409 NOT_STARTED` で不変、開始以降の承認記録は `204`、再承認も `204` で不変。
- AC-005 (REQ-004): 申込・承認記録・公開要求ごとに、操作種別・対象 id・結果コードを含む1行が `audit.log` に追加される。

## Verification Plan
- TEST-001 (AC-001): 合成データ200件で一覧を100回呼び、件数・順序・必須項目・p95 を AC-001 に照合する。期間の両端・期間外・空結果・同時刻の id 順も含め、各応答の完了時間をローカルの呼出側で計測する。
- TEST-002 (AC-002): オフセットなし日時、`2026-02-30T10:00:00+09:00`、逆転した範囲をそれぞれ送り、エラーコードを確認する。 必須パラメータ欠落と未認証の要求も送る。
- TEST-003 (AC-003): 開始前の定員2のワークショップで異なる member を u1、u2、u3 とし、u1、u1、u2、u3 の順に申込む。開始日時ちょうどの申込も行い、各応答・状態不変・残席を REQ-002 と AC-003 に照合する。別の未申込の定員2対象では3人が同時に申込んでも成功は2件だけで確定申込数が2であることを確認する。
- TEST-004 (AC-004): 開始前の admin 承認拒否と開始以降の member 承認・公開拒否を確認する。その後、未承認で公開要求、`admin` が承認記録、公開要求、再公開要求の順に行い、各応答、状態不変、`roster-outbox` の件数・内容を AC-004 に照合する。再承認も AC-004 の不変条件を確認する。
- TEST-005 (AC-005): TEST-003 と TEST-004 の実行後に `audit.log` の追加行を確認する。

## Manual Validation Surface
- MV-001: 隔離されたローカル環境でスタブ `roster-outbox`（ローカルファイルへの書き込みのみ）を使い、TEST-004 を手動で再現できる。外部ネットワークには接続しない。
