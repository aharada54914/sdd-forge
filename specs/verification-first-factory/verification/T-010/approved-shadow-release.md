# T-010 の Shadow リリースと T-011 の strict 昇格

2026-11-26、所有者は Shadow リリースと利用者既定の strict 昇格を別々に判定することを承認した。今回の承認は [タスク計画](../../tasks.md) の分割に適用する。T-010 の Done は品質ゲートが判定する。T-011 は Planned・Draft とし、実行には別途承認を要する。

## T-010 のリリース候補で照合する証跡

| 判定項目 | 受入条件 |
|---|---|
| local-posix | クリーンなリリース候補 SHA の単一実行。レシートの `revision` と `revision_after` が候補 SHA に一致し、選択した195スイートすべてに成功結果が1件ずつあること。 |
| ローカルの純増時間 | 候補の同じホスト・同じスイートで、追加検査を無効・有効にして比較し、純増が +15 秒以内であること。 |
| PR CI の純増時間 | 候補と比較元で Test と Guardrails の成功経路を測る。実行ジョブの最初の開始から最後の完了までを比較し、純増が +120 秒以内であること。両側の SHA と実行 ID を記録する。 |
| Shadow スキャン | 候補の実 PR 差分で Gitleaks と Semgrep diff-only の双方が完走し、対象の base・head およびツール別の所見件数を追跡できること。0件は実行結果として記録する。 |

カテゴリ2のテストを廃止する場合は、従来どおり個別に SELF-REQ-006 と SELF-AC-006 を満たす。既存 CLI と MCP の互換性は AC-013、夜間 CodeQL と PR の CI 統合は元の T-010 に従う。

## T-011 の昇格対象と判定

T-011 の実行承認時に、変更するキーを指定する。候補 SHA の設定から、キー、変更前後の mode、enabled の既定値、アダプタまたはルール、実際の入力範囲を判断記録に転記する。改訂時の既定は次のとおり。[既定値の定義](../../../../plugins/sdd-quality-loop/scripts/v2/v2-pure-lib.mjs)

| 候補キー | 利用者が有効化したときの既定と、照合する経路 |
|---|---|
| `formal_verification.mode` | `enabled: false`、`mode: shadow`。既定のチェッカーは TLC。対象モデルと設定を使った利用者の形式検証経路で評価する。 |
| `agent_lint.mode` | `enabled: false`、`mode: shadow`、`diff_only: true`。利用者の差分ハンクに同じ AST ルールを適用する。 |
| `security_audit.mode` | `enabled: false`、`mode: shadow`。既定アダプタは `builtin-secret-pattern` と `builtin-slopsquatting`。影響を受けるアダプタごとに、利用者のセキュリティゲートで評価する。 |

T-010 の CI は Gitleaks を Git 範囲に、Semgrep を PR 差分に適用する。利用者がこの2アダプタを選択した場合の CLI はプロジェクト全体を対象にする。差分 SAST の実行結果は T-010 に記録し、T-011 の各対象には、候補の利用者経路を実行した独自の証跡を対応付ける。モード変更が複数アダプタに及ぶ場合は影響範囲全体の証跡が揃うまで保留する。変更可能なのは承認・実証されたキーの mode だけで、全 enabled 値・アダプタ既定・既に strict の anti_tampering は変更対象外とする。[PR のスキャン](../../../../.github/workflows/sdd-guardrails.yml)・[利用者向けアダプタ](../../../../plugins/sdd-quality-loop/scripts/v2/run-security-gate.mjs)

1. 昇格候補 SHA のクリーンな checkout で `python3 tests/verification.py --profile local-posix --receipt <path>` を1回実行する。開始・終了がともにその SHA で、正規プロファイルの全件が1件ずつ成功したレシートを保存する。同じ候補について T-010 の表の方法でローカルの純増 +15 秒以内と PR CI の純増 +120 秒以内を実証する。lint に影響する場合は100ファイルの実測値が3秒以内であることも記録する。
2. 同じ候補のゲートを実 PR の入力に適用し、候補 SHA・PR の base/head・実行 ID・ルールと所見位置・判定根拠を保存する。再実行や重なる差分で検出した同一所見は元の変更と所見位置に照合して1件と数える。対象ゲートごとに、重複排除後の全所見を分母、うち誤検知を分子として率を算出する。全件判定済みで率が 5% 未満の場合に限り、そのゲートの昇格を認める。分母0件、未判定、入力範囲またはアダプタの不一致は保留とする。
3. 限定した利用先で当該ゲートを明示的に有効化し、mode 省略時の新既定、明示指定した `shadow` の優先、設定で旧 mode の `shadow` に戻した際の動作を確認する。設定を省略した通常導入ではゲートが無効のままであることも確認し、候補 SHA とともに各結果、切り戻す設定キーと値を記録する。

改訂前の候補 `ff7157a93` までに集計した82通りの実差分では Gitleaks・Semgrep の所見は各0件だった。この候補の PR CI 純増は0秒。いずれも当時の候補に対する観測であり、新たな候補での合格判定にはその SHA の証跡を用いる。[候補の実行時刻と所見集計](shadow-pr976/hosted-ff7157a93.json)

## 既存仕様への適用

[要件](../../requirements.md) の SELF-REQ-005 と SELF-AC-005 は、誤検知率と時間予算を組み合わせた昇格条件として T-011 に適用する。T-010 はそのうち NFR-004 の時間予算を検証し、Shadow の実行結果を残す。T-004 の SELF-AC-005 参照は AST lint の Shadow 運用に関する証跡に適用する。T-010 の CI とカテゴリ2廃止には [設計第3節](../../design.md) を適用する。旧タスク計画が T-010 に割り当てた昇格は、本決定以後 T-011 が引き継ぐ。
