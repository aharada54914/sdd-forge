## Recommended minimal implementation decision

Retain `facet-manifest/v1.resolved_gates` unchanged. Reuse the resolver's matched Capability IDs and canonical Registry gates; filter `stage == implementation` **only in a new selected-plan projection**, never in the Foundation field. The generated `gate-capabilities.json` can be checked against its Registry digest as a cache but is not a second authority. Do not alter `check-contract.py`'s baseline IDs, tier sets, stack waiver semantics, or existing `verification-contract/v2` fields.

The proposed **single new persisted contract** is `selected-verification-plan/v1`, with its versioned schema at `contracts/selected-verification-plan.schema.json`. It is deliberately produced at evaluation time, not at candidate-selection time: the selected candidate comes from the existing resolver/facet manifest, while the evaluation also needs the current verification contract and actual check evidence. The new producer is a narrowly scoped `evaluate-selected-plan.py` companion to the existing quality-gate checks; it reads the active Facet Manifest, canonical Registry, current task verification contract, and reruns the unchanged `check-contract.py` validation (never trusts a caller's pass flag). It writes one deterministic plan/evaluation record bound by all three input SHA-256 hashes. Its schema/semantic validator is the first consumer. The mandatory workflow consumer is the existing `quality-gate/SKILL.md` scripted-gate sequence: immediately after `check-contract`, invoke the companion for an enabled, valid active Project Context; a missing/failed companion invocation blocks the quality-gate rather than being an optional evidence attachment. The independent quality-gate evaluator is the decision consumer. The QG report cites the exact plan digest and may claim PASS only if the selected-plan verdict and the unchanged legacy `check-contract` both pass. No-context or invalid-context takes the unchanged legacy path; it must not create a new plan or convert a legacy failure to success.

Concrete QG invocation boundary: use the existing `specs/<feature>/facet-manifest.yaml` emitted by `resolve-project-context.py` (the `.yaml` filename contains canonical JSON bytes per `_canonical_payload` at `resolve-project-context.py:1541-1547`), the same canonical Registry file used by that resolver, and the current task's `verification-contract/v2`. The companion accepts explicit `--facet-manifest`, `--registry`, `--contract`, `--repo-root`, and `--output` paths; it does not rescan the tree to choose a different context or contract. The QG chooses a new evidence output under `specs/<feature>/verification/<task-id>/`; the output is no-replace, and the QG report names and hashes it. The producer validates the manifest/Registry binding before selection, then validates the contract using the existing checker; any invalid input or failed legacy contract returns nonzero and cannot produce `PASS`. This is the producer/consumer handoff, not permission for the producer to change the protected checker.

The current consumer edit baseline is `plugins/sdd-quality-loop/skills/quality-gate/SKILL.md` SHA-256 `d0326f3617f0bf6de6ba7f99d7edc2388c79a6731866328133cff7bb1815b722` (2026-10-04 UTC). Because that file is an intended output, a fresh implementer must check this live baseline hash before reading/editing it, just as the first handoff checked the resolver output; do not place the same file in both immutable inputs and allowed outputs. Drift requires a new orchestrator decision, not an overwrite.

For each Registry gate selected by matched Capabilities, join by gate ID to the **canonical** Registry, reject a dangling reference, and emit only `stage: implementation`. `blocking:true` is required; `blocking:false` is optional. Under the current `capability-registry/v1` schema, a Capability has a `trigger`, but a gate has **no independent conditional predicate** (`contracts/capability-registry.schema.json:22-35,40-68`). Consequently every implementation gate referenced by a matched Capability is emitted; never infer a condition or omit a gate merely because its verifier is missing. Reserve the `conditional` vocabulary for a later explicitly versioned source rule; do not emit it from this Registry version. Preserve gate ID uniqueness and deterministic sort. Also project every existing verification-contract check that is required under the current unchanged `check-contract.py` validation into the record with `sources: ["legacy-contract"]`; if the same check ID appears from Registry, merge obligation by the stricter required/blocking rule and list both sources in the record. A legacy-required check cannot be `not-applicable` without a separately approved versioned verification-contract migration.

`applicability` is distinct from `result`. In v1, the only admitted `not-applicable` path is an *unselected, legacy-optional* contract check (`required:false`, no matched blocking Registry gate), with the machine-checkable code `legacy-optional-not-selected`; no selected required gate is excluded. A required check with no runnable implementation is `unavailable`, a check with no execution is `not-run`, and an ambiguous result/evidence is `unknown`. Required `unavailable`, `not-run`, or `unknown` produces `BLOCKED`; for a legacy-required check, use `migration-pending-required` (not a waiver). An actually executed required failure produces `NEEDS_WORK`; only inspected success evidence for every required check can produce `PASS`. Optional unrun alone cannot block. A missing, malformed, stale, or digest-mismatched input is `BLOCKED`, never an empty-plan PASS. The producer may use `verification-contract/v2` entries as observations only after checking `required`, `passes`, and the existence of the referenced evidence under the existing path policy; a bare `passes:true` assertion is not independent proof and requires QG inspection. A missing selected Registry ID in that contract remains `not-run`, not success. A `passes:false` entry without a recorded execution is `not-run`, while a documented executed nonzero result is `failed`; a missing verifier implementation is `unavailable` and an ambiguous evidence/exit status is `unknown`. No existing contract field may be silently reinterpreted or overwritten. The plan has no artifact/promotion/deployment-success value.

The candidate JSON Schema fixes names, allowed values, and content hashes, but **cross-field rules above still require deterministic validator tests**. In particular, the validator must reject duplicate IDs, source/Registry mismatches, promotion-stage entries, N/A on an unmigrated legacy-required check, a PASS with any required non-pass result, empty-plan PASS where required checks exist, absent evidence for a claimed pass, and a mismatched digest. The schema is not a substitute for those tests.
