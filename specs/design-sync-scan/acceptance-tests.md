# Acceptance Tests: design-sync-scan

Two verification techniques coexist in this feature, and each Test Matrix row uses the one that actually proves its claim. The scanner (`design-sync-scan.sh` / `.ps1`) has real executable behaviour, so criteria about it are verified by **running the script against fixtures and asserting on exit codes and report content** — the style `tests/check-placeholders.tests.sh` already establishes in this repository. The `SKILL.md` wiring has no executable code path of its own — it is instructions an agent follows — so criteria about it are verified by **document conformance**, the technique `specs/design-sync-consent/acceptance-tests.md` uses throughout. A row's Test Type column says which applies; neither technique is used where the other would be weaker for that claim.

Where a criterion's own language enumerates branches or quantifies over conditions, it is expanded below into individual branches, each with its own TEST row and its own concrete assertion, per AGENTS.md `## Rules` → "Author-time sweeps that replace case-by-case vigilance", item 4.

## Test Details

### TEST-001 – TEST-004 (AC-001 – AC-004) — the script contract's basic shape

- **TEST-001** — both runtimes exist at `plugins/sdd-bootstrap/scripts/` and error when invoked with no arguments (the specific error code is TEST-010's claim, not this one — this row only asserts an argument is required).
- **TEST-002** — mockups are organised per view and per state, so a scan that only reads the top level of the target directory would silently miss most real mockup sets; the fixture nests a flagged file at least two directories deep.
- **TEST-003** — asserts the absence of a category-selecting flag by using a fixture with findings in two categories and confirming both appear in one run with no extra argument.
- **TEST-004** — the non-blocking invariant the Loop already states ("absence of mockups... never blocks specification review") must hold for this check specifically: an existing, empty-of-HTML directory is not an error.

### TEST-005 – TEST-009 (AC-005, AC-006) — the detection branches, one row per category and one for the mix

Each category must independently reach exit 1, and the mix must not let one category's finding mask another's absence from the report. Five fixtures: clean, placeholder-only, secret-only, PII-only, and one file carrying a finding from two categories at once — TEST-009 additionally asserts the report names both.

### TEST-010, TEST-056, TEST-011 – TEST-013 (AC-007, AC-008) — the tool-error branch, and its exit code is not 1

Four tool-error causes, each its own row because a caller triaging a red run needs to know which one occurred without reading the diagnostic first — and because AC-007's own text now enumerates zero-arguments and too-many-arguments as two separate branches (adversarial-review item 6: a single "missing/invalid argument" row conflated two distinct mistakes a caller could make, and a diagnostic tuned for one shape need not fire correctly, or at all, for the other):

- **TEST-010** — **zero** arguments.
- **TEST-056** — **more** arguments than the contract defines (one required positional argument) — its own row, added in response to adversarial review, because a diagnostic that correctly names "no target directory given" is not guaranteed to say anything sensible about "too many given," and a suite that only exercised the empty case could not tell the two apart.
- **TEST-011** — the argument is well-formed but the path does not exist.
- **TEST-012** — the path exists but a file under it cannot be read (permissions, or a fixture removed mid-scan); the assertion requires the *rest* of the set still gets a diagnostic-bearing exit 2, not a partial clean report — the same fail-closed discipline `check-placeholders.sh`/`.ps1` established for issue #127 applies here on first principles, not by inheritance, since this is a different script.
- **TEST-013** — a regression row specifically contrasting this script's exit 2 with `check-placeholders.sh`'s exit 1 for the same class of error (`check-placeholders.sh:6-9`), so a future edit that "fixes" this script to match that convention is caught rather than silently accepted.

All four branches additionally require **no override affordance appears anywhere in the exit-2 output or in the caller's documented handling of it** (AC-007's fourth clause, AC-037) — a claim distinct from, and in addition to, the exit code itself.

### TEST-055 (AC-037) — the skill, not only the script, says exit 2 has no override

Added in response to adversarial review (item 9). TEST-013 and the row above prove the *script's* exit code is 2, never 1, on a tool error. TEST-055 proves the *skill text* a human or agent actually reads states the same thing in its own words: that this branch is unconditionally blocking, that its diagnostic is worded so it cannot be mistaken for a finding, and — the substantive clause — that **no override affordance is offered at this branch at all**. Without this row, a `SKILL.md` edit could correctly wire the script's exit code while still describing step 5's exit-2 branch with language borrowed from the exit-1 branch ("present the findings and consider an override"), which would misinform a reader even though the underlying script never behaves that way. This is the skill-text counterpart to AC-016 in exactly the sense AC-016 is the skill-text counterpart to AC-013.

### TEST-014 (AC-009) — placeholder detection is the same detection, not a lookalike

Runs `design-sync-scan`'s placeholder path against the same corpus `tests/check-placeholders.tests.sh` uses (or an equivalent corpus built from the same two pattern strings) and asserts the same verdicts. A reimplementation that "looks like" `check-placeholders.sh:18-19` but drifts in one character is exactly the failure this row exists to catch — AC-009 requires the source be cited, not retyped, and this test is the check that the citation was honoured rather than merely claimed.

### TEST-015 – TEST-021, TEST-083 (AC-010) — one row per secret pattern, including a named sub-format

Each of S1–S7 gets its own fixture and its own row, because a secret scanner that silently drops one vendor format is a scanner with an undocumented gap — the same reasoning `design-sync-consent`'s TEST-033–036 applied to reconciliation sites, applied here to pattern coverage. TEST-021 is the one row with two assertions in the same fixture family: S7's value-length-and-quoting requirement must both catch a real assignment and *not* catch a bare keyword or an empty value, since both halves are load-bearing (a pattern that only ever fires is as broken as one that never does). **TEST-083** (added in response to adversarial review, item 4/Ruling D) exercises S5's `sk-proj-` sub-format specifically, distinct from TEST-019's bare `sk-` case: S5 enumerates its sub-formats by name (`design.md`'s Design Decisions) rather than relying on the character class to absorb them incidentally, and this row is what makes that enumeration a checked claim rather than an assumed one.

### TEST-022 – TEST-024, TEST-057 – TEST-062, TEST-080 – TEST-082 (AC-011) — PII, the exclusion that keeps it usable, and its exact boundary

**TEST-022** and **TEST-023** are the positive cases for the two PII patterns. **TEST-024, TEST-057 – TEST-062** are the seven negative cases — one per RFC 2606/6761 reserved domain or TLD (`example.com`, `example.net`, `example.org`, `.test`, `.example`, `.invalid`, `.localhost`) — that make P1 usable at all: without them, every mockup's conventional `user@example.com`-style placeholder would flag, and `design.md`'s Design Decisions section states plainly what that does to an operator's attention — they learn to override reflexively, which defeats the signal. Split into seven rows, added in response to adversarial review (item 7), rather than one row covering "a reserved domain" with an illustrative ellipsis: an ellipsis in an acceptance criterion's assertion text is not a claim about the other six, and an implementation could correctly exclude `example.com` while missing `.invalid` and still pass a single ellipsis-shaped row. Each row is also what makes the P1/`.edu` correction (Ruling D) checkable in the negative direction: `.edu` deliberately has **no** row here, because it is not RFC 2606/6761 territory and must still trigger a finding — see TEST-022's positive case, which any `.edu` address exercises identically to any other non-reserved domain.

**TEST-080 – TEST-082** are P2's three negative boundary fixtures (7-digit too short, 16-digit too long, digit-adjacent), added for the same reason and in the same round: a length-quantifier bound alone does not prevent a substring match inside a longer digit run, and these three rows are what makes P2's both-sides boundary (AC-011, AC-038) a checked property rather than an assumed one. TEST-080–082 are unit rows against the fixture directly; **TEST-084** (REQ-009 section, below) is the separate claim that both the POSIX ERE and `.NET` forms agree on all three.

### TEST-025 (AC-012) — findings are labelled, not just counted

Reuses TEST-009's mixed-category fixture and asserts the report's per-finding labels are correct for all three categories present in the one run — a single fixture suffices because the property under test (correct labelling) is falsifiable by any one mislabelled finding in a mixed set; testing categories in isolation again here would not strengthen the claim.

### TEST-026 – TEST-030 (AC-013 – AC-015) — the report is actionable and not itself a new disclosure surface

- **TEST-026** — a fixture spanning three files with findings in different files and different lines; the report's location data must not collapse or misattribute across files.
- **TEST-027 / TEST-028 / TEST-063** — the failing shape for all three is a report line that reproduces the exact matched substring; the assertion greps the *matched value itself*, not merely the word "REDACTED", against the report output and requires it absent. TEST-028 and TEST-063 were one combined "PII" row until adversarial review split it (item 8): P1 (email) and P2 (phone) are two different patterns matching two different string shapes, and a masking implementation could correctly redact one while a regex-specific bug left the other's matched span intact — a combined row would pass on either alone.
- **TEST-029** — the mirror-image assertion: a placeholder marker must appear in full, so a masking implementation applied indiscriminately to all three categories (over-broad, easier to write, wrong) is caught here rather than passing by accident.
- **TEST-030** — runs the script with stdin explicitly closed and asserts it still completes and produces a verdict; a script that blocks waiting for input would hang a caller that does not expect an interactive step, exactly the failure AC-015 exists to prevent.

### TEST-031 – TEST-035 (AC-016 – AC-019) — the skill text states what the script does, in the right place and the right order

- **TEST-031 / TEST-032** — the two halves of step 5's branching (exit 1 presents before pushing; exit 0 proceeds without a prompt) are asserted as separate rows because a text could state one half correctly while getting the other wrong, and a combined check would hide that.
- **TEST-033 / TEST-034** — the egress-hygiene-only scope statement is required in *both* the skill and the script's own header comment, so either artifact read alone still carries the boundary; two rows because either one going stale independently of the other is a plausible drift (an editor updating the skill's wording without touching the script header, or vice versa).
- **TEST-035** — reuses the structural, position-comparing technique `design-sync-consent`'s TEST-010/TEST-014 established: parse the Loop's numbered list and assert step 5 (the check point) still falls between step 4 (consent) and step 6 (push), and that the cycle at step 7 still returns to step 2, none of which is disturbed by this feature's edit.

### TEST-036 – TEST-043, TEST-064 – TEST-068 (AC-020 – AC-025) — the override procedure, in full

- **TEST-036** — the affordance itself, and the negative half in the same row: absent an explicit "yes," the text must not permit a push.
- **TEST-037 / TEST-038** — the no-carry-forward rule, split because "a fresh scan needs its own decision" and "this holds even for identical findings" are different claims a text could satisfy one of while failing the other; an implementation that special-cases "the findings are the same as last time" to skip re-presentation passes TEST-037 and fails TEST-038, which is exactly the failure mode Edge Case 3 in `requirements.md` names.
- **TEST-039 / TEST-040** — the two possible values of `Egress-Scan`, each its own row for the same reason `design-sync-consent`'s AC-022-equivalent field-value checks were split: a record that only ever writes one value cannot be distinguished from a record that never runs the other branch.
- **TEST-041 / TEST-064** — the timestamp requirement applies to both values, not only the exceptional one; split (adversarial review, item 10) because a skill edit could state `Egress-Scan-At` for `overridden` (the branch that reads as needing an audit trail) while forgetting to state it for the mundane `clean` branch, or vice versa — a combined row would pass on either alone, the same defect class TEST-039/TEST-040's split already guards against for `Egress-Scan` itself.
- **TEST-042, TEST-065 – TEST-068** — a regression row **per frozen field**, one for each of `design-sync-consent`'s five existing field names (`Egress-Consent`, `Egress-Consent-Scope`, `Egress-Consent-Subject`, `Egress-Destination`, `Egress-Consent-Expiry`), rather than a single "the table matches" atomic check. **Choice and rationale (adversarial review, item 11 — a binary choice was required and is recorded here):** an atomic whole-table equality assertion was considered and rejected in favour of five independent rows, because this document rejects combined checks everywhere else on exactly this ground — AC-003/TEST-005–007 in `design-sync-consent` (the precedent this suite's own opening paragraph invokes) explicitly reject asserting three distinct disclosure elements as one check, because a combined check passes if any one element alone is correct and hides which one broke. An atomic table-match assertion has the identical failure mode here: it would tell a reviewer "the table regressed" without saying which field, forcing a manual diff to recover the information five separate rows give for free. The five-row form costs four extra lines in the Test Matrix and buys back the diagnosis the atomic form throws away.
- **TEST-043** — the decline outcome and its distinction from `Egress-Consent`'s vocabulary are asserted together because the distinction is the substantive half — the same pattern `design-sync-consent`'s TEST-043 used for AC-026's decline/not-permitted distinction, applied here to a different pair of concepts that are equally easy to conflate in prose.

### TEST-044 – TEST-046 (AC-026 – AC-028) — the point is not duplicated, not mispositioned, and the old baseline still holds

- **TEST-044** — asserts step 5 appears exactly once in the Loop's numbered list and that steps 4 and 6 retain their adjacency to it.
- **TEST-045** — **narrowed in response to adversarial review (item 15).** The row previously claimed to verify "no upload path bypasses the check point" by "enumerating every path... and asserting each passes through step 5 first," described as mirroring `design-sync-consent`'s TEST-026. On inspection, `design-sync-consent`'s actual TEST-026 technique is a **positional comparison over a numbered list** — it confirms step 5 sits between step 4 and step 6 in the text's stated order — not a dataflow or path-enumeration proof that no *implementation* could route around the check. Claiming the stronger property overstated what a text-order comparison can establish: an agent could still, in a given real run, simply not follow the skill. TEST-045's assertion is now written to match what it actually checks: the Loop's numbered list, as text, contains exactly one route from generation to push, and step 5 sits on it — i.e., the specification does not *itself* describe or imply a second, step-5-avoiding path to push. This is a claim about the document's internal consistency, not a runtime guarantee; `acceptance-tests.md`'s closing Notes paragraph already carries the broader version of this caveat ("these rows prove... They cannot prove an agent actually invokes step 5... on a given real run"), and TEST-045's own wording is now consistent with it rather than quietly claiming more.
- **TEST-046** — **reworded to a baseline-relative claim (Ruling B, adversarial review item 16).** The row previously asserted the entire existing `tests/design-system-contract.tests.{sh,ps1}` suite "passes" after this feature's `SKILL.md` edit — which is false on its face, because that suite already contains `design-sync-consent`'s TEST-039 as a *designed* red, pending a CI-registration patch this feature has no authority to apply. The assertion now runs the suite, records its pre-edit result set as the baseline (one designed red, TEST-039; everything else green), runs it again post-edit, and requires the **diff between the two runs to be empty** — no test that passed before this feature's edit is allowed to fail after it, and TEST-039 is permitted to still be exactly as red as it already was. A failure here is proof this feature broke a locked invariant; the fix is to correct this feature's edit, never to edit the suite to accommodate it, and TEST-039 remaining red is explicitly not such a failure.

### TEST-047 – TEST-048, TEST-069 (AC-029, AC-030) — the manual/Codex path, verified by what is actually checkable

- **TEST-047** — the manual-fallback documentation must name the scan and how to run it standalone, at the point a Codex operator (or anyone on a host without `DesignSync`) would actually be reading when deciding what to do before falling back.
- **TEST-048 — redefined in response to adversarial review (item 12).** The row previously required proving "no host- or runtime-conditional branch exists" without qualification — an unbounded universal claim over the space of all possible conditionals, which no static check can actually establish (absence-of-anything-matching-any-possible-branch-shape is not decidable by grep, or by anything short of a full semantic read of the source, which is not what a suite in this repository does). AC-030 itself carried the same overclaim and is reworded alongside this row. TEST-048 now checks a **finite, named set** of forbidden identifiers plausibly indicating a host/tool branch — `CLAUDE_CODE`, `CODEX`, `DesignSync`, `ANTHROPIC`, `OPENAI` (case-insensitive grep, both scripts) — and requires none appears as a branch condition (an appearance in a comment citing this very requirement is not a violation; the check targets conditional syntax, not the string's mere presence). This finite list is itself a stated bound, not a claim of completeness — a future host-marker convention this list does not anticipate is a gap in the list, to be added when discovered, not a property this test can detect in advance.
- **TEST-069 (new, added alongside TEST-048's redefinition)** — the check the static grep cannot provide: a **behavioural** parity fixture. The script is invoked twice against the same input, once under an environment representative of a Claude-Code-style caller (a plausible marker variable set) and once representative of a bare-terminal/Codex-style caller (that variable absent), and the two runs are required to be exit-code- and report-identical. This is what actually substantiates "runtime-neutral" as an observed property of the artifact's behaviour, rather than an inference from the absence of certain strings in its source — the two techniques are complementary, not redundant: TEST-048 catches a literal conditional an author wrote; TEST-069 would catch a behavioural difference produced by some mechanism TEST-048's finite list did not anticipate (an environment variable read implicitly by a library call, for instance).

### TEST-049 – TEST-051, TEST-070 – TEST-079, TEST-084 (AC-031 – AC-033, AC-038) — the two runtimes agree with each other, branch by branch, not just with their own suites

**Expanded in response to adversarial review (item 13).** The original TEST-049/TEST-050 asserted cross-runtime exit-code and classification parity over "the shared fixture corpus" as one aggregate claim per row. Per AGENTS.md's branch-expansion discipline (item 4 — already applied to AC-006's category branches at TEST-006–009 and to AC-007's error branches at TEST-010/011/012/056), an aggregate parity claim over an enumerated set of branches is exactly the shape that discipline requires expanding: a single "the corpus agrees" row can pass because six of seven branches agree while the seventh silently diverges, exactly as a single "the suite passes" claim could hide which test failed.

- **Exit-code parity (AC-031): TEST-049 (placeholder), TEST-070 (secret), TEST-071 (PII), TEST-072 (mixed), TEST-073 (clean), TEST-074 (zero-argument), TEST-075 (nonexistent directory), TEST-076 (unreadable file)** — eight branches, one per fixture class this feature defines (four detection shapes, one clean shape, three of AC-007's four tool-error shapes; the too-many-arguments branch, TEST-056, is not separately re-parity-tested here because it shares its diagnostic-wording mechanism with the zero-argument branch and TEST-074 already exercises that mechanism cross-runtime). Each row runs both `design-sync-scan.sh` and `design-sync-scan.ps1` against the same fixture and requires the same exit code.
- **Classification parity (AC-032): TEST-050 (placeholder), TEST-077 (secret), TEST-078 (PII), TEST-079 (mixed)** — four branches, one per shape that actually produces a finding to classify (clean and tool-error branches have no findings to compare, so they are not repeated here — that would be asserting agreement on an empty set, which is vacuously true and adds no coverage). Each row requires both runtimes to agree on every finding's category and file:line.
- **TEST-084 (AC-038)** — the dual-form-specific parity claim: runs TEST-021's (S7 bare-keyword) and TEST-080–082's (P2 boundary) fixtures specifically, and requires the POSIX ERE form (`.sh`) and the `.NET` form (`.ps1`) to classify every one of them identically. This is not redundant with TEST-070–079: those rows exercise the *general* cross-runtime claim over ordinary detection fixtures; TEST-084 exercises specifically the fixtures whose per-engine expression differs by construction (design.md's dual-form block) — the fixtures most likely to reveal a translation error the general rows would not happen to hit.
- **TEST-051** — the case-sensitivity sweep's own row (AGENTS.md item 1): a lower-cased mutation of each case-sensitive pattern group's fixture (the reused placeholder markers, and the S1/S2/S3/S4/S5/S6 vendor-prefix group, including S5's `sk-proj-` sub-format) must be rejected by both runtimes identically. Unlike `design-sync-consent`, which recorded this sweep as narrowly applicable (no real port existed there), this feature is a real `.sh`→`.ps1` translation and the sweep applies at full strength.

### TEST-052 – TEST-053 (AC-034, AC-035) — the verification surface itself, and TEST-054's move to Deferred

- **TEST-052 — redefined in response to adversarial review (item 14).** The row previously asserted "the two suites cover REQ-001 through REQ-009," a claim about the *suite's* content that is not directly mechanically checkable — coverage of a requirement is a property of the specification's traceability, not something a test runner observes about itself. Redefined into a **traceability manifest** check: every `#### AC-NNN` heading in `requirements.md` attributed to REQ-001–REQ-009 must appear at least once in this file's AC column (Test Matrix or Deferred section). This is mechanically verifiable — a script can extract both lists (headings from `requirements.md`, AC-column values from this file's tables) and diff them — and it is what "the suite covers the REQs" actually cashed out to: a suite cannot cover a requirement no acceptance criterion names, and this row is the check that no acceptance criterion was left namechecked nowhere.
- **TEST-053** — both `tests/run-all.sh` and `tests/run-all.ps1` list the new suite; neither file is protected (`guard_invariants.py:4`), so this is agent-applicable directly, unlike a protected-file change would be.
- **TEST-054 moved to the Deferred section (Ruling C, adversarial review item 5).** It previously sat in this blocking Test Matrix, mirroring `design-sync-consent`'s AC-024/TEST-039 in substance (`.github/workflows/test.yml` is protected, registration is a separately staged human-applied patch) but not in *placement* — `design-sync-consent` left its own equivalent row inside its blocking matrix with a "designed to stay red" note, which this feature's Deferred section makes structurally explicit instead: a row that cannot pass without an action outside this feature's authority is not part of this feature's pass/fail surface, and saying so with a heading rather than a note in a cell is what keeps a reviewer from having to read every row's prose to find the one exception.

## Notes

- **Test type vocabulary.** `unit` and `unit (fixture)` rows execute the actual scripts against files created for the test; `document conformance`, `document conformance (positional)`, and `document conformance (structural)` rows read and parse `SKILL.md` text without executing anything — `(positional)` is a narrower claim than `(structural)` (see TEST-045's Test Details): it asserts an ordering property of the text only, not a bypass-proof; `cross-runtime parity` and `representative-caller parity` rows execute scripts against shared input and diff the output — the former across the two runtimes, the latter across two caller-representative environments within one runtime; `regression` and `regression (baseline-relative)` rows assert something already true stays true, the latter measured against a documented baseline that may itself include a known, designed red (TEST-046); `static (finite identifier set)` and `case-sensitivity sweep` rows inspect source without executing the scanned-for behaviour, and `(finite identifier set)` records that the check is bounded by a named list rather than an unbounded universal claim (TEST-048); `traceability manifest` (TEST-052) is a claim about this specification's own internal consistency, not about any script; `registration conformance` and `CI-registration conformance` rows are about the verification surface itself, mirroring `design-sync-consent`'s TEST-038/TEST-039 vocabulary for the same class of claim — the latter now lives in the Deferred section rather than the blocking Test Matrix (Ruling C).
- **Dual-runtime parity, with the same carve-out discipline `design-sync-consent`'s BL-008 established.** Every `.sh`-suite assertion in TEST-001–TEST-053 has a `.ps1` counterpart; where an ASCII-only `.ps1` source cannot carry a literal the `.sh` twin asserts, the reason is stated where the asymmetry is created. TEST-049–TEST-051, TEST-069–TEST-079, and TEST-084 are the additional, stronger cross-runtime and representative-caller rows described above and are not a substitute for this per-suite parity.
- **Case-sensitivity sweep (AGENTS.md item 1) applies at full strength here**, unlike in `design-sync-consent`. This is a genuine `.sh`→`.ps1` port of new regex-bearing logic; TEST-051 is its dedicated row, but the sweep itself — both the operator-level and the cmdlet-level passes AGENTS.md describes — must be performed across the whole `.ps1` script, not only at the one row that names it.
- **Re-verify every `file:line` in this document at implementation start**, per the same recurring-defect discipline `requirements.md` → Assumptions states (WFI-011).
- **This suite proves detection and wiring; it cannot prove an agent runs the scan.** Precisely as `design-sync-consent/acceptance-tests.md` states for its own document-conformance tests: these rows prove the script detects correctly and that `SKILL.md` describes the right procedure. They cannot prove an agent actually invokes step 5 before pushing on a given real run — REQ-007's positional assertion (TEST-045, narrowed per adversarial review item 15) is the strongest structural guarantee this specification can offer, and it is a claim about the text's internal single-path property, not about runtime behaviour no mockup generation has ever produced in this repository to observe, and not a proof against a non-conforming implementation.
