## Friction Patterns

### FP-01: A guard/spec contradiction — sdd-hook-guard denies the agent the human-copy staging path that design.md and tasks.md assumed the agent would write (T-003, the feature's highest-risk task)

**Evidence.** `sdd-hook-guard.py`'s `_is_protected_gate_file` (:976-989) matches by path SUFFIX against `PROTECTED_GATE_SUFFIXES` (`guard_invariants.py:4`, which lists `.github/workflows/test.yml`) with no `human-copy` carve-out. The approved `tasks.md` Planned Files and `design.md` both directed the implementing agent to write the staged candidate at `specs/epic-136-phase3/human-copy/.github/workflows/test.yml` — a path that ends with the protected suffix and is therefore denied identically to the live file. Confirmed empirically: a direct write attempt at the staging path was denied by the live PreToolUse hook, creating neither file nor directory. `PHASE2_HUMAN_COPY_TARGETS` (`guard_invariants.py:18`) is import/export bookkeeping only and grants no write exception.

**Cost.** Two full T-003 implementation-agent attempts died before the contradiction was isolated (one at the write attempt, one to a stall), and the task's delivery shape had to change: the candidate is authored at a NON-protected draft path, and its placement at the staging path became a documented human action alongside the live application. A human decision (2026-07-28) selected the draft approach over changing the guard.

**Proposed improvement (WFI candidate).** Either (a) add a `specs/*/human-copy/` carve-out to the guard's protected-path match so agents can author staged candidates (noting the circularity: the guard scripts are themselves R-10-protected, so the change needs its own human-copy round), or (b) amend the bootstrap/design guidance so a feature that stages a protected file explicitly records "staging is a human action" in tasks.md Planned Files, rather than assigning the write to the agent. Option (b) is lower-risk and removes the spec/guard contradiction at the source.

### FP-02: A "document/YAML conformance" acceptance criterion was verified only by text-marker assertions, so an invalid-YAML Critical survived into the second gate round (T-003, AC-016)

**Evidence.** The staged candidate emitted every prefixed step name as a BARE YAML scalar, `- name: [deterministic] X`. An unquoted scalar beginning with `[` opens a flow sequence, so the document failed to load — the round-2 evaluator reproduced the failure with two independent parsers (ruby/Psych, Deno @std/yaml) at line 21. `design.md:348` had written the prefix as a QUOTED scalar; the transform did not. The self-check suite (`tests/deterministic-lane-selfcheck.tests.sh`) asserted only line SHAPES via grep, never that the candidate was loadable YAML, so it reported 20 passing against a file no CI runner could parse. Applying it would have made `.github/workflows/test.yml` unloadable and silently dropped `test`/`cli-hook-enforcement`/`required-checks` — the exact opposite of the BL-001 preservation the report claimed "by construction".

**Cost.** One extra full gate round (round 2 → round 3) for T-003. The round-2 evaluator, running a real parser rather than the suite's own proxy, is what caught it.

**Proposed improvement (WFI candidate).** When an acceptance criterion is scoped as "document/schema/YAML conformance", its test MUST invoke a real conformance check (a parser/validator), not a proxy that inspects line shapes. The remediation added exactly this to TEST-016 (a dependency-free scalar-shape guard plus a `ruby -ryaml` parse); the general rule is worth encoding so future conformance ACs are not satisfied by markers alone. Corollary for gate design: this is a case where the independent evaluator running the real check — not the suite's self-report — is load-bearing; the gate worked as intended.

### FP-03: A self-check that re-derived its baseline from a live file broke idempotency across the very transition its task produces (T-003, round-1 Critical)

**Evidence.** The round-1 self-check recaptured its coverage baseline from the live workflow on every run and grepped for the `[deterministic] ` prefix. After the human applies the candidate to live, the live names already carry the prefix, so the check would search for `[deterministic] [deterministic] X` — 67/67 missing, TEST-017-GREEN FAILS, and (because the RED fixture becomes identical to the candidate) the RED leg goes vacuous. The suite is registered in run-all.sh, so run-all would have gone permanently red exactly when the task became completable.

**Cost.** One gate round (round 1). Fixed by stripping any existing prefix from the baseline so the check reduces to the same base set before and after application; verified with a post-apply simulation (25 passed / 0 designed-red / exit 0) and a still-non-vacuous RED leg in both states.

**Proposed improvement.** A test that spans a human-applied state transition (staged → live) must be idempotent across it — normalize the observed state before comparing, and prove non-vacuity in BOTH the pre- and post-transition states. Recorded for visibility; likely a calibration note rather than a WFI.
