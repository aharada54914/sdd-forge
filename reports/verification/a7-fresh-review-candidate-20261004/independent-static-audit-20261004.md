# Fresh-review recovery candidate: independent static audit

Status: NEEDS_WORK (informal, read-only code review; not an SDD review verdict)
Scope: this package's `.candidate` files and `recovery.patch`, compared with the existing validators and `reports/verification/a7-spec-attempt9-first-turn-audit-20261004.md`. Candidate code, fixtures, and apply runner were not executed; protected files, ledger, and reservations were not changed.

## Findings

1. **Major — approved recovery authority is not bound to the contract.** `fresh-review-recovery.py.candidate:54-59` accepts an exact schema with no field identifying the already granted, specific recovery authority. The wrappers at `spec-review-precheck.sh.candidate:393-407` and `spec-review-precheck.ps1.candidate:600-623` validate this schema but have no independent authority check. The user has already authorized this recovery; the issue is that the persisted contract does not mechanically identify that approval, as required by the prior audit at `a7-spec-attempt9-first-turn-audit-20261004.md:52`. A different locally assembled contract with correctly pinned evidence is indistinguishable from the authorized one. Minimal repair: add one exact approval-reference field to the contract and validate it against the existing specific authorization record; do not request the same approval again.

2. **Major — the 8→9 recovery edge is not established.** `fresh-review-recovery.py.candidate:104-143` checks the attempt-8 no-output inventory, both reset prechecks, invocation bindings, and allocations independently. It does not establish that attempt 9 was opened *from* the attempt-8 interruption through the authorized no-output route. Attempt 9's `reset: true` precheck contains no recovery-source binding, which the prior audit explicitly identified at `a7-spec-attempt9-first-turn-audit-20261004.md:54`. The helper therefore proves three adjacent evidence sets, but not their required transition chain. Minimal repair: bind the exact attempt-8 interruption evidence and reservation as the declared predecessor of attempt 9 in the fresh contract, then check that declared edge alongside the already present terminal and reservation validators. Do not rewrite either historical attempt.

3. **Major — the fresh contract is not durably locatable from the new precheck.** The wrappers persist only `fresh_review_contract_sha256` (`spec-review-precheck.sh.candidate:535-538`, `spec-review-precheck.ps1.candidate:809-812`). They accept a caller-selected contract path and neither copy it to a fixed evidence location nor record a canonical path. Later `validate_contract` checks precheck identity and input hashes but never resolves this digest (`spec-review-precheck.sh.candidate:263-266`, `spec-review-precheck.ps1.candidate:391-399`). If the external contract is moved or replaced after attempt 10 opens, the durable precheck no longer suffices to re-evaluate why this otherwise nonterminal predecessor was admitted. Minimal repair: require a canonical retained contract path, persist path and digest together, and verify that pair in the later contract-validation path.

4. **Major — diagnostic transcript matching is weaker than the stated first-turn proof.** `fresh-review-recovery.py.candidate:151-173` requires event order, two `end_turn` events, matching session IDs, a `BLOCKED` substring in the first assistant text, and equality of final JSON to the preserved reviewer output. It does not check a structured first-turn `BLOCKED` result or any transcript field distinguishing the later prompt as a resumed host turn. Thus an input transcript with those textual features, without the required failed-first-turn lifecycle, can satisfy admission. The fixture's synthetic transcript is appropriate test data; its use is not itself a defect. Minimal repair: check the concrete event/command fields present in the real pinned host export that establish the first-turn BLOCKED outcome and resumed same-session invocation, with a negative fixture that omits or changes each field. Keep the old PASS output diagnostic only.

## Observed controls and limits

The new route requires `--reset`, checks next attempt and Pending current inputs, invokes the existing terminal and reservation validators before and after the lock, and rejects an existing destination. The candidate emits only a new precheck; it does not itself promote attempt 9 PASS, reserve a fresh reviewer, or set specification status to Passed. These observations are from static reading. No behavioral pass or formal gate result is claimed.
