## Specification Differences

1. **`provider-terms.json` reused as the "provider-API client" allowlist,
   confirmed empirically first.** AC-025/design.md name "any provider-API
   client" without pointing at a specific list. Epic A4's own
   `facet-manifest-parity.tests.sh` (TEST-043) already treats
   `plugins/sdd-quality-loop/references/provider-terms.json` -- ADR-0018's
   provider-neutrality allowlist -- as the concrete mechanism for the
   identical "no provider-specific reference" concept, and design.md's own
   Security Boundaries section ties this feature's "no provider API"
   guarantee explicitly to "ADR-0020's own DSL-layer Provider-neutrality
   boundary". Before relying on it, this task ran the scan against the six
   real target files directly (not assumed): the only hit was the `lambda`
   term inside the pre-existing `key=lambda entry: ...` sort idiom already
   present in both `resolve-project-context.py` and `validate-resolver-
   evidence.py`, the identical false-positive class `facet-manifest-
   parity.tests.sh`'s own TEST-043 already solved with idiom-level masking
   (`key\s*=\s*lambda\b` -> a placeholder token before scanning). That exact
   mask was reused verbatim rather than re-derived; a dedicated
   `provider-term-dirty.txt`/`provider-term-clean.txt` canary pair proves
   the reused scan is neither vacuous nor over-broad on its own.
2. **TEST-024's diagnostics-sort clause is proven by citation, not a second
   fixture.** AC-024 names two arrays: `capability_evaluations[]` (by
   `capability_id`) and `diagnostics[]` (by `(id, detail)`). This task
   builds one NEW, dedicated fixture (the reordered Registry) for the first
   -- the case AC-024's own text names by name -- and, for the second, cites
   `resolve-project-context-block-check.py`'s own already-registered,
   already-regression-locked `dsl-warn-unsorted-affected-components`
   fixture (that driver's own module docstring already labels it an
   AC-056/AC-024 stable-sort case) rather than re-deriving a parallel one.
   Reasoning: sort CORRECTNESS is a property of the ONE shared `.py` master
   every dispatcher forwards to byte-for-byte verbatim (`resolve-project-
   context.sh`/`.ps1` are thin `exec`/`Process.Start` dispatchers with no
   logic of their own, confirmed by reading both files directly); this
   suite's OWN job, per its own Goal text, is CROSS-runtime byte-identity
   (TEST-023) and Registry-order independence (TEST-024's own named case),
   not re-deriving every sort-order fixture Epic-A4-adjacent suites already
   established. `run_test_024_diagnostics_sort_reuse` asserts the reused
   call actually ran a nonzero number of assertions (6), so the citation
   itself is not vacuous.
3. **TEST-024's Facet-Manifest-array-sort clause is proven white-box, with
   no subprocess.** `_assemble_facet_manifest` is a pure function of its six
   arguments (confirmed by reading it directly, `resolve-project-context.py`
   `:1604-1622`); this suite loads the staged module the same way
   `resolve-project-context-match-check.py` already does for its own
   oracle-reconstruction (`_load_module`, that driver's own module docstring:
   "call the real staged function directly ... never a mocked stand-in") and
   calls it with a hand-built, deliberately out-of-order Registry AND a
   fed-in-the-same-out-of-order `capability_evaluations` list, so a mutant
   that merely echoes input order back out (rather than genuinely
   re-sorting) cannot pass by accident. This is faster and more targeted
   than building a second full fixture-repo/subprocess path for a pure
   function.
