## Specification Differences

1. **New RULE-IDs minted for the input stage.** design.md `## Error Handling`
   enumerates rule ids for the cross-reference, structural, and version
   families, but names none for the argument/path/size/parse paths -- it only
   requires "non-zero + a one-line cause". The Global Constraint "Every check
   emits its own RULE-ID so that acceptance tests can tell adjacent failure
   paths apart" makes distinct ids mandatory there, so six were minted, all in
   the established `V2-` namespace: `V2-USAGE`, `V2-INPUT-NOT-FOUND`,
   `V2-INPUT-NOT-FILE`, `V2-INPUT-UNREADABLE`, `V2-INPUT-TOO-LARGE`,
   `V2-PARSE`. Two more guard failure modes the spec does not enumerate:
   `V2-RUNTIME` (`python3` absent from PATH, `.sh` only) and `V2-INTERNAL`
   (last-resort catch-all, so no traceback can ever escape).
2. **The 10 MiB ceiling is an explicit pre-parse gate.** acceptance-tests.md
   Notes leaves "implement the size threshold, or merely stay fail-closed on
   large input" to design.md; design.md `## Error Handling` then lists
   oversized input as its own category alongside JSON-parse failure, and
   requirements.md Edge Cases says such input is rejected without a
   best-effort parse. Both were satisfied by checking `st_size` BEFORE opening
   the file and rejecting with a distinct id. The constant is 10485760 bytes
   (10 x 1024 x 1024) in both twins. Without an explicit gate an oversized but
   well-formed contract would be accepted, and AC-017's second fixture could
   not distinguish the size path from the parse path.
3. **The `V2-WRONG-SCHEMA` message expands the spec's example.**
   requirements.md Edge Cases gives the message as "schema is
   domain-contract/v1; this validator checks v2 only". The emitted message is
   `schema is domain-contract/v1; this validator checks domain-contract/v2
   only` -- the trailing `v2` was expanded to the full const so the line
   literally names the v2-only constraint, which is what AC-012 requires. A
   superset of the spec's wording, not a departure from it.
4. **Three root-level checks land in T-002 rather than T-003, by necessity.**
   Step (b) cannot be well defined without deciding what happens when there is
   no `schema` value to dispatch on. Leaving those cases to T-003 would make
   T-002 fail OPEN (empty accumulator, exit 0) on a non-object root, an absent
   `schema` key, or a non-string `schema` value -- which directly contradicts
   this task's "Fail-closed" Done-When item. They are therefore handled here,
   deliberately using the rule ids design.md already assigns to the structural
   family -- `V2-TYPE-MISMATCH` for a non-object root and for a non-string
   `schema`, `V2-MISSING-KEY` for an absent `schema` key -- so T-003's
   structural pass inherits them unchanged instead of having to replace them.
   No fixture was added for these three paths: they are AC-021(1) and
   AC-024(1), which the `## Negative Fixture Allocation` table assigns to
   T-003, and inventing fixtures here would have broken that allocation. This
   is flagged under Quality Gate Focus.
5. **A non-v2 document halts before the structural pass.** design.md requires
   all violations to be enumerated rather than stopping at the first, but that
   rule governs check violations within an admitted document. A document that
   does not identify itself as `domain-contract/v2` is rejected with one line
   and is not then measured against v2's structure, since doing so would emit
   noise about a contract that never claimed to be v2 (DD-6). Admission
   failures are single-line by construction; the enumerate-everything rule
   applies from the structural pass onward, which is where T-003 and T-004
   add their checks.

## Quality Gate Focus

**The accumulator and extension seam T-003 and T-004 must extend.** Two later
tasks depend on this, so it is stated precisely:

1. There is exactly ONE violation accumulator per twin -- the module-level
   `violations` list in the `.sh` twin's embedded python, and the
   `$Violations` `ArrayList` in the `.ps1` twin. Every violation is appended
   through `add(rule_id, message)` / `Add-Violation -RuleId -Message`, which
   formats it as the single string `RULE-ID: message`. Nothing else may write
   to stderr, and nothing may ever write to stdout.
2. New checks go in the two named extension points and nowhere else:
   `check_structure(document, add_violation)` / `Invoke-StructureCheck
   -Document` for REQ-004(c), and `check_cross_references(document,
   add_violation)` / `Invoke-CrossReferenceCheck -Document` for
   REQ-004(d)-(i). Both are already called, in that order, after admission,
   and both are currently no-ops. Their contract: append through the
   accumulator, never write to stderr, never call `exit`/`sys.exit`, never
   return a verdict.
3. Flushing and exiting is owned solely by `finish()` / `Complete-Validation`,
   which prints the accumulator in insertion order and yields 1 when it is
   non-empty and 0 when it is empty. There is no third status.
4. The `.ps1` twin never calls `exit` inside a `try` block; every status is
   returned up to one top-level `exit $exitCode`. Keep it that way -- see
   Working Notes for why. The extension-point calls are wrapped in `[void](...)`
   so that a future check accidentally emitting to the pipeline cannot corrupt
   the returned status.
5. Steps run in the design.md `## Architecture` order: parse, dispatch,
   structure, cross-reference. T-003's type conformance must precede its own
   pattern/minLength/minItems checks (REQ-004(c)); nothing in this task
   constrains that beyond providing the ordering slot.

- **The Red run caught a real harness defect, and it was fixed before Green.**
  The first execution against the finished twins still showed 14 failures, all
  with the same cause: `Get-StdErrViolationLines` returns a one-element array,
  PowerShell unrolls that to a bare string on return, and `.Count` on a string
  throws `PropertyNotFoundException` under `Set-StrictMode -Version Latest`
  (which T-001 set at the top of this shared suite). Fixed by re-wrapping at
  every call site with `@(...)`. Worth noting the failure mode: the indexing
  site `(...)[0]` would NOT have thrown -- it would have silently returned the
  first *character* of the line and then matched a truncated string, which is
  exactly the kind of quiet false PASS this task is supposed to avoid. Both
  sites were corrected.
- **`exit` inside `try` was removed from the `.ps1` twin on purpose.** The
  first draft called `exit` from inside a `try` block and guarded it with
  `catch [System.Management.Automation.ExitException] { throw }`. Empirically
  confirmed on pwsh 7.6.2 that `exit` propagates through a bare `catch`
  uncaught (a probe script exited 7 without entering its catch), which makes
  that guard dead code on this host. But the guard itself was an untestable
  PS5.1 liability in two directions: if that type is not public on .NET
  Framework the whole script fails to parse on Windows, and if PS5.1 *did*
  catch `exit` in a bare `catch` the validator would report `V2-INTERNAL` for
  every verdict including the successful one. Both risks were removed
  structurally instead of guarded: `Complete-Validation` now RETURNS the
  status, every early termination returns it up the stack, and there is a
  single `exit $exitCode` at top level outside every `try`. This makes the
  exit path version-independent rather than version-dependent-but-guarded.
- **Honest statement of which shells were actually run.** Executed on this
  host: pwsh 7.6.2 (the `.ps1` twin, driven by the Pester suite, which
  launches it through the same PowerShell executable that is running the
  suite -- resolved at runtime from
  `[System.Diagnostics.Process]::GetCurrentProcess().MainModule.FileName`
  rather than hard-coded); and bash 3.2 with Python 3.14.5 (the `.sh` twin).
  Windows PowerShell 5.1 was NOT exercised -- this host is macOS 26.5.2 on
  arm64 and has no PS5.1. The task's Done-When claim that the `.ps1` side runs
  on PS5.1 therefore rests on construction and code review, not on execution.
  What was actually done to support it: avoided the PS6+ JSON-schema test
  cmdlet, the PS6+ hashtable switch on `ConvertFrom-Json`, .NET 5+
  hex-conversion helpers, ternary and null-coalescing operators, and the
  `$IsWindows`-family automatic variables; used `New-Object` rather than
  `::new()`; used `[Console]::Error.WriteLine` for stderr, matching the
  existing `domain-review-precheck.ps1`; pinned `Set-StrictMode -Version 2.0`
  explicitly rather than `Latest`, whose meaning differs between 5.1 and 7;
  and read every contract member through `PSObject.Properties[...]` rather
  than dot-notation. A grep sweep for those constructs over both twins returns
  nothing. This is a construction argument. It is not a test result, and it
  should not be recorded as one.
- **Windows-illegal filenames were avoided in fixtures.** No fixture path
  contains a byte in 0x00-0x1F. Every temp name is
  `sdd-v2-t002-<32 hex chars>` with a plain extension, which is legal on both
  Win32 and POSIX, so the `.ps1` twin cannot be killed on Windows by a name
  that is merely legal here.
- **Contract values are sanitized before they reach stderr.** The
  `V2-WRONG-SCHEMA` message interpolates a value read from an untrusted
  contract. Both twins fold every character below 0x20 (and 0x7F) to a space
  and truncate at 120 characters before interpolating, so a `schema` value
  containing a newline cannot forge a second violation line and a huge value
  cannot flood stderr. The same helper is applied to the input path. This is
  rendering only -- no contract value is ever used to build a command, resolve
  a path, or reach `eval` / `Invoke-Expression` (security-spec.md).
- **A BOM is stripped identically in both twins.** Python's `json.loads`
  rejects a leading U+FEFF while `ConvertFrom-Json` may tolerate it, which
  would have been a silent twin-parity divergence for T-005 to discover. Both
  twins now strip one leading U+FEFF before parsing.
- **One known cosmetic twin divergence, documented rather than hidden.** For a
  root-level JSON array, python sees a `list` while PowerShell collapses an
  empty array to `$null` on assignment. The `.ps1` twin recovers the declared
  type from the raw text's first non-whitespace character so both emit
  `root: expected object, found array`. Exit code and violation count agree
  regardless, which is what AC-013 compares.
- **Two identifiers were renamed to avoid poisoning repository-wide scans.**
  The helper originally named `Test-JsonPropertyPresent` contains the
  contiguous substring of the PS6+ cmdlet this feature's Global Constraints
  ban, and the header comments originally listed the banned dependency names
  literally. Both would have made these files false positives for any scan
  looking for those tokens (AGENTS.md "Detection-suite sources must not be
  their own false positives"). The helper is now
  `Test-ContractMemberPresent`, the comments describe the avoided constructs
  without naming them literally, and a grep for the banned tokens over both
  twins returns nothing.
