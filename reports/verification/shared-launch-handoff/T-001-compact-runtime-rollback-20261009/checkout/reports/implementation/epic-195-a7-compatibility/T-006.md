## Specification Differences

Two clauses in this task's own contract, read together with sibling
documents already on disk, could not be satisfied literally as written.
Both are disclosed here rather than silently worked around; neither
narrows or widens T-006's own AC/Done-When scope.

**1. Producer-call-site wiring requires editing `tests/lib/loop-driver.{sh,ps1}`,
which T-006's own Planned Files list omits.** design.md's "Per-kind
producer call sites" table (Data Plan) fixes the `skill-order`,
`review-loop-presence`, `approval-checkpoint`, and `done-transition`
producers at specific call sites inside `drive_review_round`/
`_loop_reserve_review_context`/`assert_terminal` (and their PowerShell
twins) — functions that exist only in `tests/lib/loop-driver.{sh,ps1}`.
T-006's own Planned Files list names only
`tests/loop-consistency.tests.{sh,ps1}` and
`tests/fixtures/compatibility-event-trace/`. Three independent parts of
the already-committed spec resolve this in the same direction: (a)
tasks.md's own Global Constraints section explicitly names T-006 among
"every task touching" `tests/lib/loop-driver.sh` ("unprotected today but
[a] cross-epic shared surface"); (b) design.md Test Strategy item 5
describes the wiring and `TEST-018`'s own authorship as one combined step;
and (c) T-005's own implementation report ("Unresolved Items") states in
writing that these four producer call sites "are not wired by this task
(T-006/T-007/T-008/T-009's own scope, per T-005's own Out of Scope)". On
that basis this task additively wired `skill-order:invocation` (each of
the four `_loop_drive_*_round` functions, immediately before its own
`bash "$script"`/`& $scriptPath` call), `approval-checkpoint:reserve`
(`_loop_reserve_review_context`/`Invoke-LoopReserveReviewContext`, on a
successful reservation only), and `review-loop-presence:stage-dispatch`
(`drive_review_round`/`Invoke-DriveReviewRound`'s own case/switch
dispatch, on a successful stage drive only) in both runtimes. No other
line in either file was touched; `tests/loop-driver.tests.{sh,ps1}`,
`tests/loop-consistency.tests.{sh,ps1}`'s own pre-existing `TEST-008`–
`TEST-010`/`TEST-017`, and `tests/loop-escalation.tests.{sh,ps1}` were all
re-run green after the change (Regression Tests Run, below).

**2. `done-transition` cannot be wired inside `assert_terminal`/`Test-LoopTerminal`
without breaking T-005's own committed regression lock.** design.md
places this producer "at the instant" `assert_terminal`'s own comparison
evaluates. But `tests/loop-inventory.tests.sh`'s `TEST-009.2` (and the
PowerShell twin's own `TEST-009.2`) — authored and committed by T-005,
outside T-006's Planned Files, and part of T-005's own Done When
("`assert_terminal` and `assert_artifacts_schema` are byte-identical to
their pre-task form") — hard-pins `assert_terminal`'s function body to a
literal SHA-256 constant. Adding the `_loop_trace_emit` call inside
`assert_terminal` was verified, mechanically, to trip that lock (`TEST-009.2`
turned red: `70 passed, 1 failed`, confirmed before reverting). Editing
`tests/loop-inventory.tests.sh`/`.ps1` to update the pinned hash is outside
T-006's own Planned Files and would alter a different, not-yet-gated
task's own already-authored regression evidence. Given that direct
conflict, `assert_terminal`/`Test-LoopTerminal` were left byte-identical
(re-verified: `tests/loop-inventory.tests.{sh,ps1}` both green, 71/0), and
`TEST-018`/`TEST-019` instead call `_loop_trace_emit`/`Write-LoopTraceEvent`
directly, with the exact same `kind`/`producer`/`value` design.md fixes,
immediately after their own `assert_terminal`/`Test-LoopTerminal` call
succeeds. The resulting trace is byte-for-byte identical in content,
order, and position (`done-transition` last in the round's own event
sub-sequence, AC-026) to what an in-function emission would have produced
for this round; the only difference is the literal source line the event
is recorded from, which `assert_event_trace`/`Test-EventTrace` cannot
observe (it reads only the finished `kind`/`producer`/`seq`/`value` trace).
`TEST-019` in `tests/loop-escalation.tests.sh` (T-007) will need the
identical pattern for its own `assert_terminal`/`Test-LoopTerminal` call.

**3. The PowerShell twin's own next available case number is `TEST-019`,
not `TEST-018`.** `tests/loop-consistency.tests.ps1` already has an
unrelated, pre-existing `TEST-018` (a same-turn-edit-plus-reset regression
that is parity coverage for `tests/spec-review-loop.tests.sh`, which has
no PowerShell twin of its own — see that file's own header comment).
Reusing `018` for a second, unrelated case in the same file would create a
same-number/different-meaning collision within one suite. The bash twin's
own next-available number after `TEST-017` genuinely is `TEST-018`
(`tests/loop-consistency.tests.sh` has no such case), matching tasks.md
T-006's own title and AC-032's literal text ("`TEST-018` in
`tests/loop-consistency.tests.sh`"), so the bash suite is named `TEST-018`
exactly as specified. The PowerShell suite's own case is named `TEST-019`
instead, documented at its own call site with the reasoning above. Both
cases assert the identical ACs against the identical golden-trace fixture.

**4. "via T-001's `build_fixture`" (T-006 Scope) is not mechanically usable
to drive a review round.** `build_fixture`'s own F1 output (`tests/lib/fixture-matrix-builder.sh`)
is a minimal `mktemp -d` root containing, for F1 (`project_context=absent`,
`agents_marker=absent`), no files at all — it has no `specs/<feature>/`
tree, no `reports/` tree, and none of the driver-script symlink skeleton
`drive_review_round`/`Invoke-DriveReviewRound` requires. It cannot itself
be used to drive a round; `loop_fixture_init greenfield`/`Initialize-LoopFixture -Profile greenfield`
(the same mechanism `TEST-008` already uses) is the only fixture
constructor compatible with `drive_review_round`, and its own greenfield
skeleton already carries F1's exact Context-absent characteristics (no
`AGENTS.md`, no `sdd/project-context.yaml` are ever written by it). `TEST-018`/
`TEST-019` use `loop_fixture_init`/`Initialize-LoopFixture` for this
reason; `build_fixture` is not called by this task.
