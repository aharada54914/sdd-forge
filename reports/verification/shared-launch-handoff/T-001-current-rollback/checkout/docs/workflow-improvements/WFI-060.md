## Problem Evidence

`check-cross-model` requires EVERY panelist verdict to be `PASS`
(`check-cross-model.sh` step 6: `all_pass = all(v.get("verdict") == "PASS" ...)`,
and `if not all_pass or any_critical: ... result "FAIL"; sys.exit(1)`). It has
exactly one human-decision outcome, `NEEDS_HUMAN`, and that outcome is
reachable only from step 7, where the **evaluator** diverges from an
already-unanimous panel. There is no path at all for panelists diverging from
**each other**.

Observed on `epic-193-a5-capability-resolver` T-007 (`Risk: high`,
`Security-Sensitive: true`, so `sdd-ship` Step 4 makes a fresh panel a hard
pre-gate requirement). Fifteen panel rounds, two vendor slots (anthropic via
the Agent tool, openai via `run-panelist-gpt`'s codex transport), each round
against a freshly rebuilt bundle at the then-current bytes:

| Round | openai | anthropic |
|---|---|---|
| 13 | PASS, 0 findings | NEEDS_WORK, 2 Major |
| 14 | NEEDS_WORK, 1 Major | PASS, 0 Major |
| 15 | NEEDS_WORK, 2 Major | NEEDS_WORK, 3 Major |

The slots never both passed. Two specific observations make this a workflow
problem rather than an implementation one:

1. **Same bytes, different verdict.** Round 14 changed documentation and one
   mutation-log capture only — zero production-code change from round 13 —
   and the openai slot moved from PASS/0-findings to a Major.

2. **The slots contradict each other on substance.** On round 14 the anthropic
   slot examined the `artifact-publication-failed` branch's discard asymmetry
   and stated it was justified. On round 15 the openai slot filed the same
   asymmetry as a Major. Remediating for either vendor moves the artifact
   away from the other's stated position.

Every finding in that sequence was acted on; several were real defects and are
fixed. The point is not that the panel was wrong, it is that the gate has no
terminating condition when two honest reviewers do not converge, and no way to
record that state as a decision for a human.

## Root Cause Hypothesis

The consensus rule was written for the case it names in its own reference
(`cross-model-verification-policy.md`): catching a single model's blind spot
by requiring agreement. Unanimity is a sound rule for that. But the schema
already anticipates non-unanimity — the aggregate carries `divergence` and
`requires_human_decision` fields, and `NEEDS_HUMAN` is already a defined
`result` value — and step 6 simply never produces them. The gap is that
panelist-vs-panelist disagreement was modelled in the data and not in the
control flow, so the only representable outcomes are unanimous-pass and
fail-forever.

A second contributing factor: `sdd-ship` Step 4 makes the panel mandatory for
`Security-Sensitive: true` and offers exactly one escape, a
`Cross-Model-Waiver:` that is valid only alongside a human `Approval: Approved`
audit mark naming a **second distinct human approver**. On a single-maintainer
repository that escape is unreachable, so a non-converging panel is terminal.

## Proposed Change

In `check-cross-model.{sh,ps1}` step 6, split the failure branch:

- `any_critical` → `FAIL`, exit 1. Unchanged. A Critical from any vendor still
  blocks unconditionally.
- `not all_pass` and no Critical, with **at least two distinct vendors having
  reported and at least one PASS among them** → write the aggregate with
  `divergence: true`, `requires_human_decision: true`, `result: "NEEDS_HUMAN"`,
  and exit with a distinct non-zero code (proposed: 3) so callers can tell it
  apart from `FAIL`.
- `not all_pass` with no PASS at all → `FAIL`, exit 1. Unchanged. A panel that
  unanimously says NEEDS_WORK is not a divergence.

`sdd-ship` Step 4 then treats exit 3 as a stop-and-ask rather than a stop:
print the per-vendor verdicts and findings and require an explicit human
ruling, recorded the way `investigation.md` already records rulings, before
the task may proceed to the quality gate.

## Expected Effect

A Security-Sensitive task whose panel does not converge reaches a human with
the disagreement stated, instead of consuming unbounded remediation rounds.
The unanimity requirement is preserved for its actual purpose: no task ships
on a single vendor's approval, and no task ships over a Critical.

## Verification Metric

- `check-cross-model` exits 3 and writes `result: "NEEDS_HUMAN"` for a verdict
  set with two distinct vendors, one PASS, one NEEDS_WORK, no Critical.
- It still exits 1 with `result: "FAIL"` for (a) any Critical, (b) all-vendors
  NEEDS_WORK, (c) fewer than two distinct vendors, (d) any digest mismatch.
- `tests/cross-model.tests.{sh,ps1}` gain a case per row above, and each new
  case is shown to fail against the current script.

## Verification Plan

1. Add the divergence case and the three unchanged-failure cases to
   `tests/cross-model.tests.{sh,ps1}`.
2. Run them against the CURRENT script first and record that the divergence
   case fails (the script exits 1, not 3) while the other three already pass —
   proving the new case is not vacuous and the change is narrow.
3. Implement the split, re-run, and confirm all four pass in both runtimes.
4. Re-run the full `tests/run-all.{sh,ps1}` to confirm no other suite depended
   on `not all_pass` meaning exit 1.

## Rollback-Plan

Revert the step-6 split in both runtimes and the four test cases. The aggregate
schema is unchanged by this WFI — `divergence`, `requires_human_decision` and
the `NEEDS_HUMAN` result value already exist and are already written by step 7
— so no consumer of the aggregate needs to change in either direction.
