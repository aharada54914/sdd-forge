## Quality Gate Focus

- **The `-ccontains` / `-ceq` / `-cne` case-sensitive operators are load
  bearing throughout this task's new checks**, following the exact hazard
  T-003/T-004 already documented for this file: Pester's `Should Be` /
  `Should Not Be` and PowerShell's `-contains` are case-insensitive by
  default, which would let e.g. a `must_not_own` entry differing only in
  case silently satisfy a value-retention assertion it should not. Every
  set-membership and array-equality check in this task's additions uses the
  case-sensitive form.
- **The AC-015 `main` dependency (Specification Differences item 2) is the
  most environment-fragile part of this task.** If a future host runs this
  suite without a local `main` branch, the `git diff` check will ERROR
  rather than skip (the `-Skip` guard only covers `git` itself being
  absent), which is a visible red rather than a silent pass -- but a
  reviewer re-running this suite in an unfamiliar clone should check for a
  local `main` ref first if that specific check fails.
- **AC-013's twin-parity loop is the single most expensive part of this
  suite** (~47 of ~103 total seconds, 78 fixtures x 2 twins x 1 process
  each = 156 child-process spawns, dominated by `pwsh` per-process startup
  overhead). It is also the strongest single piece of evidence in this
  task: every fixture across all five tasks' corpora, not just this task's
  own five, was independently re-verified to produce IDENTICAL sh/ps1
  verdicts in this run.
- **The oversized (>10 MiB) T-002 fixture is included in the AC-013 corpus
  as-is**, re-generated via the existing `New-OversizedContractFixture`
  function rather than cached, so it is regenerated and rewritten to a new
  temp file on every full-suite run. This is intentional (proving parity
  holds on the actual oversized input, not a stand-in), but a future editor
  adding more large fixtures to the corpus should be aware this pattern
  multiplies suite runtime linearly.
- **AC-003's third concept (`APIOrder` / `order-taking-2`) is deliberately
  NOT the primary `Order`/`Fulfillment` pair.** REQ-005(a) and AC-003's Test
  Target describe the boundary values as living somewhere in "the fixture
  system," not necessarily on the named `Order` concept itself, so a third,
  minimally-specified concept was added to carry them without diluting the
  primary pair's REQ-005(a) content (purchase-only / delivery-only
  responsibilities, mutual `distinguished_from`, `must_not_own` naming
  `purchase price`). A reviewer checking AC-003 should confirm this reading
  matches intent.
