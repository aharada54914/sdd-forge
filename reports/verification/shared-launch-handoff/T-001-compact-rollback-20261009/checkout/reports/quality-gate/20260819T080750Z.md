## The cycle-1 Critical — resolved

Cycle 1 found that the ps1 twin decided validity with `ConvertFrom-Json`, a
lenient parser, while the sh twin used python3 `json.loads`, a strict one, so
the same document was VALID to one twin and INVALID to the other. A 17-case
characterisation probe found twelve divergent classes.

The fix replaced the decision point: a hand-written strict JSON scanner now
decides validity and `ConvertFrom-Json` only builds the object from text
already accepted, with its failure still yielding the same single `V2-PARSE`
line so both paths stay fail-closed.

Verified independently at three levels:

- **Gate's own re-probe.** All 17 original cases now agree on exit code and
  stderr. A well-formed v2 contract still exits 0 on both twins; the same
  contract with a trailing comma or an embedded NUL now yields byte-identical
  `V2-PARSE` on both, where the ps1 twin previously exited 0.
- **Evaluator's independent corpus.** 95 cases built from scratch without
  reading the fix's fixture list: **0 under-rejections**. 2 over-rejections,
  both proven pre-existing by executing the pre-fix twin (`HEAD~1`) on the
  same bytes.
- **Differential fuzz.** 7989 inputs through the extracted scanner bodies
  versus `json.loads`: **7989/7989 exact agreement, 0 over, 0 under, 0
  exceptions** — establishing the scanner generalises rather than being
  hardcoded to its fixtures.

The parity contract was respected in the opposite direction too. The target was
`json.loads`, not RFC 8259, because the ticket forbade changing the sh twin.
`NaN`, `Infinity`, `-Infinity` and duplicate keys remain accepted, while
`nan`, `NAN`, `INFINITY`, `NULL`, `True`, `TRUE` are rejected — so the
case-significant comparison is real and load-bearing, and the fix did not
"improve" on `json.loads` and thereby create a new divergence.
