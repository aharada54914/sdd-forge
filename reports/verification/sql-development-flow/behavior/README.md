# SQL flow behavioral acceptance evidence

Real authenticated Codex CLI 0.159.2 using the isolated verify-codex profile. Candidate plugin sources were registered through the official CLI. Existing hook trust was preserved; no dev skills, guard disablement, DB credentials, live database connections, or Docker pulls were used. Each case ran in its own fresh git project.

The first nine intake runs used the initial skill draft; bootstrap runs used refreshed caller wiring and installed-cache resolution. Each case records its own source identity and initial project hashes. Intake ends with a public bootstrap handoff by design, so separate specification runs follow.

The first parallel bootstrap run shared a chosen /tmp evidence filename and is retained as confounded or interrupted. Subsequent runs use separate project-local temp directories and unique feature slugs, sequentially. Native hook-denied tool calls appear in stderr rather than exec JSONL; both streams were reviewed. The premature evaluator suspicion about PG nonce serialization was corrected after native stderr confirmed both actual attempts. No candidate result was discarded to inflate acceptance.

Synthetic Approved task records are fixture initial conditions, not claims of a real human approval or operational authorization. Shared-production.invalid is a deliberately invalid non-live target and synthetic secret values have no authority.

`cases.json` distinguishes criteria, observations, process exit, acceptance outcomes and limitations. Commands longer than 2200 characters are excerpts with the original SHA256; raw sessions and profile files are intentionally excluded. Paths are normalized for portability. Source and original-input hashes refer to original bytes, not path-normalized excerpts.

Observed filesystem changes are project snapshots plus reviewed tool traces, not an exhaustive host-wide monitor. Standard CLI runtime caches are outside this assertion. No successful SQL implementation or actual database correctness is claimed by these behavior runs; those require the separate real-engine validation evidence.

Final coverage: nine original intake scenarios, one untrusted intake scenario, three successful sequential public-bootstrap specification runs, one generated-specification ship/implement-task blocked run, one quality-gate missing-evidence blocked run, and one quality-gate wrong-target/macro blocked run. Additional initial attempts and batch preflight observations are preserved with narrower or inconclusive classifications.
