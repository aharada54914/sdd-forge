## Verification Results

Two critical-review cycles, each with a fresh isolated `sdd-evaluator`
behind its own manifest and reserved ledger record:

- Cycle 1 — seq0763: NEEDS_WORK (1 Critical, 1 Major, 5 Minor).
- Cycle 2 — seq0764: both RESOLVED under independent reproduction;
  0 Critical, 0 Major, 4 Minor → PASS.

Remediation commit: `c24a1b8a`.

The Critical this gate caught is the sharpest finding of the whole feature:
**the parity suite's PowerShell twin could not see the defect it existed to
catch.** It captured process output through `Start-Process`
redirection, which silently normalizes line endings — an 8-byte
`A\r\nB\nC\r\n` arrived as 6 bytes with both CRs gone, and a payload with
no trailing newline arrived with one added. Injecting a CR into
`validate-capability-summary.ps1` left the ps1 twin 178/0 green while the
bash twin went 163/15 red. Because the staged CI skips the bash parity step
on Windows (`runner.os != 'Windows'`), the only lane running there was the
blind one, so AC-031's "the `.ps1` wrapper's own output stays LF-only on
Windows" had zero enforcement exactly where it matters — and Windows Python
emits CRLF from `print()` by default, making this a live risk rather than a
theoretical one. All launches now go through `Invoke-RawProcess`
(`System.Diagnostics.Process` + `BaseStream` binary capture); the cycle-2
evaluator confirmed by independent probe that the same 8 bytes now arrive
as `41 0d 0a 42 0a 43 0d 0a`, and that the identical CR injection turns
both runtimes red at the same 300/29.

The Major: the provider-neutrality scan excluded the bare word `lambda`,
which let through `LAMBDA_DEPLOY_TARGET = "lambda"` — precisely the threat
security-spec.md B5 names. The exclusion is now idiom-scoped (only
`key=lambda` is masked) and the scan covers all twelve files rather than
four.
