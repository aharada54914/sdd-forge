### Critical

**The ps1 twin accepts syntactically invalid JSON and exits 0.**
`plugins/sdd-domain/scripts/validate-domain-contract.ps1:211` parses with
`ConvertFrom-Json`, a lenient parser; the sh twin at `:169` parses with python3
`json.loads`, which is strict. The same document is therefore INVALID to one twin
and VALID to the other.

Reproduced by the gate itself, independently of the evaluator, on a structurally
complete v2 contract both twins accept at exit 0, mutated by one trailing comma:

```
$ bash …/validate-domain-contract.sh trailing-comma.json
V2-PARSE: input is not well-formed JSON and was not parsed further
exit=1
$ pwsh -NoProfile -File …/validate-domain-contract.ps1 trailing-comma.json
exit=0
```

The same split occurs for an embedded NUL byte. The evaluator demonstrated four
classes in total (embedded NUL, trailing comma, leading NUL bytes, single-quoted
key), all `sh=reject(1) / ps1=accept(0)`, against both T-002's committed bytes and
the current post-T-004 tree — so it was not fixed downstream.

This violates REQ-004(a)'s fail-closed parse and the security-spec statement that
a validator which silently passes an invalid contract "would weaken every
downstream gate built on it". It is the exact untrusted-input boundary T-002's own
Risk Rationale cites to justify the `high` tier. T-005's AC-013 parity corpus
contains no fixture of this class, so it would survive the whole feature unnoticed.

Recorded in `docs/review-tickets/RT-20260819-001.yml`.
