**2. `quality-gate-outcome:escalation` is recorded from the test case
itself, on the real, already-driven production scripts, never a
`plugins/**` edit.** See Summary, above, for the full reasoning. Concretely:
`TEST-019` drives `check-quality-gate-cycle-limit.sh`/`.ps1` to a real
3-gate-report Escalate-Human decision (`rc=1`, `Escalate-Human`) and
`select-agent-model.sh`/`.ps1` to two real escalation decisions
(lightweight→standard, standard→strong, reading each decision's own real
`.escalation.next_tier` from the script's JSON output), then calls
`_loop_trace_emit`/`Write-LoopTraceEvent quality-gate-outcome
quality-gate-outcome:escalation {next_tier: <observed>}` for each,
immediately after the real observation. No `plugins/sdd-quality-loop/
scripts/check-quality-gate-cycle-limit.{sh,ps1}` or
`plugins/sdd-implementation/scripts/select-agent-model.{sh,ps1}` line was
edited; both are driven strictly read-only, exactly as `TEST-011` already
does (security-spec.md B2, this suite's own file-header discipline).
`next_tier: "human"` for the cycle-limit script's own Escalate-Human
decision is the same schema-legal value `tests/loop-inventory.tests.sh`'s
own `TEST-009` fixture already establishes as a valid `next_tier` string
(that script's own real output is plain-text `Escalate-Human`, not a
`next_tier`-shaped JSON value — "human" is this task's own translation of
that real observed decision into the schema's `{next_tier: <string>}`
shape, the same translation discipline the design.md producer table's own
prose implies by grouping both scripts under one producer name).

**3. `done-transition:assert-terminal`'s value is the chain's own real
`terminal-tier` `BLOCKED` outcome, not `quality-gate`'s own `Escalate-Human`
terminal.** `assert_terminal`/`Test-LoopTerminal` hard-requires
`exit_code == 0` (`tests/lib/loop-driver.sh:1556`); `check-quality-gate-
cycle-limit.sh`'s own contract signals `Escalate-Human` via `exit 1`
(its exit code IS the verdict), so `assert_terminal quality-gate
Escalate-Human 1` can never pass — the same incompatibility `TEST-011.4`'s
own inline comment already documents for that exact reason (it asserts
`rc`/`out` directly instead). `TEST-019` instead asserts
`assert_terminal terminal-tier BLOCKED 0`/`Test-LoopTerminal -LoopId
"terminal-tier" -Observed "BLOCKED" -ExitCode 0` — the identical,
already-proven-working call `TEST-011.9` uses — on the chain's own final
`select-agent-model.sh` strong-tier-recurrence decision (real `exit 0`,
`status: "BLOCKED"`, `reason: "terminal-tier-recurrence"`), then records
`done-transition:assert-terminal` with value `"BLOCKED"` from the test
case itself immediately after, per T-006's own established pattern
(`assert_terminal`/`Test-LoopTerminal`'s function body is not edited;
re-verified byte-identical via the no-regression sweep, below).

**4. F1's own `capability_applicability` fixture state is `disabled-legacy`.**
`tests/loops/loop-inventory.json`'s `quality-gate` loop entry maps
`capability_applicability["disabled-legacy"] = "not-applicable
(disabled-legacy)"` — the literal Context-absent (non-active
`capability_enforcement`) cell design.md's own Compatibility Matrix F1 row
describes. `TEST-019.5` calls `assert_capability_applicability quality-gate
