## モデルと実装の対応

- TaskLock は `task-lock.mjs` の排他的 acquire、同一所有者の renew、TTL expiry、stale reclaim、所有者限定 release を表す。初期／acquire／renew／release の直後に `getLockStatus` が返した owner / stale を NDJSON の holders / leaseActive に変換した。別所有者の acquire が拒否されることも同じ実装テストで確認した。
- GateLifecycle は人の承認、実装完了、機械判定、品質ゲートの決定、再試行上限、改ざん・drift・OQ の分岐を表す。テストフィクスチャが tasks.md に与えた状態を実ゲートの前提検査で読み戻し、保存した execution.json の結果を使った。正常系は機械 PASS まで、異常系は実際の Git 基準に対する保護ファイルと仕様書の変更、TAMPER_DETECTED、UNDECLARED_DRIFT、保存された Provisional OQ まで観測した。独立レビューと最終 Done はモデル上の遷移で、フィクスチャは実タスクを Done に書き換えない。
- `specs/self-verification/formal/mapping.json` の `source_sync_commit` は比較の起点 fc166bd1a8b8303531c0445ff78965897ea59c61。`source_sha256` がこの作業ツリーの対象 6 ファイルの正確なバイト列を識別する。回帰テストは sources の和集合と全 SHA-256 の一致を要求する。更新時は対応するアクション・実トレースを再検証してからハッシュを更新する。
- [Cursor Pstack](https://github.com/cursor/plugins/tree/main/pstack/skills/create-formal-verification-skill) に沿い、コードとの対応、意図的に規則を破る変異、反例、探索境界を一緒に保持した。TLC の有限状態探索に加え、[Apalache](https://apalache-mc.org/docs/apalache/principles/assignments.html) で同じ TaskLock を検査した。遷移を観測条件と連言するため、フレーム条件を通常の次状態の等式で表して両チェッカーで実行した。
