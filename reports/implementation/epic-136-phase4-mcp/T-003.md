## Summary

`listGuardedFilesWithDiagnostics(root, relDir): GuardedListResult` is added,
returning `{ files: string[], errors: GuardedListError[] }`. The pre-existing
exported `listGuardedFiles` is reduced to a thin wrapper that returns
`.files` and nothing else, so its three existing call sites keep their exact
current behaviour and were not edited.

Three failure classes that previously all collapsed into a silent `[]` are now
distinguishable in `errors[]`:
1. guard rejection of `relDir` itself (allowlist/denylist/traversal),
2. a top-level or mid-walk `readdirSync` failure,
3. a per-entry `statSync` failure.

## The security-boundary ordering proof (security-spec.md B3)

This is the check that mattered most for a high-risk edit to the read choke
point, so the orchestrator re-derived it by reading the committed source rather
than accepting any claim about it.

`mcp/sdd-forge-mcp/src/path-guard.ts:293-332`:

```ts
export function listGuardedFilesWithDiagnostics(
  root: SddRoot,
  relDir: string,
): GuardedListResult {
  const guardResult = resolveGuardedDirectory(root, relDir);   // :297
  if (!guardResult.ok) {                                       // :298
    return { files: [], errors: [{ path: relDir, reason: guardResult.error.message }] };
  }
  ...
```

- `resolveGuardedDirectory` — which owns the allowlist, the denylist, and
  traversal/symlink resolution — is called at `:297`, **outside every
  `try`/`catch` in the function**.
- On rejection the function `return`s at `:299` with `files: []` **before any
  `readdirSync` or `statSync` is reached**. A denial can therefore never be
  swallowed into `errors[]` in a way that would let a denied path's contents
  through: the denial is reported in `errors[]` *and* `files` is empty.
- The two `try`/`catch` blocks (`:306` around `readdirSync`, `:316` around
  `statSync`) sit inside `walk`, which is only ever invoked at `:330` on
  `guardResult.data.resolvedPath` — i.e. only after the guard has passed.

The suite pins this behaviourally as well as structurally. From `green.log`,
two dedicated cases:

```
(AC-005, security-spec B3): a READABLE, NON-EMPTY directory outside the
  allowlist is denied BEFORE any walk-level readdirSync
(AC-005, security-spec B3): a denylisted directory reached through an
  allowlisted parent is denied BEFORE any walk-level readdirSync
```

Both use a readable, non-empty directory, so a regression that moved the guard
inside the try/catch would surface as non-empty `files` and fail the case.

## The AC-006 behaviour-preservation proof

`listGuardedFiles` is now (`path-guard.ts:350-352`):

```ts
export function listGuardedFiles(root: SddRoot, relDir: string): string[] {
  return listGuardedFilesWithDiagnostics(root, relDir).files;
}
```

The orchestrator diffed the pre-change body (`git show
9091f96b:mcp/sdd-forge-mcp/src/path-guard.ts`) against the new
`listGuardedFilesWithDiagnostics` body line by line. They are structurally
identical except for the added `errors.push(...)` calls:

| pre-change `listGuardedFiles` | new `...WithDiagnostics` | same? |
|---|---|---|
| `resolveGuardedDirectory` first, outside try/catch | same, `:297` | yes |
| guard failure -> `return []` | guard failure -> `files: []` | yes |
| `readdirSync` failure -> `return` (stop this dir) | `errors.push(...)` then `return` | yes for `files` |
| `statSync` failure -> `continue` (skip entry) | `errors.push(...)` then `continue` | yes for `files` |
| recurse on `isDirectory()`, push on `isFile()` | identical | yes |
| `walk(resolvedPath, relDir.replace(/\/+$/, ""))` | identical | yes |

Every divergence is an append to a *new* array. `files` is therefore
value-equal to the old `results` for every input, not merely "believed
equivalent". The suite also pins it empirically against the real fixtures of
all three call sites (from `green.log`):

```
(AC-006): report-lookup.ts's nested reports-directory scan shape lists
  byte-identically through both functions
(AC-006): quality-report.ts's own aggregation fixture lists byte-identically
  through both functions
(AC-006): review-ticket.ts's own aggregation fixture lists byte-identically
  through both functions
(AC-006): the real repository directories the 3 call sites scan list
  byte-identically through both functions
(AC-006): every guard-failure class still collapses to [] for the legacy
  function
(AC-006, BL-003): none of the 3 existing call sites was changed to opt into
  the diagnostics function
```
