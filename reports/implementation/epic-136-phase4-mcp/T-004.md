## How the partition property is verified

requirements.md's Field Definitions require every entry of `required` to land in
EXACTLY ONE of `present`/`missing`/`undeterminable`. `assertPartitionsRequired`
(`evidence.test.ts:255`) asserts that directly, in four parts, and is applied to
every fixture the suite touches:

1. **Covering, as a multiset.** `[...present, ...missing, ...undeterminable]`
   sorted must `deepEqual` `required` sorted. A dropped entry shortens the
   concatenation; a stray entry lengthens it. This alone forbids omissions.
2. **No duplicates anywhere.** `new Set(union).size === union.length`. Combined
   with (1) — which already forbids omissions — this is exactly "exactly one
   of", because a value appearing twice across the three arrays would have to
   displace another to keep the multiset equal, and (1) forbids that.
3. **Pairwise disjointness named explicitly** for all three pairs
   (present/missing, present/undeterminable, missing/undeterminable), so a
   failure reads directly at the failure site instead of being inferred.
4. **`required` itself unaffected** — still exactly the 3 baseline names
   (AC-007's "with `required` unaffected").

(1)+(2) is the load-bearing pair; (3) is redundant with them by construction and
is present for diagnosability, which is stated here rather than left to look
like an independent proof. It is applied at: TEST-008's no-artifacts fixture,
the no-pass-verdict fixture, both TEST-007 sub-cases, and every Done task of
both fixtures inside the parity test.

## The parity assertion, and why it is satisfiable

Implemented form (`evidence.test.ts:431`), for each of TEST-007's and
TEST-008's own two fixtures, and within each for every task whose
`Status` is `Done`:

```
taskId in (missing ∪ undeterminable)  <=>  parseTaskState reports
                                            done-quality-gate-report-missing
```

asserted as `assert.equal(inUnion, parserReportsFailure, ...)` — a
biconditional, not a one-way implication.

**Why the union form is satisfiable and the `missing`-only form is not.** For
TEST-007's scan-failure fixture, REQ-004 routes the requirement to
`undeterminable` and *out of* `missing`, while `task-validation.ts` is
deliberately unchanged and still reports the failure. So `missing`-only reads
`false === true` and is false for that fixture no matter how the code is
written. The union form reads `true === true`. For TEST-008's scan-succeeded
fixture `undeterminable` is empty and the union reduces to the original
`missing`-only parity, which still holds exactly.

**Why the two scope restrictions are real, not conveniences.**

- *Done-scoped*: `done-quality-gate-report-missing` is emitted only by
  `validateDoneEvidence`, which `task-validation.ts:74-77` calls only for
  `Status: Done` tasks. A non-Done task can never satisfy the right-hand side
  regardless of what `evidence_find_missing` returns — and
  `evidence_find_missing` is deliberately Status-independent. The test does not
  skip the non-Done tasks: it asserts they emit no `done-*` failure at all,
  so the restriction is backed by a check rather than assumed.
- *Fixture-scoped*: a **partial-success** scan (`errors` non-empty AND
  `matches` non-empty — e.g. a readable `reports/quality-gate` with one
  unreadable subdirectory that still yields a matching report at the top level)
  would put the requirement in `undeterminable` while the unchanged
  `anyFileContaining` still returns matches and so reports no failure. That
  breaks the biconditional. Neither fixture has that shape — each scan either
  wholly fails or wholly succeeds — which is exactly why the assertion is
  satisfiable here.

This last point is a genuine limit of design.md's surrounding prose, which
states the invariant more broadly than is universally true. The implemented test
pins the scoped, satisfiable form and says so in its own comment; the broader
claim is not asserted. Recorded here as a specification difference below.

**The asymmetry is separately pinned** (`evidence.test.ts:491`): for TEST-007's
scan-failure fixture the test asserts the requirement IS in `undeterminable`,
is NOT in `missing`, `parseTaskState` STILL reports
`done-quality-gate-report-missing`, and — as an executable statement, not prose
— that `missing.includes(...) === parserReportsFailure` is **false**. A future
change that undid REQ-004's routing, or that reintroduced the unsatisfiable
`missing`-only form, fails this test.
