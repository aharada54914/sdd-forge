## Specification Differences

1. `contracts/context-projection.schema.json` is a byte-for-byte
   transcription of design.md's API / Contract Plan JSON block for this
   file (design.md lines 504-587), including `source_sha256`'s and
   `provider_bindings_sha256`'s `pattern:
   "^sha256:[0-9a-f]{64}$"` constraint and `components.propertyNames:
   {"minLength": 1}`. design.md's own separate keyword-audit paragraph
   ("keywords each committed schema instance actually uses, cross-checked
   against this list") states `context-projection.schema.json` uses only
   `type, additionalProperties, required, properties, enum, propertyNames,
   items, oneOf, const, $ref/definitions` — omitting **both** `pattern`
   and `minLength`, which contradicts the committed JSON block in the same
   document (confirmed by a recursive walk of the committed schema:
   `$ref, additionalProperties, const, definitions, enum, items,
   minLength, oneOf, pattern, properties, propertyNames, required, type`).
   `validate-context-projection.py` implements both `pattern` and
   `minLength` support (the same `_ecma_anchor`/`_compile_pattern`
   ECMA-262 `$`-semantics fix T-001's/T-002's engines already carry) so
   both fields' constraints are actually enforced rather than silently
   unconstrained. This is a design.md self-contradiction, reported here
   (and in `verification/T-003/metaschema-conformance.md`) rather than
   patched — design.md is not a Planned File of T-003. Per RT-20260817-003
   expected_fix item 2 (which asked a future task to check the *full*
   scope of this same design.md keyword-audit gap rather than stop at the
   one keyword T-002's report found), this report records **both** dropped
   keywords, not just `pattern`.
2. `validate-context-projection.py` is an independent copy of T-001's/
   T-002's hand-rolled draft-07 subset engine (same functions, same
   keyword coverage), not an import from a sibling script. design.md
   defines four standalone validator scripts; none is described as
