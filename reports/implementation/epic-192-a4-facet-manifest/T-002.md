## Specification Differences

1. `contracts/capability-summary.schema.json` is a byte-for-byte
   transcription of design.md's API / Contract Plan JSON block for this
   file, including the `feature` field's `pattern:
   "^[a-z0-9][a-z0-9-]*$"` constraint. design.md's own separate
   keyword-audit paragraph ("keywords each committed schema instance
   actually uses, cross-checked against this list") states
   `capability-summary.schema.json` uses only `type,
   additionalProperties, required, properties, const, items,
   uniqueItems` — omitting `pattern`, which contradicts the committed
   JSON block in the same document. `validate-capability-summary.py`
   implements `pattern` support (the same `_ecma_anchor`/`_compile_pattern`
   ECMA-262 `$`-semantics fix T-001's engine already carries) so this
   field's constraint is actually enforced rather than silently
   unconstrained — the same failure mode design.md's own history already
   names for a different keyword (the `items` keyword omission,
   "adversarial review" note in the same paragraph). This is a design.md
   self-contradiction, reported here (and in
   `verification/T-002/metaschema-conformance.md`) rather than patched —
   design.md is not a Planned File of T-002.
2. `validate-capability-summary.py` is an independent copy of T-001's
   hand-rolled draft-07 subset engine (same functions, same keyword
   coverage), not an import from `validate-facet-manifest.py`. design.md
   defines four standalone validator scripts; none is described as
   importing a sibling script, and tasks.md's own Planned Files section
   lists each validator's `.py`/`.sh`/`.ps1` as independently authored
   files. `load_manifest()`'s file-extension dispatch (`.yaml`/`.yml`
   through the mandatory canonicalizer subprocess, `.json` directly via
   stdlib `json.load`) is carried over unchanged from T-001, for the same
   reason T-001 documents: it lets the regression suite exercise
   `validate_document()` against pre-canonical JSON fixtures without
   depending on Epic A1's canonicalizer being present, while not weakening
   the YAML parse contract's fail-closed behavior for real `.yaml` inputs
   in any way. Epic A1's canonicalizer was re-verified present in this
   checkout at this task's own implementation-start time (`ls
   plugins/sdd-quality-loop/scripts/canonicalize-sdd-yaml*` returned all
   four runtime files), so the YAML round-trip fixture
   (`canonicalizer-roundtrip-valid.yaml`) exercises the real subprocess
   end-to-end, not a deferred/skipped path.
3. The fixture subdirectory `tests/fixtures/facet-manifest/capability-summary/`
   is a naming choice not spelled out verbatim in tasks.md's Planned Files
   (which only names the existing `tests/fixtures/facet-manifest/` parent
   directory as "agent-editable — adds this task's Capability Summary
   fixtures"). Chosen for parity with T-001's own `schema/`/`semantics/`
