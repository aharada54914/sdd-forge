## Summary

Implemented `plugins/sdd-quality-loop/scripts/validate-approval-sidecar.py`
(+ `.sh`/`.ps1` dispatch-only wrappers): the six REQ-005 standard
validation gates, run in order with short-circuit-on-first-failure and a
stable, category-specific exit code per rejection; the `--verify-provenance`
historical re-check mode (HMAC self-check + weakening-provenance internal
consistency, no `--content` required); and a promoted-to-production port
of the minimal draft-07 JSON Schema subset validator T-001's and T-004's
own test suites had only ever proven as a test-side reference harness
(`type`/`required`/`additionalProperties`/`properties`/`items`/`enum`/
`const`/`minLength`/`oneOf` — sufficient for `contracts/project-context
.schema.json`, `contracts/provider-bindings.schema.json`, and
`contracts/approver-registry.schema.json`, none of which use `$ref`/
`pattern`/`minimum`).

**Independent-verification design decision**: this validator imports
NOTHING from `generate-approval-sidecar.py` or `detect-policy-weakening.py`
— every check (canonicalizer dispatch, `SDD_CONTEXT_KEY` resolution,
preimage construction, the `sdd/.staging/*/TRANSACTION.json` journal
check) is independently reimplemented, matching the SAME per-script
duplication convention T-003 and T-005 already established for the
canonicalizer-dispatch wrapper (each has its own small copy, never
importing the sibling's). This is deliberate: an imported, shared
implementation would silently mirror a generator-side bug rather than
catch it, defeating a validator's entire purpose. Byte-parity with the
established `_resolve_sudo_key` pattern is instead PROVEN EXECUTABLY
(obligation 1, below), not achieved by code sharing.

**Carry-forward obligations discharged** (see "Carry-Forward Obligations"
section below for full detail and evidence paths): (1) executable
key-parity proof; (2) non-bootstrap null-`weakening_verdict` backstop
(`WEAKENING_VERDICT_MISSING`); (3) AC-045 PRODUCTION discharge
(`DUPLICATE_APPROVER_REGISTRY_ID`) plus an explicit ordering-assertion
reconciliation statement; (4) TEST-019 exercised end-to-end from this
suite's side, with an explicit discharge note documenting the ACTUAL
current `generate-approval-sidecar.py` behavior for case (a); (4b)
`WEAKENING_PROVENANCE_UNDERAPPROVED` enforced at BOTH the standard
validation path and `--verify-provenance`.

**Scoping decision (documented, not a silent gap)**: design.md's REQ-004
text describes `validate-approval-sidecar.py` re-deriving
`predecessor_context_sha256`/`weakening_verdict`/`approval_epoch` against
a STILL-live, about-to-be-superseded anchor for a STAGED (pre-publish)
candidate, rejecting on disagreement. T-006's own frozen Goal/Scope/Done
When names no TEST id for this behavior (the six gates, `--verify-provenance`,
and the carry-forward obligations are the entirety of this task's
authorized scope), and design.md's own Test Strategy items (6, 10f) confirm
neither TEST-014/015/019/020/043/046 exercises it. This is NOT implemented
here — implementing untested behavior beyond a frozen Done When would
itself violate strict-TDD discipline (no acceptance criterion exists to
write a Red test against) and scope discipline. Flagged here as a residual
design-vs-task-decomposition gap for a future task (likely folded into
T-007's `apply-human-copy` publish-time validation call, or a dedicated
follow-up) — NOT silently papered over.

**T-005 residual gap noted, not fixed (out of T-006 scope)**:
`detect-policy-weakening.py`'s `_count_distinct_registry_identities` still
silently deduplicates a malformed (duplicate-`id`) registry via a bare
`set()`, rather than rejecting it — this validator's own independent
`DUPLICATE_APPROVER_REGISTRY_ID` check does not touch or depend on that
function, so REQ-005's own validation contract is never fooled by it, but
T-005's internal count itself remains unremediated (T-005 is `Status:
Done`; "the weakening detector's own category/verdict computation" is
explicitly Out of Scope for T-006).
