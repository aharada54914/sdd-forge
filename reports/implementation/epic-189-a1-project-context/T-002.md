## Quality Gate Remedy (seq0346, verdict NEEDS_WORK)

The independent evaluator (`reports/quality-gate/2026-07-29T045606Z-T-002.md`)
confirmed the implementation core genuine — an independent JCS
number-formatting differential across 8,023 doubles vs. Node's
`JSON.stringify` found zero mismatches, and an independent whole-document
differential across 400 pseudo-random accepted-subset documents vs. a
from-scratch RFC 8785 reference found zero mismatches/rejections — and
scoped the remedy to 3 Major findings, all addressed in this follow-up
session:

1. **Lone-surrogate escapes crashed uncaught** (report cites py:742/:759):
   `a: "\ud800"` (value, YAML mode), a lone surrogate as a mapping KEY, and
   the same via JSON input mode all reached the serializer and raised an
   uncaught `UnicodeEncodeError` — exit 1, a raw Python traceback, outside
   the documented category/exit-code contract. **Fixed**: added
   `_reject_if_lone_surrogate()`, called on every string (key and value
   alike) during the post-parse `normalize_and_validate` walk, raising
   `INVALID_UTF8_REJECTED` (exit 10, an EXISTING category — no new
   category or exit code was introduced).

   **Category-assignment rationale (design.md citation)**: design.md's
   Canonicalization procedure step 1 is "Read file bytes; decode as UTF-8
   (reject on decode error)"; step 6 is "Emit: the canonical UTF-8 byte
   sequence." Together these establish the pipeline's foundational
   invariant — it operates only on text that is valid Unicode and
   therefore always representable in UTF-8. A lone (unpaired) UTF-16
   surrogate (U+D800–U+DFFF) is, per RFC 3629, categorically excluded from
   UTF-8's codespace — there is no valid UTF-8 encoding for it, full stop.
   In this parser such a surrogate can be produced only via a `\uXXXX`
   escape inside a double-quoted scalar, which the accepted subset's own
   text explicitly allows ("double-quoted (JSON's escape set exactly,
   incl. `\uXXXX`)", Design Decisions) — so it cannot be rejected at parse
   time as an out-of-subset construct; it is syntactically valid escape
   syntax that resolves to semantically invalid Unicode content, discovered
   only once the pipeline tries to treat it as text (NFC normalization /
   UTF-8 re-encoding). This is the SAME defect step 1's decode-error check
   exists to prevent, just surfaced at a different pipeline stage (an
   escape-produced invalid scalar rather than an invalid input byte
   sequence) — `INVALID_UTF8_REJECTED`'s own plain meaning ("this is not
   valid UTF-8/Unicode text") covers both without strain.
   `UNSUPPORTED_SYNTAX_REJECTED` was considered and rejected as a fit: its
   own enumerated scope (Design Decisions' "everything else" list —
   non-empty flow, block scalars, directives, explicit/merge keys, tab
   indentation, leading `---`, reserved-sigil scalars) is specifically
   GRAMMATICAL/syntactic out-of-subset shapes, not post-resolution content
   validity (which the design already treats as a separate class — see
   `NUMBER_OUT_OF_RANGE_REJECTED` and `POST_NFC_DUPLICATE_KEY_REJECTED`,
   both post-parse content checks, not syntax checks). Since exactly one
   existing category fit defensibly, no new category/exit code was
   introduced and no Block-and-Stop was needed.

2. **Plain-scalar embedded `": "` was best-effort interpreted** (report
   cites py:454,488,516): `a: b: c` produced `{"a":"b: c"}` (rc=0) instead
   of being rejected, and `key: value:` similarly produced `{"key":"value:"}`
   — YAML 1.2 forbids `": "` inside a plain scalar for exactly this
   ambiguity, and design.md's Design Decisions states "never a best-effort
   interpretation." **Fixed**: `resolve_value_str` now calls the existing
   `_looks_like_mapping_entry()` probe on every plain (unquoted,
   non-reserved-sigil) scalar value and rejects with
   `UNSUPPORTED_SYNTAX_REJECTED` (exit 26) plus the quote-the-scalar hint
   when the value contains `": "` or ends with `":"`. Applies uniformly to
   mapping values, sequence bare-scalar items, and inline `- key: value`
   values (all funnel through `resolve_value_str`). Verified NOT to
   over-reject: URLs (`http://example.com`, no `": "` since it's `"://"`,
   not colon-space) and quoted values containing `": "` still succeed.

3. **Test gaps**: neither suite exercised `UNSUPPORTED_SYNTAX_REJECTED`
   (26), `INVALID_UTF8_REJECTED` (10), `INVALID_JSON_REJECTED` (11), or
   JSON input mode at all (which is exactly why findings 1 and 2 reached
   the gate). **Fixed**: added 23 new regression assertions per runtime —
   see Tests Added Or Updated. Also replaced the Minor-finding tautological
   exit-code-table test (asserted only literals typed into the test file,
   never read the script's own table) with one that reads
   `CATEGORY_EXIT_CODES` directly out of `canonicalize-sdd-yaml.py` via
   `importlib.util` (sh) / a `python3` subprocess (ps1) and diffs it
   against the documented table — a real comparison that now fails if the
   two diverge (report's Recommended/optional item (d)).

  content, which also correctly keeps a genuinely single-document

  instead.

  treated ANY content starting with a quote character as a mapping-entry
  probe, misrouting a bare top-level quoted-scalar document (e.g. a
  document whose entire content is `"just a string"`) into mapping
  parsing. Fixed by actually locating the quoted token's closing quote
  and checking for an immediately-following `:`.

  the parser): when this wrapper's own stdout is redirected (as any
  CI/automation invocation does), PowerShell's `&` call operator routes

  child via `[System.Diagnostics.Process]` directly with
  `UseShellExecute=$false` and no redirection, which makes it inherit this
  process's raw OS-level stdout/stderr handles instead of going through
  PowerShell's pipeline. Confirmed byte-exact (51 bytes, no trailing
  newline) both via the test suite's own `[System.Diagnostics.Process]`
  + `MemoryStream` capture and via plain shell redirection
  (`pwsh -File ... > file`).
