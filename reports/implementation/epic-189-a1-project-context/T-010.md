## Summary

Added a two-runtime acceptance suite proving that a write attempt against
each of the four basenames REQ-007 registered
(`sdd/project-context.approval.json`, `sdd/provider-bindings.approval.json`,
`sdd/approver-registry.yaml`, `sdd/.hook-canary-sentinel`) is DENIED through
every one of design.md Test Strategy item 8's 12 mutation surfaces, including
under an active, fixture-signed `SDD_SUDO` token — 4 × 12 × 2 = 96
independent assertions per runtime, against the live post-application guard.

The guard is driven directly: each cell pipes a synthetic hook payload on
stdin to the real guard entry point and reads its exit status (0 = allow,
2 = deny), the mechanism `tests/guards.tests.sh` and
`tests/guard-r10-port.tests.ps1` already use. No agent is in the loop; an
agent observing its own tool call being blocked would be evidence about the
environment's hook, not about the guard's decision function, and would not be
reproducible in CI.

initially omitted `content`, so all four of its cells were denied by the

the protected-file rule. The paired `MUT-*` block caught it — the cell kept
denying after de-registration. That defect class is now permanently guarded
by `MUT-*` and is reproduced as mutation M5 below.
