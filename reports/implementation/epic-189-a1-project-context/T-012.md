### The settled REQ-010 scope ruling, and how it is made falsifiable

T-011 handed forward an apparent conflict about whether an entirely-legacy
project may continue after a non-`HOOK_ACTIVE` handshake. It is resolved from
the frozen spec text, not re-litigated:

- `design.md:1112` — "the calling skill MUST stop **Capability Mode**, never
  silently fall back to legacy". The object of "stop" is Capability Mode, not
  the skill invocation.
- `requirements.md:1078` — the handshake is invoked "as its first
  **Capability-Mode-relevant** action before trusting `HOOK_ACTIVE`-gated
  behavior". The gate is scoped to `HOOK_ACTIVE`-gated behaviour.
- `requirements.md:1821-1827` — `CAPABILITY_RUNTIME_UNAVAILABLE` is "distinct
  from any Capability-mode-inactive state (ADR-0016's `disabled-legacy`),
  which is a **normal, expected condition for a project with no Project
  Context, not an error**."
- `design.md:1734` — the two are "**never conflated with `disabled-legacy`**".

Therefore a project with **no** Project Context is in `disabled-legacy` and
continues on the compatibility-fallback path; a non-`HOOK_ACTIVE` handshake
does not stop it, because it never entered Capability Mode. A project **with**
a valid Project Context that receives a non-`HOOK_ACTIVE` handshake MUST stop
with `CAPABILITY_RUNTIME_UNAVAILABLE` and MUST NOT degrade to legacy. The
prohibited transition is Capability Mode → legacy, never legacy → legacy —
which preserves exactly the silent-downgrade failure ADR-0023 exists to close.

No spec text contradicting this reading was found.

Both staged candidates encode it as a second machine-readable block,
`<!-- sdd:capability-gate-scope v1 -->`, over the two axes that actually
decide the question:

| Gate | Project Context | Handshake | Resolution |
|---|---|---|---|
| G1 | physically present and valid | `HOOK_ACTIVE` | `CAPABILITY_MODE` |
| G2 | physically present and valid | not `HOOK_ACTIVE` | `CAPABILITY_RUNTIME_UNAVAILABLE` |
| G3 | physically absent | `HOOK_ACTIVE` | `DISABLED_LEGACY` |
| G4 | physically absent | not `HOOK_ACTIVE` | `DISABLED_LEGACY` |

**Both directions are asserted, and neither assertion restates its own
fixture.** Three comparisons are DERIVED from each document's own table, so
they survive a rename of every token:

| assertion | what a violation would be |
|---|---|
| `G2 != G4` | conflating a valid Context's runtime failure with `disabled-legacy` |
| `G3 == G4` | letting the handshake outcome change an absent-Context project's fate (legacy → legacy treated as a downgrade) |
| `G1 != G2` | a decorative gate that never actually stops Capability Mode |

and two mutations inject exactly those two defects, one per direction, per
staged document: `g2-degrade-to-legacy` (a valid Context degrading to legacy)
and `g4-conflate-disabled-legacy` (an entirely-legacy project reported as the
runtime error). A future change that conflates the two fails a test in
whichever direction it conflates them.

carry the unscoped step-4 wording only, and they are not in T-012's

### AC-026 coverage — the two previously-unproven named cases

AC-026 (`requirements.md:1462-1466`) names "HMAC mismatch (**including a
rotated-key fixture**)" and "unregistered **or duplicate** approver identity".
At seq0370 the suite exercised a bit-flipped HMAC and an unregistered approver
only. Both gaps are now closed, and neither is left as an open question:

- **Rotated key — ADDED here** (TEST-026 4b). Nothing in `tests/` covered it: a
  sweep for `rotat*`/`key_id`/`KEY_ROTATED`/`superseded` across every `.sh` and
  `.ps1` suite found no rotated-key fixture anywhere. The existing bit-flip
  produces a *corrupt* MAC no key ever generated; a rotated key produces a
  *structurally perfect* MAC the REAL generator genuinely emitted under the key
  in force at signing time. `sign_project_with_key` / `Invoke-SignWithKey`
  parameterizes the signing key (with `sign_project` / `Invoke-Sign` delegating
  to it, so the two paths cannot drift in anything but the key), a second
  fixture project is signed under `$ROTATED_OLD_KEY`, and validation under the
  current key is asserted to exit **40 `HMAC_MISMATCH`**. Three companion
  assertions keep it honest: the two keys are asserted distinct; a **pristine
  baseline** — the byte-identical project signed under the CURRENT key — is
  asserted to exit **0**, so the mutant's rejection is attributable to the
  rotation alone; and the two sidecars' `hmac` fields are asserted to differ,
  proving the generator really signed twice under two different keys.
- **Duplicate approver identity — CITED, deliberately not re-proven.** Covered
  by T-006's own validator suite at
  `tests/validate-approval-sidecar.tests.sh:375-392` (`.ps1` twin at `:360-373`):
  a hand-signed fixture with `primary_approval.approver ==
  second_approval.approver == "alice"`, asserted to exit **10** with
  `DUPLICATE_APPROVER_IDENTITY` on stderr, driving the real validator. Two
  further sites cover the generator side
  (`tests/generate-approval-sidecar.tests.sh:735-757`) and the
  `--verify-provenance` path (`:776-806`). It is not duplicated here because
  `generate-approval-sidecar.py` **refuses to produce** that shape, so the
  fixture must be hand-signed, and T-006 owns that machinery. This citation was
  established by reading those files at remedy time, not assumed.

### Cross-pair atomicity — why splitting the publish is sound, and what replaces it

Publishing the two consumers as two single-target batches forfeits cross-pair
filesystem atomicity. That forfeit is derived from the spec, not chosen:

1. **The design never required it for this pair.** `design.md:988-993`
   introduces multi-target atomicity by ENUMERATING the batches it exists for —
   "REQ-004's sidecar+anchor publish, REQ-007's own six-file guard-invariants
   batch, the REQ-007 self-protection batch that includes
   `apply-human-copy.{sh,ps1}`'s own two basenames". T-012's pair is not among
   them. The gap it names is the reader-consistency class ("the anchor
   publishes but the sidecar doesn't (or vice versa)"), and step 6 of the same
   contract binds only "any script reading more than one of a transaction's
   targets together, and depending on them being mutually consistent". Nothing
   reads `ship/SKILL.md` and `lite-spec/SKILL.md` together; each is read by its
   own skill invocation alone. Neither file's validity depends on the other.
2. **The END state is nevertheless constrained.** `ADR-0023:59-62` requires
   Epic A1 to enumerate every CLI-flag consumer "before migrating any of them,
   to avoid a partial migration where some skills honor the new precedence and
   others still honor the old one" — precisely a half-applied pair.
3. **Nothing asserted it.** The evaluator's finding is confirmed independently
   here: mutation **M2** shows a half-applied pair trips **exactly one**
   assertion, and before remedy-1 that assertion did not exist, so the suite
   was fully green on a half-migrated repository.

So the replacement is a **pair-consistency assertion on the terminal state**,
not a re-creation of filesystem atomicity: TEST-PUB now asserts both protected
consumers are in the SAME publication state.

**Why it cannot produce a spurious failure.** It reports a difference that
genuinely exists on disk at the moment of observation, and there is no state in
which the two live files sit in different publication states while ADR-0023 is
nevertheless satisfied. The one window in which they legitimately differ is
BETWEEN the runbook's batch 1 and batch 2 — and the runbook runs this suite only
at step 7, after BOTH batches, so the documented procedure never observes it. If
a human runs the suite inside that window anyway, the assertion is a TRUE report
of a real half-applied pair, and the runbook's Rollback case B states both ways
to converge. There is no configuration in which it fires on a correct
repository: it is green both before any apply (both `unpublished`) and after
both batches (both `published`), which is exactly what the 139/0 tallies below
and the M2 baseline demonstrate.

### Why the assertions cannot pass vacuously

1. **Expectations never come from the artifact under test.** `EXPECTED_ROWS`
   and `EXPECTED_GATE_ROWS` are transcribed from ADR-0023 / AC-024 / AC-039
   and the settled ruling into each suite.
2. **Which case applies is observed, not assumed.** C1/C2 are decided by a
   real filesystem probe plus the real validator's real exit code; C3..C6 read
   `spec_profile` back OFF DISK. TEST-025 chains fixture → case id →
   resolution → stop/continue disposition, so the fixture picks the row and
   the document supplies the answer.
3. **AC-025's prose is turned into a partition, not a string match.** The six
   resolutions are split into STOP `{ERROR_STOP, PROJECT_CONTEXT_INVALID}` and
   CONTINUE `{COMPATIBILITY_FALLBACK, PROMOTE_FULL, NO_OP_LITE, NO_OP_FULL}`,
   and the error-stop and promotion cases are asserted to have OPPOSITE
   dispositions. A rename cannot satisfy that.
4. **The load-bearing assertions are inequalities**, not restatements:
   `resolution(C1) != resolution(C2)` per consumer, and the three gate-scope
   comparisons above.
5. **Every mutation is a DELTA** over a pristine baseline that must CONFORM,
   *and* re-runs the ROUTING extractor against the mutated copy and requires
   it to report something other than the pristine value. That second half is
   this task's answer to T-011's only substantive Minor: the mutation lane now
   covers `doc_resolution()` / `gate_resolution()` — the functions behind the
   30-assertion matrix and the scope ruling — **inside the committed suite**,
   so there is no unpersisted external harness and the baselines can never
   drift out of sync with the suite.

### Deliberate runtime divergence (a variant axis, not duplication)

Continuing T-011's discipline: the `.sh` suite extracts and classifies with a
Python helper; the `.ps1` twin reimplements every extractor natively in
PowerShell — including the flag-cell splitting TEST-025 depends on — and
derives its expectations independently. Both lanes drive the same real
`generate-approval-sidecar.py` / `validate-approval-sidecar.py`, because those
tools *are* the production behaviour under observation.

**That divergence paid for itself during the Red capture.** With the staged
candidates absent, the two lanes disagreed 60/74 vs 58/76. The cause was a
real defect in the `.ps1` twin: its G4 assertion was written as
`$g4 -ne 'CAPABILITY_RUNTIME_UNAVAILABLE'`, which **passes vacuously when the
document has no gate table at all**. The POSIX lane's `assert_ne` requires
both sides non-empty and correctly failed. The `.ps1` assertion was fixed to
require non-empty, after which both lanes agree at 58/76. A second `.ps1`
defect surfaced in the same run: `Copy-Item` under
`$ErrorActionPreference = 'Stop'` aborted the whole suite with no tally when a
source document was missing — meaning the twin could not produce a Red
measurement at all. Both fixes are in the committed suite.
