### The settled REQ-010 scope ruling, and how it is made falsifiable

T-011 handed forward an apparent conflict about whether an entirely-legacy
project may continue after a non-`HOOK_ACTIVE` handshake. It is resolved from
the frozen spec text, not re-litigated:

- `design.md:1112` — "the calling skill MUST stop **Capability Mode**, never
  silently fall back to legacy". The object of "stop" is Capability Mode, not
  the skill invocation.
- `requirements.md:1078` — the handshake is invoked "as its first
  **Capability-Mode-relevant** action before trusting `HOOK_ACTIVE`-gated
  behavior". The gate is scoped to `HOOK_ACTIVE`-gated behaviour.
- `requirements.md:1821-1827` — `CAPABILITY_RUNTIME_UNAVAILABLE` is "distinct
  from any Capability-mode-inactive state (ADR-0016's `disabled-legacy`),
  which is a **normal, expected condition for a project with no Project
  Context, not an error**."
- `design.md:1734` — the two are "**never conflated with `disabled-legacy`**".

Therefore a project with **no** Project Context is in `disabled-legacy` and
continues on the compatibility-fallback path; a non-`HOOK_ACTIVE` handshake
does not stop it, because it never entered Capability Mode. A project **with**
a valid Project Context that receives a non-`HOOK_ACTIVE` handshake MUST stop
with `CAPABILITY_RUNTIME_UNAVAILABLE` and MUST NOT degrade to legacy. The
prohibited transition is Capability Mode → legacy, never legacy → legacy —
which preserves exactly the silent-downgrade failure ADR-0023 exists to close.

No spec text contradicting this reading was found.

Both staged candidates encode it as a second machine-readable block,
`<!-- sdd:capability-gate-scope v1 -->`, over the two axes that actually
decide the question:

| Gate | Project Context | Handshake | Resolution |
|---|---|---|---|
| G1 | physically present and valid | `HOOK_ACTIVE` | `CAPABILITY_MODE` |
| G2 | physically present and valid | not `HOOK_ACTIVE` | `CAPABILITY_RUNTIME_UNAVAILABLE` |
| G3 | physically absent | `HOOK_ACTIVE` | `DISABLED_LEGACY` |
| G4 | physically absent | not `HOOK_ACTIVE` | `DISABLED_LEGACY` |

**Both directions are asserted, and neither assertion restates its own
fixture.** Three comparisons are DERIVED from each document's own table, so
they survive a rename of every token:

| assertion | what a violation would be |
|---|---|
| `G2 != G4` | conflating a valid Context's runtime failure with `disabled-legacy` |
| `G3 == G4` | letting the handshake outcome change an absent-Context project's fate (legacy → legacy treated as a downgrade) |
| `G1 != G2` | a decorative gate that never actually stops Capability Mode |

and two mutations inject exactly those two defects, one per direction, per
staged document: `g2-degrade-to-legacy` (a valid Context degrading to legacy)
and `g4-conflate-disabled-legacy` (an entirely-legacy project reported as the
runtime error). A future change that conflates the two fails a test in
whichever direction it conflates them.

**Scope limit, stated plainly**: the `capability-gate-scope` block is carried

### Why the assertions cannot pass vacuously

1. **Expectations never come from the artifact under test.** `EXPECTED_ROWS`
   and `EXPECTED_GATE_ROWS` are transcribed from ADR-0023 / AC-024 / AC-039
   and the settled ruling into each suite.
2. **Which case applies is observed, not assumed.** C1/C2 are decided by a
   real filesystem probe plus the real validator's real exit code; C3..C6 read
   `spec_profile` back OFF DISK. TEST-025 chains fixture → case id →
   resolution → stop/continue disposition, so the fixture picks the row and
   the document supplies the answer.
3. **AC-025's prose is turned into a partition, not a string match.** The six
   resolutions are split into STOP `{ERROR_STOP, PROJECT_CONTEXT_INVALID}` and
   CONTINUE `{COMPATIBILITY_FALLBACK, PROMOTE_FULL, NO_OP_LITE, NO_OP_FULL}`,
   and the error-stop and promotion cases are asserted to have OPPOSITE
   dispositions. A rename cannot satisfy that.
4. **The load-bearing assertions are inequalities**, not restatements:
   `resolution(C1) != resolution(C2)` per consumer, and the three gate-scope
   comparisons above.
5. **Every mutation is a DELTA** over a pristine baseline that must CONFORM,
   *and* re-runs the ROUTING extractor against the mutated copy and requires
   it to report something other than the pristine value. That second half is
   this task's answer to T-011's only substantive Minor: the mutation lane now
   covers `doc_resolution()` / `gate_resolution()` — the functions behind the
   30-assertion matrix and the scope ruling — **inside the committed suite**,
   so there is no unpersisted external harness and the baselines can never
   drift out of sync with the suite.

### Deliberate runtime divergence (a variant axis, not duplication)

Continuing T-011's discipline: the `.sh` suite extracts and classifies with a
Python helper; the `.ps1` twin reimplements every extractor natively in
PowerShell — including the flag-cell splitting TEST-025 depends on — and
derives its expectations independently. Both lanes drive the same real
`generate-approval-sidecar.py` / `validate-approval-sidecar.py`, because those
tools *are* the production behaviour under observation.

**That divergence paid for itself during the Red capture.** With the staged
candidates absent, the two lanes disagreed 60/74 vs 58/76. The cause was a
