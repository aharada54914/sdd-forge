## Working Notes

Validated the following PowerShell-specific runtime behaviors empirically
in a scratch harness before relying on them in the script or the suite,
each because an incorrect assumption here would have silently produced a
wrong verdict rather than an obvious error:

- `Get-ChildItem -Filter '*.html'` matches `.HTML`/`.Html`/`.html` all
  case-insensitively by default on this runtime (confirmed against a
  three-file upper/lower/mixed-case fixture set), so AC-002/AC-039's
  case-insensitive extension requirement needed no extra code -- this is
  also the reason `Get-ChildItem`'s own default filtering is *not* treated
  as a case-sensitivity-sweep site: the `.sh` twin's own `-iname` is
  equally case-insensitive, so both sides already agree by construction.
- `.NET` regex lookbehind/lookahead (`(?<!\d)`, `(?!\d)`) behaves as
  `design.md`'s dual-form block specifies, including correctly rejecting
  the leading-adjacent-digit fixture (`ID9+123456789`) while still
  matching the same digits with a space instead (`ID +123456789`).
- Piping an empty collection into an external process call
  (`@() | & pwsh ... 2>&1`) closes that process's stdin immediately after
  zero bytes, rather than leaving it connected to the parent's own stdin --
  confirmed against a blocking `cat` with no arguments (which would hang
  indefinitely on a live terminal) returning in under 200ms this way. This
  is the mechanism `Invoke-Scan`/`Invoke-ScanSh` use for every call in the
  suite, not only TEST-030's dedicated row, mirroring the `.sh` twin's own
  `</dev/null` discipline stated in its `run_scan` comment.
- **A genuine PowerShell return-value pitfall was found and fixed during
  authoring, not left latent.** A function that does `return @($collection
  | Sort-Object -Unique)` does not reliably return an array to its caller:
  `return`'s implicit `Write-Output` unrolls the array back into
  individual pipeline objects, which the caller's assignment then
  re-collects as `$null` (zero objects), a bare scalar (one object), or an
  array (two-plus objects) -- silently collapsing exactly the array-typed
  return value the code was trying to construct. Reproduced empirically
  with `Set-StrictMode -Version Latest` (which turns the resulting
  `$null`/scalar's missing `.Count` property into a terminating error
  rather than a silent `$null`) before it could reach GREEN. Fixed in
  `Get-FindingSet` (the cross-runtime classification-parity helper) with
  the unary-comma idiom, `return , @(...)`, which wraps the built array as
  a single pipeline object so `Write-Output` does not unroll it -- this is
  the standard PowerShell idiom for this exact situation, not a novel
  workaround. Recorded here because this pitfall is easy to reintroduce in
  any future function in this file (or elsewhere) that returns a
  collection and is checked with `.Count`.
- Read `check-placeholders.ps1` directly at authoring time (rather than
  transcribing) to confirm its `$patternCs`/`$patternCi` literal text is
  byte-identical to `check-placeholders.sh`'s `pattern_cs`/`pattern_ci`
  T-001 cites, before hardcoding the same literal text into
  `design-sync-scan.ps1` -- confirmed identical, so AC-009's "reused
  verbatim" claim holds on this runtime by the same reasoning T-001's
  report states for its own runtime.
