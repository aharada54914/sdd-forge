## `upgrade_reasons` element validation -- fixed 2026-08-25 (second pass)

The first pass reported this as open because editing the staged payload was
out of scope. That constraint was corrected: `specs/<feature>/human-copy/` is
the implementation deliverable, not a frozen review document, and re-issuing
`MANIFEST.sha256` entries is the designed way to deliver a protected-file
change.

**The reported defect.** `requirements.md` Field Definitions fixes the field
as `"upgrade_reasons": [<token>, ...]` and AC-001 as "array of **non-empty
strings**". The container was type-checked and its elements were not, then
coerced: `capability_triggers.extend(str(token) for token in reasons)` /
`$capabilityTriggers += [string]$token`. Measured before the fix,
`{"id":"a","eligible":false,"upgrade_reasons":[5]}` exited **10** with
`full-required: 5; triggers=5` on both runtimes.

**The sibling sweep found two more instances of the class, one worse than the
reported defect.** The sweep asked where else a container is type-checked
while its elements are not, and where else a coercion stands in for a
validation.

1. **Output-grammar forgery.** The `id` field carries a bounded grammar for a
   stated reason -- the code's own comment says it exists "so a hostile id can
   never forge a second trigger entry or break the single-line output-grammar
   contract", and `TEST-013m/n/p` prove a `,`, `;` or newline in an id is
   rejected. Reason tokens are emitted into the **identical** record,
   `full-required: {first}; triggers={joined}`, and carried no validation at
   all. Measured, both runtimes:

   | fragment | before the fix |
   |---|---|
   | `["evil,forged"]` | `full-required: evil,forged; triggers=evil,forged` |
   | `["x; triggers=NONE"]` | `full-required: x; triggers=NONE; triggers=x; triggers=NONE` |
   | `["x\ntriggers=NONE"]` | a **multi-line** record, breaking the single-line contract outright |

   The exact attack the id grammar blocks, wide open one field over.

2. **A silent sh/ps1 divergence no test caught.** The twins already disagreed
   on three element shapes, because each runtime's own stringifier ran:
   `null` (sh `None` / ps1 empty), an object (sh `{'k': 'v'}` / ps1 `@{k=v}`),
   and a nested array (sh `['x']` / ps1 **flattened** it to `x`). Three
   shapes, two answers each, reachable from untrusted fragment content. This
   is the failure mode this repository has shipped before -- an sh-side
   property whose PowerShell twin quietly diverged.

**The fix.** Both twins validate every element as a non-empty string matching
a bounded reason-token grammar, and the coercions are **removed** rather than
guarded, so their absence is itself the property.

- Grammar `[a-z0-9][a-z0-9_-]*`, `fullmatch` / `\A..\z` (the same
  trailing-newline reasoning as the id pattern). An allowlist, not a
  delimiter blacklist -- the doctrine already audited for
  `capability_id_pattern` and NEW-01/INV-021's `required_lite_checks`. The
  character class is the union of the check-id grammar (hyphen, AC-001) and
  the snake_case catalog vocabulary (AC-004's twelve tokens are all
  `[a-z0-9_]`). Not a guess: every reason token in this repository's own
  fixtures -- `financial_settlement`, `durable_workflow`, `pii`,
  `explicit_reason`, `should-not-appear` -- passes it, and
  `should-not-appear` is why a snake_case-only grammar would have been wrong.
- **Not the catalog enum.** Field Definitions state each token is "already
  validated against `lite-upgrade-reason-catalog.json` by whichever upstream
  mechanism computed it", and AC-009 forbids this script reimplementing
  Registry-side logic. This validates shape, not vocabulary.
- The ps1 twin validates the **raw** array before `@()` touches it, because
  `@()` flattens one level -- validating after it would have left the
  nested-array divergence in place.

**Assertions.** `TEST-013v`..`TEST-013ae` cover number, boolean, null, object,
nested array, empty string, `,`, `;`, embedded newline and uppercase -- ten
