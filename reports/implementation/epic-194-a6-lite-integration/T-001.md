## C resolved -- the human took the code change (2026-08-25)

Ruling: fix the runner so it reports which targets landed, then document
that. The grounds were sharper than my own framing: the mitigation I cited
(point 4's post-copy re-verification) does not run at all on the failure
path, because `Fail` throws out of `Copy-Payload` and `Test-PostCopyHashes`
sits on the next line. A partial application was therefore left **both
unenumerated and unverified** -- the exact state the four-point contract
exists to prevent. Writing that into the contract would have sanctioned it.

### Where the reporting went, and why

In the **entry-point catch**, fed by script-scope state that `Copy-Payload`
maintains. Three placements were considered:

- **Not in `Fail`.** Roughly twenty call sites reach `Fail`, and nearly all
  of them -- `Assert-AnchoredPath`, `Test-ExactSet`, `Test-ManifestHashes` --
  fire *before* any copy is attempted. Reporting publish state from there
  would attach an install report to failures where nothing was installed.
- **Not in `Copy-Payload`'s three catch blocks.** It would have to be
  repeated in each, and it would still miss the case where `Copy-Payload`
  succeeds and `Test-PostCopyHashes` then fails -- a fully-applied batch with
  a corrupt member, where the operator needs the enumeration just as much.
- **The entry-point catch** sees every failure after the copy phase began,
  in one place, and leaves `Fail` a pure thrower.

`Copy-Payload` sets `$Script:CopyPhaseStarted` before the loop, appends to
`$Script:PublishedTargets` only *after* `CopyOne` returns (so membership
means "live and verified", not "rename issued"), and records
`$Script:FailedTarget` in each of the three catch arms. The report is emitted
**before** the stack trace: the operator's first question after a failed
protected-file application is "what is live now?", and burying that under a
PowerShell trace answers it last.

Verified against ground truth -- a real mid-batch failure with all five live
destinations pre-seeded, the filesystem inspected independently of the
report:

```

  INSTALLED     plugins/sdd-lite/references/risk-upgrade-policy.md
  FAILED        plugins/sdd-lite/scripts/check-risk-upgrade.sh
  NOT ATTEMPTED plugins/sdd-lite/scripts/check-risk-upgrade.ps1
  NOT ATTEMPTED plugins/sdd-lite/skills/lite-spec/SKILL.md
  NOT ATTEMPTED .github/workflows/test.yml
apply-protected-files(epic-194-a6): the INSTALLED files above are LIVE and
were not rolled back; each was published atomically and its published digest
verified. Re-run this runner after fixing the cause -- re-applying an
already-correct target is a no-op.
```

Filesystem, measured separately: #1 INSTALLED, #2 UNCHANGED, #3-#5 UNCHANGED.
The report matches exactly.

### Point 4 -- documented, not changed, and why

`CopyOne` **already performs per-target post-copy verification**: it re-opens
each just-renamed file and re-compares its digest before returning, on both
the Unix path (`published digest mismatch`, after `renameat`) and the Windows
path (after `RenameWindows`). The per-target property point 4 reads as
promising is therefore already implemented -- inside the publish step, not in
`Test-PostCopyHashes`.

`Test-PostCopyHashes` is a *second*, batch-wide re-read after all targets. It
is not redundant (it would catch corruption occurring between targets) but a
**third**, separate per-target pass would duplicate `CopyOne`'s own check
without adding a property -- the condition the ruling named as grounds to
document instead. Cost was not the deciding factor and is not claimed as one;
five SHA-256 reads would be negligible. The deciding factor is that the
property already holds.

So point 5 states the scope correctly rather than point 4 being rewritten --
`design.md` beyond the fifth point was off-limits, and folding the
clarification into point 5 respects that while still making the document true.
