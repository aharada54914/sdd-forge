## Quality-gate remediation addendum (2026-08-09, cycle 2)

`reports/quality-gate/20260809T081500Z-epic-191-a3-path-ownership-T-005.md`
found the PowerShell twin's `Test-InventoryConformance` (already rewritten
once, by `T-005-remedy-1.md`, to assert set equality against the parsed
`shared_paths` structure) was still not fail-closed on three divergence
classes its hand-rolled line-based parser could not see structurally, all
proved by mutation against the real, landed
`contracts/project-context.template.yaml` in an isolated scratch copy
(never the repository's own file):

1. **Case-insensitive classification comparison.** PowerShell's `-eq`/`-ne`
   compare strings case-insensitively by default, so `classification:
   Cross-Cutting` on a canonical entry passed silently even though the
   resolver itself rejects that exact string with exit 1 (TEST-018.3).
2. **No `shared_paths:` block tracking.** The line scanner matched
   `^\s*-\s*pattern:` on every line with no awareness of which top-level
   key it fell under, so all six canonical entries relocated under an
   unrelated key (e.g. `old_shared_paths:`) still satisfied the check even
   with the real `shared_paths: []` empty.
3. **Block-form-only `components:` detection.** `^\s*components:\s*$`
   only matched when nothing followed the colon, so a canonical entry
   combining `classification: cross-cutting` with an inline `components:
   [x]` went undetected (`HasComponents` never flipped true), even though
   that "both" shape is exactly what TEST-018.1 proves the resolver itself
   rejects.

Root cause was architectural, not three independent bugs: bash already
delegated to `resolve-component-paths.py`'s own `parse_minimal_yaml` and
read `data.get("shared_paths")` structurally; the PowerShell side
hand-rolled a parser instead, reproducing the resolver's discipline in
prose but not in code. `T-005-remedy-1.md`'s stated reason for not
dot-sourcing `resolve-component-paths.ps1` (that its CLI dispatch/`exit`
logic sits at script scope) no longer holds: that script now guards its
CLI body behind `if ($MyInvocation.InvocationName -ne '.')` (added for
T-004's `check-component-coverage.ps1`, which already dot-sources it the
same way), so a bare `. resolve-component-paths.ps1` with no bound
parameters only defines functions/classes. `Test-InventoryConformance` was
rewritten to dot-source that script (scoped to the function call only —
confirmed not to leak into or clobber this test file's own script-scope
variables, e.g. `$repoRoot`, which collides case-insensitively with the
dot-sourced script's `-RepoRoot` parameter) for its own
`ConvertFrom-MinimalYaml` parser, then read `$data["shared_paths"]`
structurally with case-sensitive (`-ceq`/`-cne`/`-ccontains`) comparisons
throughout, matching this codebase's established WFI-012 convention and
giving both twins the same structural delegation.

Each of the three mutations was applied to an isolated copy of the real
template (never the repository's own `contracts/project-context.template.yaml`),
confirmed bash already failed closed and pre-fix pwsh reported
`Conformant=True` (a false green), then confirmed post-fix pwsh now fails
closed identically to bash, then reverted with both runtimes re-confirmed
green. Six new `TEST-042-negative` sub-cases (`.4`/`.5`/`.6` in both
runtimes — `.1`-`.3` already existed from the first remedy) were added to
both suites, one per divergence class, since the prior negative fixtures
were shaped to exactly what the old parser could detect (block-form
`components:`, exact-case `cross-cutting`) and could not have caught any
of the three. Both suites now report 66 passed / 0 failed (up from the
63/0 baseline), on both runtimes; the verification GREEN logs under
`specs/epic-191-a3-path-ownership/verification/T-005/` (previously stale
at 40/3, recording a state before Epic A1's template landed) were
regenerated at this current state.
