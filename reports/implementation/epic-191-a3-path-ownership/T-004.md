1. **Fail-open on a security-sensitive surface (the live defect) — fixed.**
   `derive_state` in `check-component-coverage.py`/`.ps1` caught
   `ConfigError`/`OSError` across the WHOLE function, so a
   `project-context.yaml` that EXISTS but fails to parse silently
   downgraded to `disabled-legacy` (exit 0, zero evaluation) instead of
   reaching `main()`'s existing hard-error path. Reproduced directly before
   fixing: a config with a bare top-level sequence (not a mapping) yielded
   `state: "not-applicable (disabled-legacy)"`, exit 0, on both runtimes.
   Fixed by having `derive_state` raise a new `ConfigParseHardError`
   (python) / propagate a terminating error (pwsh) for a present-but-
   unparseable file — never for genuine absence, and never for a
   present-and-parseable document whose `capability_enforcement` field is
   merely absent/invalid (that remains legitimate `disabled-legacy` per
   ADR-0016 point 4). Callers turn this into `EXIT_HARD_ERROR` (2), never a
   silent downgrade.
   - **Twin exit-code disagreement, also fixed**: for a config that parses
     but fails `resolve-component-paths`' own structural validation (e.g.
     an empty `paths.include` list), python already returned exit 2, but
     pwsh returned exit 1. Root cause: `Write-Error` under
     `$ErrorActionPreference = "Stop"` (set at the top of the script)
     itself throws a terminating error, so the `exit $EXIT_HARD_ERROR` line
     that followed it never ran, and PowerShell's default
     uncaught-exception exit code (1) leaked out instead. Fixed by
     replacing that `Write-Error` call with `[Console]::Error.WriteLine`
     (the convention already used elsewhere in this plugin, e.g.
     `check-cross-model.ps1`).
   - **`capability_enforcement: Required` twin verdict disagreement, also
     fixed**: pwsh's `Get-DerivedState` used PowerShell's default `-eq`,
     which is culture-aware/case-insensitive, so `Required` (capital)
     matched as `required`; python's `==` is case-sensitive and correctly
     fell through to `disabled-legacy`. Fixed by switching pwsh to
     `[string]::Equals(...,[System.StringComparison]::Ordinal)`, this
     repository's own established convention (already documented in
     `resolve-component-paths.ps1`) for exactly this class of bug.
   - New fixtures: `config-parse-error.yaml` (bare top-level sequence, not
     a mapping — triggers a genuine `ConfigError`, NOT the tab-indentation

### 2026-08-09 quality-gate remediation

- **A sixth distinct PowerShell pitfall**: `Write-Error` under
  `$ErrorActionPreference = "Stop"` (set at the top of
  `check-component-coverage.ps1`) itself raises a terminating error, so
  any code AFTER a `Write-Error` call in the same scope — including the
  `exit $EXIT_HARD_ERROR` line that was meant to set the intended exit
  code — never runs. PowerShell falls through to its own default
  uncaught-exception exit code (1) instead. This is exactly why the
  Python/pwsh twins disagreed on exit code for a post-parse config
  structural error (python correctly exited 2; pwsh silently exited 1).
  Fixed by switching to `[Console]::Error.WriteLine`, which writes to
  stderr without raising — the convention several OTHER scripts in this
  plugin already use (`check-cross-model.ps1`,
  `check-hook-activation-handshake.ps1`, `canonicalize-sdd-yaml.ps1`,
