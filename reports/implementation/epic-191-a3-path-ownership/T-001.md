## Working Notes

- **Delegation**: none. Given the scope and the specificity of the
  algorithm design, this task was implemented directly in this session
  rather than delegated to a survey subagent; no large-scope
  investigation was needed beyond reading the four spec documents and the
  `check-contract.{sh,ps1,py}` INV-008 convention precedent already cited
  in the task's Must Read list.
- **PowerShell pitfall 1 (null-pipeline)**: `$null | ForEach-Object { ... }`
  invokes the scriptblock ONCE with `$_ = $null`, unlike an empty array
  `@() | ForEach-Object { ... }` (zero iterations) — discovered when a
  component with no `exclude:` key crashed with "pattern must be a
  non-empty string". Fixed by using the `foreach` statement keyword
  (which correctly performs zero iterations over `$null`) instead of the
  `ForEach-Object` cmdlet/pipeline wherever the input could be null/empty,
  and by ensuring every array-returning helper uses `return ,$array`
  (leading comma) so a zero-element result does not collapse to `$null`
  across a function-call boundary.
- **PowerShell pitfall 2 (culture-aware string comparison)**: `-eq`/`-ne`
  use .NET's default culture-aware string comparison, under which an
  NFD-encoded and NFC-encoded form of the same visual text compare EQUAL
  even though their UTF-16 code points differ (confirmed:
  `"café" -eq "café"` is `$true` with one composed, one decomposed).
  This silently broke the AC-010 NFC-collision check. Fixed with
  `[string]::Equals($a, $b, [System.StringComparison]::Ordinal)` and an
  ordinal byte-comparison-based sort for the raw-path stable sort,
  replacing `Sort-Object`'s own default (also culture-aware) comparer.
- **PowerShell pitfall 3 (case-insensitive `@{}`)**: a bare `@{}` hashtable
  literal defaults to CASE-INSENSITIVE key comparison (confirmed:
  inserting `"Src/x"` then `"src/x"` as two "different" keys collapses to
  one entry). This caused a false-positive NFC-collision report for two
  paths differing only by case. Fixed with an explicit
  `[System.Collections.Generic.Dictionary[string,string]]::new([System.StringComparer]::Ordinal)`.
- **Test-suite-specific issue (not a product bug)**: the PowerShell test
  twin's diagnostic-substring checks (`-match "empty paths.include"`, etc.)
  initially failed even though the resolver's actual behavior was
  correct, because (a) invoking the product script in-process via `&`
  let its `Write-Error` (under `$ErrorActionPreference = "Stop"`) become
  a terminating error that aborted the calling test script too — fixed by
  invoking it as a genuine subprocess (spawning `pwsh -File`, mirroring
  `tests/run-all.ps1`'s own convention) — and (b) PowerShell 7's
  ConciseView error formatter wraps a long `Write-Error` message across
  `Line | ...` gutter-prefixed continuation lines, inserting a literal
  `" | "` sequence mid-message — fixed by flattening captured subprocess
  output (collapse whitespace runs, strip `" | "` gutter markers) before
  any `-match` check. Also discovered and fixed a parameter named `$Args`
  shadowing PowerShell's own reserved automatic `$args` variable, which
  silently broke argument splatting to the nested subprocess.
- All three PowerShell pitfalls and the parameter-name collision are
  documented inline as code comments at their fix sites in
  `resolve-component-paths.ps1` and `tests/component-path-resolver.tests.ps1`,
  not only in this report, so a future editor does not reintroduce them.
