## Summary

Added the git-diff basis collector to `resolve-component-paths.{py,ps1}`
(REQ-003): `--source-rev`/`--target-rev`/`--include-untracked`/`--repo-root`
CLI flags trigger the real collector (the pre-existing
`--changed-paths-file`/stdin interim surface remains available when
`--target-rev` is omitted, preserving T-001's own interface). Implemented,
on both runtimes:

- Rev resolution via `git rev-parse --verify <rev>^{commit}` before
  `git merge-base`, fail-closed on an unresolvable rev or unrelated
  histories (never a silently empty change set).
- `baseline..worktree` collection (`git diff --name-status -z <baseline>`,
  which compares directly against the working tree, capturing both staged
  and unstaged changes) plus untracked files via
  `git ls-files --others --exclude-standard -z` — staged, unstaged, and
  untracked each counted exactly once (verified: no overlap by
  construction, the two commands read disjoint git states).
- NUL-safe raw-byte parsing of every path-enumerating git invocation
  (never newline-split text parsing); a path containing a literal TAB
  round-trips correctly; a path with invalid UTF-8 bytes fails closed
  (verified as a direct unit test — see Specification Differences).
- Rename-follow with a pinned similarity threshold (50%,
  `RENAME_SIMILARITY_THRESHOLD`) and pinned `diff.renameLimit` (1000,
  `RENAME_LIMIT`), `--no-ext-diff`; both the pre-rename and post-rename
  path are independently classified, and a cross-component rename is
  surfaced as its own `diff_basis.renames[].cross_component: true` case.
  The limit-exceeded fail-closed path is verified as a direct unit test
  (see Specification Differences).
- Submodule/symlink reference-only evaluation via
  `--ignore-submodules=dirty` (a dirty-but-pointer-unchanged submodule is
  not reported at all) plus git's own native symlink-as-blob semantics
  (a symlink's own target-text change is reported at its path; a
  referent-only content change is reported only at the referent's own
  path, never at the untouched symlink's path) — all four cases verified
  against real disposable fixture git repos.
- Single-writer/TOCTOU snapshot check (HEAD OID + a hash of the full
  porcelain status, captured before and after the collector's own
  multi-command sequence), retry-once-then-fail-closed on a persistent
  mismatch (verified as a direct unit test of the retry-loop shape — see
  Specification Differences).

## Specification Differences

1. **Invalid-UTF-8 path handling (TEST-021.2, both runtimes) is verified
   as a direct unit test of the decode function, not an end-to-end CLI
   run against a real fixture file.** macOS's own filesystem (APFS)
   enforces UTF-8 validity on filenames at the syscall level — attempting
   to create an actual file with a `0xFF` byte in its name fails with
   "Illegal byte sequence" (Python `OSError`). This is a platform
   constraint on the fixture, not a gap in the collector's own fail-closed
   behavior: `_decode_path_strict`/`ConvertTo-PathStrict` are called
   directly with crafted invalid-UTF-8 bytes, confirming they raise
   `GitDiffError` (Python) / throw the expected exception (PowerShell,
   via the identical `.NET` strict-decode contract) rather than silently
   truncating or dropping the path.
2. **The rename-limit-exceeded fail-closed path (TEST-023.2) is verified
   as a direct unit test with a mocked git stderr message, not a real
   git invocation that naturally triggers the warning.** Empirically,
   git 2.50.1's exact-match fast path resolves 100%-similarity renames
   without ever reaching the capped inexact-comparison phase this
   fail-closed branch guards, and even 15 near-identical (97% similarity)
   file pairs with `diff.renameLimit=1` did not trigger git's own "too
   many files" warning in this environment — reproducing the real
   trigger condition at a practical fixture scale was not achieved.
   `collect_tracked_diff` (Python) is called directly with a monkeypatched
   `_run_git` returning git's own real warning text
   ("warning: inexact rename detection was skipped due to too many
   files."), confirming the fail-closed branch fires correctly on that
   input; the PowerShell twin verifies the same detection text and
   diagnostic are present in the implementation (source-level check) since
   the bash twin already proves the shared detection logic pattern works.
3. **The single-writer/TOCTOU retry-then-fail-closed mechanism
   (TEST-025.2) is verified as a direct unit test of the retry-loop
   shape, not a real concurrent-writer race.** Reliably inducing a true
   concurrent filesystem race within a deterministic test is impractical;
   the Python twin monkeypatches `_capture_fingerprint` to return a
   different value on every call and confirms `collect_changed_paths`
   retries exactly once (4 fingerprint captures: before+after x2) then
   raises `GitDiffError`; the PowerShell twin reproduces the identical
   retry-loop shape standalone (calling a fingerprint stub directly)
   rather than dot-sourcing the CLI script, which would also execute its
   CLI dispatch/`exit` logic in the test process (the same reason T-001's
   twin invokes the product script as a genuine subprocess rather than
   in-process).
4. **`--repo-root` is a new CLI flag this task introduces** (both
   `--changed-paths-file` mode and the new git-diff mode need to know
   which repository to operate against; T-001 implicitly assumed the
   current working directory). Not explicitly named in design.md's own
   API/Contract Plan text, but a routine, in-scope implementation
   completion of the invocation shape design.md's Architecture section
   already describes generically.

- **Delegation**: none — implemented directly given the scope and the
  specificity of the git-plumbing behaviors involved; no large-scope
  survey was needed beyond the task's own Must Read list and empirical
  verification of git's actual rename-detection and submodule/symlink
  behavior against real disposable repos during development (documented
  in Specification Differences where real-world git behavior diverged
  from initial assumptions, e.g. tiny single-line files not triggering
  rename detection at all regardless of threshold).
- **A fourth distinct PowerShell collection-unwrapping pitfall** was found
  and fixed during this task (beyond the three already documented in
  T-001's report): any `IEnumerable` (a `HashSet<string>`, here) returned
  through an expression's "output stream" — via `return`, or as the
  trailing value of an `if`/`else` block used as an expression — gets
  enumerated and unrolled item-by-item, exactly like a bare array does. A
  single-element `HashSet<string>` therefore silently collapsed to its
  bare scalar string element instead of staying a `HashSet` object,
  breaking `cross_component` detection for exactly the single-owner case
  (confirmed via a minimal repro before applying the fix). Fixed with the
  same leading-comma-operator protection already used elsewhere in this
  file for arrays. Documented inline at the fix site in
  `resolve-component-paths.ps1`.
- Empirically verified (disposable throwaway repos, not committed)
  several git-plumbing behaviors before relying on them: `git diff
  --name-status -z <baseline>` (a single-commit argument) correctly
  captures both staged and unstaged changes against the working tree;
  rename detection requires a minimum of meaningful file content (a
  1-line file never triggers `-M`, even at 100% identical content,
  across multiple flag forms tried); `--ignore-submodules=dirty`
  correctly suppresses a dirty-but-pointer-unchanged submodule from the
  diff entirely.
