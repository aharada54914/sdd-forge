This report supersedes the initial T-003 implementation after TWO independent
quality-gate NEEDS_WORK verdicts. Round 1 raised 1 Critical + 5 Major + 2
Minor (self-check broken post-apply, draft banner, tautological AC-020 leg,
unnamed step, missing AC-023 record, own suite unregistered). Round 2
confirmed all eight resolved but raised a NEW Critical that only a YAML
parser could see, plus the Major that explains why it survived:

- **Critical (round 2): the candidate was not valid YAML.** Every prefixed
  step name was emitted as a BARE scalar, `- name: [deterministic] X`. An
  unquoted YAML scalar beginning with `[` opens a flow sequence, so the
  trailing text is a syntax error and the whole document fails to load — two
  independent parsers (ruby/Psych, Deno @std/yaml) rejected it at line 21.
  Applying that candidate to the live workflow would have made
  `.github/workflows/test.yml` unloadable, so `test`, `cli-hook-enforcement`
  and `required-checks` would never report — the exact opposite of the BL-001
  preservation this report claimed "by construction". `design.md:348` writes
  the prefix as a QUOTED scalar; the transform did not.
  **Fixed**: `build-candidate.py` now emits `- name: "[deterministic] X"`
  (double-quoted, with `\` and `"` escaped). Verified: `PARSE OK jobs=6
  test_steps=69 needs=["test", "cli-hook-enforcement"]`.
- **Major (round 2): AC-016's YAML-conformance half had no test.** The suite
  is text-marker only, so it asserted line shapes against a file no parser
  would load — which is precisely how the Critical survived round 1.
  **Fixed**: TEST-016 gains two fail-closed assertions — a dependency-free
  scalar-shape check (no `- name:` value may begin with `[`, `{`, `*`, `&`,
  `!`, `%`, `@`, `` ` ``, `,` unquoted) and, when a parser is available, a
  real `ruby -ryaml` load. Mutation-tested: un-quoting a single step name
  turns three assertions red at once.

Round 2's three Minors are also addressed: the eval-lane comment no longer
claims to be a terminator ("every step in this job is deterministic"),
`build-candidate.py` takes SOURCE/DEST arguments and defaults to
repository-relative paths so a reviewer can re-run it, and the three new
steps are blank-line separated to match the surrounding file style.

The Specification Differences and Test Evidence sections below record every
remediation from both rounds.

## Summary

Stream D marks a deterministic lane boundary INSIDE the CI workflow's single
`test` job rather than splitting the job (design.md Design Decisions OQ-5).
The staged candidate produced here:

1. gives **every** step inside the `test` job a `[deterministic] ` name
   prefix — the 65 already-named steps have their names prefixed, and the one
   step that was **unnamed** in the live file (`- uses: actions/checkout`) is
   given the name `[deterministic] Checkout`, so AC-016's "each step gains the
   prefix" holds with no exception;
2. adds **one** documented, currently-empty YAML comment placeholder marking
   where a future LLM-invoking eval lane would be added **as a separate job**;
3. appends the new bash-only CI steps for Stream A's, Stream B's, **and Stream
   D's own** self-check suite inside the same job (REQ-005: every new suite
   this feature adds gets a staged CI step) — bringing the candidate's
   `test`-job step count to **69**;
4. leaves job count, job names, and `required-checks`' `needs:` membership
   **byte-unchanged** (BL-001 preserved by construction; verified by diff, the
   only differences are inside the `test` job).

The candidate is produced by a deterministic transformation script
(`verification/T-003/build-candidate.py`, committed as reproducibility
evidence) applied to a read-only byte copy of the live workflow. It carries
**no draft/banner comment**: the file is the byte-exact content intended for
the live workflow, so it contains nothing that would not belong there.

**A guard constraint changed this task's delivery shape** (Specification
Differences 1): the staged candidate lives at a NON-protected draft path, and
placing it at the human-copy staging path is a human action.

## Tests Added Or Updated

bash 3.2 compatible:

- **TEST-016 (AC-016)** — job list byte-identical between live and candidate;
  **every** `test`-job step entry is named AND carries the prefix (the check
  compares total `- ` step-entry count against the named-and-prefixed count, so

  what catches the previously-missed unnamed checkout step); the eval-lane
  comment placeholder is present.
- **TEST-017 (AC-017)** — **idempotent** RED-then-GREEN. The coverage baseline
  is the live `test`-job step names with any existing `[deterministic] ` prefix

  human applies the candidate to the live file. RED: a fixture with one
  baseline name dropped FAILS the check; GREEN: the real candidate passes. Plus
  a byte-equality assertion on `required-checks`' `needs:`.
- **TEST-018 (AC-018)** — sibling-workflow graph isolation (no `uses:`, job, or
  `needs:` coupling; independent triggers).
- **TEST-020 (AC-020)** — **DESIGNED-RED**. For each new suite, the candidate
  runs it and the suite file exists (both asserted `ok`), but the LIVE file's
  registration is checked with a `designed_red` result until the human applies
  the candidate — mirroring the fail-closed precedent
  `tests/quality-gate-cycle-limit.tests.sh:434-437`. A designed-red result
  makes the suite exit non-zero (fail-closed) pre-apply and exit 0 post-apply.

## Specification Differences

**1. Staged candidate at a draft path (guard constraint; human decision).**
sdd-hook-guard's `_is_protected_gate_file` (sdd-hook-guard.py:976-989) matches
by path SUFFIX with no human-copy carve-out, so the human-copy staging path is
denied to agents identically to the live file (confirmed by reading the guard
and by a denied write attempt that created nothing). Human decision (2026-07-23):
the draft approach — the agent authors the byte-exact content at a non-protected
draft path; placing it at the staging path and applying it to live are human
actions. The guard was not bypassed or circumvented.

**2. Banner removed (QG remediation).** The initial candidate carried a 20-line
"STAGED CANDIDATE (DRAFT)" comment banner outside the `test` job, which would
have been copied into the live workflow and falsified the "differences only
inside the test job" claim. The banner is gone; its rationale lives in this
report and in the MANIFEST comment only.

**3. Unnamed checkout step named (QG remediation, AC-016).** The live `test`
job has one unnamed step (`- uses: actions/checkout`). An unnamed step cannot
carry a name prefix, so AC-016's "every step" could not hold. The candidate now
names it `[deterministic] Checkout`, and TEST-016 counts total step entries so
any future unnamed step fails the check.

**4. Stream D self-check registered in the batch (QG remediation, REQ-005).**
The initial candidate staged CI steps only for Streams A/B. REQ-005 requires
every new suite this feature adds to have a staged CI step, and Stream D adds
`deterministic-lane-selfcheck.tests.sh`. Its CI step is now in the same ONE
shared batch (no second batch — Non-goals honored), and TEST-020 covers it.

**5. Self-check made idempotent + DESIGNED-RED (QG remediation, Critical + AC-020).**
The initial suite re-derived the coverage baseline from the live file and used
always-`ok` live-registration branches. It would have failed the moment the
human applied the candidate (searching for a doubly-prefixed name) and never
exercised AC-020's fail-closed window. The baseline is now prefix-stripped
(idempotent), and the live-registration leg is a real `designed_red` mirroring
the `quality-gate-cycle-limit.tests.sh` precedent.

**6. `tasks.md`'s approved Planned Files / Done-When prose was not rewritten**
— deviations are recorded here, per the T-001/T-002/T-004 convention.
