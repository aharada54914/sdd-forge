- **TEST-009's single-compound-payload-per-combination shape**: design.md's
  API/Contract Plan prose for `tests/guard-negative-corpus.tests.sh`
  describes the triple-quote payload as "asserting the guard's tokenizer

  a doubled matrix (separate read-only-expect-ALLOW and write-shaped-
  expect-DENY sub-cases per combination). `acceptance-tests.md`'s own
  table row for AC-009 and its Notes section are explicit and
  authoritative on cardinality instead: "the same 4-runtime x
  3-tool_name-shape, 12-combination matrix" and "36 total leaf assertions

  kind of hash-frozen-column precedence T-001's own report already

  citing tasks.md's own T-002 Test Type field note: "the same
  hash-frozen-column situation recorded in T-001's Test Type field applies
  identically here"). The suite as found resolves this by constructing
  EACH of the 12 combinations' payload as ONE compound command carrying
  BOTH a read-only segment (`cat ... README.md`) and a write-shaped
  segment against the protected path (`echo ... > sdd-hook-guard.py`),
  both `"""`-decorated, asserting DENY uniformly (the write segment
  targets a protected path, so DENY is the correct decision regardless of
  the adjacent read-only segment) — this proves "no read/write
  misclassification" (a tokenizer confused by the embedded `"""` into

  cardinality. This reading is consistent with design.md's own prose read
  as describing behavior WITHIN one compound payload's two segments,
  rather than mandating two separately-enumerated payloads, and is the
  only reading that keeps TEST-008/009/010 symmetric at 12 combinations
  each (36 total), matching acceptance-tests.md's Notes verbatim. This
  design choice was made by the prior authoring instance (Summary) and is
  recorded here as the deferred Specification Differences note its own
  suite-header comment (`tests/guard-negative-corpus.tests.sh:24-28`)
  points to.
