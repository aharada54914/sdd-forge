## Summary

Authored `contracts/domain-contract.v2.schema.json`, a standalone draft-07
JSON Schema that adds `concepts[]` as a required, first-class top-level
array alongside the v1-shaped `contexts[]` / `relations[]` / `meta` shape.
Per design.md DD-3, the v1 `boundedContext` / `term` / `aggregate` /
`contextRelation` definitions are duplicated in-file rather than
`$ref`-ing `contracts/domain-contract.v1.schema.json`; a new `concept`
definition and its nested `stakeholderPerspective` / `distinguishedFrom`
definitions carry the seven required concept fields, three regex patterns,
and every `minLength 1` / `minItems 1` constraint that requirements.md's
Field Definitions table declares. `contexts[].terms[].concept_id` was added
as an optional field carrying the same concept-id pattern (REQ-003).

Created `tests/sdd-domain/contract-v2-schema.Tests.ps1` following the
acceptance-first workflow: wrote TEST-001 (schema-shape assertions, AC-001)
and TEST-002 (v1 byte-identity drift lock, AC-002) before the v2 schema
file existed, captured the failing run, then authored the schema until the
suite passed. The v1 baseline SHA-256 pinned by TEST-002 is
`0ab46b74c1e2561431b42b76106698339e79cd64ce0513b02aec5527b8b73841`
(measured via `shasum -a 256 contracts/domain-contract.v1.schema.json` at
this task's start and independently re-verified against the live file
before writing this report -- both measurements agree). This suite file is
the shared file that T-002 through T-005 will append their own Describe
blocks to; T-001 wrote only the TEST-001/TEST-002 blocks.

Added the `CHANGELOG.md` `## Unreleased` / `### Added` entry citing #290.

No validator scripts, no fixtures beyond TEST-001/TEST-002, and no change
to `contracts/domain-contract.v1.schema.json` or any pre-existing

  `0ab46b74c1e2561431b42b76106698339e79cd64ce0513b02aec5527b8b73841`,
  matching both the manifest's `allowed_inputs` entry and the task
  prompt's "known-good literal" verbatim. This is the literal recorded in
  TEST-002 and in this report.
- **`tasks.md` pre-existing modification**: at the start of this session,
  `git status` already showed `specs/sdd-domain-concept-contract/tasks.md`
  as modified (T-001's `Status: Planned` -> `Status: In Progress`, a 1-line
  diff). This task never opened that file with a write tool. Re-checked
  `git diff -- specs/sdd-domain-concept-contract/tasks.md` at report time:
  still exactly that same 1-line status-flip diff, unchanged since session
  start. Concluded this is the orchestrator's own status transition
  (consistent with tasks.md's Lifecycle section: "`implement-task` may set
  `In Progress`") applied before this fresh agent was launched, not an
  effect of this task's work.
- **File hygiene verification**: wrote a small Python byte-scan (mirroring
  `tests/guard-ps1-ascii.tests.sh`'s method, which itself only targets
  three fixed hook-guard/precheck files and does not cover this task's new
  files) against both new files. Result for both
  `contracts/domain-contract.v2.schema.json` and
  `tests/sdd-domain/contract-v2-schema.Tests.ps1`: 0 non-ASCII bytes, no
  UTF-8 BOM, 0 CR bytes (LF-only). Because the JSON schema's own
  descriptive text needed to stay ASCII-safe, all `description` fields in
  the new schema were written in English rather than mixing in Japanese
  prose (unlike some of this feature's spec documents).
  Learned from the environment prompt: "Every new .ps1 and .json file must
  be ASCII, no BOM, LF line endings" applies to the schema JSON file too,
  not only the `.ps1` suite -- broader than tasks.md's Global Constraints
  bullet, which names only `.ps1`/`.sh`.
- **TEST-001 false positive found and fixed during Red->Green**: the first
  draft of the "does not `$ref` the v1 schema file" assertion did a bare
  substring/regex search for the literal text
  `domain-contract\.v1\.schema\.json` anywhere in the v2 schema file. That
  matched the schema's own `"description"` field, which mentions the v1
  filename in prose to explain the DD-3 duplication decision (a legitimate,
  intended piece of documentation, not a `$ref`). Narrowed the regex to
  `"\$ref"\s*:\s*"[^"]*domain-contract\.v1\.schema\.json[^"]*"` so the
  check targets an actual JSON Schema reference rather than any mention of
  the filename. Re-ran the full red->green cycle after this fix (schema
  file temporarily moved out and back) to keep red.log/green.log
  synchronized with the final suite content; both logs in this report
  reflect the final test file, not the earlier draft.
- **Environment fact (per task instructions)**: this host is macOS with
  pwsh 7.6.2; Pester was absent and Pester 4.10.1 was installed to the
  CurrentUser scope by the orchestrator so the required tests could run.
  Prior sdd-domain tasks were verified on Windows PowerShell 5.1 with
  Pester 3.4.0. Assertion-syntax consequence hit: this repo's existing
  sdd-domain suites (e.g. `contract-schema.Tests.ps1`) use Pester 3.x
  LEGACY assertion syntax (`Should Be`, `Should Not Throw`, `Should
  BeGreaterThan`, `Should Match`) rather than the Pester v5 `Should -Be`
  operator form. Pester 4.10.1 still supports the legacy syntax, so no
  compatibility shim was needed -- `tests/sdd-domain/contract-v2-schema.Tests.ps1`
  was written entirely in the legacy form for consistency with the rest of
  `tests/sdd-domain/`, and it ran cleanly under 4.10.1 without any syntax
  translation.
