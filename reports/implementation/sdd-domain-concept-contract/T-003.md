## Summary

Extended both validator twins with REQ-004 step (c), the structural check
pass, in the order REQ-004(c) fixes: JSON type conformance first, then
required-key presence, then pattern, minLength and minItems. The precedence
rule is implemented as a single gate rather than as scattered guards --
`check_member` (Python) and `Test-DeclaredMember` (PowerShell) are the only
way a declared member is read, and each returns the value (respectively
`$true`) *only* when the member is present and its JSON type conforms. Every
caller treats the negative return as "stop": the value is never handed to a
regex, a length test, or a minItems test. That is what keeps a mistyped field
from producing a raw interpreter exception, which `security-spec.md` names as
a fail-closed violation.

`requirements.md` `## Field Definitions` is the authority the pass enforces:
the concept object's seven required fields with their three patterns, its
three optional fields with their nested required sub-fields, the minLength 1
rule on every declared string, the minItems 1 rule on `responsibilities`,
`evidence` and `distinguished_from[].reasons`, the root required set, the
`meta` required set, and `contexts[].terms[].concept_id` -- the single member
the table declares inside the contexts subtree.

Violations are appended through T-002's existing accumulator only. No second
output path, no new `exit` site, and no change to the argument handling, the
fail-closed acquisition, the parse, or the `schema` dispatch T-002 owns. The
`.ps1` twin keeps both properties the seam requires: no `exit` inside `try`
(every status still returns to the one top-level `exit $exitCode`), and the
extension-point calls stay `[void]`-wrapped.

Rule ids are the ones `design.md` `## Error Handling` fixes:
`V2-TYPE-MISMATCH` (message carries the field path and the expected type),
`V2-MISSING-KEY`, `V2-PATTERN`, `V2-EMPTY-ARRAY`, `V2-EMPTY-STRING`. The two
twins emit byte-identical stderr for every fixture in this task's corpus.

Two implementation hazards were found by probe rather than by assumption and
are guarded in both twins:

1. A trailing `$` in a regex matches immediately before a trailing newline in
   both Python and .NET, so `"Order\n"` would have been accepted as a valid
   concept `name`. Every declared pattern is therefore matched in a
   `\A ... \Z` (Python) / `\A ... \z` (.NET) anchored form, with the declared
   `^ ... $` source text kept beside it only for the violation message.
2. PowerShell's `-match` is case-insensitive by default, which would have
   accepted `concept-order` against `^CONCEPT-...`. The `.ps1` twin matches
   through `[System.Text.RegularExpressions.Regex]::IsMatch` instead.

A third hazard is guarded in the `.ps1` twin's `Get-ContractValue`: returning
a member value directly from a function unrolls an empty JSON array to
`$null`, which would have made a `minItems` violation indistinguishable from
an absent key or a type mismatch. The value is returned comma-wrapped so
exactly one object is emitted whatever its type.

checks (30 pre-existing -> 169 total):

- **62 structural negative fixtures x 2 twins = 124 checks.** Each fixture is
  one single-point mutation of a common, fully valid base contract, expressed

  test deletes again (DD-5, INV-006 -- no permanent fixture directory). The

  AC-023 / AC-020 / AC-018 / AC-019 / AC-016. Two further checks assert that
  all 62 expanded bodies are distinct (no fixture silently duplicates
  another) and that all 62 are well-formed JSON (so only the declared
  structural defect is under test, never a syntax error).
- **2 base-acceptance checks (one per twin).** The unmutated base contract
  exits 0 with nothing on either stream. This is the non-vacuity guard for
  the 62: it establishes that each negative differs from an *accepted*
  contract at exactly one point, so a rejection cannot be attributed to
  anything but the mutation under test. It is not an AC-003..AC-026 positive
  fixture and is not counted in the 62.
- **2 enumeration checks (one per twin).** A contract carrying two
  independent defects (`concepts[0].name` mistyped and `concepts[0].definition`
  empty) produces exactly two stderr lines, one `V2-TYPE-MISMATCH` and one
  `V2-EMPTY-STRING`, proving the pass does not stop at the first violation.
  This is the tasks.md `### Done When` enumeration item, not a 63rd allocated
  fixture -- the same convention T-002 used for its argument / path-error
  checks.

Every negative fixture asserts the shared shape: exit 1, empty stdout, no
stack trace or raw interpreter error anywhere in stderr, exactly one
`RULE-ID: <field path>: ...` line for the check under test, and zero lines
carrying any rule id the check must stay textually distinguishable from. The
forbidden-rule-id assertions are what make the precedence and
path-discrimination claims falsifiable rather than merely stated. All 62
matches use `-cmatch`, not `-match`, so a rule id differing only in case
cannot satisfy them.

   `reviewed_hash_accepted()` and tolerates several hash forms,
   `traceability.md` has no rebind path, so any edit -- including a correct
   one -- turns every feature in the repository red until it is reverted.
2. **`contexts[]` intermediates are walked past rather than reported.** The
   pass enforces `contexts[].terms[].concept_id` (the one member the Field
   Definitions table declares in that subtree, REQ-003) but does not report a
   `contexts[]` element that is not an object, or a `terms` value that is not
   an array. Those cells are absent from the `acceptance-tests.md`
   Negative-path coverage matrix, whose blank-cell-free state is the stated
   completeness criterion, and the v1-inherited `boundedContext` / `term`
   shape is outside the Field Definitions table this pass is scoped to. The
   schema file still declares that shape; only the hand-rolled validator's
   coverage of it is out of this feature's AC matrix.
3. **`meta` is type-checked but not pattern- or enum-checked.** The v2 schema
   file declares `meta.version` with a semver pattern, `meta.status` with a
   three-value enum, and `meta.generated_from` with `minItems: 1` and string
   items. The Negative-path coverage matrix gives the `meta` row cells only in
   the key-absent and type-mismatch columns (AC-021 and AC-024), and the Field
   Definitions table does not list `meta` at all, so this pass checks the three
   declared types and stops there. Widening it would add validator behaviour
   no fixture in this feature's AC set constrains, and could reject a T-005
   positive that no AC forbids.
4. **AC-024 (7) uses a JSON number for `meta.generated_from`.** The AC text
   groups items (5)-(7) as "not a string" while `generated_from` is declared
   as an array. A number satisfies both readings simultaneously -- it is
   neither a string nor an array -- so the fixture is unambiguous under either
   parse, and the emitted line is
   `V2-TYPE-MISMATCH: meta.generated_from: expected array, found number`.
5. **The pattern check for the two reference fields is left to T-004.**
   `distinguished_from[].concept_id` and `contexts[].terms[].concept_id` share
