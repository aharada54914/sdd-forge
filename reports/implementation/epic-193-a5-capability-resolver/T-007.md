## Summary

This is the first and only code path in this feature that writes a live
artifact, so every live write -- on a clean resolve and on a Block alike --
now goes through one journaled transaction.

**Step 0.5 (crash-recovery scan).** Every invocation, immediately after
argument validation and before step 1, scans
`specs/<feature>/.resolver-staging/*/TRANSACTION.json`, scoped to this
invocation's own `--feature` value. Absent -> proceed with no diagnostic.
Present -> re-hash every journal-listed target's current live bytes and
classify: all-POST (SAFE completion) or all-PRE (SAFE abandonment) delete
the journal and proceed; a MIX rolls every already-committed target back to
its own PRE bytes via the journal's `pre/<target-basename>` backups and then
deletes the journal; an unrecoverable state (a backup missing/unreadable/no
longer matching its recorded hash, a target matching neither PRE nor POST, a
mis-shaped journal document) Blocks `publication-journal-recovery` before any
Registry/ownership/Context-Projection work begins, leaving live state exactly
as found.

**Step 14 (journaled publication).** Prepare (hash every staged candidate as
one step; byte-exact PRE-image backup of every target with live content) ->
Journal (`TRANSACTION.json` written all-or-nothing via
temp+fsync+round-trip-rehash+atomic-rename, before ANY live rename) -> Commit
(atomic rename per target, in journal order) -> Post-publication verification
(a third `resolve-component-paths` invocation plus a fresh
digest/`affected_components` recompute; a mismatch rolls every just-completed
rename back through the journal and Blocks
`post-publication-generation-mismatch`) -> Complete (delete the journal,
exit 0). An in-process write/fsync/rename failure during Prepare/Journal/
Commit Blocks `artifact-publication-failed`, rolling any already-committed
sibling rename back to its own PRE bytes **from the journal's backup, never a
bare `unlink`**, and recording the rollback attempt (including a rollback that
did not itself complete) in that diagnostic's own `detail`. When that
in-process rollback is INCOMPLETE the journal is retained, but the next
invocation's scan Blocks `publication-journal-recovery` for manual
intervention rather than converging automatically -- see Panel Round 1
Remediation, MAJOR 2, for why that is a frozen-contract conflict rather than a
defect in this code.

Every path the crash-recovery scan writes or unlinks is validated against the
Resolver's own fixed publication target set first (requirements.md:1144-1151),
because the journal it reads lives in an unprotected, repository-local staging
area -- see Panel Round 1 Remediation, MAJOR 1.

Design-faithful detail worth flagging for review: design.md:1208-1210 states
that a Block reached at step 1/9/10/12/13 publishes "Resolver Evidence alone
... **via that journaled transaction**", and design.md:1261-1262 calls that
"exactly one target". `_write_evidence` was therefore rerouted onto the same
`_publish_bundle` primitive as a one-target instance, rather than keeping a
second, bare-rename write path. Observable Block behaviour is unchanged (all
256 pre-existing checks stayed green), and the transient staging directory is
removed at Complete.

## Specification Differences

None. The implementation follows the frozen contract; the four decision points
that required reading two clauses together are recorded here so a reviewer can
check the reasoning rather than re-derive it:

1. **Block-path Evidence goes through the transaction.** design.md:1208-1210
   ("... or (on any Block reached at step 1/9/10/12/13, above) Resolver
   Evidence alone, is published via that journaled transaction") and
   design.md:1261-1262 ("exactly one target ... on a Block") are explicit, so
   `_write_evidence` was rerouted rather than left as a second write path. The
   degenerate one-target case skips only step 4 (post-publication
   verification), which is defined against a step-13 recheck snapshot a Block
   path never has.
2. **`publication-journal-recovery` still writes Resolver Evidence.**
   design.md's recovery clause says the Block leaves "the live state exactly
   as found", while REQ-002 (requirements.md:383-388) closes the
   Evidence-always rule at exactly two named exceptions, neither of which is
   this row, and AC-012 requires every TEST-010 fixture except those two to
   write a full record. The ACs settle it: Evidence is written, and the scan
   performs no PARTIAL recovery -- it pre-validates every backup before its
   first restore, and the journal and backups are retained for the operator.
   **Correction (panel round 3, Minor 1):** an earlier revision of this item
   also claimed "live state exactly as found" is honoured for "the journal's
   own targets". That is not strictly true. `resolver-evidence.yaml` is
   itself one of the four allowlisted targets a retained journal may list, so
   writing the AC-012-mandated Block record moves that target off both its
   recorded PRE and POST hashes -- which can convert an operator-fixable
   batch into an unconvergeable one (the same interaction the 2026-08-27
   ruling accepted as a known limitation). The Evidence write is defensible
   and disclosed; the over-broad "journal's own targets untouched" phrasing
   was the defect, and it is withdrawn here.
3. **A content-corrupted pre-image backup is unrecoverable.** design.md
   enumerates "missing or unreadable"; AC-047 requires the fixture that
   "corrupts the journal's own recorded pre-image backup" to Block. The
   implementation therefore also rejects a backup whose own hash no longer
   matches the journal's recorded PRE value -- strictly fail-closed, and the
   only reading under which AC-047's companion fixture can pass.
4. **A post-publication verification that cannot RUN is not a mismatch.**
   design.md defines the rollback for "any mismatch" and is silent on a
   verification dependency that fails to launch. Re-labelling such a failure
   `post-publication-generation-mismatch` is exactly the defect the
   cross-model panel rejected for step 13, and the diagnostic enum is closed
   at sixteen, so `_POST_PUBLICATION_DEPENDENCY_BLOCKS` rolls back identically
   and reuses the SAME id the corresponding step-13 handler already uses, with
   a `<detail>` naming the post-publication window. This branch has no fixture
   (the four fixtures this task owns are enumerated by tasks.md) and is
   documented in-code as defense-in-depth.

### MAJOR 1 — PRE-image provenance / arbitrary content into an allowlisted target: **REAL, but OUT OF SCOPE per frozen threat model**

The finding is technically accurate: `_recover_journal` validates that a
journal's target paths are allowlisted (round 1) and that its self-declared
PRE/POST hashes are internally consistent, but it cannot authenticate the
PROVENANCE of the journal or its `pre/` backup bytes. A crafted MIX journal
can declare an allowlisted target's current bytes as POST and attacker-chosen
backup bytes as PRE, and recovery will "roll back" that target to the attacker
bytes. Self-declared hashes give integrity, not provenance. I reproduced the
mechanism mentally and it holds.

The coordinator's decision procedure asks: does the frozen threat model treat
the `.resolver-staging` area's CONTENT as attacker-authored, or does it trust
the single-writer staging area? I answer the latter — this is out of scope —
on four independent, citable grounds, and the answer is not ambiguous because
one of them makes the in-scope reading contradict the spec:

1. **Single-writer assumption, explicit deferral (design.md:1407-1419).** "This
   feature's Resolver assumes a single writer to a given `--feature` value's
   own Resolver-owned output paths ... A concurrent second invocation ... or a
   concurrent human/tool edit to the same live output paths outside this
   Resolver's own transactional commit, is **out of this feature's own scope (a
   future epic's own file-locking concern, Non-goals)**." A planted journal is

2. **No consuming caller exists yet (security-spec.md:106, Authorization row).**
   "Future Gate/CI caller / a future Epic A6 consumer ... the caller's own
   enforcement path — **no live wiring exists yet (Non-goals)**." The exploit
   requires a later legitimate Resolver invocation to consume the planted
   journal in the real protected repo; the design states no such live
   invocation path exists, and the consumer is a future epic.

3. **The fix is cryptographically impossible within the frozen boundary
   (security-spec.md:132; requirements.md Security Boundaries).** "N/A — this
   feature ... defines no signing key, no HMAC, and carries no credential."
   Authenticating on-disk journal provenance against an adversary who can
   write the same disk REQUIRES a secret. The spec definitively excludes
   secrets/crypto. A requirement to authenticate journal provenance would
   therefore contradict the frozen no-crypto boundary — the spec cannot
   mandate the impossible, so the in-scope reading is not merely disfavored,
   it is self-contradictory. This is what makes the determination
   unambiguous rather than a judgment call I should STOP on.

4. **The clean line round 1 already drew, and the human accepted.** Round 1

### MAJOR 2 — parent-directory symlink escape: **VERIFIED-REAL-IN-SCOPE, fixed**

This is the complement of MAJOR 1 and lands on the opposite side of the same
line: it is a write OUTSIDE the fixed named set, the exact invariant round 1
committed to (requirements.md:1144-1151) — reached through a mechanism round 1
left open. Round 1's `_normalized` is `os.path.normpath(os.path.abspath(...))`,
which collapses `..` but does not resolve symlinks; its own docstring justified
that by asserting the symlink case is "closed separately by the write
primitives themselves" (`os.replace` replaces a symlink AT THE TARGET). That
reasoning covers only a symlink at the FINAL component. A symlinked PARENT
(`generated/`, `specs/<feature>/`, or the staging dir) passes the lexical
allowlist while `mkdir`/`mkstemp`/`os.replace` follow it and write outside.

Crucially, this is NOT gated on the out-of-scope "plant a journal" capability:
it fires on the ORDINARY clean publication path (step 14) the first time a
Full-track resolve runs in a tree where `generated/` is a symlink — a
symlinked worktree, a relocated build dir, or a deliberately-planted one. So it
is also a plain correctness/containment bug, not only an adversarial one, which
is a second reason it is in scope where MAJOR 1 is not. And leaving it open
means round 1 did not actually deliver the "never writes outside the set"
invariant it claims — the lexical check is bypassable — so closing it completes
round 1's own accepted fix rather than adding a new requirement.

RED (`red-panel2-sh.log` / `red-panel2-ps1.log`, 323 passed / 4 failed, both
runtimes, captured against the pre-fix resolver in a scratch tree): the new
`publication-target-parent-symlink` fixture symlinks `generated/` to a sibling
directory holding a sentinel and runs a clean Full-track resolve. Against the
round-1 code the projection escaped — `outside-generated/project-context.resolved.json`
was overwritten with the real projection JSON — and the run returned `exit 0`
silently.

**Fix.** `_target_escapes_via_symlink(repo_root, feature, target)` resolves the
candidate the way the kernel will at write time (`os.path.realpath`, which
follows every ancestry symlink and, with `strict=False`, resolves the existing
prefix while leaving a not-yet-created leaf lexical) and requires the result to
be one of the fixed target locations in `_allowed_publication_targets_real` —
computed by resolving the TRUSTED BASES (`repo_root`, the script dir) once and
joining the fixed lexical subpath WITHOUT following further symlinks. Resolving
the base first is deliberate: on macOS `/var` is a symlink to `/private/var`
and every fixture temp repo lives under it, so a check that forbade any symlink
from the filesystem root down would reject every legitimate run; the threat is
a symlink INSIDE the controlled subtree, not one above the repository. The
check is wired into BOTH write surfaces — `_publish_bundle` (step 14, before
any live write; a hit raises `OSError` → `artifact-publication-failed`,
fail-closed before the journal exists) and `_recover_journal` (alongside the
round-1 lexical allowlist; a hit raises `PublicationJournalUnrecoverable` →
`publication-journal-recovery`). A companion check contains the staging batch
directory itself (`os.path.commonpath`) **on the publish path only** -- this
sentence originally claimed it meant "a symlinked `.resolver-staging` cannot
put the journal/backups outside `specs/<feature>/` either", which was true of
`_publish_bundle` and false of the crash-recovery scan; that asymmetry is the
panel-round-3 CRITICAL, corrected below. The realpath
check also subsumes the lexical `..`-traversal case, so the two checks are
belt-and-suspenders.

### Standing note for the next reviewer (updated, round 4)

Four rounds, ONE defect class, each fix trusting the layer beneath it:

| Round | Where the unvalidated path entered | Fix |
|---|---|---|
| 1 | the journal's own recorded target paths | allowlist targets against a fixed set |
| 2 | a symlinked target PARENT on the publish path | realpath the target, compare to the fixed set |
| 3 | the staging root / batch dir on the RECOVERY path | contain the staging area and each batch dir |
| 4 | the containment REFERENCE itself (`specs/<feature>` resolved as if trusted) | build every reference from the anchor + fixed lexical subpath |

The generalised lesson, now specific enough to act on: **a containment
reference must be built from the anchored root plus a FIXED LEXICAL SUBPATH,
never from a resolved intermediate path.** Resolving an intermediate component
makes the reference move with the attacker, so the comparison cancels and
passes vacuously — a check that cannot fail is worse than no check, because it
reads as coverage. The anchor is `os.path.realpath(repo_root)`: the directory
containing `.git`, which cannot be planted or redirected by committed content
because `.git` is unrepresentable inside a git tree.

Concretely, for any new filesystem operation on either path:

- Build its reference with `_allowed_publication_targets_real` /
  `_expected_staging_root_real` (anchor + fixed subpath). Never call
  `os.path.realpath` on a partial path and then append to it.
- Compare with `_path_contained_in` (which also absorbs `commonpath`'s
  `ValueError`), never with a bare `startswith` or `commonpath`.
- Use `_normalized` for lexical set membership ONLY; it is symlink-blind by
  design and must always be paired with a realpath check.
- Validate BEFORE the `try` that creates anything, so a refusal cannot route
  into the rollback/discard path.

Two guards in this file are deliberate defence-in-depth that kill zero
mutants — `_discard_batch`'s self-containment check (covers an escaping nonce
dir only) and the round-4 refusal/discard ordering. Both are documented as
such and should not be counted as test-covered.
