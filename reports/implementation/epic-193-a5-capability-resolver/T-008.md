## Summary

Authored a new stdlib-only Resolver Evidence validator implementing design.md's
own closed, **twelve**-value check-id enum, the B6 provenance-binding
procedure, and the B1 reader-side generation-consistency check, plus a
21-fixture / 117-assertion dual-runtime suite, CI staging, and the CHANGELOG
entry.

- **Twelve-value check-id enum** (`resolver-evidence: <check-id>: <detail>`,
  matching Epic A4's own three-validator diagnostic-line convention, drawn
  from this script's own enum independent of REQ-002's Block taxonomy):
  `schema-invalid`, `registry-digest-unbound`, `capability-set-mismatch`,
  `capability-evaluation-id-duplicate`,
  `affected-component-provenance-mismatch`, `trigger-evaluation-set-mismatch`,
  `component-evaluation-id-duplicate`, `matched-result-contradiction`
  (bidirectional), `conditional-facet-set-mismatch` (`declaration_index`-keyed,
  B7), `conditional-facet-evaluation-set-mismatch`,
  `applied-result-contradiction` (bidirectional), `array-not-stable-sorted`.
- **Provenance binding (B6).** `--registry` and
  `--affected-components`/`--context` are optional overrides, never sole
  ground truth. The Registry is self-resolved by default via ADR-0025
  (`registry_discovery.discover_artifact`, the identical procedure
  `resolve-project-context` uses); whether self-resolved or overridden, the
  whole-Registry digest is computed and required to equal
  `context_binding.registry_digest` **before** any exact-set check runs
  against that Registry's own `capabilities[]`. The affected-component set is
  derived from the Evidence's own `context_binding.dependency_pointers[]`,
  cross-checked against a co-located Facet Manifest's own, with any override
  required to be set-identical to that derivation.
- **Reader-side journal check (B1/AC-054).** Before `--evidence`/`--manifest`
  is read at all, a live `RESOLVER_PUBLICATION_IN_PROGRESS` journal naming a
  path about to be read fails this validator closed. Fixtured against T-007's
  own already-implemented `TRANSACTION.json` shape
  (`sdd-resolver-transaction/v1`, `live_path`/`pre_hash`/`post_hash`).
- **Never re-runs predicate evaluation.** Every check is
  structural/set-membership/provenance-binding against already-recorded
  evidence. `contracts/resolver-evidence.schema.json` is read, never edited.
  No environment variable is consulted on any path.

2. **Fail-closed short-circuit on `affected-component-provenance-mismatch`.**
   design.md states the ordering requirement explicitly only for
   `registry-digest-unbound` ("checked **before** `capability-set-mismatch`
   ... fired first"). This implementation applies the identical
   short-circuit to `affected-component-provenance-mismatch`: when the
   Evidence's own `dependency_pointers[]` derivation, the sibling Manifest's
   own, and/or a CLI override disagree, there is no single affected-component
   ground truth for `trigger-evaluation-set-mismatch` /
   `conditional-facet-evaluation-set-mismatch` to be evaluated against, so
   the validator refuses rather than silently picking one of the conflicting
   claims. This is the same reasoning design.md gives for the Registry case
   ("an exact-set check against a Registry that is not provably the one this
   Evidence instance itself claims to be about is meaningless") applied to
   the set whose ground truth is likewise unestablished. `schema-invalid`
   short-circuits for the analogous reason (the remaining checks are defined
   over a schema-conformant document).

3. **`.yaml` input-format selection.** This feature's own Resolver publishes
   every artifact -- `resolver-evidence.yaml` included -- as canonical,
   key-sorted **JSON** bytes (`resolve-project-context.py`
   `_canonical_payload`; `resolve-project-context-block-check.py` reads the
   published file with `json.loads`). `canonicalize-sdd-yaml`'s `yaml` input
   format rejects non-empty flow-style collections, so it rejects those exact
   production bytes. This validator therefore attempts both of that
   canonicalizer's own declared input formats for a `.yaml`/`.yml` target, in
   the fixed order `json` then `yaml`, failing closed and naming both attempts
   if neither accepts the bytes. This is **not** a lenient fallback parser
   (security-spec.md B1): it is the same canonicalizer subprocess in both
   attempts, no hand-rolled parser is ever used, and the two forms are
   mutually exclusive under it (canonical JSON is rejected outright by the
   `yaml` reader, block YAML outright by the `json` reader), so the selection
   is deterministic rather than a guess. Found by the suite, not assumed:
   the first GREEN run surfaced
   `canonicalizer-invocation-failed: ... non-empty flow-style collections are
   not accepted`.

4. **Registry-digest single-sourcing.** design.md says this validator
   "always computes `generate-registry-digest --whole` over the Registry file
   it ends up using". That CLI performs its own ADR-0025 discovery and exposes
   no path argument, so it cannot be *pointed at* a `--registry` override as a
   subprocess. Rather than reimplement its serialization -- a second,
   silently-divergable digest rule, and exactly the kind of default-vs-override
   divergence B6 exists to prevent -- this validator imports that script's own
   module and calls its own `canonical_digest()`, the exact function the
   `--whole` branch itself calls, applying it identically to the self-resolved
   Registry and to an override. There is therefore exactly one digest code
   path. Agreement with the real CLI is asserted rather than assumed: the
   driver binds every clean fixture's `registry_digest` to the value the REAL
   `generate-registry-digest.py --whole` subprocess emits, so each `exit 0`
   case is itself an equality assertion against that CLI.
