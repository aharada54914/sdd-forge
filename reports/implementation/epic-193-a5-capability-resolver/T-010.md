## Specification Differences

1. **design.md item 9(g)'s own "Registry discovery" label names a position
   with no real subprocess at all; the spy targets the genuine subprocess
   at that position instead.** Read literally against `resolve-project-
   context.py`, step 5's own Registry discovery (`_discover_registry`) is a
   co-located sibling-module IMPORT, never a `subprocess.run` call -- the
   only genuine subprocess step 5 invokes is `validate-capability-registry`
   (`_validate_capability_registry`), confirmed directly by reading both
   functions before writing this fixture. This is the only reading under
   which item 9(g)'s own list of SEVEN names maps onto SEVEN real
   `subprocess.run` call sites in `resolve-project-context.py` at all; the
   driver's own module docstring and the spy fixture's own assertion label
   both disclose this reading in full.
2. **`generate-registry-digest.py` internally invokes `canonicalize-sdd-
   yaml.py` as its own nested dependency** (to hash the Registry it
   discovers), confirmed by reading `generate-registry-digest.py:38-48`
   directly. An unguarded canonicalize-sdd-yaml spy would therefore also
   fire on that GRANDCHILD call one position after `generate-registry-
   digest`, polluting the seven-call sequence this fixture exists to prove.
   Solved by propagating `SDD_SPY_SUPPRESS=1` into every spy's own delegate
   environment before calling its `-real` sibling, and having every spy
   skip its own logging/fail-check entirely whenever that flag is already
   set on entry -- confirmed empirically: the clean run's own log holds
   exactly the seven expected entries, never more, across the actual test
