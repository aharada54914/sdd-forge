## Summary

Authored `plugins/sdd-quality-loop/scripts/validate-capability-registry.py`
implementing all nine independently identifiable REQ-003(a-i) checks:
(a) `gate-id-duplicate`, (b) `implementation-ref-missing` (both a missing
field and a non-existent path), (c) `unregistered-script` (the Gate
implementation identity schema -- canonical `.py`-only reference, sole
scan root `plugins/sdd-quality-loop/scripts/`, `check-` prefix rule,
same-directory/same-basename `.sh`/`.ps1`/`.js` wrapper grouping,
symlink resolution before comparison), (d) `pack-owns-gate-definition`
(repository-wide forward-guard for `capability-packs/*/gates.yaml`),
(e) `stage-missing` (defense-in-depth, independent of any schema
validation since this validator never invokes JSON Schema itself), (f)
`dangling-gate-reference` (validator-level-only referential integrity),
(g) `provider-name-detected` (case-insensitive substring scan against
`provider-terms.json`), (h) `unknown-upgrade-reason` (fail-closed against
`contracts/lite-upgrade-reason-catalog.json`, located via T-003's
`registry_discovery` module), and (i) `capability-id-duplicate`
(independent of check (a), proven via a combined-duplicate fixture where
neither diagnostic masks the other).

Added a testable `--repo-root` override (not part of the originally
enumerated CLI contract, but a reasonable, documented interface addition):
checks (b)/(c)/(d) inherently depend on the real filesystem's script
inventory, so this task's own test suite can point them at an isolated,
fixture-controlled fake repository root instead of coupling every test to
this repository's own, evolving real script layout. Checks (a)/(e)/(f)/
(g)/(h)/(i) operate purely on the registry JSON content and always ran
against the real, default repo root in this task's tests.

Also authored `plugins/sdd-quality-loop/references/provider-terms.json`
(three categories: cloud_provider, distribution_channel,
workflow_runtime_product_name), matching design.md Components' exact term
list.

TDD Red->Green was followed literally: the 23-check suite (both runtimes)
was authored first and run against a deliberately permissive stub (always
reports "all 9 checks passed" regardless of input) -- RED showed 12/23
meaningful failures per runtime (the remaining 11 incidental passes are
individually explainable: the structural-placement, negative/absence
assertions, the fully-clean fixture, and the registration self-checks all
trivially hold against a stub that never produces any diagnostic at all).
The stub was then replaced by the real implementation above -- GREEN
shows 23/23, both runtimes.
