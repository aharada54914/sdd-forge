# ADR-0053 DDDの概念判断を対話ターミナルで記録する

状態は提案。2026-11-22。

## 背景

既存の概念に収まらない要求を見つけたとき、旧形式の Concept Test は署名付きの人間判断を要求する。日常的な DDD で人が判断するたびに、署名鍵と承認者登録を準備する負担が発生する。ローカルでの人間の明示操作と、共有時の独立レビューを使う v2 の方針を、概念判断にも適用する。[軽量ガードレールの設計](0051-lightweight-guardrails-and-sdd-core.md)

## 決定

新規の `concept-test/v2` は要求と承認済みドメイン入力の SHA-256、分類、根拠、概念の区別を記録する。既存概念への適合以外では、担当者が対話ターミナルで対象を確認し、進行・保留・却下のいずれかを選ぶ。確認記録は feature、判断、JSON と Markdown の両方のダイジェストを持つ。通常の検査は記録の読み取りだけを行う。入力の変更時は再確認し、保留・却下の判断では後続工程を停止する。

ローカルのファイル編集フックは、エージェントによる確認記録への直接編集を抑止する。SHA-256 で検証できるのは内容の対応関係である。本人の認証や署名者の証明を必要とするプロジェクトは、ホスト上の認証済みレビュー等で承認者を確認する。

## 互換性

`concept-test/v1` の署名付き記録は従来の方式で検証する。欠けた鍵や無効な旧署名を、新形式の判断で補完しない。固定リビジョンの審査では、提案と判断の両方を同じリビジョンから取得する。通常の v2 判断に承認鍵の登録やネットワーク接続は不要である。

Git ワークツリー内のサブディレクトリをプロジェクトにした場合も、各審査段階はそのプロジェクトの概念判断を照合する。旧形式の固定入力一覧にはプロジェクトの位置を記録する欄がないため、その一覧を使った審査の受け入れはワークツリー直下で行う。サブディレクトリでは現在のファイルを対象に審査できる。
