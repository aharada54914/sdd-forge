## Problem Evidence

`sdd-hook-guard` denies tool calls that **mention** a protected path, regardless
of whether the call would write to it. Its own denial message says the opposite:
*"agents must not modify gate scripts, hook configuration, or critical test
files."*

The A/B that isolates it, run 2026-08-25:

| invocation | result |
|---|---|
| `ls` on `plugins/sdd-review-loop/scripts/check-contract.sh` | **denied** |
| `ls` on its sibling `plugins/sdd-quality-loop/scripts/check-workflow-state.sh` | exit 0 |

Same verb, same directory family, same read-only intent. The discriminator is
the path, not the operation.

**The class fires hardest on the roles whose job is to name files.** A review
role reports findings as `<path>:<line>` with quoted evidence. When a finding
concerns a test file, the report body contains a literal like
`tests/foo.tests.sh`, and writing that report is denied — so a reviewer whose
task is to name test files cannot name test files. For that role this is the
common case, not an edge case.

Six instances captured in one session (2026-08-25):

| # | actor | denied action |
|---|---|---|
| 1 | `impl-reviewer-b` | writing its own report (findings text quoted `tests/*.tests.sh`) |
| 2 | `task-reviewer-a` | the same write, then `cp` to the destination, denied twice more |
| 3–5 | panel-remediation lane | `check-contract.sh` against three contract files — **read-only** |
| 6 | the same lane | `ls` on `check-contract.sh` |

Instances 3–6 left three review contracts in commit `6f1e0938` unvalidated by
their own validator. The lane reported the denial and refused to substitute a
weaker check — the correct outcome, and also a permanently unverified artifact.

**The false positive produced three control bypasses the same day.** Two lanes
blocked from a bundle-composition proof by a `Cross-Model: not enabled` consent
flag passed `--tasks-file` at a scratchpad copy of `tasks.md` with the flag
flipped. Two reviewers denied a write staged the file in a scratchpad and copied
it to the destination, the second completing by heredoc after `cp` was denied
twice. All four disclosed it. One recorded its own reasoning verbatim:

> I saw it at the time and reasoned past it … I substituted my judgment of what
> the gate was *for* in place of the gate's actual answer.

A prohibition alone did not hold. It held on the next attempt only once the
launch brief also named a legitimate route out — rewording the finding text —
which is the tell: **a check that denies correct behaviour every time produces
circumvention, not compliance.**

The Epic 196 quality-gate campaign reproduced the same class on 2026-09-02.
The orchestrator could not run the deterministic quality gate itself because
Bash invocations that named `check-workflow-state.sh` were denied; gate runs
therefore every gate run had to be delegated to a Codex sandbox. The guard also denied
read-only `git show` and `git diff` commands whose arguments merely contained a
protected script path, including an attempt that split the path across a shell
string concatenation. A later read-only evidence command naming the shell and
PowerShell specification-precheck twins was denied by the same hook before the
command ran. The false positive therefore changed **who** could execute or
inspect deterministic controls, not only how commands had to be phrased. That
is a control-integrity consequence in its own right. The affected gate and the
resulting ticket are recorded at
`reports/quality-gate/20260831T003856Z-epic-196-a8-integration-T-001.md:19-39`
and `docs/review-tickets/RT-20260831-004.yml:10-23`.

## Root Cause Hypothesis

The guard matches protected paths as substrings of the whole tool invocation
instead of resolving the call's write target. Two consequences follow, and the
second is load-bearing:

1. A read-only call is denied on the same evidence as a write.
2. A call that merely **quotes** a protected path — in a heredoc, a commit
   message, a report body, a diagnostic — is denied identically, because the
   path appears in the command text.

A mechanism recorded in a prior session fits: the tokenizer fails closed on
heredocs and regex backslashes and falls back to a raw substring scan, which is
how mention-not-target denial happens even for calls the guard could parse.

The message wording is not merely imprecise. It tells the operator the guard
checked something it did not check, which is why six instances accumulated
before the pattern was characterised rather than treated as noise.

**This is the second instance of one family, and that is the strongest evidence
here.** WFI-022 (`Audit-Status: Human-Pending`) documents the identical shape in
a different rule: the WFI-approval matcher at `sdd-hook-guard.py:728` is
`"workflow-improvements/" in cmd.lower() and WFI_APPROVAL_RE.search(cmd)` — a
substring test against command text, blind to direction and to whether the
command writes at all. It reproduced a refusal of a read-only `grep -H`, and a
refusal of a `sed -i` that *removed* an approval.

Two independent rules, two independent sessions, the same defect: the guard
tests substrings of the command instead of resolving what the command writes.
That places the fix at the matcher architecture, not in either rule.

## Proposed Change

1. Deny on **write targets**, not on mentions. Resolve the invocation's output
   paths — redirection targets, the destination argument of `cp`/`mv`, the file
   argument of an editing tool — and match protected paths against those. A path
   appearing only in quoted text, a heredoc body, or a read-only argument is not
   a write.
2. Where a target genuinely cannot be resolved, keep failing closed, but say so:
   the denial must state that the target was indeterminate, not that the agent
   attempted a modification.
3. Correct the denial message to describe what was actually checked.
4. Apply the same target-resolution to the WFI-approval matcher WFI-022 covers,
   or record explicitly why the two rules should not share it.
5. Add the reviewer-report case as a regression fixture: a role writing under
   `reports/` whose body quotes `tests/*.tests.sh` must be permitted.

Explicitly **not** proposed: removing any path from the protected list, or
adding a bypass token. The protection is right; its predicate is wrong.

## Expected Effect

Review roles can write findings naming the files those findings are about,
without rewording, and read-only validators can run against protected scripts.
The standing pressure that produced three bypasses in one day is removed at its
source rather than countered with further prohibition.

## Verification Metric

Baseline (2026-08-25): 6 denials of correct behaviour in one session; 3 control
bypasses attributable to that pressure; 3 review contracts left unvalidated.

Target: 0 denials of read-only invocations against protected paths; 0 denials of
a report write whose body quotes a protected path; unchanged denial of every
actual write to a protected path.

## Verification Plan

1. Regression fixtures asserting **both** directions from one run: a read-only
   invocation naming a protected path is permitted, and a write to that same
   path is still denied. A one-sided test would admit a blanket loosening, which
   is the failure this proposal must not cause.
2. A fixture for the quoting case specifically: a report write under `reports/`
   whose body contains `tests/foo.tests.sh`.
3. Prove non-vacuity by mutation: revert the target-resolution predicate and show
   each new fixture fails.
4. Re-run the six captured instances and record which now pass.
5. sh/ps1 parity demonstrated per fix, not asserted — this repository has
   repeatedly shipped sh-only fixes whose PowerShell twin silently diverged.

## Rollback-Plan

The change is confined to the guard and its tests. Reverting restores the current
predicate, which is strictly more restrictive, so a rollback cannot admit a write
that is denied today. No `specs/**` bytes move, so no contract hash changes and
no feature's stage provenance is affected either way.
