## Problem Evidence

Measured in `sdd-domain-concept-contract` on 2026-08-19, immediately after
T-002 reached Done and before T-003 had been gated even once:

```
$ bash plugins/sdd-quality-loop/scripts/check-quality-gate-cycle-limit.sh T-003 sdd-domain-concept-contract
Escalate-Human            (exit 1)
```

Per-task measurement across the three remaining tasks:

| Task | count the script returns | gate reports whose `Task ID:` is that task |
|---|---|---|
| T-003 | 3 → Escalate-Human | **0** |
| T-004 | 3 → Escalate-Human | **0** |
| T-005 | 3 → Escalate-Human | **0** |

The three files counted for every one of them are the same three, and none is
a gate report for the task being counted:

| File | `Task ID:` (its actual subject) | where the counted id appears |
|---|---|---|
| `reports/quality-gate/20260819T042254Z.md` | T-001 | line 117, Traceability And Drift table: "T-002/T-003/T-004/T-005 appended fixtures to the shared corpus file" |
| `reports/quality-gate/20260819T052000Z.md` | T-002 | line 79, Out-Of-Scope Waivers table: "Owned by T-003, T-004 and T-005 respectively" |
| `reports/quality-gate/20260819T080750Z.md` | T-002 | line 115, Out-Of-Scope Waivers table: "Owned by T-003, T-004, T-005" |

Three tasks are therefore barred from their first quality gate by a limit that
exists to stop a fourth.

## Root Cause Hypothesis

`check-quality-gate-cycle-limit.sh` lines 74-88 count a file when **the task id
appears anywhere in its content** and its `Feature:` header matches:

```sh
task_matches="$(grep -rlwF -e "$task_id" "$reports_dir" 2>/dev/null)"
...
if grep -qE "^Feature:[[:space:]]*${feature_re}[[:space:]]*\$" "$f" ...; then
    count=$((count + 1))
fi
```

The word-boundary and feature predicates are both correct as far as they go —
they were added for BL-001 (`T-0010` must not match `T-001`) and issue #167
(a `Feature:` line must not be counted). Neither addresses the actual question.

The report template already carries the field that answers it: every gate
report opens with `Task ID: T-NNN`, naming its one subject. The counter ignores
that field and substitutes a full-text search, so it measures "reports that
mention this task" instead of "gate cycles this task has had".

The failure is self-inflicting rather than incidental. The same template
mandates a `## Out-Of-Scope Waivers` section, and filling it in honestly means
naming the sibling tasks that own the out-of-scope surfaces; the
`## Traceability And Drift` section likewise names which tasks changed a shared
file. A feature whose tasks extend the same files — the ordinary case for a
sequential decomposition — therefore accumulates cross-references at exactly
the rate that trips the limit. The better the reports, the sooner the siblings
are falsely escalated.

## Proposed Change

| Target File | Change Description |
|---|---|
| Quality-gate cycle-limit counter (generic workflow surface, sh and ps1 twins) | Count a report only when its own `Task ID:` header names the task being counted, instead of when the task id appears anywhere in the file. Keep the existing `Feature:` header predicate and the word-boundary matching unchanged, and keep the fail-closed behaviour on scan error and the zero-on-absent-directory rule. |
| Cycle-limit parity tests (generic workflow surface) | Add a case proving that a report whose `Task ID:` is a different task in the same feature is NOT counted, even when it mentions the target task id in prose. Without it the fix could regress silently, and the case is the exact shape observed here. |

Both twins must change together; the existing sh/ps1 parity test already
enforces that they agree.

## Expected Effect

A task's cycle count becomes the number of gate cycles it has actually had.
The limit then does what it is for — stopping a task that has genuinely failed
its gate three times — instead of barring first gates.

Removing the false positives does not weaken the limit: the count for a task
with three real gate reports is unchanged, because those reports carry that
task's `Task ID:` header. The change is strictly a reduction in over-counting,
which is why the parity test above is required — it is the only thing that
distinguishes "fixed the over-count" from "broke the limit".

## Verification Plan

For each of the next ten quality-gate runs, record the count the script returns
alongside the number of gate reports whose `Task ID:` header names that task.
The WFI is verified when the two numbers agree in all ten cases.

Two controls are required before claiming success, because this WFI reduces a
count and an unverified reduction is indistinguishable from a disabled limit:

1. **Negative control.** Construct a task with three real gate reports and
   confirm the script still returns `Escalate-Human`. If it does not, the fix
   has disabled the limit rather than corrected it.
2. **Positive control.** Construct a report for task A that mentions task B in
   prose, in the same feature, and confirm B's count is unaffected. This is the
   observed failure and must be pinned.

## Rollback-Plan

Revert the commit whose message contains `WFI-035`. That restores the full-text
counting in both twins and removes the added parity test. No state migration is
needed: the counter is stateless and derives entirely from files already on
disk, so reverting changes only how existing reports are counted. No gate
report, contract, evidence bundle or ledger record is modified by either the
change or its rollback.

## Result

Applied on 2026-08-20 on branch `claude/wfi-035-cycle-limit`.

Both twins now count a report only when its OWN identity header names the task.
**Three anchored forms are accepted, not one.** Measured across all 220 reports
under `reports/quality-gate/`: 219 carry `Task ID:`, 77 carry `Task:`, 16 carry
the `# Quality Gate Report: T-NNN` heading, and exactly one
(`2026-07-15T133723Z-epic-136-phase2-gates-T-005.md`) carries only the heading.
The union covers 220 of 220, so no existing report stops counting. Anchoring on
`Task ID:` alone would have dropped that one report and quietly weakened the
limit for its task -- the opposite of the intended effect.

**Both required controls are implemented and proven non-vacuous by mutation.**

| Mutation | Killed by |
|---|---|
| revert to the whole-file word-boundary search | **exactly** QGCL-009c and QGCL-009g -- the two positive controls, and nothing else |
| count nothing at all | QGCL-004, QGCL-005, QGCL-009a, QGCL-009d, QGCL-009e, QGCL-009f |

That the first mutation killed only the two positive controls is the useful
result: they are the precise discriminators for this defect rather than
incidental coverage.

Suite: 73 passed / 0 failed on both twins, up from 59 passed / 2 failed. The two
pre-existing failures were `QGCL-009a`, which asserted the defective behaviour
directly -- it required a report whose ONLY reference was punctuation-adjacent
prose to count as a cycle. That case is rewritten rather than deleted: the
punctuation-robustness intent is preserved by keeping the prose line and adding
the identity header the counter now requires.

Effect on the feature that surfaced this: with `sdd-domain-concept-contract`'s
reports present, every task's count now equals the number of gate reports whose
own `Task ID:` header names it.
