## Problem Evidence

`scripts/sync-human-copy-mirrors.py` — the remediation half of WFI-039 — cannot
sync a mirror it has already synced once on the same branch. It reports the
bundle as `pending` and refuses to touch it, while the suite that enforces that
bundle fails on the same bytes. Both halves are working as written; they
disagree about what "applied" means.

The classifier is `scripts/human_copy_mirrors.py:14-34`, which defines three
states over (staged, live, `origin/main`-live):

| State | Condition | Tool behaviour |
|---|---|---|
| `fresh` | staged == live | nothing to do |
| `stale` | staged != live **and** staged == `origin/main` live | synced |
| `pending` | staged != live **and** staged != `origin/main` live | left alone (safety) |

The `pending` rule is WFI-039's data-loss protection and is correct for its
designed case: `specs/epic-159-pillar-c/human-copy/` stages reviewed role
definitions a human has not yet applied, and treating "staged differs from live"
as stale would silently overwrite them.

It is wrong for a second, unmodelled case: a mirror **already applied**, synced
once on a feature branch, and then edited again on that same branch. After the
first sync, staged equals the branch's live bytes at that moment — which are not
`origin/main`'s. The second edit moves live again, so staged now differs from
live *and* from `origin/main`. The classifier reads that as un-applied human
work and refuses; the bundle's own byte-identity suite reads it as staleness and
fails.

Measured twice in two days, in two different bundles:

| # | Date | Bundle / files | Symptom |
|---|---|---|---|
| 1 | 2026-08-22 (PR #328) | `specs/epic-189-a1-project-context/human-copy` — the `apply-human-copy` pair | tool classified `pending` and refused; sync performed by hand (`cp` + `MANIFEST.sha256` row rewrite) |
| 2 | 2026-08-23 (PR #336) | `specs/epic-136-phase2-gates/human-copy` and `specs/epic-189-a1-project-context/human-copy` — the three guard twins | `sync-human-copy-mirrors.py --check` printed `no stale mirrors; nothing to sync` while `tests/phase2-guard-invariants.tests.sh` failed `WFI-016 staged targets are byte-identical to live` (41 passed, 1 failed); sync again performed by hand, recorded in commit `918c6831` |

Both occurrences are recorded as FP-01 (Confidence: High) in
`reports/retrospective/2026-08-23T125111Z-wfi-application-horizon-check.md`.

### Why the disagreement is silent

`--check` exits 0 and prints `no stale mirrors; nothing to sync` in exactly the
state the enforcing suite fails. The silence is in the **exit code and summary
line**, not in the whole output: the tool does name every affected bundle first,
printing 15 `pending (left alone): …` lines. What misleads is that the summary
and the exit code contradict those lines. The tool's report and the gate's verdict are
opposite, and nothing compares them: the developer sees a clean check, pushes,
and learns otherwise from CI (occurrence 1) or from running the byte-identity
suite by hand (occurrence 2). Both times the recovery was a manual `cp` plus a
`MANIFEST.sha256` line rewrite — the exact operation whose absence WFI-039
measured at three CI rounds.

The chain terminates at a controllable mechanism — a single-shot applied-test
with no memory of the branch's own earlier sync — which is what `## Proposed

tool": re-running produces the same refusal, twice measured.

## Root Cause Hypothesis

In `scripts/human_copy_mirrors.py`, `classify()` (`:145-159`) decides
applied-vs-pending by comparing staged bytes against `origin/main` alone, via
`_MainDigests.get` (`:54-75`). That comparison answers "was this bundle applied
*before this branch started*" — not "is this bundle applied". Those two questions coincide only until the branch itself
syncs the bundle once. From the second edit onward the tool's answer is
structurally wrong, and it is wrong in the safe direction, so it fails silently:
the refusal looks identical to the protection it was designed to provide.

The enforcing suites ask the other question — staged equals live, now — so the
two surfaces disagree precisely in the branch-iteration case, which is what
occurrence 1 hit in `specs/epic-189-a1-project-context/human-copy` and
occurrence 2 in `specs/epic-136-phase2-gates/human-copy`, and the disagreement
surfaces as a red suite rather than as a tool diagnostic.

## Proposed Change

| Target File | Change Description |
|---|---|
| `scripts/human_copy_mirrors.py` | Widen the applied-test from "staged equals `origin/main`'s live bytes" to "staged equals `origin/main`'s live bytes, **or this branch recorded a sync of this bundle**". Implement the second clause as: keep today's answer when the `origin/main` comparison already says `stale`; otherwise walk `git rev-list origin/main..HEAD -- <staged path>` and treat the mirror as `stale` only when some commit in that range holds the staged file and the live file byte-identical **to each other** and equal to today's staged bytes. Keying on the bundle's own staged path is what makes the evidence a record of a sync rather than a coincidence — see the failure mode below. A mirror with no such commit stays `pending`. |
| `scripts/sync-human-copy-mirrors.py` | Report the widened decision honestly: when a mirror is synced because of the branch sync-record match rather than the `origin/main` match, name that in the output line, so an operator can see which rule fired. **Correction to an earlier draft:** `--check` already exits non-zero whenever a mirror is syncable (`:67-69`, `if check_only: … return 1`); it returns 0 on the current tree only because 0 mirrors are stale. What it does *not* do is fail when a `pending` mirror belongs to a bundle whose own suite enforces byte-identity unconditionally — `tests/phase2-guard-invariants.tests.sh:315-328` ignores the classification entirely. Make `--check` exit non-zero in that case too, naming the bundle and the enforcing suite. Do **not** make `--check` fail on pending mirrors generally: 15 are pending today and would all become failures. |
| `tests/human-copy-mirror-freshness.tests.sh` and its `.ps1` twin | Add the branch-iteration fixture: a bundle applied, synced once, then edited again — assert the enumeration classifies it syncable, not pending. Add the safety counter-fixture: a bundle staged at bytes matching no commit on either branch stays pending and is left untouched by the tool. Assert the pair fails against the current classifier, so the fixtures are known to discriminate. |
| `docs/contributor/shared-file-mirrors.md` | State the branch-iteration case from the editing side: editing a shared file twice on one branch requires the sync tool twice, and until this change the second run silently refused. |

**Failure mode this change introduces.** Any applied-test built on branch history
can fire on bytes that appeared live for a reason other than an apply. The
concrete case, reproduced end to end on 2026-08-23: a bundle stages reviewed
un-applied work V2; the branch applies V2 live in one commit and rolls live back
to V1 in the next (routine when CI rejects an apply and the reviewed bundle is
kept for the next attempt); the staged V2 is untouched throughout. A rule that
asks *"did the live file ever hold the staged bytes?"* answers yes and classifies
the mirror syncable — and `sync-human-copy-mirrors.py` then overwrites the
reviewed work with V1 and rewrites its `MANIFEST.sha256` digest to match,
exiting 0. The reviewed human work is destroyed silently, which is exactly the
hazard WFI-039's `pending` state exists to prevent.

The staged-path sync-record test above is chosen because it is the narrowest
evidence that excludes this: it requires a commit where staged and live were
identical *to each other*, which an apply-then-rollback never produces. It is
also immune to a second problem the live-path rule has — 66 mirrors cover only 34
distinct live paths (`.github/workflows/test.yml` alone is mirrored by 5
bundles), so a live-path match cannot be attributed to any particular bundle.

**An earlier draft of this WFI proposed the live-blob-match rule** and asserted
that it "adds a second way to prove applied, it does not relax the requirement
that applied be proven." That was false: a live-blob match proves only that the
bytes once appeared live, not that the bundle is applied now. The claim is
withdrawn and recorded here rather than deleted, because the distinction between
the two rules is the whole safety argument.

**Not proposed.** Removing or weakening the `pending` classification. It is the
safety property WFI-039 was built around and the reason a blanket "staged differs
from live means stale" rule was rejected there.

**Interaction with WFI-039.** WFI-039 carries the Applied state with its
Verification Plan item 7 still open, and its Secondary (safety) metric requires
that `specs/epic-159-pillar-c/human-copy/`'s `task-reviewer-a.md` classify as
`pending` and be left untouched. This WFI changes that classifier inside WFI-039's
open horizon, and epic-159-pillar-c is among the 12 of 15 protected mirrors whose
staged bytes match a historical `origin/main` version of their live file. The
deep-branch safety replay in `## Verification Plan` item 3 is what keeps WFI-039's
safety metric measurable; it must run before this WFI is applied, and its result
recorded against WFI-039.

## Expected Effect

Editing a repository-shared file more than once on one branch stops requiring a
manual `cp` plus `MANIFEST.sha256` rewrite, and `--check` stops reporting clean
in a state an enforcing suite fails.

Concretely: manual mirror syncs fall from 2 in the measured two-day window
(PR #328, PR #336) to 0, and the `--check`-clean-while-suite-red state — observed
once, in occurrence 2 — becomes unreachable because `--check` fails whenever a
mirror is syncable.

## Verification Plan

1. Build the branch-iteration fixture in
   `tests/human-copy-mirror-freshness.tests.{sh,ps1}`: a temporary repository
   with an applied bundle, one sync commit, then a second live edit. Assert the
   current classifier calls it `pending` (the defect) and the changed one calls
   it syncable. The before/after pair is what proves the fixture discriminates.
2. **Data-loss counter-fixture** — the hazard fixture, not the trivial one. A
   temporary repository where a bundle stages reviewed un-applied bytes V2, the
   branch applies V2 live in one commit and rolls live back in the next, and the
   staged bundle is untouched. Assert the changed classifier still reports
   `pending`, and that `sync-human-copy-mirrors.py` leaves both the staged file
   and its `MANIFEST.sha256` row byte-identical. Assert the same fixture **is**
   classified syncable by the rejected live-blob-match rule, so the fixture is
   known to discriminate between the two mechanisms rather than merely to pass.
2a. Aliasing fixture: two bundles mirroring one live path at different staged
   bytes; the branch applies bundle A and edits live again. Assert bundle A
   becomes syncable and bundle B stays `pending`.
2b. Trivial counter-fixture, kept: staged bytes matching no commit on either
   branch stay `pending` and are left untouched.
3. Re-run the full enumeration against the current tree and assert the 15
   informational `pending` mirrors are still 15, still spread across the same 9
   bundles. **This assertion is not discriminating on a shallow branch**: `git
   rev-list origin/main..HEAD --count` is 1 on the branch this WFI was drafted
   on, so the walk inspects almost nothing and flips 0 of 15 whatever the rule.
   Pair it with a deep-branch replay: pin `origin/main` 600+ commits back and
   assert none of the 15 becomes syncable. That matters because 12 of the 15
   stage bytes matching a *historical* `origin/main` version of their own live
   file — `specs/epic-159-pillar-c/human-copy` matches commit `825d6c66`, 1021
   commits back — so a stale local `origin/main` is the condition under which a
   live-path rule would have fired on protected work.
4. Run `tests/phase2-guard-invariants.tests.sh` and
   `tests/guard-invariants-epic-a1.tests.sh` unchanged: the widened classifier
   must make their byte-identity assertions reachable by the tool, not alter what
   they assert.
5. Twin parity: run both suites, with a `pwsh` capability probe and a visible
   `skip -` line when the shell is absent.
6. The next retrospective records manual-mirror-sync count per multi-edit branch
   against the baseline of 1.0 per branch recorded here, in the Improvement
   Verification Plan table.

## Rollback-Plan

Revert the commits whose messages contain `WFI-043` — plural: the change spans a
classifier, a tool, a test pair and a doc, and WFI applications here routinely
land across several commits (WFI-039 took `f5184a47` plus `d53c4123`). Note the
WFI document's own commit message also contains the ID, so a message-grep revert
can remove the proposal along with the change.

**The revert restores the classifier, not any staged bytes the tool already
overwrote.** A mirror wrongly synced before the revert must be recovered per file
with `git checkout <pre-sync commit> -- <staged path>` plus a `MANIFEST.sha256`
row rewrite, and is unrecoverable if the overwrite was committed and the branch
has since been squashed. Given the failure mode recorded in `## Proposed Change`,
this is the rollback cost most likely to be paid. The classifier returns to the
`origin/main`-only applied-test, `--check` returns to exiting 0 when it finds
nothing it will touch, and the added fixtures are removed with the same revert.

Nothing on disk needs migrating: the change alters which mirrors the tool is
willing to rewrite, not the bytes it writes when it does. Mirrors synced by the
changed tool are byte-identical to mirrors synced by hand today, which is what
the byte-identity suites already assert.

If the branch-history walk proves too slow on large histories or ambiguous in
repositories with rewritten branches, the proportionate retreat is to keep the
`--check` exit-code fix and the documentation, and replace the walk with an
explicit marker file recording which bundles this branch has applied.
