## Problem Evidence

All three false positives were produced, not hypothesised, during ordinary work
on 2026-08-04 while applying WFI-012/013/014/015. The guard is
`plugins/sdd-quality-loop/scripts/sdd-hook-guard.py` and its three twins.

The matcher at `sdd-hook-guard.py:53` is unanchored: a compiled regex of
`Status:` followed by optional whitespace and the word Approved, with no line
anchors and no multiline flag.

There are three decision paths, and only one is correct.

1. **Write path — correct.** `_wfi_write_content_increases` (`:748`) compares
   `wfi_count(new_content)` against `wfi_count(old_content)` read from disk. It
   fires only on a net increase, which is the intended semantics.

2. **Edit path — broken.** `:741` evaluates `wfi_count(new_string) > 0` and
   never looks at `old_string`. Reproduced: an edit replacing
   `## Result` / `Pending` with a Result section whose PROSE named the field in
   backticks, mid-sentence, while leaving the field line itself untouched, was
   refused. No approval was being granted.

3. **Bash path — broken.** `:728` is
   `"workflow-improvements/" in cmd.lower() and WFI_APPROVAL_RE.search(cmd)` —
   a substring test against the command text, blind to direction and to whether
   the command writes at all. Two refusals reproduced:
   - a `grep -H` listing the field across five WFI files — read-only, no write
     token, no redirect;
   - a `sed -i ''` substituting the approved value with `Applied` across four
     WFI files — a command that REMOVES the approval.

4. **This document is itself a fourth instance.** The first attempt to create
   `WFI-022.md` was refused, because the Problem Evidence above *quotes* the
   field while describing the defect. The file exists only because the field is
   written in split form throughout.

Consequence, observed: advancing four WFIs to `Applied` after their
implementation landed could not be done by the agent at all, even though the
template states that the AI sets `Applied`. The status fields were left lagging
and the discrepancy recorded in commit 41fae3ff, because the guard declares it
is never bypassed and no string-avoiding workaround was attempted on it.

## Root Cause Hypothesis

The guard was written to answer "does this operation grant an approval?", but on
two of its three paths it actually answers "does this operation's text mention
the approval field near a WFI path?". The Write path already implements the
intended semantics as a net-count delta; the Edit path omits the comparison
operand, and the Bash path has no notion of direction or of read versus write.
The unanchored matcher compounds both, since it matches the field name anywhere
— including inside prose that merely describes the rule, which is why a document
about the defect cannot be written in plain form.

## Proposed Change

| Target File | Change Description |
|---|---|
| `plugins/sdd-quality-loop/scripts/sdd-hook-guard.py` | Anchor the field matcher to a column-0 full line (start-of-line, the field name, optional horizontal whitespace, the approved value, optional trailing horizontal whitespace, end-of-line, multiline), so prose mentions are not matched. Make the Edit path compare `new_string` against `old_string` — and each element of an `edits` list likewise — so it fires on a net increase exactly as the Write path already does. On the Bash path, exempt commands that are read-only under the guard's own existing invariants (`SHELL_READ_ONLY_START_RE` with no write or redirect token present), and otherwise KEEP the current broad match unchanged. |
| `plugins/sdd-quality-loop/scripts/sdd-hook-guard.js` | The identical change; the four twins are parity-locked. |
| `plugins/sdd-quality-loop/scripts/sdd-hook-guard.ps1` | The identical change. |
| `plugins/sdd-quality-loop/scripts/sdd-hook-guard.sh` | The identical change. |
| `tests/guard-parity.tests.sh` | Regression cases for the three reproduced false positives that become allowed (prose-quoting edit, read-only grep, and creating a WFI document that quotes the field), AND for three operations that must stay refused: the approval-removing sed (write-capable, expected-strict — paired with an allowed Edit-path equivalent of the same transition), a Write whose content adds the column-0 field, and an append via a shell redirect. The last is why the broad Bash match is kept — its literal sits inside quotes mid-line, so anchoring alone would miss it. |

Deliberately NOT proposed: relaxing the Bash path for write-capable commands.
Deciding from shell text whether a command nets out to a removal is not
tractable, and attempting it is how the redirect-append bypass would slip
through. Fixing the Edit path opens a supported route for the transition the
blocked `sed` was performing, so no capability is lost by leaving that path
strict.

## Expected Effect

Agent operations that do not grant an approval stop being refused: reading a WFI
status with a read-only command, editing a WFI section whose prose names the
field, advancing a WFI status through the Edit path even when the surrounding
edit quotes the field in prose (the minimal transition is already allowed and
green-tested on all four twins; the 2026-08-04 blockage was the shell-path
route, and no literal-bearing route was attempted because the guard declares it
is never bypassed), and authoring a document that describes this rule.
Operations that would grant an approval remain refused on every path, and the
guard's own suite gains cases proving both halves.

Concretely, the status-advance blockage class recorded in commit 41fae3ff is
closed for future WFIs: the next WFI to reach the approved state — including
this one — can be advanced to `Applied` by the implementing agent through the
Edit path, whereas WFI-012/013/014/015 required a human commit (5aa079c5,
2026-08-07) to flip.
