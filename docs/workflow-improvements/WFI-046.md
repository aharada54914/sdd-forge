## Problem Evidence

The write-protection gate that shields enforcement-chain files has a read-only
short-circuit: a command that carries no compound operator, starts with a
read-only verb, and contains no write verb or redirect token is exempted from
write-target analysis. That triple does not account for shell syntax that
*executes a further command*, so a reader-shaped command can carry an
unmodelled writer inside a substitution and be exempted.

Measured directly on 2026-08-23 against the current tree, on both runtimes:

| Command | Python guard | Node guard | Expected |
|---|---|---|---|
| `rm plugins/sdd-quality-loop/scripts/sdd-hook-guard.py` | exit 2 | exit 2 | denied — control case, the gate works |
| `cat "$(tar -xf /tmp/x.tar -C plugins/sdd-quality-loop/scripts)" plugins/sdd-quality-loop/scripts/sdd-hook-guard.py` | **exit 0** | **exit 0** | denied — the substitution extracts an archive over the protected directory |
| ``cat `tar -xf /tmp/x.tar -C plugins/sdd-quality-loop/scripts` plugins/sdd-quality-loop/scripts/sdd-hook-guard.py`` | **exit 0** | **exit 0** | denied — backtick form of the same |

The exempting condition is `sdd-hook-guard.py:1462`, inside
`_shell_targets_protected_gate_file` (def `:1436`)
(`not _SHELL_COMPOUND_RE.search(cmd) and SHELL_SUDO_READ_ONLY_RE.match(cmd) and
not has_write`), with the twins at `sdd-hook-guard.js:617` inside
`shellTargetsProtectedGateFile` (def `:598`) and `sdd-hook-guard.ps1:967` inside
`Test-ShellTargetsProtectedGateFile` (def `:947`, clauses built at `:964-966`).
`tar` is not in the write vocabulary, so
`has_write` is false; `$(...)` and backticks are not compound operators, so the
compound test is false; the command starts with `cat`, so the read-only test is
true. All three clauses hold and the command is exempted before any write-target
analysis runs.

### There are TWO early returns, and the short-circuit is the redundant one

Immediately below the short-circuit sits a second, unconditional early return:

```
has_write = bool(SHELL_SUDO_WRITE_RE.search(cmd))
if not _SHELL_COMPOUND_RE.search(cmd) and SHELL_SUDO_READ_ONLY_RE.match(cmd) and not has_write:
    return False          # :1462 — the short-circuit
if not has_write:
    return False          # :1464 — returns False for every input :1462 could catch
return not _shell_write_targets_are_safe(cmd)
```

Twins: `.js:617` and `:618`; `.ps1:967` and `:968`.

Because the short-circuit's third clause **is** `not has_write`, the set of
commands it exempts is a strict subset of the set `:1464` exempts. Every command
`:1462` returns `False` for, `:1464` would return `False` for one line later.
**The short-circuit is therefore redundant today, and a disqualifier added to it
alone cannot change any verdict.**

Measured 2026-08-23 by patching a scratch copy of each runtime with the
disqualifier at the short-circuit only: both bypass probes still exit 0 on both
runtimes. Deleting the `:1462` branch outright produces no verdict change across
the guard's own command corpus. The line that actually decides these commands is
`:1464` / `.js:618` / `.ps1:968`, and it is the one that must be gated.

This is recorded here because an earlier draft of this WFI targeted the
short-circuit alone. Applying that draft would have produced a change that reads
as a fix, passes review, and leaves the measured bypasses open.

### This is a known class, closed once already in the neighbouring gate

The same defect was found by external review in the approval-field exemption on
PR #336 and fixed on 2026-08-23 in commit `918c6831`, which added an
executing-syntax disqualifier — `$(`, backtick, `<(`, `>(`, `&`, and a physical
line break — with four must-refuse regression cases. That fix defines the pattern
as a module-level constant (`sdd-hook-guard.py:67`, `.js:119`, and the ps1
equivalent) and applies it inside the *approval-field* exemption
(`sdd-hook-guard.py:753` in `wfi_approval_increases` (def `:725`); `.js:1163` in
`wfiApprovalIncreases`, def `:1139`).

**These are two different exemptions and must not be confused.** The approval
exemption governs whether an agent may run a command that touches a WFI approval
field; the write-protection short-circuit governs whether a command may write to
a protected enforcement-chain file. They live in different functions, roughly 700
lines apart, and share only the three-clause shape. This WFI targets the
write-protection site (`py:1462` / `js:617` / `ps1:967`) and leaves the already-
patched approval site untouched.

The write-protection short-circuit uses the same three clauses and did not
receive the disqualifier, because the review that found the class was scoped to
the change under review. Recorded as Observation 3 in
`reports/retrospective/2026-08-23T125111Z-wfi-application-horizon-check.md`.

### What the exemption is for

The short-circuit exists so that reading a protected file is not denied merely
because some other part of the command mentions a write verb — the behaviour
issue #62 introduced. That purpose is served entirely by commands with no
executing syntax; nothing about a genuine read requires a substitution that runs
another command.

The chain terminates at a controllable mechanism — an exemption whose conditions
model verb text but not command execution, granted ahead of the fail-closed pass
that would otherwise catch it, and duplicated across two sites with no check
binding them — which is what `## Proposed Change` acts on.

## Root Cause Hypothesis

The read-only exemption decides whether a command can write by inspecting the
words of the command for known write verbs and redirect tokens. Shell syntax that
runs a further command defeats that inspection completely: the embedded command's
verb is not part of the outer command's verb set, and the exemption is granted
before any target analysis could notice. The exemption therefore holds in exactly
the case where its premise — "this command only reads" — is unverifiable.

The condition is written twice, once for each exemption the guard grants. One
copy was hardened when the class was found; the other was not, and nothing
compares them, so the guard now enforces two different definitions of "read-only"
at two gates that should share one.

## Proposed Change

| Target File | Change Description |

**On the `&` token.** `&&` is already matched by `_SHELL_COMPOUND_RE`
(`&&|\|\||;|\|`), so `&&`-carrying commands are already outside the
short-circuit and `&` buys nothing there. At the `:1464` gate it does bite, and
it over-triggers: it matches `&&` inside a subshell, `&` inside quoted arguments
and URLs, and it turns the routine `cat $(git rev-parse --show-toplevel)/...`
idiom into a denial. Either narrow the token to an unquoted, segment-terminating
`&`, or keep it and accept the 7 measured false positives listed in
`## Verification Plan` item 7. This WFI does not decide that; it requires the
decision be made and recorded before the change lands.

**Mirror targets.** The identical sibling change (`918c6831`) touched 14 files,
not 4. The six mirrored runtimes under
`specs/epic-189-a1-project-context/human-copy/` and
`specs/epic-136-phase2-gates/human-copy/` are byte-identical to the live files
today, so all six go stale under `tests/human-copy-mirror-freshness.tests.sh`
unless synced in the same commit — as do
`specs/epic-136-phase2-gates/human-copy/tests/guard-parity.tests.sh` and the two
`MANIFEST.sha256` files. `specs/epic-136-phase1-guards/human-copy/` already
diverges from live by design and is out of scope.

**Application route.** Every file named above is itself a protected gate file, so
neither applying nor reverting this change is possible through ordinary agent
edits: both directions go through the human-copy bundle route
(`specs/*/human-copy/` plus `apply-protected-files.ps1`), exactly as `918c6831`
did.

**Not proposed.** Adding `tar` — or any further verb — to the write vocabulary.
The bypass does not depend on `tar`: any command that writes and is not in the
vocabulary reproduces it, so extending the list treats one instance and leaves
the class. The disqualifier addresses the mechanism.

## Expected Effect

The write-protection gate stops exempting commands whose read-only appearance
cannot be verified, so a protected enforcement-chain file can no longer be
overwritten by a writer embedded in a substitution.

Concretely: of the three probes measured in `## Problem Evidence`, the two
bypasses move from exit 0 to exit 2 on both runtimes while the control stays exit
2 — measured bypasses of this gate fall from 2 to 0 — and a genuine read of a
protected file with no executing syntax stays exit 0, so the exemption's purpose
is preserved. This holds **only** with both early returns gated; with the
short-circuit alone the count stays at 2.

**What this does not close.** Two of the four executing-syntax forms remain
allowed after the change, and are recorded here rather than assumed fixed:

| Form | After the change | Why |
|---|---|---|
| `$(...)` command substitution | **denied** | the disqualified command reaches the write-target analysis, which fails closed on the substitution's unmodelled token |
| backticks | **denied** | same |
| `<(...)` process substitution | **denied** | same |
| bare `&` backgrounding | still allowed | with no write verb the command reaches `_shell_write_targets_are_safe`, which fails closed only on a write-target *token* containing one of `$ ` ` ( ) { } * ? [ ]`. A bare `&` introduces none |
| physical line break | still allowed | same reason |

So the `## Proposed Change` claim that a disqualified command "falls through to
the write-target analysis, which fails closed on anything it cannot prove safe"
is true only for the forms that introduce such a token. Closing the `&` and
newline forms needs a change to the write-target analysis itself, which is out of
scope here and left as a stated residual.

## Verification Metric

Target-Metric: count of commands that write to a protected enforcement-chain file
yet exit 0 at the write-protection gate, over the measured probe set
Expected-Direction: decrease
Horizon: this change's verification run, then the next completed feature whose
work modifies the guard
Baseline: 2 (the command-substitution and backtick probes, both runtimes,
measured 2026-08-23; the control probe was correctly denied)
Target: 0

Secondary (no capability lost): commands that genuinely only read a protected
file must still exit 0. Baseline: allowed today. Target: unchanged, asserted by a
must-allow case.

Secondary (drift): the two exemptions must share one disqualifier. Baseline: 1 of
2 exemptions carries it. Target: 2 of 2, asserted **at source level** by the
`constant-parity` assertion — not as a behavioural claim about both gates
refusing one command, which the guard's single-verdict output cannot express.

**Instrument independence.** The primary metric counts exit codes from the very
function this WFI modifies, which is self-grading. It is made honest by
pre-registration rather than by a different instrument: the probe set is the
fixed list of literal command strings in `## Problem Evidence`, with pre-change
exit codes already recorded there, replayed black-box against the guard's exit
code. The control probe (a plain write, must stay denied) and the must-allow
probe (a genuine read, must stay allowed) are what detect a metric moving for the
wrong reason. The inert-patch measurement recorded in `## Problem Evidence` is
the precedent for why this matters: without it, a change that moved nothing would
have been reported as moving the metric to 0.

## Rollback-Plan

Revert the commits whose messages contain `WFI-046` — plural: this change spans
the three runtimes, two test suites, six mirrors and two manifests, and WFI
applications in this repository routinely land across several commits. Note the
revert is itself a protected write and must go through the human-copy apply route
(see `## Proposed Change`), and it must re-sync the same six mirrors and two
`MANIFEST.sha256` files in the same commit or the mirror-freshness suite fails.
The short-circuit returns to its three-clause form, the added regression and invariant cases are removed with
the same revert, and the sibling exemption's disqualifier — which predates this
WFI — is untouched.

Reverting restores the measured bypasses, so the rollback should be treated as
reopening a known hole rather than as a neutral undo. Nothing else depends on the
change: no stored artifact records which clause set exempted a given command, and
no manifest, ledger or evidence bundle changes shape.
