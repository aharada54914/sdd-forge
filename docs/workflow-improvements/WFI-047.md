## Problem Evidence

Commit `726240f9` (branch `claude/plugins-pin-stability`) added an Amendment
Re-Review Context lane to the spec-review stage: when
`specs/<feature>/investigation.md` carries a structured entry — full amendment
commit hashes, per-document SHA-256 at the amendment commit, and a verbatim
dated quotation of the human's approval — the reviewer calibration suppresses
findings whose sole basis is that later-phase artifacts exist while
`Spec-Review-Status` is Pending.

The lane exists because it was measured to be missing, twice, in one evening.
epic-194's and epic-195's spec stages were legitimately re-reviewed after
human-approved post-implementation amendments (the human's words, 2026-08-23:
「194/195/196の凍結文書について人間は承認する」), and both loops walled at the
same place. epic-194 attempt-2 round-2's reviewer B, verbatim:

> it asserts, in the artifact currently being spec-reviewed, that later-phase
> work already occurred before the approval gate this same package still
> awaits.

epic-195 attempt-3 round-3's reviewer A rejected the narrative remedy and
enumerated the evidence forms it would have accepted — file:line + sha256,
PR/commit reference, or ledger record. The lane's evidence bar is that
enumeration, taken from a persisted verdict rather than invented. Round
counts: epic-194 burned two rounds, epic-195 three (terminal BLOCKED), on a
recovery the workflow had no vocabulary for. The impl stage has had this
vocabulary twice over (`--provenance-rereview`, `legacy_design`) since long
before; the spec stage had neither.

The deployment was explicitly limited. A security review of `726240f9` flagged
the mechanism as an instruction-poisoning surface, and its analysis is
accepted as accurate by the lane's own author:

> An agent can write fabricated prose into investigation.md: a fake quoted
> "approval," invented-but-well-formed commit hashes and SHA-256 fingerprints
> — nothing here is cross-checked against git or the filesystem by this gate.

The human then authorized exactly two uses plus this filing (2026-08-23:
「限定デプロイ + WFI 起票でやれ」). What bounds the damage today is scope,
not detection: a forged entry can suppress only the phase-sequencing class,
never coverage, testability, contradiction or ambiguity findings, and cannot
relax any hash, contract or identity check. The safety property is
scope-boundedness. This WFI exists because scope-boundedness is the right
floor and the wrong ceiling.

## Root Cause Hypothesis

The repository has exactly two mechanisms that prove a human acted, and both
prove it by making the agent's imitation *mechanically impossible* rather
than semantically discouraged: the `SDD_SUDO` token, whose HMAC needs a key
stored outside the repository, and the `Second Approval:` line, which the
hook guard refuses to let an agent write at all. Every other "a human
approved this" claim in the tree is prose, and prose is exactly what agents
produce.

The lane's entry is prose. It raises the *cost* of a convincing forgery
(full hashes, per-document digests, verbatim quotes) without raising its
*possibility*. The root cause is therefore not the lane — it is that the
workflow offers no reusable, agent-unforgeable primitive for "a human
approved this specific thing on this specific date" that a document could
cite. `SDD_SUDO` is close but wrong in two ways: it expires (approvals are
archival), and it authorizes a session, not a statement.

## Proposed Change

| Target File | Change Description |
|---|---|
| New: an approval-attestation primitive | A durable, statement-scoped human attestation: a small record (statement text, date, scope) signed with the same out-of-repo key machinery `SDD_SUDO` already uses, verifiable by any gate via the existing key-resolution order, and committed alongside the document that cites it. Issuing one is human-only for the same reason `/sdd-sudo` is: the agent lacks the key... but note the residual risk honestly — in this repository's actual practice the human has directed the agent to run the token-issuance procedure, so "the agent lacks the key" is organizationally rather than technically enforced. The design must state which threat it defends against (a *silently* self-authorizing agent) and which it cannot (a human who delegates signing wholesale). |
| `plugins/sdd-review-loop/references/spec-review-calibration.md` | Replace the entry's "verbatim quotation is the record" clause with "the entry cites an approval attestation by path, and the reviewer treats the attestation's signature validity as reported by the precheck". Keep every other element of the evidence bar (full hashes, per-document digests, no bare paths) — those verify the *amendment*, the attestation verifies the *approval*, and the two halves answer different forgeries. |
| `plugins/sdd-review-loop/scripts/spec-review-precheck.sh` (guard-protected — human-copy staging route) | Verify the cited attestation's signature during precheck and record the result in `precheck-result.json`, which is already in every reviewer's allowlist. Reviewers never do cryptography; they read a field the deterministic gate computed. |
| The other review stages | Once the primitive exists, retire the impl stage's prose-based `legacy_design` relaxation in its favour, so the workflow converges on one attestation mechanism instead of three ad-hoc ones. |

## Expected Effect

A future amendment re-review needs no per-case human risk decision: the lane
stops being "limited deployment under explicit authorization" and becomes an
ordinary, verifiable workflow step. The forgery analysis shifts from "bounded
damage if forged" to "not forgeable without the signing key", which is the
same standard the repository already trusts for sudo.

## Verification Plan

1. **The primitive resists its threat**: an agent-authored attestation with a
   fabricated signature must be rejected by the precheck's verification, in a
   scratch fixture, with the failure recorded in `precheck-result.json`.
2. **Detection is real, not ceremonial**: a fixture entry citing a *valid*
   attestation whose statement text does not cover the amendment in question
   (wrong scope, wrong date) must leave the default calibration in force —
   scope matching is part of verification, or the signature only proves "a
   human once signed something".
3. **The retirement holds**: after the impl stage migrates, grep confirms no
   review-stage instruction file accepts prose-only human-approval claims.
