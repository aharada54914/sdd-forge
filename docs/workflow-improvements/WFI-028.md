## Problem Evidence

`traceability.template.md` and `validate-layer-traceability.py` disagree about
which column holds the Layer Spec. An author who follows the template produces a
file the validator rejects, and the rejection message names the wrong problem.

**Column disagreement.** The template's header is ten columns wide:

```
| Requirement | Investigation | Design | Layer Spec | API/Schema | Code Target | Test ID | Test Target | Evidence | Status |
```

Layer Spec is the fourth column — index 3. The validator reads index 2:

```python
value = cells[2] if len(cells) > 2 else ""      # validate-layer-traceability.py:34
```

Writing `specs/sdd-context/traceability.md` from the template produced, verbatim:

```
invalid Layer Spec for REQ-001: design.md#components
```

`design.md#components` is a correct Design cell. The validator read it as a Layer
Spec, and the message blames the author for a cell that was right.

**The template is the stale side, not the validator.** The existing
`specs/agent-cost-context-isolation/traceability.md` is six columns:

```
| Requirement | Design | Layer Spec | Code Target | Test ID | Status |
```

Here Layer Spec *is* index 2, and that file passes. So the validator matches the
repository's actual corpus; the ten-column template matches nothing that
validates. Every feature authored from the template is either failing this gate
or was silently rewritten to the six-column shape without the template being
corrected.

**Second defect: every requirement-keyed table is inspected.** The validator
selects rows by first-cell pattern alone:

```python
if cells and re.fullmatch(r"REQ-\d{3}", cells[0]):   # :32
```

It does not scope this to the traceability table. After fixing the column order,
adding a separate "Investigation Grounding" table — a different table, with
different columns, under its own heading — produced:

```
invalid Layer Spec for REQ-001: Manifest registration was not a contested assumption; no INV finding applies.
```

The prose in that table's third column was read as a Layer Spec anchor. The
workaround was to demote the second table to a bullet list. That is a real
constraint on how a traceability document may be structured, and it is written
down nowhere.

## Root Cause Hypothesis

The template and the validator were changed at different times and neither
references the other. Nothing in the repository asserts that the template's
column order agrees with the index the validator reads, so the two drifted
without any gate noticing — the validator only ever sees files, never the
template that produced them.

The second defect has a separate cause: the row selector encodes "a row about a
requirement" when it means "a row in the traceability table". Those coincide in
a single-table document and diverge the moment an author adds any other
requirement-keyed table. The validator's own error text cannot distinguish the
two cases, so the failure surfaces as a nonsense complaint about prose.

## Proposed Change

1. **Correct the template to the shape the validator parses.** Replace
   `traceability.template.md`'s header with the six-column form the existing
   corpus uses and the validator reads (`Requirement | Design | Layer Spec |
   Code Target | Test ID | Status`). This is a template-only edit: no existing
   traceability file changes, and no gate behaviour changes.

2. **Scope the validator's row selection to the traceability table.** Select
   rows by position relative to the table whose header contains `Layer Spec`,
   rather than by first-cell pattern alone, so a document may carry other
   requirement-keyed tables. Until this lands, record the constraint explicitly
   in the template.

3. **Add a drift lock.** A test that parses the template's header, locates the
   `Layer Spec` column index, and asserts it equals the index the validator
   reads. This is the check whose absence let the two drift; without it, item 1
   fixes today's mismatch and nothing prevents tomorrow's.

## Expected Effect

- An author following the template produces a file that passes on the first run.
  Today it fails, and the message points at a correct cell.
- Traceability documents may carry supporting requirement-keyed tables without
  a spurious failure, or — until item 2 lands — the author is told not to.
- The template and validator cannot drift apart again without a test failing.

## Verification Plan

1. Author a fixture traceability file mechanically from the corrected template
   and assert it passes the validator unmodified. Before item 1 this fails with
   `invalid Layer Spec for REQ-001: design.md#...`, which is what establishes the
   test is not vacuous.
2. Add a second fixture carrying a supporting requirement-keyed table and assert
   it passes after item 2 (and that the template documents the restriction until
   then).
3. The drift-lock test from item 3 must fail if either the template's column
   order or the validator's index is changed alone.
4. Re-run the existing corpus (`specs/*/traceability.md`) and confirm no file
   that passes today starts failing.

## Rollback-Plan

Revert the template edit, the validator change, and the drift-lock test
together. No traceability file's content depends on the change — the six-column
shape already validates under both the old and the new validator, so existing
artifacts are unaffected either way. Reverting restores the drift, not a
breakage.
