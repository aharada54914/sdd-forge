## Problem Evidence

Observed during the T-002 quality gate of `sdd-domain-concept-contract`
(gate report `reports/quality-gate/20260819T052000Z.md`, evaluator run
`RUN-sdd-domain-concept-contract-qg-T-002-seq0789`, ledger sequence 789).

The independent evaluator reported, unprompted, in the "Could NOT verify"
section of the preceding T-001 gate
(`reports/quality-gate/20260819T042254Z.md`, run
`RUN-…-qg-T-001-seq0788`):

> my scratchpad already contained the implementing agent's working files
> (`contract-v2-schema.Tests.ps1.bak`, `red.log`, `green.log`,
> `t003-tests-append.ps1`, `t005-addition.ps1`). I deliberately did **not**
> read them — they are unauthorized inputs — and none of my evidence derives
> from them. Flagging it because it is an isolation weakness in the harness.

The implementation agents for T-001 through T-005 and the evaluators for
T-001 and T-002 were all given the same session scratch directory. The
evaluator could therefore see intermediate artifacts of the very work it was
grading, including a `.bak` of the suite under review and per-task append
scripts that reveal how each fixture batch was authored.

Nothing was compromised in this instance: the evaluator recognised the files
as outside its `allowed_input_manifest` and declined to read them, and it
reported the exposure rather than staying silent. That is the point — the
guarantee held because the grader behaved well, not because the harness
prevented the exposure.

## Root Cause Hypothesis

The quality gate enforces evaluator isolation only at the *declared-input*
layer. `validate-review-context-set` binds a hash-verified
`allowed_input_manifest`, reserves an identity in the canonical ledger, and
rejects unlisted paths, chat-only input and session reuse. That machinery
governs what the evaluator is *authorized* to read.

It does not govern what the evaluator can *reach*. The evaluator runs with a
working filesystem and needs command execution to produce its own evidence —
it must be able to run test suites, hash files and reconstruct prior states
from git. Nothing in the launch contract says where its scratch space lives,
so an orchestrator that reuses one session-wide scratch directory for both
implementation and evaluation silently places the generator's intermediate
output inside the grader's reachable working set.

The isolation guarantee is therefore enforced by manifest validation plus
evaluator good behaviour, rather than by construction. Because the evaluator
is the workflow's grader, an isolation property that depends on the grader
policing itself is the weakest possible form of that property.

## Proposed Change

| Target File | Change Description |
|---|---|
| Quality-gate evaluator launch contract (generic workflow surface) | Require the launching orchestrator to allocate a scratch directory dedicated to the evaluator run, distinct from any directory an implementation context for the same feature has used, and to pass its path explicitly in the launch brief. |
| Review-context invocation contract (generic workflow surface) | Add an optional declared scratch-root field to the invocation record so the reserved identity names the working directory it was launched with, making the property auditable after the fact rather than assumed. |
| Implementation launch contract (generic workflow surface) | Require implementation contexts to write intermediate artifacts only under their own per-task scratch root, so a shared parent cannot accumulate cross-role residue. |

The change is a launch-time convention plus one recorded field. It does not
relax any existing check: the manifest hash verification, ledger reservation,
unlisted-path rejection and session-reuse rejection all stay exactly as they
are. It closes the gap underneath them.

## Expected Effect

Evaluator isolation becomes a structural property of the launch rather than a
behavioural one. An evaluator that reached for a generator intermediate would
find nothing there, so a future grader that is less scrupulous than this one
cannot silently contaminate a verdict.

Secondary effect: the exposure becomes auditable. Today the only reason this
instance is known is that the evaluator volunteered it in prose. With the
scratch root recorded on the invocation, a deterministic check can compare it
against the implementation runs for the same feature and fail closed.

The metric key does not exist in the run record today; adding it is part of
this WFI and is the reason `Meta-Change: true` — auditor-b should confirm the
addition measures the property honestly and that no existing gate, test or
check count decreases as a result.

## Verification Plan

The next five quality-gate runs each record the evaluator's scratch root on
the `review-context-invocation` record at reservation time. For each run,
compare that path against the scratch roots used by every implementation
context for the same feature. The WFI is verified when five consecutive
evaluator launches show no overlap, and the deterministic comparison is in
place so a regression fails the gate rather than depending on an evaluator
noticing and mentioning it.

A negative control is required before claiming success: deliberately launch an
evaluator with a shared scratch root in a scratch feature and confirm the new
comparison rejects it. Without that control the check could pass vacuously,
which is the failure mode `Meta-Change: true` exists to catch.

## Rollback-Plan

Revert the commit whose message contains `WFI-034`. That restores the previous
evaluator launch brief, removes the declared scratch-root field from the
review-context invocation contract, and removes the run-record metric key. No
data migration is needed: the field is additive and optional, existing
invocation records without it stay valid, and no reserved ledger identity is
affected because the ledger record shape is unchanged.
