## Problem Evidence

The traceability validator takes `traceability.json` as its first positional
input and exits 1 when the file does not exist
(`plugins/sdd-quality-loop/scripts/check-traceability.sh:2-27`). Epic 196 had
the canonical Markdown matrix but no JSON companion, so T-001's gate recorded
the missing artifact as a traceability failure
(`reports/quality-gate/20260831T003856Z-epic-196-a8-integration-T-001.md:25-49`)
and review ticket RT-20260831-005 required a canonical artifact or approved
migration path (`docs/review-tickets/RT-20260831-005.yml:9-26`).

The JSON form is established elsewhere rather than an Epic 196 invention.
Examples include `specs/epic-159-pillar-a/traceability.json:1-5`,
`specs/ci-mcp/traceability.json:1-5`, and
`specs/sdd-forge-mcp/traceability.json:1-5`; Epic 195 also added one in all-ref
history at commit `e5643d04`.

Epic 196 could pass only after this session wrote a purpose-built generator and
committed its output in
`0d6068206ab2c379f1b6c432451f2280e1ef0776`. The script derives REQ rows from
`traceability.md`, takes the authoritative AC-to-REQ and AC-to-TEST mapping from
`acceptance-tests.md`, and never invents missing IDs
(`specs/epic-196-a8-integration/verification/qg-backfill/derive-traceability.py:2-49`).
It also emits evidence paths only for files that exist on disk
(`specs/epic-196-a8-integration/verification/qg-backfill/derive-traceability.py:51-71`).
That is a useful generator shape, but its feature-specific absolute path and
backfill location prove production currently depends on per-feature luck.

## Why-Why Analysis

1. Why did validation fail before evaluating any links? Because its required
   machine-readable input did not exist.
2. Why did the feature omit it? Because the authoring workflow creates the
   human-readable matrix but has no canonical JSON producer.
3. Why do some features have one? Because individual authors or remediation
   campaigns created bespoke companions.
4. Why is that unreliable? Because the validator and bootstrap workflow do not
   share an artifact contract or generation step.
5. Why should generation be centralized? Because deterministic derivation can
   preserve the authoritative mappings and existing-file constraint without
   feature-specific judgment.

## Root Cause Hypothesis

The workflow distributes a validator without distributing its corresponding
producer. Artifact presence is therefore accidental, and a feature may satisfy
the human-readable traceability process yet fail before machine validation can
assess its actual links.

## Proposed Change

| Target File | Change | Evidence |
|---|---|---|
| New canonical traceability generator in the shared plugin, with portable entry points | Derive the JSON companion from the Markdown matrix and acceptance mapping using repository-relative paths. | The Epic 196 derivation at lines 24-58 demonstrates the mapping algorithm. |
| Bootstrap/task-decomposition workflow | Generate or refresh the companion when the source artifacts are first complete. | Established features already store this companion beside the Markdown source. |
| Gate precheck | If the companion is absent or stale, invoke the same deterministic generator or emit the exact remediation command before validation. | RT-20260831-005 failed solely because no producer had run. |
| Generator tests | Cover multiple requirements, multiple ACs/tests, absent evidence directories, stale output, malformed source rows, and deterministic ordering. | The backfill currently restricts evidence to existing `.log`/`.json` files at lines 51-58. |

The promoted generator should accept a repository root and feature slug rather
than embedding an absolute path. It must use `acceptance-tests.md` for AC
ownership, use `traceability.md` for REQ/task rows, include only evidence that
exists, sort deterministically, and write atomically. Generation must not turn
missing source mappings into empty success: ambiguous, duplicate, or malformed
authoritative rows fail with a named diagnostic.

## Expected Effect

Every feature receives the same canonical machine-readable companion from the
same authoritative sources. Validation failures then describe broken or stale
links, not whether a particular feature author happened to invent a generator.

## Verification Metric

Baseline (Epic 196): 1 of 1 quality-gate runs failed immediately on an absent
JSON companion and required a one-off 74-line derivation script.

Target: 0 missing-companion failures for newly bootstrapped features; 100%
byte-identical output across two consecutive runs on unchanged inputs; 100% of
emitted evidence paths exist at generation time.

## Verification Plan

1. Run the canonical generator against Epic 196 and compare its semantic output
   with commit `0d606820...`; all REQ/AC/TEST links must match.
2. Run it twice without source changes and require an empty diff.
3. Exercise representative existing companions from Epic 159, CI MCP, and the
   forge MCP; document any schema migration rather than silently rewriting it.
4. Remove an evidence file in a fixture; prove its path is not emitted.
5. Add malformed, duplicate, and unmapped source rows; each must fail with a
   specific diagnostic and leave the prior output untouched.
6. Run the existing traceability validators on generated output in both runtime
   twins and mutation-test the mapping source and existing-file restriction.

## Rollback-Plan

Remove automatic invocation while retaining the standalone generator for
explicit remediation. Existing generated companions remain ordinary tracked
artifacts and require no rewrite. The validator continues to fail closed when
no valid input is present.

## Result

Result: Blocked as written on 2026-09-02; status remains `Approved`.

The Epic-196 backfill in `0d606820` is feature-specific and parses one concrete
Markdown table shape, while current tracked companions and source documents use
multiple established shapes. The WFI does not define the canonical Markdown
grammar, companion schema version/migration rule, authoritative handling of
planned versus already-existing evidence, or which bootstrap/gate entry point
owns atomic refresh. Verification Plan item 3 explicitly requires documenting
schema migration rather than silently rewriting existing companions, so
promoting the one-off parser would not satisfy the proposal. No shared runtime
or frozen-spec files were changed. A human-authored input/output schema and
migration decision are required before the portable generator and both entry
points can be implemented and mutation-tested truthfully; this note is not a
human rejection. The existing Epic-196 companion remains attributable to
`0d606820`, but that feature-local remediation is not claimed as WFI-062.
