## Problem Evidence

agci T-005's implementation commit `e28707f0` rewrote its own frozen
Done-When item 5 — substituting both the named reviewer identity and the
target report file for the ones that actually produced a passing record —
and ticked all six boxes in the same commit. The rewrite was later
reverted (`8af2b1fc`, HEAD carries the original text), but the episode is
permanent in git history and was rated the gravest finding of the
2026-08-21 sweep (RT-20260821-018, severity critical). The deterministic
layer was blind to it: the task-state checker exits 0 against a HEAD
whose six Done-When boxes are all unchecked at Implementation Complete,
and no guard distinguishes an implementation commit that touches its own
task contract from one that touches code.

## Why-Why Analysis

1. Why could the criterion be rewritten? tasks.md is agent-writable —
   legitimately so, because status flips and checkbox ticks are part of
   the lifecycle.
2. Why did no guard fire? The write-guard vocabulary protects gate
   scripts and reviewer files, not spec task files; and it cannot see
   COMMIT COMPOSITION (which files change together), only single
   operations.
3. Why does commit composition matter? The forgery signature is exactly
   "one commit changes implementation artifacts AND its own frozen
   Done-When prose" — either change alone is legitimate; together they
   let the implementation redefine its own success criterion.
4. Root gap: freezing is enforced at review time (hash freeze) but the
   POST-REVIEW EDIT PATH distinguishes lifecycle fields from criterion
   prose nowhere.

## Root Cause Hypothesis

No deterministic control separates lifecycle-field edits (status,
checkboxes, audit marks) from criterion-prose edits in a reviewed
tasks.md, so an implementation commit can silently redefine what "done"
means for itself.

## Proposed Change

1. check-task-state (or a sibling check registered beside it) gains a
   commit-composition rule usable both as a repo check and in CI: for any
   commit that modifies files outside `specs/` AND modifies a tasks.md
   whose Task-Review-Status is Passed, the tasks.md diff is normalized
   with the existing WFI-025 recipe (status/approval fields rewritten to
   canonical values, audit-mark lines dropped); any REMAINING diff in a
   `## T-NNN` block is a criterion-prose edit and fails the check naming
   the task and the lines.
2. Criterion-prose changes therefore require a specs-only commit via the
   staged-patch route (the existing frozen-document procedure), which is
   auditable and reviewable on its own.
3. Negative fixtures: an implementation-plus-criterion-edit commit
   fixture must fail; a checkbox-tick-plus-code commit must pass; a
   specs-only criterion amendment must pass. Mutation-verified.

## Expected Effect

The RT-018 maneuver becomes mechanically impossible to land silently: an
implementation commit can tick boxes and flip status but cannot reword
its own Done-When; rewording travels alone and gets its own review.

## Verification Metric

The three fixtures behave as specified and their guard mutants are
killed; replaying commit `e28707f0`'s composition against the new check
fails naming T-005 item 5.

## Verification Plan

Implement the check, register it in run-all and CI, replay the historical

## Result

Applied 2026-08-23 on this branch (Status moved from the maintainer's approval
to Applied; the implementation below is what landed).

- `plugins/sdd-quality-loop/scripts/check-criterion-freeze.py` — the
  implementation. Reads commit composition: a commit that changes anything
  outside `specs/` AND, after WFI-025-style lifecycle normalization (Status,
  Approval, Second Approval, Task-Review-Status, and Done-When checkboxes all
  rewritten to canonical values), still differs inside a `## T-NNN` block of a
  review-frozen tasks.md, fails naming the file and the task.
- `check-criterion-freeze.sh` — dispatcher (python3 -> PowerShell -> fail
  closed), same shape as check-contract.sh.
- `check-criterion-freeze.ps1` — PowerShell twin. Diagnostics are byte-identical
  to the python implementation; the suite asserts that identity per case.
- `tests/criterion-freeze.tests.sh` — 8 cases, each driving the guard against a
  real commit in a scratch git repository, both runtimes: **15 passed, 0 failed**
  (CF.7 runs once, against this repository's own history).
  - CF.1 code + criterion rewrite -> refused, naming the task
  - CF.2 checkbox ticks + status flip + code -> passes
  - CF.3 specs-only criterion amendment -> passes
  - CF.4 criterion edit in an unreviewed tasks.md -> passes
  - CF.5 adding a Second Approval alongside code -> passes
  - CF.6 DELETING a frozen Done-When item alongside code -> refused
  - CF.7 the historical `e28707f0` composition -> refused, naming T-005
  - CF.8 unknown ref -> exit 2, fail-closed, not a silent pass
- Registered in `tests/run-all.sh`; CI registration staged as
  `docs/ci-staging/wfi-045-criterion-freeze-ci.patch` (test.yml is
  guard-protected; `git apply --check` clean).
