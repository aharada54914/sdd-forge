## Problem Evidence

A task-stage provenance binding made over a status-mixed `tasks.md` breaks on
the very next lifecycle transition, and there is no validator-legal way to make
one that does not.

`check-workflow-state.sh` accepts four canonical forms of the task-plan hash:

1. `normalized_hash` — every `Status:` rewritten to `Planned`, every
   `Approval:` to the draft value
2. the raw bytes
3. `rereview_normalized_hash(..., "Implementation Complete")`
4. `rereview_normalized_hash(..., "Done")`

Forms 1, 3 and 4 are invariant under status transitions: they normalise the
status lines away before hashing. Form 2 is not.

A plan whose tasks are in mixed states — the normal condition for any epic
mid-flight — matches only form 2, because forms 1/3/4 all require the file's
statuses to be uniform. So the binding is raw bytes, and any subsequent flip
of any task invalidates it.

That would be a tolerable convention if a durable binding were reachable. It is
not:

- `validate-review-context-set.sh` requires every manifest entry's declared
  `sha256` to equal the live file's raw sha256.
- The round-consistency check requires the manifest to agree with the
  precheck's `tasks_sha256`.
- `task-review-precheck.sh:494` computes `tasks_sha256` as the raw hash.

The only binding the sanctioned reservation path can produce is therefore the
one form that is guaranteed to break.

Observed directly, three times in one session, on three separate features:

- `epic-190-a2`: rebound at attempt-5 after T-007 reached Done.
- `epic-194-a6`: rebound at attempt-3; the attempt-2 binding recorded raw bytes
  while T-004 was `Implementation Complete`, and the quality gate's flip to
  `Done` — the only byte change to `tasks.md` since — broke it. Both reviewers
  independently raised that the replacement binding is mixed too and will need
  redoing.
- `epic-191-a3`: rebound at attempt-5 after T-002 and T-005 reached Done.

Demonstrated on a scratch copy of `epic-191-a3`'s `tasks.md` (the real file
untouched): simulating T-003 flipping to `Done` invalidates the freshly made
attempt-5 binding immediately, while the normalized and both
rereview-normalized hashes come out **byte-identical before and after** the
same flip.

Each rebind costs two reviewer launches, two ledger reservations and a
full contract artifact set — for a file whose semantic content did not change.

## Root Cause Hypothesis

The four accepted forms were designed to make the binding survive lifecycle
transitions, and three of them do. But the *producing* side — precheck and
validator — only ever emits raw. The accepting side is more permissive than
the producing side can exercise, so the durable forms are dead code in
practice: reachable only by hand-authoring a manifest, which the validator
then rejects for other reasons.

This is consistent with the forms having been added to `check-workflow-state.sh`
without a corresponding change to `task-review-precheck.sh`.

## Proposed Change

Make the producing side able to emit a durable binding for the case that needs
it.

1. In `task-review-precheck.sh` / `.ps1`, when the plan's task statuses are
   **not** uniform, compute `tasks_sha256` as `normalized_hash` rather than raw,
   and record which form was used in the precheck result under a new
   `tasks_sha256_form` field (`raw` | `normalized`).
2. In `validate-review-context-set.sh` / `.ps1`, allow a `tasks.md` manifest
   entry to declare the normalized hash **only** when the precheck result for
   the same attempt/round declares `tasks_sha256_form: normalized`. Every other
   manifest entry keeps the current strict raw-hash requirement — this
   exception is scoped to the one file whose status lines the normalization is
   defined over.
3. Leave `check-workflow-state.sh` unchanged: it already accepts the normalized
   form.

The scope is deliberately narrow. It does not weaken hash binding — a
normalized hash still binds every byte of the plan except the status and
approval fields, which are exactly the fields the lifecycle is *supposed* to
change. It does not touch the identity ledger or the reservation protocol.

## Expected Effect

A task-stage binding made mid-flight survives every subsequent status
transition of that feature, so a rebind is needed only when the plan's
substance changes — not when the workflow does its job.

Concretely: `epic-191-a3` would have needed one binding instead of five, and
`epic-194-a6` one instead of three.

## Verification Metric

Number of task-stage rebinds attributable solely to a `Status:` transition,
measured over the next full epic run. Current value: 3 in a single session
across three features. Target: 0.

## Verification Plan

1. A new test in `tests/task-review-precheck.tests.{sh,ps1}`: build a fixture
   plan with mixed statuses, run the precheck, assert `tasks_sha256_form` is
   `normalized` and the hash equals the normalized hash. Build a uniform plan,
   assert the form is `raw`.
2. A non-vacuity mutation for each: flip the fixture's mixture and assert the
   emitted form changes. A test that passes under both shapes proves nothing.
3. An end-to-end test: bind a mixed-status plan, flip one task's status, and
   assert `check-workflow-state.sh` still exits 0 — the property this WFI
   exists to create. Assert the same sequence fails before the change, so the
   test is known to discriminate.
4. Confirm the scoped exception cannot be used on any other file: attempt a
   manifest declaring a normalized hash for a non-`tasks.md` entry and assert
   the validator rejects it.

## Rollback-Plan

Revert the precheck and validator changes. Bindings return to raw-only;
existing normalized bindings would then fail `check-workflow-state.sh` and each
affected feature would need one rebind, which is the current steady state
anyway. No data migration, no ledger surgery.
