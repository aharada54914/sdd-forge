## Problem Evidence

An implementation report could authorize an ARBITRARY file into an
evaluator's readable input set by padding one section heading with a single
invisible character.

Two components disagreed about what `## Outputs` means:

- `validate-implementation-report.sh` keyed a section by the raw captured
  heading text, so `## Outputs ` became the section `"Outputs "` — a section
  it then never row-parsed, never path-checked, and never added to
  `seen_paths`.
- `validate-review-context-set.sh`'s `evaluator_output_is_declared` matched
  headings by PREFIX, so it *did* treat `## Outputs ` as an Outputs section
  and honoured the rows inside it.

Measured end-to-end on a scratch clone (gate seq 851): a report with a
second, padded heading declaring `plugins/SMUGGLED-SECRET.md` returned
`IMPLEMENTATION_REPORT_OK` and then `REVIEW_CONTEXT_OK`, with the smuggled
path in the authorized set. The same shape carrying `../../etc/passwd` also
passed, although that exact row is rejected as `invalid output path` when
placed in the real table. Markdown renders both headings identically, so
human review cannot see the difference.

The first fix (seq 851) was incomplete and the next gate broke it on
request (seq 853): it stripped only space and tab, leaving form feed,
vertical tab, NBSP, NUL and mixed pads exploitable — and it tightened only
the TABLE heading, leaving the LEGACY `## Output Paths And Hashes` heading
on a prefix test at the boundary, which is matched by a different rule.

## Why-Why Analysis

1. Why did a padded heading smuggle a path? Two components applied
   different equality rules to the same heading.
2. Why did that matter rather than merely differing? The lenient side is
   the one that GRANTS authorization; the strict side is the one that
   VALIDATES. Leniency downstream of validation is a bypass, not a
   difference of opinion.
3. Why did the first fix not close it? It enumerated the characters it had
   seen (space, tab) instead of the class, and it fixed the heading it had
   been looking at instead of every heading the boundary matches.
4. Why did the suite not catch either? The pad loop enumerated two sample
   characters, and no test pinned the boundary's matcher construct at all,
   so the half-fix was invisible.
5. Root cause: a parsing contract shared by two enforcement components was
   never written down or pinned, so each side drifted to its own tolerance.

## Root Cause Hypothesis

The section-heading grammar is an implicit contract between the report
validator and the authorization boundary. Nothing states it and nothing
pins it, so any divergence in whitespace tolerance becomes an authorization
bypass rather than a formatting nit.

## Proposed Change

1. State the heading grammar explicitly in one place both components cite:
   a heading is `## ` followed by a name containing no control characters,
   compared after full-Unicode whitespace stripping.
2. Both components implement exactly that. Control characters are refused
   with their own diagnostic (they cannot be stripped away silently); every
   other whitespace form normalizes so a padded heading collides with its
   clean form and the duplicate-section guard fires.
3. Every heading the boundary matches is covered, not just the one under
   discussion — currently `## Outputs`, `## Output Paths And Hashes` and
   `## Post-Fix Artifacts`.
4. Pin the CLASS, not samples: the suite enumerates space, tab, CR, form
   feed, vertical tab, NBSP and NUL on each heading, and a separate test
   pins the boundary's matcher construct so a return to prefix matching
   fails immediately.

## Expected Effect

A padded heading is either normalized to the same section (and caught by
the duplicate guard) or refused outright. The two components cannot drift
apart again without a test failing.

## Verification Metric

A matrix of every heading × every pad form yields zero end-to-end bypasses,
and each of these mutants dies: strip removed, strip narrowed to
space+tab, control-character guard removed, either boundary matcher
returned to a prefix test.

## Verification Plan

Build the smuggling report for each heading and pad form, drive each
through the report validator AND the authorization boundary on a scratch
clone, and require zero cases where both return success. Run the mutation
set above. Confirm a legitimate manifest still validates, and scan the
shipped corpus to confirm no existing report relies on a padded heading.

## Rollback-Plan

Revert both component changes and their pins together. Rolling back only
one side recreates the divergence that is the vulnerability, so they must
move as a pair.

## Result

Implemented 2026-08-24 on branch `staging/cycle2-regate`, across two gate
cycles.

- `plugins/sdd-implementation/scripts/validate-implementation-report.sh` —
  control characters in a heading are rejected with their own diagnostic;
  the remaining name is stripped over the full Unicode set before keying.
- `plugins/sdd-quality-loop/scripts/validate-review-context-set.sh` — both
  `evaluator_output_is_declared` and `implementation_report_legacy_declares`
  now require an exact heading match.
- `tests/turn-first-workflow.tests.sh` — the pad loop covers seven forms
  with per-class expectations.
- `tests/template-validator-parity.tests.sh` — both boundary matchers
  pinned (19/0).

**Verified**: twenty-case matrix (two headings × ten pad forms, including
mixed pads) — **zero bypasses**. Mutants killed: strip removed, strip
narrowed to space+tab, control-character guard removed, legacy matcher
returned to prefix, table matcher returned to prefix. A legitimate
manifest still validates. Corpus scan: 0 of 228 shipped reports carry a
padded heading, so the tightening breaks nothing already committed.

Open: the maintainer's Status flip, and the audit cycle. The related
architectural gap — that report validation is not a precondition of
authorization — is filed separately as WFI-050, because closing it is a
design decision rather than a parsing fix.
