## Problem Evidence

`prepare-panelist-input.{sh,ps1}` verifies every `## Outputs` row of the
frozen implementation report against the working tree, and — for rows that
have legitimately drifted — falls back to verifying the declared hash against
the tree **as of the last commit that touched the implementation report**
(`_ppi_declaration_commit`, `git log -1 --format=%H -- <report>`).

That anchor is wrong whenever the report is touched *after* the declared
outputs drift. Reproduced on 2026-08-28 (epic-194, merged main `555c6da0`):

1. The three T-001/T-002/T-003 reports gained machine-readable
   `- Task ID:` header lines (commit `8456b861`) because the evaluator
   launch validator requires a whole-line match. A two-line mechanical
   addition, no Outputs row changed.
2. That commit became the declaration commit for all three reports.
3. Nine T-001 Outputs rows had drifted earlier via the owner-approved apply
   chain (`80694f62`/`23ec91c3`) — drift the fallback had previously
   tolerated, because the old declaration commit predated it.
4. Result: `prepare-panelist-input` fail-closed with nine
   `declared output hash mismatch` lines and refused to write any bundle.
   The identical tree had produced valid bundles at `48b35687`, before the
   header-line commit moved the anchor.

The recovery used in the field was a mechanical hash refresh of the Outputs
tables themselves (`e5397149`) — editing a frozen report to satisfy a
collection tool, which is exactly the pressure the WFI-036
`gate_report_declaration` channel exists to avoid at the evaluator layer.
The preparer has no equivalent channel.

### Cost

The post-quality-gate re-panel of a three-task feature was blocked for one
work cycle; the unblocking edit (21 hash cells re-pinned across three frozen
reports, with annotations) is a class of edit the workflow otherwise
prohibits, performed because no sanctioned channel existed. Any future task
whose report is touched after Done-adjacent drift (status flips, header
additions, addendum notes) will hit the same wall.

## Why-Why Analysis

| # | Why (question) | Because (answer) | Evidence |
|---|---|---|---|
| 1 | Why did bundle preparation fail on a tree that had produced valid bundles days earlier? | The staleness fallback verified drifted rows against the declaration commit, and that commit had moved past the drift. | 9 mismatch lines at `555c6da0`; success at `48b35687` on the same drifted rows |
| 2 | Why did the declaration commit move? | It is defined as the last commit touching the report file, and a mechanical header-line addition (`8456b861`) touched all three reports. | `git log -1 -- <report>` |
| 3 | Why does a header-line edit invalidate hash verification of unrelated rows? | The fallback assumes report-touching commits and Outputs-declaring commits are the same event — the anchor is the file, not the table. | `_ppi_declaration_commit` reads file history, not row history |
| 4 | Why was the anchor chosen as the file? | It was the cheapest deterministic anchor available when the fallback was added, and at that time reports were never edited after freeze. | fallback comment cites WFI-017's missing-diagnostic regression, not post-freeze edits |
| 5 | Why are reports now edited after freeze? | Later machinery (evaluator launch validator's whole-line header requirement; annotated hash refreshes) added sanctioned mechanical edits that the fallback's design predates. | `8456b861`, `e5397149` |

## Root Cause Hypothesis

The staleness fallback anchors hash verification to the wrong event: the last
edit of the report *file* rather than the last edit of the `## Outputs`
*table*. Any sanctioned post-freeze edit to prose or headers silently
invalidates the fallback for every previously-tolerated drifted row.

## Proposed Change

In `prepare-panelist-input.sh` and `.ps1`, anchor the fallback to the last
commit in which the report's `## Outputs` section itself changed:

- Replace `git log -1 --format=%H -- <report>` with a walk of the report's
  history (`git log --format=%H -- <report>`) that stops at the first commit
  whose version of the report has a different `## Outputs` section body
  (extracted with the existing row parser) than the current version; use the
  last commit at which the section last changed as the declaration commit.
- Emit the chosen anchor in the existing stderr notice so a wrong anchor is
  visible in the transcript.
- No change to the primary path (current-hash match), to sanitization, or to
  any gate.

## Expected Effect

Mechanical post-freeze report edits (headers, annotations, prose) no longer
invalidate the staleness fallback; the fallback tracks exactly the event it
verifies against. The field workaround — editing frozen Outputs hashes to
appease the preparer — becomes unnecessary.

## Verification Metric

On a fixture repository with (a) an Outputs table committed at C1, (b) output
drift committed at C2, (c) a header-only report edit committed at C3:

- Before: preparer at C3 fails with `declared output hash mismatch` for every
  drifted row (reproducing the 2026-08-28 field failure).
- After: preparer at C3 succeeds, resolving each drifted row at anchor C1 and
  printing the `verified at declaration commit` notice with C1's id.
- Control: a row whose hash matches at neither the tree nor C1 still fails.

## Verification Plan

Twin regression test (`tests/`) building the three-commit fixture repo with
`git init` in a temp dir, asserting the before/after matrix above for both
runtime twins, registered in run-all per the usual serialized rules.

## Rollback-Plan

The change is confined to `_ppi_declaration_commit` (and the ps1 twin's
equivalent); reverting the two functions restores the file-anchored
behaviour. No data formats change.
