## Problem Evidence

The traceability matrix carries a per-requirement delivery-status column that
the workflow is designed to advance as tasks complete. At the task stage the
persisted-state validator binds that file with a whole-file digest and no
normalization of any kind, so advancing the column is impossible. Meanwhile the
task decomposition review gate passed a task plan that instructs the
implementation phase to write to that same file, on a recorded rationale
asserting a status-field exception that the validator does not implement.

### The binding

`plugins/sdd-quality-loop/scripts/check-workflow-state.sh:678-682`, stage
`task`:

```sh
traceability_hash="$(sha256_file "$traceability")"
[[ "$(jq -r '.traceability_sha256 // empty' "$precheck")" == "$traceability_hash" &&
   "$(jq -r '.traceability_sha256 // empty' "$contract")" == "$traceability_hash" ]] ||
  diagnostic "$feature" stage-provenance "task traceability hash is stale"
```

`sha256_file` (`:16-19`) hashes the file as it sits on disk. The comparison is
plain equality against the value frozen into the review artifacts. The same
file is checked a second time against the reviewer manifests at `:690-691`,
also by exact hash (`manifest_has_hash`). The PowerShell peer is identical in
behaviour: `check-workflow-state.ps1:883-884`.

The sibling artifact is treated differently. `reviewed_hash_accepted`
(`check-workflow-state.sh:234-244`) admits four digest forms for the task plan
at stage `task` — the status-normalized hash, the raw hash, and
`rereview_normalized_hash` for both `Implementation Complete` and `Done` — and
`manifest_has_reviewed_hash` (`:245-254`) mirrors all four for the manifest
lookup. That tolerance is applied to the task plan only. The traceability
matrix gets none of it, and neither does `design.md` (`:683-689`) or the four
layer specs (`:694-703`).

`diagnostic` (`:12-15`) calls `exit 1`, so a single mismatch ends the whole
run. The validator is invoked without `--feature` by the quality verification
gate (`plugins/sdd-quality-loop/skills/quality-gate/SKILL.md:64`) and by CI for
both twins (`.github/workflows/test.yml:98` and `:103`), so one feature's
diagnostic reds every feature's gate and the branch.

### The task plan the review gate approved

`specs/sdd-domain-concept-contract/tasks.md` carries the same Done When item on
three tasks — T-002 (`:289-290`), T-003 (`:412-413`), T-004 (`:529-530`):

```
- [ ] **Requirement traceability** — traceability.md rows for REQ-004 record
  this task's evidence paths.
```

Those tasks passed the task decomposition review gate on 2026-08-17
(`reports/task-review/sdd-domain-concept-contract/attempt-1/round-2/`,
`integrated-verdict.json` = PASS, contract `generated_at`
`2026-08-17T12:51:15Z`, commit `99ff8851`).

The rule that governs such items already exists and was in force. The review
gate's structural-coverage role definition,
`plugins/sdd-review-loop/agents/task-reviewer-a.md:233-239`:

> A Done When item that requires editing a review-frozen artifact (design.md
> after the impl review gate passes; the tasks.md body or traceability.md after
> the task review gate passes) is not satisfiable as written: those artifacts
> are content-frozen except for normalized status/approval fields once their
> gate passes. Such an item must instead name a non-frozen addendum record (an
> implementation report, `specs/<feature>/verification/`, or user
> documentation). A Done When item scoped to edit a frozen artifact is a Major
> finding.

That text entered the repository on 2026-07-06 (`8402ec6d`, located with `git
log -S "scoped to edit a frozen artifact"`), six weeks before this feature's
task review.

The rule was not overlooked. `reviewer-a.json`, check `OBSERVABLE-DONE`, status
PASS, records that it was applied and argued past, verbatim:

> The 'Requirement traceability' items in T-002/T-003/T-004 (lines 289, 412,
> 529 …) do not require editing traceability.md's frozen body: traceability.md's

> the already-declared path; **any residual reading as a Status-column flip

There is no normalized-status-field exception for this file. The emphasized
clause is false about the code at `:678-682`, and the PASS rests on it.

### Related prior art, and how it differs

The `Task ID:` versus `Task:` identity-key conflict between
`check-evidence-bundle.sh` and the retrospective's rule 3 is often cited as the
same shape of defect. It is not quite. There, two rules are mutually
unsatisfiable and a shippable feature is necessarily non-conformant. Here the
governing rule at `task-reviewer-a.md:233-239` is correct, unambiguous, and
resolves the case on its own: the item must name a non-frozen addendum. What
failed is that the rule is enforced by reviewer judgement alone, and the
judgement invoked an exception that the gate does not implement. The
distinction matters because it changes the fix: nothing needs to be
re-litigated between two rules, and the provenance guarantee does not need to be
traded away.

## Root Cause Hypothesis

Two independent gaps compound.

**One.** The provenance binding treats every task-stage input as a document
whose bytes must not move, but one of them is not that kind of document. The
task plan and the traceability matrix both carry lifecycle state that the
workflow is *designed* to advance as tasks complete; the design document and
the layer specs carry none. The binding grants a normalization tolerance to the
first of those two and withholds it from the second, for no stated reason. The
result is that the traceability matrix's delivery-status column has no legal
transition at all after the task decomposition review gate passes — measurably,
0 of 107 rows across 17 features have ever left the authoring-time default —
while the same transition on the task plan is routine.

**Two.** The rule that keeps unsatisfiable completion criteria out of an
approved task plan is prose evaluated by a reviewer, with no deterministic check
behind it. No script in either gate plugin inspects Done When text: grepping
both `scripts/` directories for `Done When` returns nothing. When the reviewer's
reasoning was wrong about what the gate normalizes, there was no second line of
defence, and the error was sealed into a hash-bound artifact by the PASS that
followed. The reviewer's reasoning is recorded only in the review report, which
the implementation phase never reads, so the implementer meets the same
ambiguous sentence with no access to the interpretation that resolved it.

Gap one is why the item cannot be satisfied. Gap two is why an unsatisfiable
item reached an approved plan.

## Proposed Change

Give the traceability matrix the same status normalization the task plan
already has — scoped to the delivery-status cell and nothing else — and put a
deterministic check behind the frozen-artifact rule.

| Target File | Change Description |
|---|---|
| `plugins/sdd-quality-loop/scripts/check-workflow-state.sh` and its `.ps1` peer | At stage `task`, accept the traceability matrix's binding when the live file's digest matches the recorded one either raw or after status normalization. Status normalization rewrites, on each row whose first cell matches `REQ-<id>`, only that row's final cell, and only when its trimmed value is one of the closed lifecycle vocabulary already pinned in the state registry (`Planned`, `In Progress`, `Implementation Complete`, `Done`, `Blocked`), replacing it with `Planned`. Every other byte of the file participates in the digest unchanged. Apply the same acceptance to the reviewer-manifest lookup for that file, so the two checks cannot disagree. |
| `plugins/sdd-review-loop/scripts/task-review-precheck.sh` and its `.ps1` peer | Emit a new `frozen_artifact_done_when` array into `precheck-result.json`, listing every `Done When` item whose joined text (continuation lines included) names a review-frozen artifact — the traceability matrix, the design document, or the task plan's own body — together with a write verb from a closed list (`record`, `records`, `update`, `updates`, `add`, `write`, `edit`, `append`). Each entry carries the task ID, the source line number, and the joined item text. **Detection only: this does not fail the precheck.** See "Why detection and not a hard failure" below. |
| `plugins/sdd-review-loop/agents/task-reviewer-a.md` | Two changes. (a) State, per artifact, exactly which fields the persisted-state validator normalizes — task plan: the `Status:`, `Approval:` and review-status header lines; traceability matrix: the per-requirement delivery-status cell, over the closed vocabulary only; design document and layer specs: none — so the frozen-artifact rule can no longer be argued past via an exception that is not implemented. (b) Require the `OBSERVABLE-DONE` check to adjudicate **every** entry of `frozen_artifact_done_when` individually in its recorded `finding`, stating for each whether the item is satisfiable without editing the frozen artifact and why. A check entry that leaves any flagged item unaddressed is itself a Major finding. |

**Both new mechanisms were measured against the real corpus before this WFI
proposed them.** Neither is asserted.

*Normalization, over all 34 `traceability.md` files in `specs/`.* The digest is
unchanged for 31 of them — the normalization is a no-op wherever the delivery
column still holds the authoring-time default, which is exactly the property
that lets the accepting side recompute instead of requiring a new recorded
field. The 3 files whose digest moves are `agent-cost-context-isolation`,
`claude-workflow-compatibility` and `workflow-state-integrity` — the same three
`profile: legacy` features identified in `## Problem Evidence`, which the
freeze does not reach. Against the reproduction fixtures: Case B′ (`Done`)
normalizes back to the recorded `a26c4651…` and is **accepted**; Case A (the
Evidence-cell rewrite) normalizes to its own raw digest `7699d777…` and is
**rejected**; Case B (`Delivered`, out of vocabulary) is likewise **rejected**.
The tolerance admits the lifecycle transition and nothing else.

*Done When detection, over all 34 `tasks.md` files.* A first cut that examined
each line independently found only 1 of the 3 known items: T-003 and T-004 wrap
the item across two lines, putting the artifact name and the write verb on
different lines. Joining continuation lines finds all 3 — and also raises 3
false positives: `epic-136-phase3:363` and `epic-136-phase4-mcp:1224`
(a frozen filename cited parenthetically as a source, next to an unrelated
"recorded"), and `sdd-domain:542` (`writes … to \`domain/context-map.md\``, a
different file entirely). Six items flagged, three of them real.

**Why detection and not a hard failure.** A 3-in-6 false-positive rate on the
live corpus is the measurement that settles the design. The false positives are
not a tuning artifact: "traceability.md rows … record this task's evidence
paths" and "… recorded in the implementation report … (design.md Test Strategy
item 1)" are the same grammatical shape, and no prose heuristic separates them
reliably. A hard failure at that rate would block half the plans it fires on,
which is how deterministic checks get disabled. Routing detection to the
reviewer instead costs one sentence of adjudication per false positive, and
closes the actual root cause more precisely: the reviewer here *did* reason
about the frozen-artifact rule — the reasoning was simply unverifiable and
wrong. Making per-item adjudication a required, inspectable field is what turns
that reasoning into something a later reader, or a re-review, can check.

**No producing-side change is needed** for the normalization. The recorded digest is taken at
authoring time, when every delivery-status cell already reads `Planned`; the
normalization target is that same default. So the recorded raw digest and the
normalized digest of any later file that differs *only* in those cells are the
same value, and the accepting side can recompute rather than requiring a new
recorded field. This is why the change is one script pair rather than the
producer/validator/authoring-instruction triple that WFI-025 needed.

**Known residual, stated rather than hidden.** Rows whose status cell carries an
annotated value outside the closed vocabulary — the four observed in
`epic-190-a2-capability-registry` and neighbours, e.g. `Planned (T-005
hard-blocked on Epic A1's canonicalizer contract…)` — stay byte-bound, because
widening the match to a prefix would let arbitrary prose ride in under a status
rewrite. Those rows keep today's behaviour exactly; nothing regresses for them.

**Options considered.** Three routes were on the table.

- *Extend the four-form tolerance to the traceability matrix.* Rejected as
  written. Those four forms rewrite `Status:` / `Approval:` / review-status
  *header lines*, which this file does not have — its state lives in a table
  cell. Reusing the function would be a no-op. The proposal above takes the
  principle and implements it against the actual shape.
- *Delete the Done When item from the task template and route implementation
  evidence elsewhere.* This is already the framework's codified position
  (`task-reviewer-a.md:233-239` routes such items to an addendum record), and
  the wording is not template-generated — grepping the plugin tree for
  `Requirement traceability` and for `record this task's evidence` returns
  nothing, so it was authored per-feature. There is no template to edit. The
  deterministic check above is what makes that codified position bind. Note
  also that the alternative destination sometimes proposed for this evidence,
  `traceability.json`, does not exist for `sdd-domain-concept-contract` (23 of
  34 features have one), so routing there would require creating it — a larger
  change that this WFI does not need.
- *Remove the evidence columns from the hash-frozen set.* Rejected. Both
  reviewer roles must list the traceability matrix in their input manifests
  (`task-reviewer-a.md:310`, `task-reviewer-b.md:276-281`) and the validator
  rejects task-stage evidence whose manifests omit it. Unbinding the columns
  that record code targets, test IDs and evidence paths would remove a real
  guarantee about what the reviewers actually saw, in exchange for a mutability
  only the status column needs.

**Why the status cell and not the design document or the layer specs.** The
narrowing is not "this file is less important". It is that this file is the only
task-stage input carrying a field the workflow is supposed to advance. The
design document and the layer specs have no lifecycle column: nothing in them is
expected to change as tasks complete, so a tolerance there would buy no
capability and would only widen what the gate admits. The task plan already has
exactly this tolerance for exactly this reason. The change makes the traceability
matrix consistent with its sibling, and leaves the two documents that genuinely
should not move fully byte-bound.

**Non-decreasing guard (`Meta-Change: true`).** No gate, check or test is
removed. Counted precisely, since the second mechanism is detection rather than
a gate: the deterministic *failure* count is unchanged by the Done When work —
what is added is one deterministic emission in the precheck result and one new
Major-finding condition in the review gate's `OBSERVABLE-DONE` check (an
unaddressed flagged item), so the number of conditions under which the review
gate can fail strictly increases while the number under which the precheck can
fail stays the same. The tolerance widens acceptance for exactly one file, by
exactly one digest form, over a closed vocabulary — and the verification plan
requires Case A and Case B to keep failing, so the provenance guarantee over
every non-status byte is demonstrated intact rather than asserted. The tests
below are added; none is removed or weakened.

**What this does not do.** It does not retroactively validate the recorded PASS
rationale, and it does not reopen the approved plan. Under the change, T-002's
Done When item is still not satisfiable by an Evidence-cell rewrite; it is
satisfied — as the frozen row already provides for — by producing evidence at
the paths that row names
(`specs/sdd-domain-concept-contract/verification/{T-002,T-003,T-004}/`). T-003
and T-004 carry the identical item and are resolved the same way, without the
per-task revert the current session needed.

## Expected Effect

A delivery-status transition on the traceability matrix stops being a gate
failure, so the column tracks delivery instead of standing at its authoring-time
default forever, and an implementation phase that advances it no longer reds
every other feature's quality verification gate.

Across the 17 features subject to the freeze today, 0 of 107 requirement rows
carry a status other than the authoring-time default. With the change, the
column becomes writable for every feature that has passed the task
decomposition review gate, and a task plan that asks for an unsatisfiable edit
is rejected at the precheck rather than at implementation time — where the only
remedies available are reverting the work or blocking the branch.

## Verification Plan

The two suites named below have asymmetric coverage today, and the plan is
written against what actually exists rather than an assumed twin pair.
`tests/workflow-state.tests.sh` (700 lines) builds fixtures under `mktemp -d`
and carries no traceability case at all, so the fixture scaffolding for this
behaviour is new. `tests/workflow-state.tests.ps1` (63 lines) is a thin adapter
that runs the real checker against the canonical registry plus one
malformed-registry case — it has no per-fixture harness.
`tests/task-review-precheck.tests.ps1` **does not exist**; only the `.sh` suite
(190 lines) does. Items 4 and 5 below say how the PowerShell side is covered
rather than assuming a peer file is there to edit.

1. In `tests/workflow-state.tests.sh`, add a fixture whose traceability matrix
   differs from its recorded digest only in delivery-status cells, and assert
   the validator exits 0. Non-vacuity: reverting only the two
   `check-workflow-state.*` changes (suite left in place) must make this fixture
   — and only this fixture — fail with `task traceability hash is stale`, then
   restoring them must return a green run.
2. In the same suite, add a fixture whose traceability matrix differs in a
   non-status cell and assert it still fails with the same diagnostic. This is
   Case A; it must fail both before and after the change, so the tolerance is
   shown to be scoped rather than a general loosening.
3. Add a fixture whose status cell carries a value outside the closed
   vocabulary (an annotated `Planned (…)` form) and assert it stays bound —
   the normalization must not rewrite it.
4. Twin parity for items 1-3: drive the same three `mktemp`-built fixtures
   through `check-workflow-state.ps1` from the `.sh` suite, guarded by a `pwsh`

   that owns the fixtures is what keeps a green PowerShell run from masking a
   real divergence; a passing `.ps1` adapter that never sees the fixtures would

5. In `tests/task-review-precheck.tests.sh`, assert `frozen_artifact_done_when`

7. Assert the review-gate side binds: a `reviewer-a.json` whose

8. Cover the PowerShell precheck twin the same way as item 4, by driving the

9. `bash plugins/sdd-quality-loop/scripts/check-workflow-state.sh` and the

10. The next retrospective reads the secondary coverage metric by counting

## Rollback-Plan

Revert the commit whose message contains `WFI-030`. That restores plain equality
in both `check-workflow-state` twins, removes the Done When scan from both
`task-review-precheck` twins, and restores the review gate role definition's
prose.

Any traceability matrix whose delivery-status cells were advanced while the
change was in force would fail the restored equality check on the next
validator run. Remediation is mechanical and local: reset those cells to the
