## Problem Evidence

`epic-192-a4-facet-manifest` needed eleven quality-gate cycles across five
tasks. Every instrument that counts cycles reported five, and one reported a
perfect first-pass rate.

The gate writes one file per task at a fixed path,
`reports/quality-gate/<feature>/T-NNN.md`, and records re-gate cycles *inside*
it as enumerated lines carrying distinct Run IDs:

```
- Cycle 1 — RUN-epic-192-a4-facet-manifest-qg-T-001-seq0754: NEEDS_WORK
- Cycle 2 — RUN-epic-192-a4-facet-manifest-qg-T-001-seq0755: all cycle-1 …
- Cycle 3 — RUN-epic-192-a4-facet-manifest-qg-T-001-seq0756: all cycle-2 …
```

| Task | Cycles enumerated in-file | Counted |
|---|---|---|
| T-001 | 3 | 1 |
| T-002 | 1 (first pass) | 1 |
| T-003 | 3 | 1 |
| T-004 | 2 | 1 |
| T-005 | 2 | 1 |

Three consumers read this the same wrong way:

1. **The retrospective.** Artifact rule 3 requires a file to carry exactly one
   `Task:` and one non-empty `Run ID`, then counts files. Eleven cycles → five.
2. **`emit-run-record.sh`.** Its emitted record for this feature says
   `"first_pass_gate": {"passed_first_try": 5, "total": 5}` and
   `"gate_reports": {"max_runs_single_task": 1}`. The actual first-pass rate was
   1 in 5. This number is generated by a script the retrospective skill
   explicitly forbids the agent to compute or edit, which is what makes it
   evidence rather than opinion.
3. **`ship`'s cycle limit.** `ship`'s Step 4 documents its three-cycle cap as
   disk-based and "survives re-invocation across sessions", computed by
   `check-quality-gate-cycle-limit.{sh,ps1}` counting this task's gate report
   files. A task on its third cycle still counts one file, so `Escalate-Human`
   cannot fire. The safety valve for a task that will not converge is
   unreachable by construction.

This is the second independent way the same metric has lost signal. The
previous three retrospectives each recorded "QG reports retained under rule 3:
0 of N", because reports carried `Task ID:` where the rule reads `Task:`.

## Root Cause Hypothesis

The gate's storage model and its measurement model disagree about what a "run"
is. The gate treats a task's report as a **living document** — one file per
task, appended to on each cycle. Every consumer treats a report as an
**immutable record of one run** — one file per run, counted by existence.

Nothing enforces either reading, so both are locally reasonable and the
disagreement is silent. No cycle is lost from the evidence: the Run IDs are all
there, in the file, in order. They are simply below the resolution of every
query anyone runs against them, and a query that returns "5 runs, all passed
first try" is indistinguishable from a healthy feature.

The `Task ID:`/`Task:` defect is the same root cause in a different place: an
identity the writer records one way and the reader looks up another way, with
no test binding them.

## Proposed Change

| Target File | Change Description |
|---|---|
| `plugins/sdd-quality-loop/scripts/check-quality-gate-cycle-limit.{sh,ps1}` | Count enumerated `- Cycle <n> — RUN-…` entries within the task's report in addition to counting report files, and take the greater. This is the change that restores the Escalate-Human stop, and it is the one worth landing first even if the rest is deferred. |
| `plugins/sdd-quality-loop/skills/workflow-retrospective/SKILL.md` | Amend artifact rule 3 so a retained report contributes one Quality-Gate Run per distinct Run ID it records, not one per file. De-duplicate on `(task ID, Run ID)` exactly as today — the key is unchanged, only its scope moves from file to entry. |
| `plugins/sdd-quality-loop/skills/quality-gate/SKILL.md` | State the storage contract explicitly: one report file per task, each cycle appended as an enumerated entry with its own Run ID. Whichever model is chosen, the point is that it be written down; consumers currently infer it. |
| `plugins/sdd-quality-loop/scripts/emit-run-record.{sh,ps1}` | Derive `first_pass_gate` and `max_runs_single_task` from enumerated cycles rather than file count. |

## Expected Effect

Cycle counts stop being systematically understated, so the retrospective's
friction detection sees rework it currently cannot, and `Escalate-Human`
becomes reachable for a task that has burned its three cycles.

The second effect matters more than the first. A cap that cannot fire is worse
than no cap, because the workflow documents a protection it does not provide.

## Verification Metric

Target-Metric: ratio of counted Quality-Gate Runs to enumerated re-gate cycles, per feature
Expected-Direction: increase toward 1:1
Horizon: the next completed feature with at least one task requiring more than one gate cycle
Baseline: 5 counted / 11 enumerated (`epic-192-a4-facet-manifest`, 2026-08-19)
Target: 1:1 — every cycle with a distinct Run ID counted exactly once

Secondary (deterministic): a fixture task whose report records three cycles
makes `check-quality-gate-cycle-limit` exit non-zero with `Escalate-Human`,
and the same fixture at two cycles exits 0 with `continue`.

## Verification Plan

Both halves must hold, and the second is the one that decides this WFI:

1. **The counts change.** The next qualifying feature's retrospective reports a
   Quality-Gate Runs total equal to its enumerated cycle total, and its run
   record's `first_pass_gate` matches the number of tasks that actually passed
   on cycle 1.

2. **Detection is real, not arithmetic.** A synthetic report recording three
   cycles for one task is presented to `check-quality-gate-cycle-limit`, which
   must return `Escalate-Human`; a two-cycle report must return `continue`.
   Run both as mutation tests — invert the counting logic and confirm the
   fixtures fail. A change that only makes the retrospective's table prettier,
   while the cycle cap still cannot fire, is **Rejected**, because the table was
   never the reason to fix this.

## Rollback-Plan

Revert the commit whose message contains `WFI-031`. The change is confined to
counting logic in two scripts and the prose of two skill files; no report
format, evidence path, or gate verdict changes, so reverting restores the prior
counts exactly. Reports written while it was applied stay readable under either
rule, because neither the file layout nor the Run IDs change.
