## Problem Evidence

Thirteen review tickets across two periods, none of them ever closed.

`epic-192-a4-facet-manifest` produced six — RT-20260817-001 through -006. All
five tasks reached `Done`, PR #301 merged on 2026-08-18, and as of
2026-08-19 all six tickets still read `status: open`. Five of the six carry
`auto_fix_allowed: true`, so they are not blocked on human judgment. One,
RT-20260817-004, is a Major describing a cross-cutting `UnicodeDecodeError`
across three validators.

The previous period was the same shape: 7 tickets, auto-fix rate 0 %.

| Period | Tickets | `auto_fix_allowed: true` | `status: resolved` |
|---|---|---|---|
| pillar-a wave (2026-08-10 – 08-14) | 7 | 0 | 0 |
| epic-192 (2026-08-16 – 08-18) | 6 | 5 | 0 |

The Improvement Loop names "auto-fix rate drops below 50 % for a ticket type"
as a friction trigger. It has been 0 % for every ticket type in both periods,
which is why this is a recurring pattern and not one feature's loose ends.

## Root Cause Hypothesis

Nothing in the workflow owns closing a ticket.

`quality-gate` creates tickets and can then return PASS — a ticket is not a
blocker unless it is Critical or Major *and* the gate says so. `ship`'s Step 4
routes the human to `fix-by-review-ticket` only on BLOCKED. So a task that
passes with minor findings emits tickets and moves on, and `ship`'s Step 5
completion check counts tasks Done, never tickets open.

The result is a queue with a producer and no consumer. That is not a discipline
failure by whoever ran these features — the loop as written has no step at
which an open ticket on a passing task is anyone's responsibility, and the
`auto_fix_allowed: true` flag has no reader.

## Proposed Change

| Target File | Change Description |
|---|---|
| `plugins/sdd-ship/skills/ship/SKILL.md` | Extend the Step 5 completion check: before printing the summary, enumerate tickets for the feature that are still `status: open`. Print them with severity and `auto_fix_allowed`, and state the disposition of each — resolved, or deferred with a reason. The feature is not reported complete while an open ticket has no recorded disposition. |
| `plugins/sdd-quality-loop/skills/quality-gate/SKILL.md` | On a PASS that emits tickets, say in the report that the tickets remain the feature's responsibility and name the completion check as where they are settled — so the gate's own PASS does not read as closing them. |
| `plugins/sdd-quality-loop/skills/workflow-retrospective/SKILL.md` | Add open-tickets-at-completion to the metrics roll-up, so the count is visible in the period it happens rather than only when someone reads the ticket directory later. |

Deliberately **not** proposed: auto-running `fix-by-review-ticket` on every
`auto_fix_allowed: true` ticket. That would trade an unclosed queue for
unreviewed edits, and `fix-by-review-ticket` is one of the six user-invocable
commands precisely because a human is meant to start it. The gap is that
nobody is *told* the queue exists, not that nobody may drain it.

## Expected Effect

Open tickets become visible at the moment a feature is declared complete, when
the context to act on them still exists, instead of surfacing in a retrospective
days later or not at all. Deferral stays available — it just has to be said out
loud and attached to a reason.

## Verification Metric

Target-Metric: count of review tickets still `status: open`, with no recorded disposition, at the moment a feature's last task reaches Done
Expected-Direction: decrease
Horizon: the next 2 completed features that emit at least one review ticket
Baseline: 6 of 6 (`epic-192-a4-facet-manifest`, 2026-08-19); 7 of 7 (pillar-a wave, 2026-08-14)
Target: 0 tickets without a disposition — every ticket either `resolved` or explicitly deferred with a reason

## Verification Plan

1. **The disposition appears.** Each of the next two qualifying features ends
   with a completion summary that lists every open ticket and its disposition,
   and the following retrospective reports the open-without-disposition count.

2. **It is a check, not a printout.** Present the completion check with a
   feature carrying one unresolved, undeferred ticket; it must refuse to report
   the feature complete. A version that lists tickets and then prints
   "Feature complete" anyway has added a paragraph, not a gate, and this WFI is
   then **Rejected**.

A caution for whoever scores this: the metric is satisfiable by writing
"deferred: low priority" on everything. If the next two features close at 0 by
deferring every ticket, that is not the target met — read the dispositions
before classifying. The point is that someone decided, not that a field was
filled.

## Rollback-Plan

Revert the commit whose message contains `WFI-032`. All three changes are
instruction text in skill files; no script, schema, ticket field, or gate
verdict is touched, so reverting restores the prior completion-check behaviour
exactly and leaves any dispositions already recorded harmlessly in place.
