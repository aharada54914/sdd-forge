## Problem Evidence

epic-196-a8-integration T-001 could not be implemented at all, because
two of its own approved documents contradicted each other on the tree
they were approved against:

| Document | Clause | Demands |
|---|---|---|
| `design.md` — SKIP Allowlist Activation Gate | activation predicate | once Epic A1's canonical artifacts exist on `main`, AC-006's `SKIP` becomes a **hard failure** |
| `tasks.md` — T-001 Done When / Out of Scope | TEST-006 | TEST-006 passes only when AC-006 is emitted as a **non-failing `SKIP`**; un-skipping AC-006 is explicitly Out of Scope |

The timing is the point. Epic A1 landed on `main` in PR #229 on
2026-08-08. T-001's own approval is stamped `2026-08-08T16:33:11Z` —
**after** that merge. So the activation condition was already true at the
moment a human approved a task whose contract required it to be false.
Neither document was wrong in isolation; the pair became unsatisfiable
because one of them keys off an external event.

Two implementation attempts, nine days apart (2026-08-09 and
2026-08-18), independently reached the same conclusion and both stopped
without writing code — the correct outcome, but 2 runs' worth of work
spent rediscovering a defect that review should have caught once.

## Root Cause Hypothesis

The activation clause was written as a predicate over **repository
state** ("when these artifacts exist on `main`") rather than over
**workflow position** ("when the task that owns this case starts"). A
predicate over repository state can flip at any moment, including
between the drafting of a task plan and its approval, and including
between approval and implementation. Nothing in the review lanes
re-evaluates such a predicate at approval time: spec review reads the
requirements, impl review reads the design, task review reads the task
plan — each in isolation, and each against whatever the tree happened to
look like when that lane ran.

So the defect class is: **an approved artifact whose truth value depends
on another epic's merge state, with no lane responsible for re-checking
it when that state changes.** AC-006 is one instance; the same shape
appears wherever a design says "until Epic X merges" or "once Epic X
lands".

## Proposed Change

| Target File | Change Description |
|---|---|
| AGENTS.md | Add a review-lane instruction: when a spec or design clause conditions behavior on another epic's merge state, the reviewing lane must evaluate that condition against the tree at review time and confirm it does not already contradict the task plan being approved. Record the evaluation in the review verdict. |
| specs/ design template | Add guidance that a gate/activation clause should be keyed to workflow position (the owning task's start) rather than to repository state, and that when repository state genuinely is the right trigger, the clause must name which task owns acting on it. |
| specs/ task template | Add a Done-When authoring note: if a task's Done When requires a case to stay in a given state, and a design clause can flip that state from outside the task, the task plan must name the design clause it depends on so the contradiction is visible at task-review time. |

## Expected Effect

Contradictions of this class are caught during review rather than during
implementation. The measurable consequence is that implementation runs
stop being spent on rediscovery: currently 2 of 2 attempts at
epic-196 T-001 produced no code and only a blocker note.

## Verification Plan

The next feature whose design carries a cross-epic activation or
"until Epic X merges" clause is the test case. Confirm both halves:

1. **The lane evaluates it**: that feature's impl-review or task-review
   verdict explicitly records the cross-epic condition's value at review
   time, and states whether it contradicts the task plan.
2. **Detection is real, not ceremonial**: a deliberately contradictory
   pair — a design clause that activates on a condition already true,
   plus a task Done When requiring it inactive — is presented to the
   lane in a scratch copy and must be rejected. A lane that records the
   condition but passes such a pair has added paperwork, not detection,
   and this WFI must then be classified Rejected.
