## Problem Evidence

The 2026-06-24 retrospective for `claude-workflow-compatibility` records two
high-risk evidence-consistency corrections: T-002 used two quality-verification
cycles and resolved major ticket RT-20260623-001 to map REQ-009 to AC-009, while

## Root Cause Hypothesis

For `claude-workflow-compatibility` T-002 and T-006, the task contracts required
tests and evidence but did not require a pre-implementation checklist that links
every persisted verdict field and traceability claim to a negative mismatch test.
That allowed cross-artifact consistency gaps to be discovered during review rather
than before implementation.

### Regressed — 2026-07-30 (epic-136-phase4-mcp retention check)

The registered condition's second clause ("an evidence fix in quality-gate cycle
2 or later on a high-risk task") recurred once.

T-001 (`Risk: high`) returned NEEDS_WORK on its first gate round. The cause was a
persisted-evidence defect, not an implementation defect: the review-context
manifest for sequence 0382 was rewritten by a second, redundant run of the
reservation step, so its `previous_record_sha256` pointed at an already-advanced
identity-ledger tip and `validate-review-context-set.sh` could no longer replay
it. The cycle-2 remedy was therefore an evidence fix — reserve sequence 0387
exactly once, confirm the chain tip equals record 0386, relaunch — which returned
PASS.

Two independent detectors caught it (T-001's own evaluator and, separately, the
T-003 evaluator as its QG-004), so the gate functioned; the cost was one wasted
high-risk gate cycle. The first clause (a persisted-evidence/traceability fix
*ticket*) did not recur — no review ticket was created in this feature at all.

Distinct from the WFI-003/005/010 regressions of the same period: those are
report-artifact parseability, this is reservation-step non-idempotency. Recorded
as FP-03 of `reports/retrospective/2026-07-29T235934Z-epic-136-phase4-mcp.md`.
