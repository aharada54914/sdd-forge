## Problem Evidence

A human-approved amendment to a frozen document stales the stage that pinned
it, so that stage must be re-reviewed. Each stage's re-review records the
amendment in `specs/<feature>/investigation.md`. But three prechecks demand
that the **predecessor** stage's already-sealed contract pin
`investigation.md` at its **current** hash:

- `plugins/sdd-review-loop/scripts/impl-review-precheck.sh:241-243`
- `plugins/sdd-review-loop/scripts/task-review-precheck.sh:210-213`
- `plugins/sdd-review-loop/scripts/spec-review-precheck.sh:249`
  (and its twin `spec-review-precheck.ps1:357`)

A contract is immutable committed evidence. So appending to `investigation.md`
at stage N instantly invalidates stage N-1, whose contract can never be
rewritten to match. `--provenance-rereview` downgrades only the
`check-workflow-state.sh` call to advisory; it does not relax any of the three.

Measured on four features in one session (2026-08-24):

| Feature | Stage that refused | Diagnostic |
|---|---|---|
| epic-194-a6-lite-integration | impl (round-opening) | `persisted spec contract reviewer manifest is missing investigation evidence` |
| epic-195-a7-compatibility | task (round-opening) | `persisted spec contract reviewer manifest is missing investigation evidence` |
| epic-195-a7-compatibility | spec (`--reset`) | `previous terminal contract is invalid` |
| epic-196-a8-integration | impl + task | same class, predicted by measurement before the run |

epic-195 is the sharpest case because every escape route was probed and each
is closed by a different rule: attempt 5 without `--reset` fails `a new attempt
requires --reset`; attempt 4 round 3 with `--edit-summary` fails `requirements.md
must declare Spec-Review-Status: Pending` (and round 2 was PASS, not
NEEDS_WORK); attempt 6 with `--reset` fails `previous attempt is required
before reset`.

The `spec-review-precheck.sh:249` instance is a plain defect rather than a
policy consequence. Inside the same `validate_contract` function, every other
expected-manifest entry is derived from immutable sources — `calibration_hash`
is read out of the contract itself via `jq` over
`.reviewers[].allowed_input_manifest[]`, with a cross-check against the
precheck file. Only `investigation.md` is hashed from the live working tree:

```bash
--arg investigation_hash "$(sha256 "${spec_dir}/investigation.md")"
```

So a sealed artifact is validated against mutable state. Both twins share it,
which removes the platform-substitution escape.

## Root Cause Hypothesis

`investigation.md` is treated as a stable per-stage input, like
`requirements.md` or `acceptance-tests.md`. It is not. By design it is the one
document that **accumulates the amendment record across stages** — that is what
the Amendment Re-Review Context lane (`726240f9`) exists for. A file whose
purpose is to grow between seal and validation cannot be pinned by exact
equality at validation time without making the sequence non-convergent.

The related asymmetry in `plugins/sdd-quality-loop/scripts/check-workflow-state.sh`
supports the same reading: lines 467-469 exempt
`requirements`/`design`/`tasks`/`traceability`/`acceptance-tests` from
live-hash comparison and omit `investigation.md`, which then falls to the
generic branch at 477-478.

Two secondary findings, recorded so the fix is not mistaken for a loosening:

1. `impl-review-precheck.sh:488-499` requires every unique `AC-[0-9]{3}` in
   `requirements.md` to be a literal substring of `design.md`. The check is
   sound for design-scoped criteria and was built on real evidence
   (epic-136-phase4-docs spent two reviewer rounds finding AC-013 then AC-012
   missing, one per round). It is unsatisfiable for criteria the requirements
   themselves scope as meta-criteria about the spec package's own registration
   commit — epic-194's AC-024 requires both status headers to read `Pending`
   "at commit time", which no design document can name and which is now
   historically false.
2. The same block's operator-facing diagnostic asserts "Each one is testable
   and traceable in requirements.md". No testability or traceability attribute
   is consulted anywhere in that script. The header comment above it is
   accurate; the diagnostic overclaims.

## Second Problem: the evidence bar and the tolerance are structurally opposed

Measured on epic-196 (2026-08-25), after the tolerance of `66a22b5a` was in place
and still failing to fire:

```
$ git diff --numstat 61d7823a HEAD -- specs/epic-196-a8-integration/investigation.md
195	3	specs/epic-196-a8-integration/investigation.md
```

The three deletions were a `tasks.md` fingerprint being **replaced in place** —
the recorded hash, its last-amended commit, and the previous-value line. The
replacement was factually correct, because `tasks.md` had genuinely moved.

That is the collision. The Amendment Re-Review Context's evidence bar
(`reviewer-calibration.md:139-149`) requires a per-document SHA-256, and updating
a fingerprint is inherently an in-place edit. The growth tolerance absorbs only
append. **Every package whose already-fingerprinted document changes a second
time hits this**, and nothing warns the author at the time of the amendment.

Two further facts, both measured rather than reasoned:

1. **Deletion-free is not sufficient.** `investigation_growth_only_change`
   requires the pinned section to be an exact *prefix* of the live section, so an
   entry spliced mid-section fails it even at zero deletions. epic-196's first
   two entries were inserted above a pre-existing closing bullet; the delta had
   to become a pure *tail* append, not merely deletion-free, before the tolerance
   fired. Final shape: 272 insertions, 0 deletions, tolerance fires on all three
   stage pins.
2. **The workable form already existed in a sibling package.** epic-194's record
   carries each commit with its own fingerprint block, "each retaining the
   superseded fingerprint alongside". Under that form the record grows and never
   rewrites. It was precedent, not invention — but nothing in the calibration
   states it, so epic-196 reached the opposite form and deadlocked.

## Third Problem: one of three call sites was fixed

`a3aa8157` corrected `spec-review-precheck.{sh,ps1}`. The identical three lines
survive in two more scripts and both their twins:

- `impl-review-precheck.sh:241-243` and `impl-review-precheck.ps1:177-181`
- `task-review-precheck.sh:212-214` and `task-review-precheck.ps1:189-193`

Confirmed by count: `grep -c 'investigation_growth_only_change\|amendment_section_bounds\|growth'`
returns 1 for `spec-review-precheck.sh` and 0 for the other two. `require_persisted_pass`
runs unconditionally, so `--provenance-rereview` grants no exemption, and the only
alternative route is a spec `--reset` — which flips a passed document to `Pending`
and costs a six-reviewer cascade.

## Proposed Change

1. In `spec-review-precheck.{sh,ps1}`, derive `investigation_hash` from the
   contract under validation, the way `calibration_hash` already is —
   preserving the "unique, exactly one value" discipline and the precheck
   cross-check. Do not drop the entry: that would stop validating it at all.
2. Decide `investigation.md`'s status once, in one place, and apply it to all
   four call sites. Either it is a stage-pinned input (in which case the
   amendment record must live somewhere else) or it is a growth-tolerated
   cross-stage record (in which case `impl-review-precheck.sh:241-243` and
   `task-review-precheck.sh:210-213` need the same append-only tolerance that
   `check-workflow-state.sh` gained in `66a22b5a`). The present state — pinned
   by three prechecks and tolerated by the walker — is the contradiction.
3. State the append-only fingerprint form in
   `plugins/sdd-review-loop/references/reviewer-calibration.md` so an author
   reaches it by default: supersede a fingerprint by appending a new block that
   names what it supersedes, never by rewriting the old one, and append at the
   section tail rather than mid-section. Both constraints come from
   `investigation_growth_only_change`'s prefix predicate, which no document
   currently explains.
4. Apply `a3aa8157`'s contract-derived pin to `impl-review-precheck.{sh,ps1}` and
   `task-review-precheck.{sh,ps1}`, which still hash `investigation.md` live.
5. Give the AC-coverage gate a narrow exception keyed on a property legible in
   `requirements.md` itself (criteria the document scopes as registration or
   process rather than behaviour), never on a hardcoded id list and never by
   accepting a citation anywhere in the package. Correct the diagnostic wording
   to state what is actually checked.

## Expected Effect

A feature whose frozen documents are amended under human approval can re-run
spec → impl → task to completion in one pass. Today that sequence terminates
at the first stage whose predecessor's contract was sealed before the
amendment record was written, and no in-band route reopens it.

## Verification Plan

1. Regression test for the sealed-contract defect that models the real shape:
   a sealed contract plus a **subsequently grown** `investigation.md`, asserting
   `--reset` is accepted. Prove non-vacuity by reverting the changed predicate
   and showing the test fails.
2. Regression test for the AC-gate exception that asserts **both** directions —
   the excepted class passes, and a genuine design-scoped AC missing from
   `design.md` still fails. A one-sided test would admit a blanket loosening.
3. Re-run the four features above end to end and record which stages open.
4. sh/ps1 parity is mandatory and must be demonstrated per fix, not asserted.
   This repository has repeatedly shipped sh-only fixes whose PowerShell twin
   silently diverged.

## Rollback-Plan

Each change is a self-contained commit touching only `plugins/**` and `tests/**`.
Reverting any one restores the prior refusal without touching feature state:
no `specs/**` bytes move, so no contract hash changes and no stage's provenance
is affected by the rollback itself.

## Result

Result: Partially implemented on `claude/plugins-pin-stability`, 2026-08-24.

**Proposed change 1 — implemented, `a3aa8157`.** `investigation_hash` is now
derived from the contract under validation in both twins, mirroring
`calibration_hash`: a unique-select over `.reviewers[].allowed_input_manifest[]`
that omits on zero, uses on one, and fails closed on more than one. No
cross-check against `precheck-result.json` was added because that schema records
no `investigation_sha256` field, unlike `calibration_sha256` — reported rather
than invented. Regression tests in `tests/spec-review-loop.tests.sh` and
`tests/downstream-review-precheck.tests.ps1` model the real shape (sealed
contract, then a grown `investigation.md`, `--reset` accepted) and each fix was
mutation-proven in both twins.

**Proposed change 2 — the `check-workflow-state.sh` half is REJECTED on
investigation.** The five-file `continue` at `check-workflow-state.sh:908` is
not "skip validation": those five are re-checked later against
lifecycle-normalized hashes at `:1099-1125` and `:1197-1254`. `investigation.md`
has no such dedicated later check, so adding it to that list would drop the file
entirely — the existence check included — and would make `66a22b5a`'s growth
tolerance at `:925-935` dead code. That tolerance already covers the legitimate
case, and covers it far more narrowly: pinned bytes re-resolved at the
introducing commit, verified, then only pure contiguous growth inside
`## Amendment Re-Review Context`. The prechecks were the defect; the walker was
not.

**Proposed change 3 — implemented, `64915ecf`.** A structural key exists and was
used: surveying every AC table row under `specs/` plus both epic worktrees, the
requirement-trace cell is strictly bimodal — a `REQ-NNN` trace or `Global`, in
two spellings (`| AC-023 | Global |`, `| AC-035 (Global) | — |`), with no third
form. `ac_scoped_global` reads only the criterion's own defining row. It is not
an id list and does not accept a citation elsewhere in the package, so the
epic-136 class stays caught: a gap-closer AC added under a `REQ-*` heading
carries a REQ trace and is still demanded. Excused ids are named on stderr
regardless of outcome, so an exercised exception is never silent. The diagnostic
now states only what is checked. Non-vacuity was proven three ways, including a
blanket-loosening mutation that the test correctly refuses.

Notably `AC-033` on epic-193 is **not** excused: `requirements.md` traces it to
`REQ-008`, so the requirements document itself scopes it inside a real
requirement. Rescoping it would be a visible edit to `requirements.md`, which is
where that argument belongs.

**New finding, filed rather than fixed.** `impl-review-precheck.ps1` has no
AC-coverage gate at all — `AC-` does not appear anywhere in its 352 lines. This
is a pre-existing sh/ps1 divergence, not one introduced here, and porting the
gate would be new behaviour rather than parity repair. It belongs in its own
change.
