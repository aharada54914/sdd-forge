## Problem Evidence

Observed 2026-08-17 while running the SDD workflow end to end for feature
`sdd-domain-concept-contract` (branch `claude/adversarial-review-plan-dhzsr1`).
Three independent defects in `impl-review-loop`'s instructions and role files,
each discovered only after the affected gate had already reported PASS.

### Defect 1 — the impl reviewer input contract omits an input the downstream gate requires

`plugins/sdd-review-loop/skills/impl-review-loop/SKILL.md` STEP 2 and STEP 4
enumerate the reviewer allowed-input manifest as the precheck result plus
`reviewer-calibration.md`, and STEP 5 adds, for full-profile features, the four
layer specs. `investigation.md` is named nowhere in the file.

`plugins/sdd-review-loop/scripts/task-review-precheck.sh:212-214` requires it:

```
if [[ -f "${repo_root}/${investigation_path}" ]]; then
  manifest_has "$role" "$investigation_path" "$(sha256 ...)" ||
    fail "persisted ${stage} contract reviewer manifest is missing investigation evidence"
```

Reproduced: impl-review-loop attempt 1 for `sdd-domain-concept-contract` ran
both reviewers, both returned PASS with zero findings, and the contract was
persisted at
`reports/impl-review/sdd-domain-concept-contract/attempt-1/round-1/impl-review-contract.json`.
The next gate then refused to start:

```
$ bash plugins/sdd-review-loop/scripts/task-review-precheck.sh sdd-domain-concept-contract 1 1
workflow-state: ok
ERROR: task-review-precheck: persisted impl contract reviewer manifest is missing investigation evidence
```

The orchestrator had additionally placed `investigation.md` under the reviewers'
hard denial list, on the reasonable reading that an input the manifest does not
name is an input the reviewer must not read. So the reviewers genuinely did not
see it: the gap cannot be closed by editing the persisted contract, because
that would record an input the reviewers were forbidden to read.

Blast radius: every full-profile feature whose spec directory contains
`investigation.md` — the normal case, since `sdd-bootstrap-interviewer` step 5
treats `investigation.md` as a first-class Phase 1 input and carries its INV-xxx
IDs into requirements and traceability. An impl-review run that follows the
SKILL.md exactly produces evidence the task stage rejects.

### Defect 2 — `--reset` is unreachable once Phase 2 artifacts exist

SKILL.md STEP 7 step 4 instructs: "Change `Impl-Review-Status:` in design.md
header to `Pending`." `plugins/sdd-quality-loop/scripts/check-workflow-state.sh:779`
rejects exactly that state once `tasks.md` exists:

```
$ bash plugins/sdd-review-loop/scripts/impl-review-precheck.sh sdd-domain-concept-contract 2 1
workflow-state: sdd-domain-concept-contract: task-lifecycle: tasks.md requires Spec and Impl Passed
ERROR: impl-review-precheck: canonical workflow-state validation failed
```

So the documented `--reset` path is a dead end for any feature that has reached
task decomposition — which is precisely when a re-review is most likely to be
needed, because that is when the downstream gate surfaces an upstream evidence
defect (defect 1 above is the worked example).

The capability exists but the instructions do not reach it.
`impl-review-precheck.sh` accepts `--provenance-rereview` (7 occurrences), and
`task-review-loop`'s SKILL.md documents the corresponding discipline in full
under "Post-Implementation Provenance Re-Review", including the exact rule that
resolves this: "Do NOT clear `Task-Review-Status:` from tasks.md — it stays
`Passed`. (Setting it to `Pending` would violate the validator's pending-review
lifecycle rule once tasks carry approved/advanced states.)"

`impl-review-loop`'s SKILL.md has no equivalent section and never mentions the
flag. An operator following it either halts, or discovers the flag by reading
the script.

### Defect 3 — `legacy_design` relief is granted to reviewer A only

`precheck-result.json` sets `legacy_design: true` for this feature.
`plugins/sdd-review-loop/agents/impl-reviewer-a.md` carries a
"Legacy Design Mode" section instructing that any check whose required
template field is absent becomes a `[LEGACY COMPAT]` Minor advisory rather
than a Major/Critical finding.
`plugins/sdd-review-loop/agents/impl-reviewer-b.md` has no such section and
never mentions `legacy_design`, although its own checks are equally
template-field-keyed (`DEPLOYMENT-CONCRETE` requires a
`## Deployment / CI Plan` section; `MIGRATION-PLANNED` and
`NO-REQ-CONTRADICTION` key off `## Data Plan` and `## Constraint Compliance`).

Observed in the attempt 2 run: reviewer A recorded absent `## Data Plan` and
absent `## API / Contract Plan` as PASS-with-Minor-advisory. Reviewer B
recorded absent `## Deployment / CI Plan` as a Major FAIL. Both are the same
class of fact about the same legacy document, judged under the same
`legacy_design: true` flag, and they receive opposite treatment purely because
one role file was updated for legacy mode and its sibling was not.

Related, and worth recording alongside it: attempt 1's reviewer B returned
PASS on design.md content byte-identical to attempt 2's (modulo the
`Impl-Review-Status:` header line); attempt 2's reviewer B returned BLOCKED.
Two of its three findings are TYPE-H. `task-review-loop`'s SKILL.md carries a
"TYPE-H convergence rule" for exactly this fresh-instance variance during a
provenance re-review; `impl-review-loop`'s SKILL.md carries no equivalent, so
the rule was not in force and was not applied. Note that this does not explain
away the run's Critical finding, which is TYPE-D and which the task-stage rule
would leave untouched: that one is a genuine gap in design.md.

Evidence path:
`reports/impl-review/sdd-domain-concept-contract/attempt-2/round-1/design-round-1-proposed-changes.md`.

### Consequence observed in this run

Recovering from defect 1 required attempting `--reset`, which hit defect 2,
which was resolved only by reading the script for an undocumented flag. Toggling
`Impl-Review-Status` `Passed` → `Pending` → `Passed` along the way changed
design.md's SHA-256 from `28bb9247…` to `28bd5415…` with no semantic change to
the document, so attempt 1's evidence and attempt 2's precheck bind different
bytes of the same content. That is inside the provenance re-review's stated
purpose ("re-binds review evidence to the current artifact hashes"), but the
hash churn was caused by following STEP 7 rather than by any content decision.

## Root Cause Hypothesis

The impl stage's input contract was specified from the reviewer's point of view
("what does this reviewer need to read?") while the task stage's validator was
specified from the provenance point of view ("what must the persisted evidence
prove was bound?"). Nobody reconciled the two lists. `investigation.md` is
optional to reviewing a design and mandatory to trusting the record, so it fell
into the gap.

Defect 2 has the same shape one level up: `task-review-loop` learned the
lifecycle constraint the hard way and documented it; that lesson was never
back-propagated to `impl-review-loop`, even though the script gained the flag.
The two skills are maintained as siblings but their instruction sets drifted.

Both are instruction-side omissions, not logic defects. Every script involved
behaves correctly and fails closed; only the documents that drive them are
incomplete.

## Proposed Change

1. **`impl-review-loop` SKILL.md, STEP 2 and STEP 4** — add `investigation.md`
   to the enumerated reviewer allowed-input manifest, conditioned on the file
   existing, with a note that the task stage's precheck requires it in the
   persisted contract. State that a reviewer may read it as supporting evidence
   and must not treat it as authority over requirements.

2. **`impl-review-loop` SKILL.md, STEP 5** — add `investigation.md` to the
   sentence that currently lists the four layer specs as contract manifest
   requirements for full-profile features.

3. **`impl-review-loop` SKILL.md** — add a "Post-Implementation Provenance
   Re-Review" section mirroring the one already in `task-review-loop`'s
   SKILL.md: start a new attempt at round 1, keep `Impl-Review-Status: Passed`,
   run the precheck with `--provenance-rereview`, invoke both reviewers with the
   complete input set, and require `check-workflow-state.sh` exit 0 afterwards.

4. **`impl-review-loop` SKILL.md, STEP 7** — qualify step 4: clearing the status
   to `Pending` applies only while no `tasks.md` exists for the feature; once it
   does, the provenance re-review path in item 3 is the sanctioned route, and
   the status stays `Passed`.

5. **`plugins/sdd-review-loop/agents/impl-reviewer-b.md`** — add a
   "Legacy Design Mode" section matching impl-reviewer-a's, so that
   `legacy_design: true` produces the same `[LEGACY COMPAT]` Minor advisory
   treatment of absent template fields in both roles. This is a symmetry fix,
   not a relaxation: it changes nothing when `legacy_design` is false, and it
   leaves every substantive (non-template-field) finding at its declared
   severity.

6. **`impl-review-loop` SKILL.md** — as part of the new provenance re-review
   section (item 3), state whether the TYPE-H convergence rule that
   `task-review-loop`'s SKILL.md applies also applies at the impl stage. The
   two stages should not differ silently. If it does apply, copy the rule
   verbatim including its TYPE-D carve-out; if it deliberately does not, say
   so and say why, so an orchestrator does not have to infer the answer from
   the other skill's text.

No script changes are proposed. `task-review-precheck.sh` and
`check-workflow-state.sh` are already correct and already fail closed;
`impl-review-precheck.sh` already implements the flag.

## Expected Effect

An impl-review run that follows the SKILL.md verbatim produces a contract the
task stage accepts on the first attempt, and an operator who needs to re-run
impl-review after Phase 2 has a documented path that does not require reading
the script.
