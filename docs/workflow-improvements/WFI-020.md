## Problem Evidence

Source: `reports/retrospective/2026-07-29T235934Z-epic-136-phase4-mcp.md`, friction
pattern FP-01, and the retention check in the same report.

Three deterministic consumers could not associate a quality-gate report with its
task in feature `epic-136-phase4-mcp`, because the reports carry their identity
in prose, a title, or a `- ` list item rather than in the bare line each consumer
greps for:

1. **`check-evidence-bundle.sh:201,228`** rejected all 5 evidence bundles —
   `quality_report missing Task ID: T-001` and
   `quality_report must contain exactly one Feature line`. The Done transition
   was blocked until commit `7b7faa23` retrofitted the two header lines into 4 of
   the 5 reports. One of those reports additionally carried a second line
   beginning `Feature: ` inside its own `## Target` section, which broke the
   "exactly one" rule and needed a formatting change on top.
2. **`emit-run-record.sh:129`** associates a gate report to a task with
   `grep -q "Task: ${tid}\b"`. Only T-004's report carries that line — its
   evaluator wrote it unprompted — so
   `reports/runs/RUN-20260729T235825Z-epic-136-phase4-mcp.json` records
   `gate_reports.total: 1` and `first_pass_gate.passed_first_try: 1` against a
   manual tally of 5 gate reports over 5 tasks. Compounding detail: file
   *selection* at `:125` succeeded only because retrofit (1) had already added
   `Feature:` lines for an unrelated consumer; without it the count would have
   been 0.
3. **workflow-retrospective artifact rule 3** requires "exactly one
   `Task: T-NNN` identity and one non-empty `Run ID`". 4 of the 5 reports fail
   it, so the retrospective retained 1 of 5 quality-gate runs and had to record
   `Data Completeness: Partial` with a Data Exclusions table.

Retention conditions this recurrence tripped, all three now `Status: Regressed`:

- **WFI-005** — "an implementation/gate report needed a retroactive format fix to
  be accepted by a deterministic consumer". Two instances: `7b7faa23` above, and
  `9e82fa5b` for the `## Outputs` hash table.
- **WFI-010** — "`gate_reports.total` disagrees with the retrospective's manual
  tally". 1 vs 5.
- **WFI-003** — "an N/A cell caused by a missing Run ID / Task Attempt Count".
  3 of 5 implementation reports carry no `Task Attempt Count`.

Scope boundary against existing work, checked before drafting: **WFI-017**
(`Status: Applied`, branch `wfi/017-impl-report-validator-outputs`) already covers
the *implementation report* side of WFI-005 by aligning
`validate-implementation-report.sh` with the `## Outputs` template contract. This
WFI deliberately does not restate that. What no existing WFI covers is the
**quality-gate report**: it has no template, no authoring-time validator, and no
stated machine-readable identity contract at all, which is why four independently
authored reports each satisfied a human reader and failed three scripts.

## Root Cause Hypothesis

**Correction applied after Cycle 1.** An earlier draft of this section claimed
the parsing contract "was never written down". That is false, and the audit
caught it. `AGENTS.md` § Rules → "Evidence report identity fields" already
states: "Quality verification gate reports (`reports/quality-gate/`) must carry a
`Task: T-NNN` line and a `Run ID:` line whose value equals the evaluator run id
reserved in the identity ledger for that gate run." That rule was added by
WFI-003 and predates this feature. It is exactly the line `emit-run-record.sh:129`
greps for, and this period's retention check records WFI-003 as `Status: Regressed`
precisely because 4 of 5 gate reports violated it. Claiming no specification
existed would have laundered a compliance failure into a documentation gap.

The gap is therefore **two distinct problems**, not one:

**(1) A visibility gap, for the fields WFI-003 already specifies (`Task:`,
`Run ID:`).** The rule exists in `AGENTS.md`, but the quality verification gate skill's own
authoring step — which is what the evaluator actually follows while writing —
never cross-references it, and instead tells the author the report is
"freely-authored (no separate template file exists for this report)". A rule that
lives only in a file the authoring agent is not reading at write time is,
operationally, invisible: four independently launched evaluators each produced a
report that a human reads correctly and `emit-run-record.sh` cannot associate.
That is a real specification defect — the instruction and the constraint are in
different documents and neither points at the other — but it is a defect of
*placement*, and the underlying obligation was already on the books.

**(2) A genuine absence, for `Task ID:`, `Feature:`, `VERDICT:`, and
`Critical:`/`Major:`/`Minor:`.** No rule anywhere in the repository requires
these, yet `check-evidence-bundle.sh:201,228` hard-fails without the first two,
and `generate-evidence-bundle.sh:249-256` silently records zeros without the
last three. Here the "missing specification" framing is accurate.

**Second correction, after Cycle 2 — and it changes the whole shape of the fix.**
An earlier draft said "the [gate] report has neither a template nor a
validator". That is also false, and it was the Critical finding that BLOCKED this
WFI at attempt 1. `plugins/sdd-quality-loop/templates/quality-report.template.md` **exists**,
and its first three lines are literally `Task ID: {{task_id}}`,
`Feature: {{feature}}`, `VERDICT: {{verdict}}` — precisely the fields this
session spent commit `7b7faa23` retrofitting by hand. It was extended by WFI-005
(`c3a7a16d`) and is still guarded by a passing parity test
(`tests/template-validator-parity.tests.sh`, 10/10 at audit time).

It is **orphaned**: `grep -rl "quality-report.template" plugins/` returns nothing.
No skill and no script points at it. And the quality-gate skill's own authoring
step tells the author the opposite — "no separate template file exists for this
report" — text introduced in `825d6c66` (2026-07-19), *eleven days after* the
template was extended and *seven days after* WFI-005 had already verified 100%
compliance using it (epic-136-phase1-guards, 6/6 reports, 0 retrofits).

The auditor's repository-wide compliance census over 135 gate reports settles
which mechanism actually works:

| Fields | Backed by | Compliance |
|---|---|---|
| `Task ID:` / `Feature:` / `VERDICT:` | the orphaned template | 134/135, 133/135, 134/135 (~99%) |
| `Task:` / `Run ID:` | AGENTS.md prose only | 69/135, 74/135 (~50%) |
| `Critical:` / `Major:` / `Minor:` | nothing | 80/135 |

So the real root cause is **not** "no specification exists". It is that a
working, tested specification was written, proven, and then disconnected — and a
false statement was added telling every future author it was never there. The
~50% column is what an AGENTS.md-only rule achieves in this repository; the ~99%
column is what a template plus a parity test achieves. An earlier draft of this
WFI proposed adding more fields to the ~50% mechanism, which the audit correctly
judged unable to deliver its own Expected Effect.

One further consequence the audit surfaced: `emit-run-record.sh:129` greps
`Task:` while `check-evidence-bundle.sh:201` greps `Task ID:` — two names for one
value, the unreconciled residue of WFI-003 (project-side, chose `Task:`) and
WFI-005 (plugin-side template, chose `Task ID:`) naming the same field
differently on opposite sides of the boundary. Reconciling the two scripts on one
canonical field retires the duplicate line entirely, rather than enshrining it.

## Expected Effect

The `Critical:` / `Major:` / `Minor:` lines are included deliberately even though
no gate currently fails without them: `generate-evidence-bundle.sh:249-256` parses
them and silently defaults each to 0 when absent, which is why all 5 bundles in
this period record `review_verdict.minor: 0` against actual accepted-Minor counts
of 3/3/5/3/2. Adding them removes a silent inaccuracy from the evidence bundle
rather than a build failure, and it is the only part of this change that fixes
something nobody had noticed.

Expected, in the next completed feature:

- zero retrofit commits needed for a gate report to be accepted by
  `check-evidence-bundle`
- `gate_reports.total` in the run record equal to the retrospective's retained
  Quality-Gate Runs total
- `Data Completeness: Complete` rather than `Partial`, with no gate report
  excluded under artifact **rule 3** for a missing association field (an earlier
  draft said rule 5; the retrospective's own Data Exclusions table assigns rule 3
  to all 4 excluded gate reports and rule 5 only to the unrelated absent
  impl-review round-2 contract — corrected after Cycle 1)

## Verification Plan

At the next completed feature's retrospective, before any other analysis:

1. Read `gate_reports.total` from that feature's `reports/runs/RUN-*.json` and
   compare it to the retrospective's own Quality-Gate Runs total. Agreement is
   the target; disagreement in either direction is a miss.
2. Check the retrospective's Data Completeness cell. `Partial` caused by a
   missing `Task:` or `Feature:` line in a gate report means the target was not
   met even if the counts happen to agree.
3. Search that feature's commit range for a commit whose message describes adding
   identity or header lines to a report so a gate would accept it. Any such
   commit is a miss, and is also a fresh WFI-005-class recurrence.
4. Confirm each bundle's `review_verdict.minor` equals the Minor count its own
   gate report records. A residual 0 against a non-zero report count means the
   `Minor:` line rule was not adopted.

**Score over two consecutive features, not one (Cycle-2 revision).** The
mechanism this WFI extends has an oscillating history: WFI-003's original rule
reached compliance once and then regressed; WFI-010's remedy held for three
consecutive features (epic-159-pillar-a/-b/-c) and then regressed again this
period. A single-feature verdict on a mechanism with that record reads noise as
signal in either direction. Wave 8b compounds it — issues #133 and #134 are both
labelled `documentation`, so the sample there is likely small. Record Wave 8b as
a data point; classify only after the second feature.

Do not credit this WFI from a "the run went smoother" impression. If the model
version changed between this baseline and the checkpoint, note it and extend the
horizon rather than classifying — the same caveat this period's retrospective
applied to every comparison row.

## Rollback-Plan

Revert the single commit whose message contains `WFI-020`. Rewritten after
Cycle 2, since the target set changed: the commit now touches `AGENTS.md`,
`plugins/sdd-quality-loop/skills/quality-gate/SKILL.md`,

AGENTS.md and CLAUDE.md" — stale on both counts.)

The revert is still complete and carries no data migration, but it is no longer
free of consequence, and that is worth stating rather than glossing:

- Reverting the template and SKILL.md changes returns future reports to the
  current ~50% compliance regime. Reports already authored under the rule stay
  valid — the header lines are additive and no consumer rejects a report for
  carrying them.
- Reverting the `emit-run-record.sh` / `check-evidence-bundle.sh` field
  reconciliation restores the `Task:` versus `Task ID:` split, so any report
  authored under the reconciled single-field rule would then satisfy only one of
  the two consumers. If the reconciliation is reverted independently of the
  template change, keep both header lines.
- No frozen evidence is touched in either direction, because the rule is
  forward-only by construction.
