## Problem Evidence

Two independent defects, one contradiction and one over-broad predicate, both
in the consent-token path of `sdd-quality-loop`.

### (1) The skill instructs the agent to do what the guard forbids

`plugins/sdd-quality-loop/skills/sdd-sudo/SKILL.md` carries an
`## Implementation` section (line 105) addressed to the agent:

> When `/sdd-sudo` is invoked with a duration:
> 1. **Ensure a signing key exists.** … If `<HOME>/.sdd/sudo-key` does not
>    exist and neither env var is set, create it
> …
> 4. **Write the `SDD_SUDO` file** at the project root with exactly these
>    fields

The same plugin's guard denies exactly that, unconditionally:

`plugins/sdd-quality-loop/scripts/sdd-hook-guard.py:100-103`

> エージェントは SDD_SUDO フラグファイルの作成・編集・削除を行えません。
> sudo モードの管理は人間のみが行えます。
> [EN] agents must not create, edit, or delete the SDD_SUDO flag file. Only a
> human may manage sudo mode.

The guard is right and the Quick Start agrees with it ("Sudo mode is
**human-only**: you type the command yourself; the agent can never enable
it"). It is the `## Implementation` section that is stranded: it is written as
agent instructions for a step no agent is permitted to take.

**Observed 2026-09-02.** The human invoked `/sdd-quality-loop:sdd-sudo 24h` in
session. Following the skill's own `## Implementation`, the agent attempted
the computation and was denied. The token was only issued after the agent
wrote a script and the **human ran it**, which is the Quick Start's model, not
the Implementation section's.

### (2) The shell predicate denies read-only commands

`_shell_targets_sdd_sudo` (`sdd-hook-guard.py:1454-1464`) is documented as
"Return True if shell command targets SDD_SUDO file for write/delete", but it
tests two things about the WHOLE command string and never relates them:

```python
if SDD_SUDO_NAME.lower() not in cmd.lower():
    return False
if SHELL_SUDO_WRITE_RE.search(cmd):
    return True
```

So any command is denied when the name appears ANYWHERE and a write-ish token
appears ANYWHERE ELSE — the write operator is never checked against the
operand. Two read-only commands denied in one session:

- `grep -n "Write the \`SDD_SUDO\` file..." <skill>` — a documentation grep.
  The name is in the search PATTERN; the word `Write` is in the same pattern.
- A `python3` heredoc that computed token fields and wrote NOTHING to the flag
  path. It matched because the env-var names `SDD_SUDO_KEY` and
  `SDD_SUDO_KEY_FILE` contain the flag name as a substring, and the script
  contained unrelated write verbs (`mkdir`, `chmod`, `write_text`) for the
  SIGNING KEY, which lives outside the repo and is not the flag file.

The second case shows a distinct precision bug: `SDD_SUDO_KEY` is a different
identifier that merely shares a prefix, and the guard's own skill documents
both env vars, so the guard denies commands that follow its own documentation.

The identical shape exists in the enforcement-chain rule: reading
`sdd-hook-guard.py` with `awk`/`grep` for a pattern was denied with "エージェ
ントはゲートスクリプト・フック設定・テストファイルを書き換えられません" —
a read reported as an attempted rewrite. Noted here only as the same predicate
shape; the protected-path list itself is a separate, already-recorded item.

## Root Cause Hypothesis

Two terminal causes, one per defect, each reached by its own chain in
`## Why-Why Analysis` below:

- Defect (2) (read-only denials): the shell predicate is a conjunction of two
  independent whole-string searches — flag-name-anywhere AND
  write-token-anywhere — so the write operator is never related to its
  operand, and a word-boundary test is missing, so two documented env-var
  identifiers that merely share the flag name as a prefix satisfy the name
  test (`sdd-hook-guard.py:1454-1464`).
- Defect (1) (skill/guard contradiction): no authoring or review step for
  this skill cross-checks agent-addressed sections against the guard's
  denial rules when either changes, so the Quick Start's "human-only" edit
  and the guard's flag-file denial rule each landed independently while the
  `## Implementation` section kept its agent-addressed imperative steps
  (`SKILL.md:105` vs `SKILL.md:9-11` vs `sdd-hook-guard.py:100-103`).

## Why-Why Analysis

**Chain A — defect (2): read-only commands are denied.**

1. Why did read-only commands get denied? Because the predicate is a
   conjunction of two INDEPENDENT string searches over the whole command, not
   a check of what the write operator acts on. — Evidence:
   `plugins/sdd-quality-loop/scripts/sdd-hook-guard.py:1454-1464` (quoted in
   Problem Evidence; independently reproduced by the cycle-1 audit, whose
   own read-only listing command was denied mid-audit).
2. Why is it written that way? Because a shell command has no parsed operand
   without tokenising, and the guard deliberately fails closed when
   tokenising is hard. — Evidence: the same function's docstring and the
   guard's fail-closed protected-path behaviour recorded in
   `docs/workflow-improvements/WFI-037.md` (the mention-vs-target class).
3. Why does the fail-closed default cost anything here? Because the flag name
   is also a NAME PREFIX of two env vars the plugin itself documents
   (`plugins/sdd-quality-loop/skills/sdd-sudo/SKILL.md:110-114`) and a
   documented literal in the skill text, so legitimate read-only work
   mentions it constantly; fail-closed is correct for ambiguity about a write
   TARGET, not for a command with no write target at all. — Evidence: the
   three denials enumerated in Problem Evidence, observed 2026-09-02 in this
   session.

Terminal cause (Chain A) = Root Cause Hypothesis, first bullet.

**Chain B — defect (1): the skill instructs what the guard forbids.**

1. Why does the skill still instruct the agent to write the flag file?
   Because the `## Implementation` section predates the guard's agent-denial
   rule and was never reconciled: the Quick Start was updated to say
   "human-only", the Implementation section was not. — Evidence:
   `SKILL.md:105` (agent-addressed steps) vs `SKILL.md:9-11` (human-only
   Quick Start) vs `sdd-hook-guard.py:100-103` (unconditional denial).
2. Why does that matter beyond tidiness? Because an agent that follows the
   Implementation section reads as trying to escalate its own privileges, the
   correct behaviour (refuse, hand the human the procedure) currently looks
   like disobeying a skill, and the incorrect behaviour (splitting the
   literal to dodge the substring test) is both easy and available. —
   (hypothesis; consistent with the 2026-09-02 session in Problem Evidence,
   where the token was issued only after the human ran the agent-authored
   script.)
3. Why was the Implementation section never reconciled with the Quick
   Start's human-only language? Because no authoring or review step for
   this skill cross-checks agent-addressed sections against the guard's
   denial rules when either changes — the Quick Start edit and the guard's
   flag-file denial rule (`sdd-hook-guard.py:100-103`) each landed
   independently with no corresponding audit of `## Implementation`. —
   Evidence: `SKILL.md:105` vs `SKILL.md:9-11` vs `sdd-hook-guard.py:100-103`
   (same citations as Level 1); (hypothesis) for the absence of a
   cross-check step.

Terminal cause (Chain B) = Root Cause Hypothesis, second bullet (level 3's
missing-cross-check mechanism).

## Proposed Change

| # | Target File | Change Description |
|---|---|---|
| 1 | `plugins/sdd-quality-loop/skills/sdd-sudo/SKILL.md` | Reconcile the skill with the guard: retitle the implementation section as human-executed, open it with a sentence naming its audience (the human, or a CLI implementation outside the agent's tool surface), and document the fallback the guard leaves as the only path — the agent may author a script, but the human runs it — so a blocked agent has a documented correct action instead of an apparent contradiction. |
| 2 | `plugins/sdd-quality-loop/scripts/sdd-hook-guard.py` (+ `.js`/`.ps1`/`.sh` twins) | Narrow the shell-command predicate that decides whether a command writes to the workflow bypass mode's flag file (implementation pointer: the function quoted in Problem Evidence, defect (2)) so the write operator must relate to the flag reference as its operand: match only when the flag name is the target of a redirection, the argument of a destructive verb, or the `file_path` of an editing tool. When the command cannot be tokenised, keep the fail-closed behaviour but restrict it to commands whose write operator is adjacent to the name (same pipeline segment) rather than anywhere in the string. |
| 3 | `plugins/sdd-quality-loop/scripts/sdd-hook-guard.py` (+ twins) | Add a word-boundary rule to the same predicate: the flag name must be followed by a non-identifier character before the name test passes, so the two documented key-resolution environment variables (named in Problem Evidence, defect (2)), which merely share the flag name as a prefix, are treated as the distinct identifiers they are. This alone clears the denial the plugin's own documented key-resolution procedure triggers. |

## Expected Effect

Read-only commands that mention the consent token — greps of the skill, of the
guard, of the policy reference, and any script that resolves the signing key —
stop being denied, while every command that actually writes, moves, or deletes
the flag file is still denied. The skill stops instructing agents to perform an
action the same plugin forbids, and the documented recovery (agent authors,
human executes) becomes explicit rather than improvised. Quantitatively:
reduce read-only-command denials mentioning the consent token from 3 observed
in one session (2026-09-02) to 0, while keeping denials of genuine
write/delete attempts against the flag file at 100%.

   and `SDD_SUDO_KEY_FILE`; and a `cat`/`sed` read of the skill file.
2. Add guard unit cases asserting DENY for: `printf ... > <root>/SDD_SUDO`,
   `rm <root>/SDD_SUDO`, `mv x <root>/SDD_SUDO`, `tee <root>/SDD_SUDO`, an
   `Edit`/`Write` tool call whose `file_path` is the flag, and an
   `apply_patch` adding it — i.e. today's whole DENY set must stay denied.
3. Mutation-check the narrowing: revert the operand restriction and confirm
   the new ALLOW cases fail; revert the word-boundary rule and confirm the
   env-var case fails. A narrowing that no test can distinguish from the old
   predicate has not been verified.
4. Re-run the guard's existing suite unchanged; no currently-denied write may
   become allowed.
5. Retrospective traceability: this friction has no retrospective metric row
   today; add a consent-token denial count column to the next retrospective
   run so the following cycle compares against a report-sourced row instead
   of only the guard's own unit-test suite.

## Rollback-Plan

The change is confined to one predicate (plus its `.js`/`.ps1` twins) and one
skill document. Reverting the predicate restores today's fail-closed
behaviour, which is strictly more restrictive and therefore never unsafe to
return to; reverting the skill edit restores the contradiction but breaks
nothing mechanical. No token, key, or evidence format changes, so no issued
token is invalidated by either direction.
