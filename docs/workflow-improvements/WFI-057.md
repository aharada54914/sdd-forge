## Problem Evidence

`install.sh` reports every plugin installed successfully and leaves the running
guard untouched, whenever the version number has not changed. During
development that is the normal case: the working tree advances, the version
does not.

Measured on 2026-08-27, immediately after WFI-048 landed on main at `8dab90ed`,
running `install.sh` from that tree, as a historical observation:

| | before the run | after the run |
|---|---|---|
| install root guard carries WFI-048 | no | **yes** |
| **cache guard carries WFI-048** | no | **no** |
| cache guard sha256 | `d0bdab97…` | **`d0bdab97…`, byte-identical** |
| cache skill flags (false/true) | 16 / 6 | 16 / 6 |

The installer's own output for that run:

```
Plugin "sdd-quality-loop" installed successfully. Installed 6 skills.
SDD plugins installed at: /Users/jrmag/.local/share/sdd-plugins
```

Nothing in it is false. Nothing in it is useful either: the plugin that
actually executes did not move, and the run that changed the install root reads
exactly like the run that changed nothing.

### The upgrade path exists and is correct — this input never reaches it

WFI-041 recorded a neighbouring defect and its fix is present and working.
`install.sh:271` collects plugins whose install output matches
`CLAUDE_ALREADY_INSTALLED_RE='already installed'` (`:179`) and puts them through
`upgrade_claude_plugins`, which runs `claude plugin marketplace update` then
`claude plugin update`.

The trigger is a message the CLI does not emit in this case. Measured, same
machine, same command, the only difference being the version:

| repo version vs cache | CLI says | upgrade path | cache |
|---|---|---|---|
| **equal** (1.16.0 → 1.16.0) | `installed successfully` | **never runs** | unchanged |
| **newer** (1.16.0 → 1.17.0) | `updated from 1.16.0 to 1.17.0` | wrapper outcome not established | updated |

The second row is this session's release, and it confirms the cache moved to
`0202c8f3…`, the digest of the guard as built. That observation does not by
itself distinguish whether the move came from the CLI update command or the
installer's upgrade wrapper.

So this is not a broken fix. WFI-041 handled "the plugin is already installed at
an older version". Nobody handled "the plugin is already installed at the same
version, and its contents changed" — which is what every development iteration
looks like.

### Cost

A whole session's work — a guard change, a skill-delegation fix, and their
verification — sat on disk believing it was live. The only reason it was caught
is that the pre-update state had been recorded on purpose, specifically to test
this. An operator who trusts the installer's verdict has no signal at all: no
warning, no version line, no diff.

The repository already knows this hurts. `install.sh:176-178` carries a comment
explaining that a plain re-run leaves the cache a version behind, and WFI-041
wrote a fix for the case it had seen. The same-version case was simply never
the case anyone hit while looking.

## Why-Why Analysis

| # | Why (question) | Because (answer) | Evidence |
|---|---|---|---|
| 1 | Why did the running guard keep the old behaviour after a successful install? | The plugin cache was never rewritten. | cache sha256 byte-identical across the run |
| 2 | Why was the cache not rewritten? | `upgrade_claude_plugins` never ran for any plugin. | `already_installed` empty; no `updated from` line in the output |
| 3 | Why did it not run? | Its trigger is the literal string `already installed`, and the CLI answered `installed successfully`. | `install.sh:179`, `:271`; the two outputs measured side by side |
| 4 | Why does the CLI answer differently for the same repository? | It keys on version. Same version, same cache entry — there is nothing it considers an upgrade. | 1.16.0 → 1.16.0 vs 1.16.0 → 1.17.0, same machine |
| 5 | Why does the installer not notice the discrepancy itself? | It never compares what it placed with what is cached. Success is derived from each CLI's exit status, not from the end state. | the run reports success with the two trees provably different |

The chain ends at one controllable mechanism: **the installer asserts nothing
about the cache it exists to update.**

## Root Cause Hypothesis

The installer's success criterion is "every command I ran returned zero". That
is a statement about the steps, not about the outcome, and the two come apart
precisely when a step is a legitimate no-op.

`claude plugin install` returning success for an already-current plugin is
correct behaviour for a package manager: the requested version *is* installed.
The installer inherits that answer and reports it onward as though it meant the
tree it just staged is now running. Version equality is doing work here that
nobody asked it to do — it is standing in for content equality, and during
development those are routinely different.

A verification step would collapse the whole class, because the question is
cheap to answer directly: are the bytes the installer placed the bytes the
cache now holds.

## Proposed Change

| Target File | Change Description |
|---|---|
| `install.sh` and `install.ps1` | After registration, compare a digest of the complete selected plugin payload in the install root with the same payload in each CLI's cache. Bind the full deterministic tree manifest: every installed file, plus path, type, bytes, and link target. That makes mutations outside the formerly chosen marker visible, and additions, deletions, file-type changes, and symlink-target changes all alter the result. On mismatch, fail the run with a message naming both digests, the plugin, and the fact that the version number did not change. |
| `install.sh` and `install.ps1` | Report the end state unconditionally from a read-only comparison: for each plugin, the version and digest the cache holds after the run, whether or not anything moved. A run that changed nothing must not read like a run that changed something, and the check must not clear or rewrite cache entries. |
| `install.sh` and `install.ps1` | When the mismatch is detected and the versions are equal, say what to do — cut a release, or remove the cache entry — rather than leaving the operator to discover that reinstalling again cannot help. |
| `tests/installer-idempotency.tests.sh` and its `.ps1` twin | Add the same-version-changed-content case: stage a tree whose version equals the cached one but whose payload differs outside the formerly chosen marker, run the installer against stubbed CLIs that emit the real `installed successfully` message, and assert the run FAILS with the digest mismatch. Add coverage for additions, deletions, file-type changes, and symlink-target changes so the digest proves each class is detected. This is the case the existing suite does not cover — it tests that a re-run of an unchanged tree stays clean, which is a different question. |

**Not proposed.** Making the installer bump the version itself, or force-clearing
the cache entry. Both make `install.sh` decide something that belongs to the
release process, and the second silently discards a cache another tool may be
mid-way through using. Detection and a clear instruction are enough; the
operator can then choose a release or a manual cache removal.

**Also not proposed.** Treating version equality as a reason to skip
registration. The install root should still be updated — it was, correctly, in
the measured run. The defect is the report, not the placement.

## Expected Effect

An installer run either updates the running plugin or fails saying it could
not. A developer stops being able to believe a change is live when it is not.

Concretely: the run measured above would have failed with the two digests side
by side instead of printing `installed successfully` six times.

## Verification Metric

Target-Metric: with an install root whose plugin contents differ from the cache
at the same version number, the number of installer runs that exit 0
Expected-Direction: decrease
Horizon: at application
Baseline: 1 of 1 exits 0 while leaving the cache byte-identical (measured
2026-08-27 against main at `8dab90ed`, cache guard sha256 `d0bdab97…` unchanged
across the run)
Target: 0 of 1 — the run fails and names both digests

Coverage note: the mismatch must be detected through a read-only comparison, and
the same suite must prove that additions, deletions, file-type changes, and
symlink-target changes all trip it. No test should rely on force-clearing a
cache entry.

Secondary (no regression on the working paths): a run against an install root
already identical to the cache still exits 0, and a run with a genuinely newer
version still upgrades and reports the transition. Baseline: both work today —
the second was measured on this session's v1.17.0 release, cache moving to
`0202c8f3…`. Target: both unchanged.

## Verification Plan

1. Record the baseline by digest, not by the installer's own verdict: the
   installer's report is the thing under suspicion, so it cannot be the
   instrument. Compare the full selected plugin payload in the install root to
   the cached payload directly, without mutating either side.
2. Assert the defect before the change: same version, different contents, run
   exits 0 and the cache digest is unchanged. This is the assertion the fix
   must flip.
3. Assert the fix: the same input fails, and the message contains both digests
   and the plugin name.
4. Assert the healthy paths still work: a same-version unchanged tree exits 0,
   and a newer-version run still upgrades end to end, with the cache digest
   actually moving and not stubbed. The newer-version observation is historical
   evidence that the cache can move; it does not by itself prove whether the
   CLI update command or the installer's wrapper made it happen.
5. Mutation: make the digest comparison always report equal, and confirm step 3
   goes back to passing-as-broken. A comparison that cannot fail is the same
   silent success in a new place. Also verify that a forced cache-clear path is
   never needed or invoked.
6. Twin parity: `install.sh` and `install.ps1` must reach the same verdict on
   the same fixture, asserted per case, with the ps1 side behind a capability
   probe and a visible `skip -` line.
7. Re-run the recorded digest comparison after application and put both digests
   in `## Result`.

## Rollback-Plan

Revert the commit whose message contains `WFI-057`. The installer returns to
reporting success without checking the cache, which is today's behaviour; the
added test case is removed by the same revert.

Nothing on disk needs migrating, and no installed plugin is affected — the
change adds a check after placement, not a different placement.

If the digest comparison proves unreliable across CLIs whose cache layout
differs (Codex and Copilot keep their own trees, and their paths are not
guaranteed stable), the proportionate retreat is to keep the unconditional
end-state report and downgrade the mismatch to a prominent warning for the CLIs
whose layout cannot be resolved, while keeping the hard failure for Claude,
whose cache path is already known to the installer.
