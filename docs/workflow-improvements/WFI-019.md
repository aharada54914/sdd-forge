## Problem Evidence

Feature `epic-189-a1-project-context`: after the task-review
post-implementation provenance re-review completed with a clean PASS
(attempt-4 round-1, contract commit `3f3b38da`),
`check-workflow-state.sh --feature epic-189-a1-project-context` still
exits 1 with `task plan hash is stale` — the provenance re-review
procedure's own completion requirement ("require exit 0 before reporting
completion") is unsatisfiable:

- `check-workflow-state.sh` (task-stage provenance) compares BOTH the
  contract's reviewer manifests and the contract's top-level
  `tasks_sha256` against the STATUS-NORMALIZED hash of the live tasks.md
  (`normalized_hash`: Approval→Draft, Status→Planned,
  Task-Review-Status→Pending, Second-Approval lines dropped). The `.ps1`
  twin (lines ~776-784) is identical.
- `validate-review-context-set.sh` performs RAW byte verification with no
  normalization (`actual_hash=$(sha256_file "$candidate")`), so reviewer
  invocation manifests — and therefore the reviewer output manifests and
  their verbatim copies in the contract — must carry the raw hash.
- With post-implementation task states (`Approved (sudo …)`, `Blocked`),
  raw (`73172ff7…`) ≠ normalized (`d22f7517…`, verified by direct
  computation), so an honestly-built contract can never satisfy both
  validators. Attempt-1 passed only because pre-implementation content had
  raw == normalized. This is also the root cause of the standing
  `task plan hash is stale` diagnostic present since commit `4bd2ec3b`.
- `diagnostic()` exits on the first failure, masking the second
  (top-level) mismatch behind the first message.

## Root Cause Hypothesis

The normalized comparison was designed to tolerate later status/approval
field flips against a contract recorded at review time (raw == normalized
back then). The post-implementation provenance re-review inverts the
situation: the contract is recorded AGAINST the already-flipped file, and
the ledger validator pins its manifests to raw bytes. The two validators
were never reconciled for this case, making the re-review procedure's
exit-0 completion structurally unreachable for its primary use case.

## Proposed Change

Git-apply-ready patch:
`reports/implementation/epic-189-a1-project-context/wfi-019-taskstage-hash-compat.patch`
(sha256 `5f89b953a21f3eec4fddc722065f0b65921716170bd5145dcdcc11d59e3ae616`,
verified with `git apply --check` at preparation time). Minimal diff, two
files, task-stage comparisons only:

1. `plugins/sdd-quality-loop/scripts/check-workflow-state.sh` — the two
   task-stage comparisons accept EITHER the status-normalized hash OR the
   raw file hash of the live tasks.md (manifest check tries normalized
   then raw; top-level `tasks_sha256` equality against either).
2. `plugins/sdd-quality-loop/scripts/check-workflow-state.ps1` — the
   identical change in the twin (`Get-NormalizedHash` OR `Get-Sha256`).

Non-weakening argument (stated in code comments): both accepted values
are fixed derivations of the SAME live file; the raw hash binds strictly
MORE content than the normalized hash (normalization only masks the three
status/approval field forms), so accepting raw-or-normalized cannot admit
any tampered content that the normalized-only rule would have caught.

## Expected Effect

- `check-workflow-state.sh --feature epic-189-a1-project-context` exits 0
  against the attempt-4 contract (raw-recorded), completing the provenance
  re-review per its own step 5 and clearing the standing stale diagnostic.
- Pre-implementation contracts (raw == normalized) are unaffected.
- Future post-implementation re-bindings across epics A2-A8 work without
  this contradiction.

## Result

Applied — recorded 2026-08-22 on explicit human direction, reconciling a
Draft whose substance had already landed.

**Where the change lives.** Commit
`6e5844116a6fe324fb25a44a39e5fc9c860121b9` (2026-08-02, "fix(gates): accept
a re-reviewed document's raw hash, not only the normalized one") implemented
this WFI's proposal — and more broadly than proposed: it covers the
implementation AND task stages with the same non-weakening argument, where
this WFI asked only for the task stage. This is not a fresh judgment:
WFI-021's `## Cross-references` section records it contemporaneously
("WFI-019's proposal is satisfied by it in substance") together with the
governance caveat that the change was orchestrator-applied although this
WFI had asked for human application — recorded there, and now here, rather
than left implicit. No commit carries a `WFI-019` marker; the Rollback-Plan
above has been rewritten accordingly.

**Since then.** The acceptance side evolved further: both
`check-workflow-state` twins now also accept the re-review canonical forms
(`rereview_normalized_hash` / `Get-RereviewNormalizedHash`, landed with
WFI-030), so the validator this WFI targeted accepts four forms of the same
live file, each binding at least as much content as the normalized-only
rule did.

**Successor: WFI-025.** The residual gap this WFI's fix did not close — the
producing side still emits only the raw digest form while the accepting
side admits multiple transition-invariant forms, with no
producer/acceptor parity control binding the two surfaces (and no
cross-validator hash-semantics regression fixture) — is exactly the problem
WFI-025 (`Status: Draft`) formalizes. WFI-025 is the successor for that
work; this WFI is complete for the acceptance-side change it proposed and
must not be re-opened for the producer side.

**Verification status.** The Verification Metric (validator exit codes plus
the workflow-state regression suites) is met on `main`: the feature-scoped
and repository-wide runs exit 0 in CI through v1.16.0, and the re-review
acceptance paths are exercised by the suites' fixtures. The next
retrospective's Applied-WFI horizon check can classify from those records.
