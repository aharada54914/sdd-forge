## Problem Evidence

`install.sh` cannot be re-run on a machine that already has the plugins
installed. Every path that registers something with an external CLI fails when
that thing is already registered, and any non-zero exit triggers a wholesale
rollback of the install root — so a routine upgrade silently reverts to the old
version while reporting an error about something unrelated.

Measured 2026-08-22 while upgrading this machine from 1.15.0 to 1.16.0. Three
consecutive runs failed; the fourth succeeded only by disabling the failing
steps.

| Run | Invocation | Failure | Result |
|---|---|---|---|
| 1 | `install.sh --ref main --plugins … --mcp …` | `Failed to add marketplace: Error: Marketplace "sdd-plugins" already registered` → `'copilot plugin marketplace add …' failed with exit code 1` | rolled back |
| 2 | same | same | rolled back |
| 3 | `--target Claude` | `MCP server sdd-forge-mcp already exists in user config` → `'claude mcp add sdd-forge-mcp …' failed with exit code 1` | rolled back |
| 4 | `--target Claude --skip-mcp` | — | exit 0, install root updated |

The two failing calls are `install.sh:224`
(`run_plugin_command copilot plugin marketplace add "$marketplace_root" || return 1`)
and `install.sh:366`
(`run_plugin_command claude mcp add "$name" --scope user -- node "$entry_point" || return 1`).
`run_plugin_command` (`:155-163`) treats any non-zero exit as fatal, and the
trap at `:585` (`trap 'rc=$?; rollback; cleanup; exit $rc' EXIT`) runs
`rollback` (`:571-583`), which does:

```sh
if [[ -n "$BACKUP_ROOT" && -d "$BACKUP_ROOT" ]]; then
    if [[ -d "$INSTALL_ROOT" ]]; then
        rm -rf "$INSTALL_ROOT"
    fi
    mv "$BACKUP_ROOT" "$INSTALL_ROOT"
```

The install root had already been replaced with the new version by that point
(`:879`), so the rollback discards a correct 1.16.0 tree and restores 1.15.0.

### The failure state is misleading, not merely inconvenient

Registration with each CLI happens *before* the trap fires, and each CLI keeps
what it was given. After run 1 the machine was in a split state:

| Location | Version | Protected suffixes |
|---|---|---|
| `~/.codex/plugins/cache/sdd-plugins/sdd-quality-loop/` | **1.16.0** | 111 |
| `~/.local/share/sdd-plugins/` (install root) | 1.15.0 | 80 |
| `~/.claude/plugins/cache/sdd-plugins/sdd-quality-loop/` | 1.15.0 | 80 |

A partial success that looks like a partial failure. The first reading of this
was "Codex worked, Claude did not", which is wrong — nothing was targeted
differently. Codex simply wrote its cache before the rollback undid the shared
source.

### A second defect: registration is not an upgrade path

Even after run 4 placed 1.16.0 in the install root, the Claude cache stayed at
1.15.0. `install.sh:209` calls `claude plugin install "${p}@sdd-plugins"`, which
reports `✔ Plugin "…" is already installed (scope: user)` and returns success
without upgrading. The version only moved after running, outside the installer:

```
claude plugin marketplace update sdd-plugins
claude plugin update <name>@sdd-plugins     # for each of the six
```

which reported `updated from 1.15.0 to 1.16.0` for all six. So `install.sh`
installs on a clean machine but cannot upgrade one, and does not say so.

### Cost

Four runs, three rollbacks, and a diagnosis that had to distinguish a rollback
from a partial failure — for a version bump that had already merged and passed
CI. The correct final command (`--target Claude --skip-mcp`, then two `claude
plugin` subcommands the installer never mentions) is not discoverable from any
error message the installer emits.

## Why-Why Analysis

| # | Why (question) | Because (answer) | Evidence |
|---|---|---|---|
| 1 | Why did re-running `install.sh` on an up-to-date machine revert it to the old version? | A registration step exited non-zero, and the EXIT trap rolls the install root back wholesale. | `install.sh:585` trap → `:571-583` rollback; runs 1-3 in the table above |
| 2 | Why did a registration step exit non-zero when nothing was wrong? | Registering an already-registered marketplace or MCP is reported as an error by the external CLIs, and `run_plugin_command` treats every non-zero exit as fatal. | `:224` and `:366`, each with `\|\| return 1`; `:155-163`; the observed `already registered` / `already exists in user config` messages |
| 3 | Why is an already-registered resource treated as fatal? | The installer models registration as a one-shot operation on a clean machine, so "already there" was never distinguished from a real failure. | The same script installs cleanly on a fresh machine; every observed failure is an idempotency case |
| 4 | Why did the upgrade still not apply after a successful run? | Plugin registration calls `claude plugin install`, which is a no-op when installed. The installer has no upgrade path, and `claude plugin update` is never invoked. | `:209`; `already installed (scope: user)` on a 1.15.0 cache while the install root held 1.16.0 |

The chain ends at one controllable mechanism: the installer models a first
install and treats every re-run as one. Rows 3 and 4 are the two faces of that
— it fails where it should be a no-op, and no-ops where it should act.

## Root Cause Hypothesis

The installer was written for the first-install case and never given a concept
of "already in the desired state". Two consequences follow from the same
omission.

Where an external CLI reports an existing registration as an error, the
installer propagates it as fatal, and because the install root is swapped before
registration runs, the rollback undoes work that was correct. The blast radius
is larger than the failure: one idempotency complaint from one CLI discards the
entire upgrade.

Where an external CLI reports an existing installation as success, the installer
accepts it and moves on — leaving the cache at the old version. The two
behaviours look opposite but come from the same place: registration outcomes are
passed through without asking whether the desired end state was reached.

## Proposed Change

| Target File | Change Description |
|---|---|
| `install.sh` and `install.ps1` | Make registration idempotent. Wrap the marketplace-add and MCP-add calls in a helper that treats "already registered" / "already exists" as success rather than failure, matching on the CLIs' own messages and exit codes, and keeping every other non-zero exit fatal. The calls to change are `:224` (copilot marketplace), `:366` (`claude mcp add`), and the Codex equivalent in the same block. |
| `install.sh` and `install.ps1` | Add an upgrade path. After `claude plugin install` reports an existing installation, run `claude plugin marketplace update <name>` followed by `claude plugin update <plugin>@<marketplace>`, so a re-run converges the cache on the install root's version instead of leaving it behind. Report the version transition, so a run that changed nothing is distinguishable from one that upgraded. |
| `install.sh` and `install.ps1` | Narrow the rollback. `rollback` should restore the install root only when the failure occurred before or during placement. A failure in an external-CLI registration step, after the tree is in place, should report the failing registration and leave the install root at the new version rather than reverting it — the tree is not what failed. |
| `tests/installer-idempotency.tests.sh` and its `.ps1` twin (new) | Re-running the installer against an install root that is already at the target version must exit 0 and leave the install root unchanged. Drive it with stubbed CLIs that emit the real "already registered" / "already exists" messages and non-zero exits, so the test fails today for the reason this WFI describes. |

**Not proposed.** Removing the rollback entirely. It is correct for the case it
was written for — a failure during download, extraction or placement should not
leave a half-written install root. The change narrows *when* it fires, rather
than removing the protection.

## Expected Effect

Re-running `install.sh` on a machine that already has the plugins becomes a
no-op or an upgrade, not a rollback, and a failure in one CLI's registration
stops discarding the whole install.

Concretely, the upgrade measured here took four runs and two undocumented
follow-up commands. With idempotent registration and an upgrade path it takes
one run, and the install root and every CLI cache converge on the same version.

## Verification Plan

1. Build the stubbed-CLI harness: fake `claude`, `copilot` and `codex`
   executables on `PATH` that emit the observed messages
   (`Marketplace "sdd-plugins" already registered`, `MCP server <name> already
   exists in user config`) with the observed exit codes.
2. Assert the defect before the change: with an install root already at the
   target version, the current `install.sh` exits non-zero and leaves the install
   root reverted. This is the failing test the fix must flip.
3. Assert the fix: the same scenario exits 0, the install root is at the target
   version, and no backup directory remains under the install parent.
4. Assert the upgrade path: with the install root at N+1 and a CLI cache stubbed
   at N, a run must invoke marketplace-update and plugin-update, and must report
   the version transition. A run where the cache is already at N+1 must report no
   change — otherwise the check passes on a tool that always updates.
5. Assert the narrowed rollback in both directions: a failure injected during
   placement still reverts the install root; a failure injected in a registration
   step after placement does not, and the run reports which registration failed.
6. Twin parity: run both suites, with a `pwsh` capability probe and a visible
   `skip -` line when the shell is absent.
7. The next release installed on a developer machine records the installer
   invocation count, against the baseline of 4 recorded here.

## Rollback-Plan

Revert the commit whose message contains `WFI-041`. The installer returns to
treating every registration outcome as fatal-or-done and to rolling the install
root back on any failure, which is today's behaviour; the new suites are removed
with the same revert.

Nothing on disk needs migrating: the change alters only what the installer does
during a run, not what it produces. A machine installed by the changed version
and a machine installed by the current one hold identical trees.

If the idempotency matching proves fragile — external CLIs changing their
"already registered" wording between versions — the proportionate retreat is to
keep the narrowed rollback and the upgrade path, and drop the message matching
in favour of a pre-check that asks each CLI whether the resource exists before
attempting to add it.

## Result

**Applied 2026-08-23** (commit whose message contains `WFI-041`). All four
Proposed Change rows landed:

- **Idempotent registration.** `run_plugin_command_idempotent` (sh) and
  `Invoke-PluginCommandIdempotent` (ps1) capture the CLI's combined output and
  treat a non-zero exit as success only when the output matches the shared
  pattern `already (registered|exists|installed|added)` — stated once per
  runtime rather than per call site. Every other non-zero exit stays fatal with
  the message the strict helper already emitted. Applied to all six
  registration calls plus `claude mcp add`: the two the WFI measured (`copilot
  plugin marketplace add`, `claude mcp add`) and the Codex/Claude equivalents in
  the same blocks.
- **Upgrade path.** `upgrade_claude_plugins` / `Update-ClaudePluginCache` run
  `claude plugin marketplace update` then `claude plugin update <p>@<market>`
  after the install loop, and report the transition: either "cache upgraded: N
  plugin(s) moved to the installed version" or "already at the installed
  version; no plugin was upgraded". A failed update is a warning, not a fatal —
  the tree is already correct at that point.
- **Narrowed rollback.** A `REGISTRATION_PHASE` / `$registrationPhase` flag is
  set once the install root is in place and every remaining step is external-CLI
  registration. `rollback()` (sh) and the `catch` block (ps1) revert the tree
  only while the flag is unset; from the registration phase onward they report
  the failing registration, name where the previous version is preserved, and
  keep the new tree. The placement-phase protection is unchanged.

  **Narrowed further than the WFI specified, on evidence found during
  application.** The suppression is additionally conditioned on a backup
  existing — that is, on this being an *upgrade*. A first draft suppressed the
  rollback for every registration-phase failure, and that broke
  `tests/install.tests.sh` scenario (c), which asserts that a registration
  failure on a **fresh** machine leaves no install root behind. That assertion
  is right and this WFI's evidence does not contradict it: the measurement is
  about upgrades ("three rollbacks of a correct 1.16.0 tree back to 1.15.0"),
  where reverting trades a correct new tree for an older one. A fresh install
  has nothing to trade — an unregistered tree on a machine that had none is
  inert, not a working version worth keeping — and the re-run is now safe
  anyway by the idempotency change. Scenario (c) passes unmodified.
- **Test suite.** `tests/installer-idempotency.tests.sh` (registered in
  `tests/run-all.sh` and in the CI matrix) drives the real installer against
  stubbed `claude`/`copilot`/`codex` executables that emit the exact messages
  and exit codes measured on 2026-08-22. Its fixture derives the source-tree
  requirements from the installer's own `REQUIRED_PATHS` array rather than
  duplicating the list. 14 passed, 0 failed.

**Discriminating order verified** (Verification Plan item 2). Replayed against
the pre-change installer (`origin/main`'s `install.sh`), the suite fails **7**
assertions, reproducing every measured defect: the re-run exits 1 on "already
registered"; the install root is **reverted to the old version** (the headline
defect — three rollbacks of a correct tree on 2026-08-22); no upgrade command is
invoked and no transition is reported; and a registration-phase failure reverts
the tree. After the change all 14 pass.

**Both control directions hold** (Verification Plan item 5). The
placement-phase rollback case (C2) and the genuine-failure cases (D) pass
against *both* the pre-change and post-change installers, so the change is shown
to narrow the rollback without removing it and to keep unrelated failures fatal
rather than swallowing them behind the idempotency matcher.

### Ripple found during application: `tests/install.tests.sh` scenario (d)

The WFI's `## Proposed Change` did not name `tests/install.tests.sh`, but that
suite already encoded the **old** rollback contract, so the change could not
land without confronting it. Two of its assertions failed:

- **Scenario (c)** (fresh machine, registration failure → no install root left
  behind). Resolved without touching the test, by narrowing the suppression to
  the upgrade case as described above. This assertion was correct and remains
  unmodified.
- **Scenario (d)** (existing install, registration failure). This one asserted
  *exactly the behaviour this WFI was approved to change*: that the installer
  reverts to the previous version. It cannot hold alongside the approved change
  — the two contracts are contradictory, and this WFI's evidence is that the old
  one was the defect.

Scenario (d) was therefore **updated to assert the new contract, not weakened or
removed**. It previously made one assertion (the previous version is back at the
install root). It now makes three: the new tree is still in place, it is *not*
the previous version, and the previous version is recoverable from a sibling
`sdd-plugins-backup-*` directory. Keeping the new tree is only defensible if the
old one is still retrievable, so both halves are now checked where one was
before. The harness gained a `fail_phase=` keyword so a scenario states which
contract applies; the default stays `placement`, leaving every other scenario's
behaviour untouched.

**The updated scenario discriminates**: replayed against `origin/main`'s
`install.sh` it fails 2 of its 3 assertions (the installer reverts to the
previous version, and leaves no backup), and passes against the changed
installer. `tests/install.tests.sh`: 41 passed, 0 failed after the change.

This is the same class of ripple recorded for WFI-042 (the MCP parser bound by
the golden shell-equivalence contract): a change to a behaviour reaches every
surface that asserted the old behaviour, and those surfaces are not always
listed in the proposal. Worth carrying into the next retrospective as an
observation about `## Proposed Change` completeness.

**Not done here.** Verification Plan item 6's `pwsh` twin suite: the ps1
installer changes are twins of the sh ones and are covered by the existing
installer suites in CI, but a dedicated `installer-idempotency.tests.ps1` was
not written — the stub harness would need a PowerShell reimplementation, and
this container has no `pwsh` to develop it against. Recorded as the one open
implementation item.
