## Problem Evidence

**Sixteen of the twenty-one installed SDD skills cannot be invoked by anyone.**
They carry `disable-model-invocation: true` *and* `user-invocable: false`, so the
agent is refused and the human is refused.

Measured from the installed plugin frontmatter
(`sdd-plugins/*/1.15.0/skills/*/SKILL.md`) on 2026-08-25:

| reachable (5) | unreachable (16) |
|---|---|
| `bootstrap` | `implement-task`, `implement-tasks`, `quality-gate`, `cross-model-verify`, `lite-gate`, `lite-spec` |
| `diagnose` | `spec-review-loop`, `impl-review-loop`, `task-review-loop`, `design-sync-loop`, `visual-verify-loop` |
| `fix-by-review-ticket` | `investigate-codebase`, `sdd-adopt`, `sdd-bootstrap-interviewer` |
| `sdd-sudo` | `workflow-retrospective`, `wfi-audit-cycle` |
| `ship` | |

`ship` is reachable. **Every stage `ship` delegates to is not.** Its Step 3 says
"Invoke `/sdd-implementation:implement-tasks`" and its Step 4 says "Invoke
`/sdd-quality-loop:quality-gate`", and both refuse:

```
Skill sdd-implementation:implement-tasks cannot be used with Skill tool due to
disable-model-invocation. Ask the user to run /sdd-implementation:implement-tasks
themselves — it cannot be invoked via the Skill tool. Do not replicate this
skill's workflow by other means — it is reserved for explicit user invocation.
```

The refusal directs the work to the user. The user is refused in turn:

```
This skill can only be invoked by Claude, not directly by users.
Ask Claude to use the "sdd-implementation:implement-tasks" skill for you.
```

Each message names the other party as the correct caller. Reproduced end to end
on 2026-08-25: a human invoked `/sdd-ship:ship`, the agent reached Step 3, was
refused, handed the user the command string, the user ran it, and was refused
with the message above. Neither instruction is wrong on its own; together they
close the loop.

**The consequence is not theoretical.** Every review stage advanced in this
session — four features through spec, impl and task review to
`workflow-state: ok` — was driven by reading the role files under
`plugins/sdd-review-loop/agents/` and executing the procedure directly, because
`spec-review-loop`, `impl-review-loop` and `task-review-loop` are all in the
unreachable set. That workaround produces correct artifacts but bypasses whatever
the skill wrapper enforces, and it is the only route that moves work at all.

The four features now sit at `Implementation Complete` or `Planned` with no
reachable path to `Done`, because `quality-gate` is the only transition to `Done`
and nothing can call it.

## Root Cause Hypothesis

`user-invocable: false` and `disable-model-invocation: true` are each individually
sensible and were plausibly added for different reasons at different times:

- `user-invocable: false` marks a skill as an internal step so a human does not
  run a sub-stage out of order — `quality-gate`'s own header says "This skill is
  invoked by `sdd-ship`".
- `disable-model-invocation: true` prevents an agent from self-authorising a gated
  action.

Together they assume a **third** caller exists: an orchestrator that is neither
the model nor the user. There isn't one. `ship` is not a separate process — it is
a set of instructions the model executes, so `ship` invoking `implement-tasks`
*is* the model invoking `implement-tasks`, and `disable-model-invocation` refuses
it.

The two flags were almost certainly never evaluated as a pair across the skill
set. Nothing checks the combination, so it can be introduced one flag at a time
with no signal.

**Correction, from an independent audit (2026-08-25).** An earlier draft of this
section implied the workflow worked before `40f1dd1a` closed the loop. It did
not, and the true history is worse:

- `fe4fc188` did **not** introduce `disable-model-invocation` across the skill
  set. It created one new skill already carrying the flag. The model prohibition
  was already policy by `0b3ca73`, 2026-06-10.
- `9af50825` (2026-06-20) introduced the two-command workflow, but its bare
  `/sdd-bootstrap` and `/sdd-ship` names collided in the plugin/skill namespace
  and returned `Unknown command`. `46ad3ee0` (2026-06-22) renamed them to
  `:run`, reaching main at `3febe638`.
- From that fix until `40f1dd1a` (2026-07-02), every stage was individually
  **human**-invocable, because `user-invocable` was unset — but every stage
  already carried `disable-model-invocation: true`.
- `40f1dd1a` added `user-invocable: false` to exactly 14 skills. Two more
  (`design-sync-loop`, `visual-verify-loop`) were created the same evening
  already carrying both flags, which is how the present count reached 16.

So there was **never a window in which one `ship` invocation could execute the
documented end-to-end delegation.** Before 2026-06-22 the entry command itself
was broken; after it, every nested stage was model-disabled. What briefly worked
was a human invoking each stage by hand, and 2026-07-02 closed that too.

An operator recalling that "`ship` used to do everything" is most likely
recalling the manual per-stage route. If an actual end-to-end run was observed,
it depended on undocumented host behaviour or on the model reproducing child
instructions by hand rather than invoking them — and the repository contains no
supported mechanism that would account for it.

The same audit confirmed no orchestration escape exists: no delegation
exception, alternate caller identity, allow-list, hook, manifest field, plugin
setting, or non-delegating `ship` mode. A nested Skill call is still a
model-originated call; it does not inherit the human identity that invoked the
parent.

**Scope correction.** "Unreachable by anyone" holds for Claude Code. Codex does
not enforce these fields — the same plugins are installed under
`~/.codex/plugins/cache/sdd-plugins/`, both skills appear in its catalog, and it
reports them as available to invoke. The SKILL.md files document a Codex
invocation form as a first-class route, so Codex is a supported caller and the
defect is Claude-Code-specific.

## Proposed Change

1. **Add a conformance check that fails on the combination.** For every skill
   manifest, `disable-model-invocation: true` together with
   `user-invocable: false` is unreachable unless an orchestration mechanism that
   is neither model nor user is documented and demonstrated. Fail the check; do
   not warn.
2. **Decide the intended caller per skill and make the flags reflect it.** For the
   delegated stages (`implement-task[s]`, `quality-gate`, `cross-model-verify`,
   `lite-gate`, the three review loops) the documented caller is `ship`, which is
   the model executing ship's instructions — so `disable-model-invocation` must be
   false for them, while `user-invocable: false` can stay to keep humans from
   running sub-stages out of order.
3. **Where an agent genuinely must not self-authorise a stage**, express that as a
   precondition the stage checks — a human approval mark, a signed token — rather
   than as an invocation ban. A precondition can be satisfied; an invocation ban
   cannot.
4. **Correct the refusal messages** so neither names a caller who is also refused.
   Each should state the actual reachable route, or say plainly that there is
   none.

Explicitly **not** proposed: removing `user-invocable: false` wholesale, or
loosening any approval gate. The controls are wanted; their composition is not.

## Expected Effect

`/sdd-ship:ship` completes the loop it describes: implementation runs, the quality
gate runs, tasks reach `Done`. Review stages run through their skills rather than
by hand-executing role files, so whatever the wrapper enforces is actually
enforced.

## Verification Metric

Baseline (2026-08-25): 16 of 21 skills unreachable; 0 of 4 in-flight features can
reach `Done`; every review stage advanced this session bypassed its skill wrapper.

Target: 0 skills carrying both flags without a demonstrated third-party caller; a

## Verification Plan

1. A conformance test over every installed skill manifest asserting the
   combination is absent. Prove non-vacuity by adding a fixture manifest carrying
   both flags and showing the test fails on it.
2. An end-to-end run: a human invokes `/sdd-ship:ship` on one feature with a task
   at `Implementation Complete`, and the task reaches `Done` with no manual step.
   Record every skill the run actually invoked.
3. Assert the negative direction still holds: an agent cannot drive a stage whose
   human-approval precondition is unmet. Whichever flag is relaxed, that must
   remain refused, and the test must show it.
4. Re-run the reproduction in Problem Evidence and record that neither refusal
   message now names a refused caller.

## Rollback-Plan

The change is confined to skill frontmatter and a conformance test. Reverting
restores the present flags, which are strictly more restrictive, so a rollback
cannot admit an invocation that is refused today. No `specs/**` bytes move, so no
contract hash changes and no feature's stage provenance is affected either way.
