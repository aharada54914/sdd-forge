## Problem Evidence

In the MCP status comparison, the owner submitted condition A (raw response)
with all four comprehension answers and the misoperation explanation recorded
as 「わからん」. The local answer interval was 30.585 seconds. The owner then
rejected raw MCP output as the human-facing presentation, selected B, and
explicitly requested B's implementation. See the sanitized
[observation and implementation report](../../reports/verification/mcp-owner-feedback-20261031/README.md).
The raw participant record remains private. This is one participant's report,
not a representative usability study or an authenticated timing receipt.

## Why-Why Analysis

| Why | Finding | Evidence |
|---|---|---|
| Why was the status not understood? | The participant answered unknown to each of four questions. | Actual A-only submitted answers. |
| Why might raw responses contribute? | They require the reader to reconstruct the current phase and next action from machine fields. | A's presentation and the owner's explicit rejection; causal attribution remains a hypothesis. |
| Why can the project reduce that burden? | The existing status view already renders the same guarded data as current phase, next command and per-stage status. | `mcp/sdd-forge-mcp/src/status-view.ts`; B's implementation and mobile checks. |

## Root Cause Hypothesis

Using raw machine output as the primary human status presentation makes the
reader perform workflow interpretation. The owner's response supports changing
the presentation, but does not establish a measured benefit for B.

## Proposed Change

Use the existing `--status-ui` view for human MCP status inspection. It is
already implemented on main; retain MCP's machine contract and original evidence.
Keep unknown approval, quality and completion states explicit, and retain raw
responses behind the optional evidence disclosure. No new approval or execution
authority is introduced. This draft records the adoption goal and recurrence
check, not a new task approval or an audit verdict.

## Expected Effect

The reader can identify the current phase and next action without reconstructing
raw JSON. A causal reduction in time, errors or effort remains unmeasured.

## Verification Metric

Use the prospectively fixed four comprehension questions and existing
`mcp-human-local-observation/v1` trial fields. Do not introduce a new gate score
or map unknown answers to successful comprehension. The target is evidence-backed
answers to all four questions in the next B observation. A's four answers are
unknown; B's answers, operation count and duration are not yet available.
Timing alone is not the success criterion. This descriptive UX observation is
not an established run-record quality metric and grants no quality verdict.

## Verification Plan

1. Preserve the original protocol, source mapping, A record and chat selection.
2. Receive an actual B observation if comparative UX acceptance is continued;
   keep stopping, missing answers and unknown times visible.
3. For status-view changes, run the existing MCP tests and check a narrow mobile
   viewport against the real loopback server: current state, next command,
   unknown later states, raw evidence collapsed, and refreshed source changes.
4. If the raw response becomes the primary view again, or known Pending/unknown
   states become approval/completion claims, record recurrence and repair it.
   Mechanical checks cannot substitute for the missing human B observation.

## Rollback-Plan

If the view misrepresents guarded data, stop using `--status-ui` until repaired;
retain the existing read-only MCP tools and original evidence. No automatic
approval change, data deletion or release rollback is authorized by this draft.

## Result

B implementation is present on main. Type checking, build, 299 MCP tests and
