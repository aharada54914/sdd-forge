## Problem Evidence

The evaluator at gate seq 853 measured something sharper than the parsing
bug it was hunting: **an implementation report that FAILS
`validate-implementation-report.sh` can still authorize an evaluator's
input set.**

Concretely, against the live tree at that moment:

```
$ bash plugins/sdd-implementation/scripts/validate-implementation-report.sh \
       reports/implementation/agent-cost-context-isolation/T-006.md
IMPLEMENTATION_REPORT_FIELD: missing or invalid Model      (exit 1)

$ bash plugins/sdd-quality-loop/scripts/validate-review-context-set.sh \
       <the live seq-0853 manifest> .
REVIEW_CONTEXT_OK ...                                       (exit 0)
```

`validate-review-context-set.sh` re-implements the declaration grammar it
needs (`evaluator_output_is_declared`, `implementation_report_legacy_declares`)
and reads the report directly. It never asks whether the report is valid.
So every rule the report validator enforces — row shape, hash format,
canonical paths, duplicate sections, duplicate paths, isolation-mode
consistency — is advisory from the authorization boundary's point of view.

This is what turned WFI-049's parsing divergence from a formatting defect
into a live bypass: the strict component's opinion never had to be
consulted. It also means any FUTURE divergence, in any of those rules, has
the same consequence.

Scope note: 66 of 228 shipped reports currently fail the report validator
on the `- Model:` requirement alone (a rule that postdates them), so this
is not a hypothetical population — a large fraction of the corpus is in the
"invalid yet authorizing" state today.

## Why-Why Analysis

1. Why can an invalid report authorize? The boundary never runs the report
   validator.
2. Why not? The boundary re-implements only the grammar it needs, which is
   cheaper and avoids a process dependency.
3. Why is that the wrong trade here? The two components are the VALIDATOR
   and the GRANTER of the same document. Independent re-implementation of a
   security-relevant grammar guarantees eventual divergence, and divergence
   at that pair is a bypass by construction (WFI-049 is one instance).
4. Why was it never noticed? Nothing tests the pair together: no fixture
   drives one report through both components and asserts a consistent
   verdict.
5. Root gap: there is no stated contract about whether report validity is a
   precondition of authorization, so neither component is wrong on its own
   terms.

## Root Cause Hypothesis

Report validity and input authorization are enforced by two components
with no stated ordering between them, so authorization proceeds on a
document no one has confirmed is valid.

## Proposed Change

The maintainer must choose the ordering; both options are defensible and
they differ in blast radius.

**Option A — make validity a precondition (fail closed).** The boundary
invokes `validate-implementation-report.sh` on the report it is about to
read and refuses to authorize when it fails. Strongest, and it makes every
existing report rule load-bearing for free. Cost: the 66 corpus reports
that fail on `- Model:` would stop authorizing, so it needs either a
grandfather (validate only reports that declare `implementation-report/v2`,
or only rules that predate the report) or a corpus repair pass first.

**Option B — single source of grammar (fail consistent).** The boundary
stops re-implementing the declaration grammar and calls one shared parser
that both components use, so divergence becomes impossible even though
validity stays independent. Weaker than A — an invalid report can still
authorize — but it eliminates the WFI-049 class specifically and costs no
corpus migration.

In either case: add a paired fixture that drives one report through both
components and asserts the verdicts are consistent, so the pair is tested
as a pair for the first time.

## Expected Effect

Under A, an invalid report cannot authorize anything. Under B, the two
components cannot disagree about what a declaration is. Under either, the
next grammar divergence is caught by the paired fixture rather than by an
evaluator two months later.

## Verification Metric

A report that fails the report validator is refused by the boundary
(Option A), or a grammar mutation applied to one component changes both
components' behavior identically (Option B). The paired fixture fails when
the two verdicts diverge.

## Verification Plan

Build a small matrix of reports — valid, invalid on each report-validator
rule class, and valid-but-padded — and assert the paired verdict for each.
For Option A, first measure the corpus impact exactly (which reports stop
authorizing, and why) and record it before applying, since that number is
the whole cost of the option.

## Rollback-Plan

Option A: remove the precondition call; authorization returns to today's
behavior with no data migration. Option B: revert the shared-parser
extraction; both components return to their own copies.

## Result

**Maintainer decision, 2026-08-26: Option A, scoped.** ("A の schema 限定版で
よい".) Implemented and verified on branch `staging/cycle2-regate`; staged for
human apply at
`docs/ci-staging/wfi-050-validity-precedes-authorization.patch` because all
three files became guard-protected mid-session (see the note at the end).

**Scoping, decided by measurement rather than by the option text.** The
maintainer approved keying the grandfather set on the schema version. That
does not work here and was rejected on data: **118 of the 147 v2-declaring
reports fail the validator today**, so a schema-keyed rule would have blocked
almost every gate. The corpus **ratchet baseline** is used instead. It is the
right list for three reasons: it already exists, it is machine-checked by
`tests/implementation-report-corpus.tests.sh`, and rule (b) forbids ADDING
entries, so the exemption set can only shrink toward zero. Same intent --
fail-closed forward, grandfathered backward, monotone -- with a grandfather
set that works.

**Two prerequisite defects surfaced while measuring, both fixed in the same
patch.** Making validity load-bearing immediately exposed documents that were
failing the validator for reasons that were not their fault:

1. The strict-branch indicators were tested with an unanchored `in text`
   substring scan, so a review report that merely CITED a validator diagnostic
   inside backticks was promoted to the strict branch and failed as a
   malformed v2 report. Anchored to line starts.
2. The indicators alone promoted documents that are not implementation reports
   at all -- an independent review report shares the section name
   `## Test Evidence` without being one. Promotion now also requires the
   document's own title to declare the kind. Sound discriminator, measured:
   all 145 schema-carrying reports claim it in their title, with no
   counterexample.

Both are the WFI-049 mention-versus-declaration confusion, one layer up.

**Cost, measured after the fixes: exactly ONE shipped report fails outside the
grandfather set** --
`reports/implementation/epic-191-a3-path-ownership/T-005-remedy-1.md`, whose
schema line reads `Report Schema: implementation-report/v2 (remedy addendum)`.
That is a genuine malformation under the ratified grammar, and it will block
epic-191's next T-005 gate until its owner either corrects the line or defines
an addendum schema. Stated rather than papered over: this report is referenced
by four historical review-context manifests, so editing it changes bytes those
manifests pin, and the fix belongs to that feature's owner, not here.

**Verified.**

- Both runtimes carry the rule and agree. Driving the seq-856 manifest through
  the sh boundary and the PowerShell twin in a disposable clone: an invalid
  report yields `REVIEW_CONTEXT_REPORT: implementation report is rejected by
  the report validator and is not grandfathered on the corpus ratchet
  baseline` on BOTH; restoring the report returns BOTH to the prior
  hash-mismatch diagnostic. Shipping this on one runtime only would have made
  the weaker runtime the bypass.
- Corpus after the patch: 228 reports, 124 failing, 129 baseline entries, **1
  failure outside the baseline**, and **0 baseline entries that now pass** (so
  no ratchet churn). The ratchet suite reports 203 checked, 203 ok, 0 failing.
- `git apply --check` on the staged patch: OK. All three files parse
  (`bash -n` twice, PowerShell `Parser::ParseFile` once).

**Option B is not abandoned.** A shared parser still eliminates the divergence
class permanently and should follow, but A is the one that makes the strict
component's refusal actually mean something, so it goes first.

**Note on the guard.** Between the start of this work and its completion, the
installed `sdd-quality-loop` guard moved 1.15.0 -> 1.16.0 and its protected
list grew from 80 to 111 suffixes, newly covering all three files this WFI
touches (and 28 others -- the CI-executed scripts WFI-037 reported as
unprotected). Earlier edits in this session predate that change; everything
from here goes through the staged-patch route.
