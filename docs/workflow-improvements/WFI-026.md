## Root Cause Hypothesis

The quality verification gate's Done decision is self-certified. Every control
the policy lists as required before that decision is selected, executed and
reported by the same agent whose verdict it constrains, and the artifact that
publishes the decision — the task's Status line — is an ordinary text edit
carrying no precondition. Omitting a control therefore emits no signal: the
report simply does not mention it, and nothing downstream compares a report
against the set of controls it was supposed to run.

Two secondary properties explain why these three controls in particular were the
ones dropped. The two that did run — the risk-tier check and the placeholder scan
(`T-004.md:73-74` shows the same pair running there) — need no artifact the gate
itself must have produced first. Of the three that did not run, two consume the
default-FAIL contract that the gate creates in an earlier step; once that step is
skipped they have no target, and "there is nothing to check" is resolved as a skip
rather than as a failure, because nothing asserts that the target must exist. The
third, `check-task-state`, has an independent target and would have failed loudly
— and it is the one control absent from the list of Done conditions the gate reads
when it decides, appearing only as a step in an ordered procedure.

This is not an instruction-coverage gap. The obligation is already stated three
times, in the two documents the gate is required to read: the ordered step list
(`SKILL.md:66-74`), the Done-decision conditions (`SKILL.md:223-231`), and the
policy's own "Before any `Done` decision, run …"
(`deterministic-check-policy.md:25-28`). Three consecutive gates read those and
produced zero runs. The failing mechanism is prose addressed to the agent that
benefits from skipping it; the missing mechanism is a precondition attached to the
transition itself, which is the shape the same enforcement chain already uses for
four approval fields and for one review-status field.

## Proposed Change

| Target File | Change Description |
|---|---|
| `plugins/sdd-quality-loop/scripts/sdd-hook-guard.py` | Add a fifth transition rule, `done_status_increases`, in the shape of the four existing `*_increases` functions. It fires only on a targeted file tool whose path ends `tasks.md`, only when the write nets an increase in column-0 `Status: Done` lines against the on-disk content (Edit paths compare `new_string` to `old_string`; Write paths compare against the file), and only when the corresponding `specs/<feature>/verification/<task-id>.contract.json` and `.evidence.json` do not both exist with a `task_id` matching the task section being flipped. Resolve the repository root by the multi-root order `impl_review_status_passed_increases` already uses (`CLAUDE_PROJECT_DIR`, then the git root discovered upward from the edited path, then CWD), so the worktree false-denial WFI-016 fixed is not reintroduced. The predicate is deliberately the cheap necessary condition — existence plus `task_id` match, mirroring `check-task-state.sh:108,118,129-134` — not a full invocation of the deterministic script. The refusal message names the two missing paths and directs the operator to the contract-creation step. |
| `plugins/sdd-quality-loop/scripts/sdd-hook-guard.js` | The identical rule; the four twins are parity-locked. |
| `plugins/sdd-quality-loop/scripts/sdd-hook-guard.ps1` | The identical rule, with the two-layer case-sensitivity sweep AGENTS.md:180-194 requires of any `.sh`→`.ps1` parity port, including a mis-cased negative fixture per layer. |
| `plugins/sdd-quality-loop/scripts/sdd-hook-guard.sh` | The identical rule. |
| `tests/guard-parity.tests.sh` | Regression cases proving the four twins agree: (a) a flip to the Done status with neither artifact present is refused; (b) a flip with both artifacts present and matching `task_id` is allowed; (c) an edit that preserves or removes an existing Done line is allowed (net-zero / net-decrease); (d) a flip performed from a git worktree whose CWD is outside the repository is still evaluated against the correct root — the WFI-016 regression; (e) the suite's own source does not become a false-positive target of any detection gate this repository runs, per AGENTS.md:196-203. |
| `plugins/sdd-quality-loop/skills/quality-gate/SKILL.md` | In the Done-decision conditions (`:219-240`), add `check-task-state` passes — no task in the file is `Done` without its contract and evidence bundle — as a named condition. This is not a restatement: that list currently omits the one script whose Done branch is the violated invariant, and names it only as the enforcer of a different, critical-tier-only condition. |

**Options considered, and why this one.**

*A — strengthen the checklist in the gate's skill definition.* Cost is near zero
and the change is uncontroversial, which is exactly why it should be suspected:
the obligation is already written three times in the two documents the gate must
read (`SKILL.md:66-74`, `SKILL.md:223-231`,
`deterministic-check-policy.md:25-28`), and the observed compliance is 0 of 3. A
fourth restatement is the same instrument already tested at this sample size.
Rejected as a primary fix; the one row above is included only because it adds a
missing condition rather than repeating a present one.

*B — a hard precondition inside the skill ("refuse to proceed to the Done
decision unless the contract exists").* This reads stronger than A but runs on the
same substrate: it is instruction text evaluated by the agent it constrains, in a
file that already has a Preconditions section (`SKILL.md:15-20`) honoured by the
same discretion. It is distinguishable from A by emphasis, not by mechanism, and
inherits the same 0-of-3 record. Its one real advantage — placing the stop at
contract-creation time, upstream of all three failures — is worth capturing, and
the guard rule captures it: refusing the Done write for a task with no contract
makes the skipped creation step surface at the moment it matters.

*C — a post-Done verification hook.* This is the option the evidence most
directly rules out as sufficient, because it has already been run by accident. A
post-hoc sweep is precisely what `check-task-state` performs when any later gate
in the same feature invokes it, and that is how the debt was found
(`T-004.md:73-79`). It did not prevent three bad Done decisions, it did not
shorten the two-day window, and when it did fire it was correctly classified as
out-of-scope inherited debt and left in place (`T-004.md:193-199`). Detection
after publication also arrives after the Status commit, after the downstream
retrospective trigger (`SKILL.md:246-263`), and after every subsequent task in the
feature inherits a red required check. Post-Done detection is a useful backstop
and already exists; it is not the missing control.

*The chosen shape — a precondition attached to the transition.* Only this option
removes the failure mode rather than the failure: a control the agent must choose
to run can be omitted silently, whereas a write that is refused cannot. The shape
is not novel here — `impl_review_status_passed_increases` (`:182-221`) already
refuses a status write unless a required artifact exists on disk, and the
Done↔evidence-bundle relation is the same relation with an existing, executable
predicate.

**Residual gap, stated rather than papered over.** Hooks are declared an
auxiliary line, not the final one (`deterministic-check-policy.md:5-8,130-132`),
and this workflow demonstrably runs stages on hosts where they do not fire: the
implementer for T-001 and T-002 is recorded as running "outside hook enforcement"
(`T-001.md:32`, `T-002.md:28`), and the policy records that plugin `PreToolUse`
hooks may not fire inside Copilot subagents (`:119-120`). On such a host the
backstop remains `check-task-state`, which fails closed for every later task in
the same file — which is why the skill row above matters more than its size
suggests: it converts that script from a step in a procedure into a condition of
the decision, in the one list a gate agent consults when deciding. Neither half is
sufficient alone; the pair covers hook-bearing and hook-less hosts respectively.

**Deliberately NOT proposed.** Invoking `check-task-state.sh` from inside the
hook. It shells out to `check-evidence-bundle.sh` once per Done task
(`check-task-state.sh:112`), which is unacceptable latency in a `PreToolUse` path
and would make every tasks.md edit depend on the validity of unrelated tasks'
bundles. The division of labour is deliberate: the hook asserts the cheap
necessary condition, the deterministic script remains the sufficient one, and the
policy's stated architecture is preserved.

## Expected Effect

A task cannot be published as `Done` by an agent on a hook-bearing host while the
verification contract and evidence bundle the quality verification gate is
required to have produced are absent. The three artifacts that were missing here
would each have refused their own Status write, and the refusal would have named
the missing paths at the moment the gate tried to publish the decision, rather
than two days and three decisions later.

Concretely, against this feature's own history: 3 of 3 Done decisions published
without their required artifacts becomes 0; the T-004 gate would have had no
inherited debt to characterise and hand forward; and no backfill of six artifacts
across five commits would have been needed.

5. **Live horizon.** For each of the next 10 `Done` decisions, record in the

   of the Status write. Ten consecutive decisions at zero absences → Verified. Any
   absence → diagnose whether the write bypassed the guard (hook-less host, in
   which case the skill row is the control under test) or the guard failed to fire
   (a defect in this change).

   lands, confirm the quality-gate report names `check-task-state` and its result.
   A report that still omits it means the added Done-decision condition is being
   read no more than the three statements that preceded it, and the instruction
