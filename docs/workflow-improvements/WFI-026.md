## Problem Evidence

The persisted-state gate rejects any feature whose task plan is partly
advanced. Measured directly on 2026-08-17/18 across three features that
were each mid-implementation:

| Feature | Task statuses present | Gate result |
|---|---|---|
| epic-193-a5-capability-resolver | Done ×2, Implementation Complete ×1, Planned ×7 | `stage-provenance: task plan hash is stale` |
| epic-194-a6-lite-integration | Done ×1, Implementation Complete ×1, Blocked ×2 | same diagnostic |
| epic-195-a7-compatibility | Done ×3, Implementation Complete ×2, Planned ×7 | same diagnostic |

The decisive measurement is on epic-193. Reverting **only** the single
`Status:` line the implementation had just advanced — no other byte
changed — flips the gate back to `workflow-state: ok`:

```
with Implementation Complete:
  workflow-state: epic-193-a5-capability-resolver: stage-provenance: task plan hash is stale
with Planned (reverted):
  workflow-state: ok
```

So the diagnostic does not report drifted *content*. It reports that a
task moved, which is the one thing every implementation run must do.

epic-194's own task-review contract already records the consequence in
its `human_edit_summary`: a re-bind "will be needed once T-001/T-002/
T-003 progress", filed as a known accepted limitation. That is the
workaround being paid for today.

## Root Cause Hypothesis

The reviewed-hash comparison for the task stage normalizes a task plan
before hashing it, so that lifecycle fields may advance without
invalidating the review that approved the plan's *content*. The
normalization recognizes a task plan in which every task shares one
status — the shape a plan has at the moment task-review signs it off,
and again once the whole feature is finished — but not the mixed shape a
plan necessarily has while it is being implemented.

Because the check is applied per feature rather than per task, the first
task to advance puts the whole feature into a state the normalizer
cannot express, and it stays there until every task reaches the same
status. The gate therefore fails for the entire duration of
implementation, which is exactly the window in which its drift-detection
value is highest.

Two secondary effects follow, both observed:

- The failure is indistinguishable from a genuine plan-content drift, so
  a real drift arriving mid-implementation would be masked by the noise.
- Implementers route around it. Three separate implementation reports in
  this wave disclose the failure as "pre-existing / out of scope", which
  is accurate but means no run in this wave was gated on the check at
  all.

## Proposed Change

| Target File | Change Description |
|---|---|
| AGENTS.md | Record that the persisted-state task-stage check is expected to fail while a feature is mid-implementation, that this is a known tool limitation rather than plan drift, and that implementers must disclose it in the implementation report rather than editing task-review artifacts to silence it — until the plugin-side fix lands. |
| specs/ task templates | Note in the task-plan template's header guidance that advancing a single task's status is expected to trip the feature-scoped provenance check, so future task authors do not record it as a task-specific blocker. |

The plugin-side correction this WFI argues for — making the task-stage
reviewed-hash normalization tolerate a task plan whose lifecycle fields
differ per task, so the check verifies plan *content* rather than plan
*uniformity* — belongs to the plugin repository and is described here in
generic workflow terms only, per the category guide. It must preserve
detection of real content drift: the normalization should continue to
hash everything except the per-task lifecycle fields, so a changed
requirement, scope line, or done-when item still invalidates the review.

## Expected Effect

The persisted-state gate becomes usable during implementation instead of
only at the two endpoints of a feature's life. Concretely: features with
a mixed task plan stop emitting `task plan hash is stale`, so the
diagnostic regains its meaning as a drift signal, and implementation
reports stop carrying a disclosed-but-unactionable gate failure.

## Verification Plan

After the change lands, the next implementation run in any feature with
a mixed task plan runs `check-workflow-state` and records the result in
its implementation report. The WFI is verified only when both halves
hold:

1. **No false failure**: a run that advances exactly one task's status,
   changing nothing else, leaves the gate green.
2. **Detection preserved (non-vacuity)**: in the same run, a deliberate
   mutation to plan *content* — edit one task's Requirements or a
   Done-When line in a scratch copy — must still produce
   `task plan hash is stale`. A change that only silences the check
   without this second half is a regression, not a fix, and must be
   classified Rejected.

The retrospective's gate-metrics table supplies both counts.

## Rollback-Plan

This WFI's project-side changes are the AGENTS.md paragraph and the
task-template note listed under Proposed Change. Revert the commit whose
message contains `WFI-026` to remove both; no other file is touched and
no gate behavior changes on the project side. The plugin-side change, if
and when it is made in the plugin repository, carries its own rollback
in that repository and is not covered by this plan.

## Result

Blocked as obsolete on 2026-09-02; status remains `Approved`.

The proposal asks `AGENTS.md` and the task template to document mixed task
statuses as an expected provenance failure until a plugin fix lands. That
premise is no longer true in this tree: the post-implementation provenance
rule now explicitly treats lifecycle-valid mixed statuses (`Planned`,
`In Progress`, `Blocked`, `Implementation Complete`, `Done`) as valid, and the
workflow-state suite contains mixed-state coverage. Adding the proposed warning
would therefore create false guidance. The WFI does not authorize replacing its
temporary documentation proposal with a different retrospective amendment, so
no implementation was improvised.
