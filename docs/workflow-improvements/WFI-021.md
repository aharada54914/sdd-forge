## Problem Evidence

All facts reproduced 2026-08-02 on `feature/epic-136-phase4` at `57261b17`.

1. `plugins/sdd-quality-loop/scripts/check-workflow-state.sh:9-12` —
   `diagnostic()` prints one line and `exit 1`s. Only the FIRST failing check
   in a run is ever visible, and this holds across independent features: the
   script iterates the feature registry, so a failure in the first feature
   aborts the sweep over every later one.

2. `.github/workflows/test.yml` — the `test` job is a single job of 65 steps
   on a 3-OS matrix. The two workflow-state validation steps are steps 5 and
   6; 59 steps run after them, including every verification suite. A non-zero
   exit at step 6 means none of the 59 ever runs.

3. Serial-discovery record, visible in this branch's own commit chain. Three
   defects with no causal relation to one another surfaced strictly one at a
   time, each invisible until its predecessor was fixed:
   - `6e584411` repaired the re-review hash comparison; only then did the
     `epic-136-phase3` review legs progress.
   - `c7cf9e2e` completed `epic-136-phase3`'s three legs; only then did the
     sweep reach `epic-136-phase4-mcp`.
   - `39d12be5` repaired THAT feature's recorded evidence shape — a different
     feature, authored by an earlier wave, causally unrelated to the first
     item; its commit message records "workflow-state now ok". Only then did
     integration advance past the validator to the verification suites.
   - `57261b17` repaired a fixture count drift introduced by `95479bb2` on
     2026-07-31 and found on 2026-08-02.

4. Cost, measured: `test (ubuntu-latest)` on the integration run for
   `57261b17` took 21m23s. Each discovery above cost at least one such round
   trip, and the item in 3(d) survived on merged history for two days.

5. The two masking layers are independent. A validator that reported every
   diagnostic in one pass would still exit non-zero and abort the job before
   step 7, so 3(d) needed BOTH the validator to pass AND the job to advance.

## Root Cause Hypothesis

Two compounding fail-fast decisions. The repository-wide state validator
stops at its first diagnostic, which is correct for checks that depend on an
earlier check's invariant within one feature but is not correct across
independent features, where nothing later depends on anything earlier.
Separately, continuous integration runs that validator as an early step of
the same job that holds every verification suite, so a conformance failure in
specification documents suppresses 59 unrelated steps. Together they convert
an unbounded set of independent defects into a strictly serial discovery
queue whose period is one full integration round trip.

## Proposed Change

| Target File | Change Description |
|---|---|
| `plugins/sdd-quality-loop/scripts/check-workflow-state.sh` | Accumulate diagnostics across independent feature iterations instead of exiting at the first one. Emit every accumulated diagnostic, then exit non-zero if any fired. The short-circuit WITHIN a single feature is retained wherever a later check presupposes an earlier one's invariant, so no check is ever evaluated against state an earlier check already rejected. Diagnostic text, per-feature ordering, and severity are unchanged, so the file's API-stability guarantee continues to hold. |
| `plugins/sdd-quality-loop/scripts/check-workflow-state.ps1` | The identical change in the PowerShell twin, so both lanes report the same accumulated set for the same input. |
| `tests/workflow-state.tests.sh` / `.ps1` | A regression fixture with two independently broken features asserting BOTH diagnostics appear in one run, plus an anti-vacuity assertion that the second diagnostic is absent under the pre-change behavior. The suite is already registered in continuous integration, so no protected file changes. |

Out of scope, deliberately: splitting the integration job so that the
validator and the verification suites cannot suppress each other. That
target is a protected file whose human-applied copy is already pending from
an earlier phase, and stacking a second pending application on it would
couple two unrelated approvals. Recorded here so the remaining half of the
friction is not mistaken for fixed — see Expected Effect.

## Expected Effect

One validator run reports every independent feature's diagnostics instead of
one, so a repository with N independently broken features is repaired in one
cycle rather than N. Applied to the record in Problem Evidence 3, the second
and third items would have been visible in the first run rather than after
two intervening round trips of roughly twenty minutes each.

Explicitly NOT addressed: the fourth item in Problem Evidence 3 required the
integration job to advance past the validator, which this change does not
alter. Half the friction remains until the job-structure change lands.

Deterministic check count: increases (regression fixtures added per twin,
none removed).

## Verification Plan

(1) Construct a fixture repository with two independently broken features.
Assert under the pre-change behavior that only the first diagnostic appears,
then under the post-change behavior that both do. Both assertions live in the
regression fixture, so non-vacuity is enforced at commit time rather than
claimed in prose.
(2) Run both twins over the same fixture and confirm identical accumulated
output, so the lanes have not diverged.
(3) Run the validator against the real repository and confirm it still exits
0 with unchanged output on a clean tree.
(4) At the next completed feature's retrospective, confirm no defect required
a second full round trip solely because an unrelated feature's diagnostic
masked it.
