## Problem Evidence

`check-workflow-state` fails a feature's stage-provenance check on any branch
that merges `main` without already carrying that feature's review evidence.
Neither side is broken on its own; the failure is created by the merge.

Measured 2026-08-24 on `chore/retro-epic-192` (PR #315):

| Tree | `check-workflow-state` |
|---|---|
| `origin/main` (`13febcce`) | `ok` |
| `origin/chore/retro-epic-192` (`6343e65e`), unmerged | `ok` |
| the two merged | `sdd-domain-concept-contract: stage-provenance: task reviewer manifest input hash is stale` |

Both readings were taken in the same worktree, because an earlier attempt
measured `main` in a different one and that is not a comparison.

### The failing entry, and why the pin moves

The contract is
`reports/task-review/sdd-domain-concept-contract/attempt-1/round-2/task-review-contract.json`.
Two of its manifest entries do not match the working tree; one is exempt and
one is the failure:

| Manifest entry | Bound | Live | Treatment |
|---|---|---|---|
| `specs/sdd-domain-concept-contract/tasks.md` | `a3914bed…` | `6bfc1b3f…` | skipped — `check-workflow-state.sh:567-569` exempts `specs/$feature/*` |
| `plugins/sdd-quality-loop/references/risk-classification-policy.md` | `21b0a61d…` | `7adb73e4…` | `plugins_hash_matches` → **fails** |

`plugins_hash_matches` falls back to comparing the plugins file's content at a
*pin commit*, and `plugins_pin_commit` defines that pin as:

```sh
git -C "$SCRIPT_ROOT" log -1 --format='%H' -- "$relative"
```

— the last commit that touched **the contract file**. Measured:

| Tree | pin resolves to | policy hash there | verdict |
|---|---|---|---|
| `main` | `a367dda1` — the commit that created the contract | `21b0a61d…` | matches the bound hash |
| merged | **the merge commit itself** | `7adb73e4…` | does not |

The merge commit is credited with touching the contract because
`chore/retro-epic-192` does not contain `sdd-domain-concept-contract` at all.
Relative to that parent the merge *adds* the file, so `git log -1 -- <path>`
stops there. At the merge commit the plugins file is at its current content,
not the content the contract was bound against — so the fallback compares
against the wrong version and the gate reports a stale hash for evidence that
never changed.

### Blast radius

`reports/{task,impl,spec}-review/` holds **301** contract files. **136 of
them, across 42 distinct features**, carry at least one `plugins/` manifest
entry and are therefore subject to this resolution. Any branch that lacks a
given feature's evidence and merges `main` fails that feature's check — which
is the normal state of every long-lived branch, since features land on `main`
after the branch was cut.

### Cost

The diagnosis is expensive out of proportion to the defect. The gate names the
feature and says "hash is stale", which points at the evidence — and the
evidence is byte-identical to `main`'s. The merged tree and `main` differ
nowhere inside the failing feature; only the commit graph differs, and nothing
in the message suggests that. Reaching the pin took reading three helper
functions and comparing `git log -1` output between two trees.

## Why-Why Analysis

| # | Why (question) | Because (answer) | Evidence |
|---|---|---|---|
| 1 | Why does a feature's provenance check fail after a merge that changed none of its files? | The `plugins/` manifest entry falls through to the pin fallback, and the fallback resolves a different commit after the merge. | The two pin measurements above; the merged tree is byte-identical to `main` inside the feature |
| 2 | Why does the pin resolve differently? | `plugins_pin_commit` is `git log -1 -- <contract>`, and a merge that introduces the contract relative to one parent is credited with touching it. | `plugins_pin_commit` in `check-workflow-state.sh`; pin = the merge commit on the merged tree |
| 3 | Why does "last commit that touched the contract" stand in for "the commit the contract was bound at"? | It is a proxy that holds while the contract file is only ever added once and never re-touched — true on a linear history, false the moment the contract arrives through a merge. | The same pin is correct on `main` and wrong one merge later, with no change to the contract's content |
| 4 | Why was a graph-order-dependent proxy acceptable? | The fallback was added (WFI-024) to stop a shared plugins file's edit from staling every past feature. It was designed against content drift; nothing in it was tested against a history shape where the contract's own commit is not reachable as its last toucher. | The fallback's helpers carry no merge-shape case |

The chain ends at one controllable mechanism: the pin is derived from history
order rather than from the contract itself.

## Root Cause Hypothesis

The fallback needs the commit at which the contract's recorded hashes were
true. It infers that from the commit graph, and the inference is only valid on
a history where the contract file was added once and never re-attributed.

A merge re-attributes it. Git's `log -1 -- <path>` reports the merge commit
whenever the merge's result for that path differs from *some* parent, which is
exactly what happens when the other branch does not have the feature. The
proxy then names a commit at which the plugins file has moved on, and the
comparison is against a version the contract never claimed.

The contract already carries the information the fallback is trying to
reconstruct — the hash it expects. What it lacks is a statement of *when* that
hash was true, and the gate guesses instead of reading it.

## Proposed Change

| Target File | Change Description |
|---|---|
| `plugins/sdd-quality-loop/scripts/check-workflow-state.{sh,ps1}` | Resolve the pin to the commit that **added** the contract rather than the one that last touched it: `git log --diff-filter=A --format=%H -- <contract> \| tail -1`. That commit is stable under merges, because adding is attributed to the commit that introduced the content, not to a merge that carries it across. Keep the existing `merge-base --is-ancestor` reachability guard so a pin outside this history still fails closed. |
| `plugins/sdd-quality-loop/scripts/check-workflow-state.{sh,ps1}` | When the add-commit cannot be resolved (shallow clone, or a contract that was moved rather than added), walk the contract's own history newest-first and accept the first commit at which the plugins file's hash equals the bound value, bounded to the contract's commits so the search cannot wander. If no commit matches, fail — the current behaviour for an unresolvable pin. |
| `plugins/sdd-quality-loop/scripts/check-workflow-state.{sh,ps1}` | When the fallback rejects, say which pin it used and what it found there. The present message names only the feature and "hash is stale", which sent this investigation to the evidence files, where nothing was wrong. |
| `tests/workflow-state.tests.sh` and its ps1 twin | A fixture that reproduces the merge shape: a repository with a feature's contract on one branch, a second branch without it, and a merge. Assert the gate passes on each branch alone **and** on the merge. The three-way assertion is the point — a fixture that only checks the merged tree would pass on a gate that accepts everything. |

**Non-decreasing.** The change narrows nothing and admits nothing new by
content: the bound hash must still equal the plugins file's hash at a commit in
this history. It corrects *which* commit that is. A contract whose hash matches
no commit in its own history still fails.

**Not proposed.** Removing the `plugins/` exemption and requiring exact
working-tree equality. That is what WFI-024 fixed: a one-byte edit to a shared
plugins file would stale all 136 contracts at once. The exemption is right; its
pin resolution is not.

**Also not proposed.** `--first-parent`. It happens to give the right answer
for this case and the wrong one when the contract genuinely arrives on a side
branch, which is how most features land here.

## Expected Effect

A branch that merges `main` stops failing provenance for features it never
touched. Concretely, PR #315's merge — currently red for
`sdd-domain-concept-contract` — passes, without any change to that feature's
evidence.

## Verification Plan

1. Reproduce the three-way reading — branch alone, `main` alone, merged — in a
   single worktree, and record the pin commit and the hash found there for
   each. Two of the three readings are `ok`, which is what makes this a merge
   artifact rather than a stale contract.
2. Assert the defect before the change: the merged fixture fails with the stale
   message, and the pin equals the merge commit.
3. Assert the fix: the same fixture passes, and the pin equals the contract's
   add-commit.
4. Assert the negative control in the same fixture: a contract whose bound hash
   matches nowhere still fails. Run it before the fix as well, so it is known
   to fail for the right reason rather than incidentally.
5. Assert WFI-024's property has not regressed: edit a shared plugins file in
   the fixture and confirm past features still pass.
6. Twin parity: the sh and ps1 gates must agree per case, with a `pwsh`
   capability probe and a visible `skip -` line where the shell is absent.
7. Mutation: revert the pin change alone and confirm the merged fixture goes
   back to failing; revert the diagnostic change alone and confirm the message
   loses the pin, so the two are known to be independently exercised.

## Rollback-Plan

Revert the commit whose message contains `WFI-051`. The gate returns to
resolving the pin with `git log -1`, which is today's behaviour; the added
fixtures are removed by the same revert.

Nothing on disk needs migrating: no contract, manifest or recorded hash
changes. The change alters only which commit the gate reads when a recorded
hash does not match the working tree.

If the add-commit resolution proves unavailable in a context that matters
(shallow CI clones being the likely one), the proportionate retreat is to keep
the diagnostic improvement and the history-walk fallback, and drop the
add-commit lookup — the walk alone fixes the merge case, just with more work
per rejected entry.
