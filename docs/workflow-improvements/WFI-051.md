## Problem Evidence

`check-workflow-state` reports

```
sdd-domain-concept-contract: stage-provenance: task reviewer manifest input hash is stale
```

for evidence whose hash is not stale. The message names the wrong condition,
and it named it convincingly enough to send this investigation down a wrong
path and produce a wrong WFI.

### What actually happens

Measured 2026-08-25 on `chore/retro-epic-192` merging `origin/main`:

| Tree | `check-workflow-state` |
|---|---|
| `origin/main` alone | `ok` |
| `origin/chore/retro-epic-192` alone | `ok` |
| the merge, **uncommitted** | fails with the message above |
| the same merge, **committed** | `ok` |

The last row settles it. Nothing about the content differs between the two
merge rows — only whether `HEAD` has moved.

During an uncommitted merge the newly-arrived evidence is in the working tree
but has no history at `HEAD`:

```
$ git log -1 --format=%H -- reports/task-review/sdd-domain-concept-contract/attempt-1/round-2/task-review-contract.json
                     (empty)
$ git cat-file -e HEAD:<same path>
                     no
```

`plugins_pin_commit` returns `git log`'s exit status, and `git log` exits 0 when
it prints nothing. So the pin is the empty string, not an error.
`plugins_hash_at_pin` rejects it at `[[ -n "$pin" ]] || return 1`,
`plugins_hash_matches` returns 1, and the caller emits its only rejection
message — "hash is stale".

The condition is "this file has no history at this HEAD". The message says the
recorded hash is wrong. Those are different problems with different fixes, and
the message points at the one that is not happening.

### The cost, measured on this investigation

The first version of this WFI claimed the pin resolved to *the merge commit*
and that the plugins file had moved on there. That reading came from:

```sh
pin_merged=$(git log -1 --format='%H' HEAD -- "$C")
echo "  $pin_merged $(git log -1 --format='%s' $pin_merged | cut -c1-50)"
```

`$pin_merged` was empty, so the second `git log -1` ran with no revision
argument and printed `HEAD`'s subject — `Merge branch 'main' into
chore/retro-epic-192`. The output read as "the pin is the merge commit". It was
"the pin is nothing, and here is HEAD".

That produced a WFI with a false root cause, a false blast-radius figure (136
contracts across 42 features, which describes exposure to a mechanism that does
not exist), and a proposed change — resolving the pin with `--diff-filter=A` —
that was then measured and **does not fix anything**: on a branch where the
contract arrived through a merge, the add *is* the merge commit.

It also cost a merge. PR #315 was reported blocked by a structural gate defect;
it was not blocked at all. Committing the merge was sufficient.

The diagnostic is not the only thing at fault here — the misread `git log`
invocation is mine. But a message that names a plausible wrong cause is what
made the wrong cause worth pursuing.

### Re-measured against `claude/plugins-pin-stability` (2026-08-25)

A parallel session changed this same function today, for a different reason.
Checked rather than assumed:

| Their change | Effect on this WFI |
|---|---|
| `7464f601` — resolve the pin at the introducing commit (`--diff-filter=A`), and `[[ -n "$pins" ]] \|\| return 1` | Closes the empty-string half. `plugins_pin_commit` now fails at the point of discovery instead of returning `""`. That proposal row is withdrawn. |
| `42d920d8` — tolerate no-git for the calibration-doc fallback | Unrelated to this path. |
| `plugins_hash_matches` | **Unchanged** — still one boolean for every failure. |
| the caller | **Unchanged** — `manifest input hash is stale` appears at all three call sites, verbatim. |

So the defect this WFI is about survives their fix, and their fix makes it
slightly worse: `plugins_pin_commit` now also fails when a path has *more than
one* introducing commit (added, deleted, re-added), which is a deliberate
fail-closed choice and a correct one. It is also a **fourth** distinct
condition arriving at the same sentence. The count in `## Verification Metric`
is 4, not 3.

That is the argument for splitting the message rather than against it. Each
time this function is correctly hardened, another cause routes into a message
that names none of them.

## Why-Why Analysis

| # | Why (question) | Because (answer) | Evidence |
|---|---|---|---|
| 1 | Why did the gate report a stale hash for evidence that is not stale? | The pin was empty, and the only rejection path in `plugins_hash_matches` emits the stale-hash message. | `git log -1 -- <contract>` prints nothing mid-merge; committing the merge makes the same tree pass |
| 2 | Why was the pin empty? | The evidence file has no history at `HEAD` during an uncommitted merge — it exists only in the working tree and the index. | `git cat-file -e HEAD:<contract>` fails on the mid-merge tree |
| 3 | Why does an empty pin reach the comparison at all? | `plugins_pin_commit` returns `git log`'s exit status, and `git log` exits 0 when it matches nothing. "No history" is indistinguishable from "here is the pin" at the call site. | `plugins_pin_commit` ends in a bare `git log`; `plugins_hash_at_pin` is where emptiness is finally caught |
| 4 | Why does one message serve every failure on the path? | `plugins_hash_matches` collapses every failure into a single boolean, so the caller has one thing to say regardless of which check failed. | The caller's `diagnostic` line is the only rejection text on this path |

The chain ends at one controllable mechanism: the gate can tell *that* the
fallback failed and not *why*, so it reports the only reason it knows.

## Root Cause Hypothesis

`plugins_hash_matches` answers a yes/no question, and three genuinely different
conditions produce the same "no": the recorded hash disagrees with every
version in history, the evidence has no history to consult, and the pin is
unreachable from `HEAD`. Only the first is a stale hash. The other two are
statements about the repository the check is running in.

Collapsing them was reasonable while the caller only needed a verdict. It stops
being reasonable once the message is the entry point for a human diagnosis,
which is what happened here: the message was believed, and the investigation
went to the evidence files, where nothing was wrong.

## Proposed Change

| Target File | Change Description |
|---|---|
| `plugins/sdd-quality-loop/scripts/check-workflow-state.{sh,ps1}` | Distinguish the failure modes in `plugins_hash_matches` and report which one fired: **no history for this evidence at HEAD** (say so, and name an uncommitted merge as the usual cause), **pin not reachable from HEAD**, and **hash matches neither the working tree nor the pinned version** — the only one that is a stale hash. Return the reason to the caller so its `diagnostic` line carries it. |
| ~~`check-workflow-state.{sh,ps1}` — make `plugins_pin_commit` fail explicitly on empty output~~ | **Already done, independently.** `7464f601` on `claude/plugins-pin-stability` rewrote the function to resolve the pin at the introducing commit and added `[[ -n "$pins" ]] \|\| return 1`. The empty string no longer travels. Row withdrawn. |
| `tests/workflow-state.tests.sh` and its ps1 twin | Assert each of the three conditions produces its own message, in a fixture built for each: evidence with no history at HEAD (a staged-but-uncommitted file), a pin outside `HEAD`'s ancestry, and a genuinely wrong recorded hash. A single fixture cannot show the messages are distinguishable, which is the whole claim. |

**Withdrawn.** The first version's proposal — resolve the pin with
`git log --diff-filter=A` instead of `git log -1` — is withdrawn on
measurement. On a branch where the contract arrived through a merge, the add
commit *is* the merge commit, so it changes nothing. It was proposed without
being tested against the case it was written for.

**Not proposed.** Making an uncommitted merge pass. The gate's subject is the
committed state; a tree whose evidence has no provenance should fail. The
defect is that it fails while describing a different problem, not that it
fails.

## Expected Effect

A gate rejection on this path names the condition that fired. Concretely, the
mid-merge failure that produced this WFI would have said "no history at HEAD
for this evidence — commit the merge, or run this on a committed tree", and the
investigation that followed would not have happened.

## Verification Plan

1. Build three fixtures, one per condition, and record the message each
   produces before the change. All three must be the stale-hash message —
   that is the defect, and asserting it first means the fixtures are known to
   reach the path rather than failing somewhere earlier.
2. Assert after the change that each fixture produces its own message and that
   the stale-hash wording appears only for the wrong-hash fixture.
3. Assert the verdicts are unchanged in all three: still failures. A diagnostic
   change that also flipped a verdict would be caught here rather than in
   review.
4. Assert the mid-merge case end to end on a real merge: uncommitted fails with
   the no-history message, committed passes. This is the case that motivated the
   WFI and it should be exercised whole, not only through a synthetic fixture.
5. Twin parity: the sh and ps1 gates must produce equivalent messages per
   fixture, with a `pwsh` capability probe and a visible `skip -` line where the
   shell is absent.
6. Mutation: revert the message split alone and confirm all three fixtures
   collapse back to one message.

## Rollback-Plan

Revert the commit whose message contains `WFI-051`. The gate returns to a
single rejection message on this path, which is today's behaviour; the added
fixtures are removed by the same revert.

Nothing on disk needs migrating, and no verdict changes in either direction, so
a revert cannot strand any evidence or unblock anything that should be blocked.

If splitting the message proves awkward in the ps1 twin's control flow, the
proportionate retreat is to keep the explicit failure in `plugins_pin_commit`
and append the pin and the condition to the existing message rather than
restructuring the return value — worse to read, same information.
