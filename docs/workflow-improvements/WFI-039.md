## Problem Evidence

Six repository-wide files exist in **five places**, under **four different
freshness rules**, enforced by **four different test suites**, and none of the
rules is discoverable from the file being edited.

The six files are the guard invariants:
`plugins/sdd-quality-loop/references/guard-invariants.json`,
`plugins/sdd-quality-loop/scripts/generate-guard-invariants.py`, and the four
generated modules under `plugins/sdd-quality-loop/scripts/generated/`.

| Location | Freshness rule | Enforced by |
|---|---|---|
| live tree | — | — |
| `specs/epic-189-a1-project-context/human-copy/` | live must equal the pre-apply baseline **or** this bundle's staged candidate | `tests/guard-invariants-epic-a1.tests.sh:72` (TEST-022) |
| `specs/epic-190-a2-capability-registry/human-copy/` | staged must be **byte-identical** to live | `tests/phase2-guard-invariants.tests.sh:328` |
| `specs/epic-191-a3-path-ownership/human-copy/` | same as above | same |
| `specs/epic-190-a2-capability-registry/drafts/human-copy-candidate/` | candidate must be a **pure superset** of live | `tests/generate-gate-capabilities.tests.sh:283` |

A seventh file, `tests/guard-parity.tests.sh`, is snapshotted in
`specs/epic-136-phase2-gates/human-copy/` under the byte-identical rule, and
`plugins/sdd-review-loop/agents/task-reviewer-a.md` in
`specs/epic-159-pillar-c/human-copy/` under no enforced rule at all.

### Measured cost: three CI rounds to land one change

Applying WFI-030 and WFI-037 to the live tree edited three shared files. PR #305
then went red three times, each round revealing one more mirror that the
previous round's fix had not touched:

| Round | Failing jobs | Diagnostic | Mirror found |
|---|---|---|---|
| 1 | `test` ×3, `version-gates` ×3 | `live … is neither the pre-apply baseline nor the staged candidate` | `epic-189-a1` human-copy |
| 2 | `test` ×3 | `out of sync: tests/guard-parity.tests.sh` | `epic-136-phase2`, and by inspection `epic-190-a2` + `epic-191-a3` |
| 3 | `version-gates` ×2 | `candidate drops 31 live-protected entr(y/ies)` | `epic-190-a2` drafts candidate |

Each round cost a full CI cycle across three runners. Nothing in the first
failure hinted that three more mirrors existed; each was found only when the
previous fix stopped masking it.

Round 3 ended only because the search was replaced with a brute-force sweep:
hashing all 6,826 tracked files and matching them against the eight pre-change
digests. That found the complete mirror set in one pass — which is precisely the
capability the repository is missing.

### The editing side is silent, except for one self-referential hint

Nothing in `guard-invariants.json`, in `plugins/`, or in
`docs/workflow-improvements/` says that editing these files touches four frozen
snapshots. The one pointer that exists is inverted and partial: the array
`phase2_human_copy_targets` — which decides *which* files
`phase2-guard-invariants.tests.sh` requires to be byte-identical — lives **inside
`guard-invariants.json` itself**. The file carries the list of its own mirrors,
for one of the four rules, in a key whose name gives no indication of that role.

### This is a recurrence, not a first occurrence

`specs/epic-189-a1-project-context/human-copy/NOTES-epic-190-a2-refresh.md`
records the same situation on 2026-08-11: epic-190-a2's apply moved the shared
guard invariants, and the bundle had to be regenerated with a prose note
explaining why, because `MANIFEST.sha256` rejects `#` comment lines with exit 13.
This WFI's own work added a second such note. A third would be the point at which
the pattern stops being incidental.

### A blanket fix would have destroyed pending work

`specs/epic-159-pillar-c/human-copy/` stages `task-reviewer-a.md` at bytes that
differ from **main's** live file, not just from this branch's. That bundle is a
reviewed change still waiting for a human to apply it. A sync tool that treated
"staged ≠ live" as "stale" would have silently overwritten it — and CI would have
gone green, because no suite enforces byte-identity for that bundle.

The distinguishing test is *staged equals main's live*, and it is not obvious.
Any tooling built for this problem has to encode it, or the tooling becomes a
data-loss hazard aimed at exactly the work the staging flow exists to protect.

## Root Cause Hypothesis

The human-copy bundle was designed as a per-epic artifact: a snapshot of the
files one epic needs a human to apply, frozen so that what the human applies is
what was reviewed. That design is sound for files an epic owns.

It was then used for files no epic owns. The guard invariants are
repository-wide, so every epic that needed a human to apply a guard change took
its own snapshot of them. The snapshots accumulate, none retires, and each epic
wrote the freshness rule that suited its moment — byte-identity here, a
two-state baseline there, a superset relation in the drafts set. Nothing
reconciles them because nothing is aware of the others.

The result is a coupling with no owner. The bundles know about the shared file;
the shared file does not know about the bundles; and the only complete
enumeration of the relationship is the union of four test suites that were
written independently. Editing a shared file therefore has a cost proportional
to the number of epics that ever touched it, discoverable only by running CI
until it stops failing.

## Proposed Change

| Target File | Change Description |
|---|---|
| `tests/human-copy-mirror-freshness.tests.sh` and its `.ps1` twin (new) | One suite that enumerates every mirror of every repo-shared file from a single source and applies the right rule to each. Enumeration is derived, not hand-listed: walk `specs/*/human-copy/MANIFEST.sha256` and `specs/*/drafts/human-copy-candidate/`, and for each entry report which of the three rules applies and whether it holds. The failure message names every stale mirror at once, so one CI round is enough. Crucially it must distinguish *pending* bundles — staged bytes equal to `origin/main`'s live bytes means applied and therefore syncable; anything else is un-applied human work and must be reported as informational, never as stale. |
| `tests/run-all.sh` and `tests/run-all.ps1` | Register the new suite. |
| `scripts/sync-human-copy-mirrors.py` (new, project tooling — not a plugin script) | The remediation half of the same enumeration: given the files changed against `origin/main`, sync exactly the mirrors whose bundle is already applied, rewrite the affected `MANIFEST.sha256` lines in place, and refuse to touch a pending bundle. This is the tool whose absence cost three CI rounds; it exists in scratch form already and should be committed rather than rewritten next time. |
| `docs/contributor/` (a short reference, path to be chosen by the reviewer) | State the coupling from the editing side: which files are repo-shared, that editing one requires a mirror sync, and that the sync tool must be run before pushing. Today this knowledge exists only in two refresh notes filed inside one epic's bundle, where nobody editing `guard-invariants.json` would look. |

**What is deliberately not proposed.** Retiring the duplicate snapshots — having
`epic-190-a2` and `epic-191-a3` stop snapshotting the same six files — would be
the deeper fix, and it is tempting because those two bundles are byte-identical
to each other and to live. It is not proposed here because a bundle is the
record of what a human reviewed before applying, and deleting one retroactively
changes the provenance story of a completed epic. That is a decision about
process history, not a cleanup, and it belongs to a human. The proposal above
makes the duplication cheap rather than removing it.

**Why a test and a tool rather than only a tool.** A tool that must be
remembered is the same failure mode one level up: the mirrors drift silently
until CI notices. The suite is what makes forgetting loud, and the tool is what
makes fixing cheap. Neither alone is sufficient.

## Expected Effect

Editing a repository-shared file costs one CI round instead of three, and the
mirror set becomes discoverable from the file rather than from failure messages.

The three rounds this change is measured against were not exceptional: each
found exactly one mirror because each was blind to the rest. A single suite that
enumerates all of them reports the complete set on the first failure, which is
the difference between one fix and three.

## Verification Plan

1. Build the enumeration and assert it finds, against the current tree, exactly
   the mirror inventory tabulated in `## Problem Evidence` — five locations for
   the six guard-invariants files, plus the `guard-parity` and `task-reviewer-a`
   snapshots. A hand-written expectation is acceptable here only as a
   cross-check; the suite itself must derive the list.
2. Replay PR #305's first-push tree (commit `338395af`) and assert the suite
   names all four stale mirrors in one failure. This is the metric above,
   measured rather than argued.
3. Non-vacuity: with the tree green, mutate one staged byte in each of the three
   rule families in turn and assert the suite fails naming exactly that mirror
   and no other.
4. Pending-bundle safety: assert `epic-159-pillar-c` is reported as pending, not
   stale, and that running the sync tool leaves its staged bytes byte-identical.
   Mutate the fixture so the bundle looks applied and assert the classification
   flips — otherwise the check could be passing for the wrong reason.
5. Twin parity: run both suites and require identical verdicts, with a `pwsh`
   capability probe and a visible `skip -` line when the shell is absent.
6. Run `tests/guard-invariants-epic-a1.tests.sh`,
   `tests/phase2-guard-invariants.tests.sh` and
   `tests/generate-gate-capabilities.tests.sh` unchanged — the new suite adds
   coverage and must not replace or weaken the three that already enforce their
   own bundle.
7. The next retrospective records CI rounds per shared-file change for the
   measurement window, against the baseline of 3 recorded here.

## Rollback-Plan

Revert the commit whose message contains `WFI-039`. The new suite and tool are
additive: removing them restores exactly today's behaviour, where the three
existing suites still enforce their own bundles and the mirrors are found one CI
round at a time. No staged bytes, manifests or bundles are modified by this WFI
itself, so there is nothing to migrate back.

If the enumeration proves too noisy — for example if `drafts/` directories from
future epics do not follow the `human-copy-candidate` convention — the
proportionate retreat is to narrow the suite to `specs/*/human-copy/` only,
keeping the byte-identity and pending-bundle logic and giving up the superset
rule, rather than removing the suite.

## Result

Implemented and verified 2026-08-21. Unlike WFI-030 and WFI-037, none of the
target files is protected, so this landed directly rather than as staged
patches.

**Delivered**

| File | Role |
|---|---|
| `scripts/human_copy_mirrors.py` | the single enumeration and classification, imported by everything below |
| `tests/human-copy-mirror-freshness.tests.sh` / `.ps1` | the suite, registered in both `run-all` twins |
| `scripts/sync-human-copy-mirrors.py` | the remediation half, `--check` for report-only |
| `docs/contributor/shared-file-mirrors.md` | the coupling stated from the editing side |

Both twins delegate the walk to the shared module, so **parity is structural
rather than maintained**: they cannot disagree about what a mirror is or whether
one is stale, because neither implements that. This is the same insight that
made WFI-037's vocabulary change data-only.

**The headline metric is met.** Replaying PR #305's first-push tree (`338395af`),
the suite names **all five stale locations — 25 mirrors — in a single failure**:

```
specs/epic-136-phase2-gates/human-copy
specs/epic-189-a1-project-context/human-copy
specs/epic-190-a2-capability-registry/human-copy
specs/epic-190-a2-capability-registry/drafts/human-copy-candidate
specs/epic-191-a3-path-ownership/human-copy
```

Against a baseline of one mirror per CI round over three rounds. The secondary
target in `## Verification Metric` said four; the enumeration found five,
because the round-by-round count never separately credited `epic-189-a1`, which
round 1 had already fixed.

**Safety property holds.** On both the current tree and the replay tree,
`epic-159-pillar-c` is classified `pending`, not `stale` — along with 12 other
un-applied mirrors across six bundles, including three `.github/workflows/test.yml`
snapshots. The sync tool leaves every one of them untouched and says so.

**Non-vacuity.** Rewriting exactly one FRESH mirror back to `origin/main`'s bytes
makes the suite fail naming exactly that mirror
(`specs/epic-136-phase2-gates/human-copy <- tests/guard-parity.tests.sh`) and
nothing else; restoring returns it to 5 passed, 0 failed. Twin parity confirmed:
both report `5 passed, 0 failed, 13 pending`.

**Not done here.** Verification Plan item 7 — the retrospective recording CI
rounds per shared-file change — needs a measurement window this WFI cannot
supply, and the duplicate snapshots are still duplicated, deliberately, for the
reason given in `## Proposed Change`.
